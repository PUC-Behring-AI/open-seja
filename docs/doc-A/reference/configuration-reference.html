Configuration Reference

Exhaustive reference for every configuration variable, periodic trigger, threshold, and structural convention in SEJA's project configuration files: product-design/conventions.md and product-design/constitution.md.

Project Identity Variables

Defined in the ## Project Identity section of product-design/conventions.md. These variables identify the project across all skills and generated artifacts.

Variable Type Description
PROJECT_NAME string Project display name. Used in report headers, commit messages, and generated documentation titles.
PROJECT_DESCRIPTION string One-line project description. Used in README generation, onboarding plans, and communication materials.
PROJECT_MODE enum: greenfield, brownfield Project mode. Greenfield indicates a new project; brownfield indicates an existing, actively maintained project. Affects /seja-setup behavior and /design questionnaire flow.

File Maintainer Classification

The "Maintained By" column uses a four-value classification scheme:

Value Meaning Agent Rule
Human Authored and updated exclusively by humans. Agents must NOT write. May read and propose changes via AskUserQuestion.
Human (markers) Human-authored prose; agent may write fixed-format structured markers only (STATUS, INCORPORATED, CHANGELOG_APPEND, DECISION_APPEND). Write only via apply_marker.py after AskUserQuestion confirmation. Enforced by check_human_markers_only.py at post-skill step 6c.
Agent Auto-maintained by agents and skills (e.g., via post-skill). Agents read/write freely. Humans typically do not edit directly.
Human / Agent Seeded by an agent (e.g., /design), then human-owned; both may update. Agents may write per file-specific rules. Humans are primary curators after seeding.

Review Configuration

Defined in the ## Review Configuration section of product-design/conventions.md.

Variable Value Description
MINIMUM_REVIEW_DEPTH standard Minimum review depth for project changes. Valid values: light, standard, deep. Standard is the floor; /critique can raise the depth but not lower it below this minimum. Plans invoke plan-reviewer at this depth or higher.

Review Depth Tiers

Depth Perspective Count Deep-Dives Use Case
light 3--4 shortlisted 0 Quick sanity check for low-risk changes (CHORE, DOCUMENT prefixes).
standard 4--6 shortlisted Up to 3 Default for most plans. Balances thoroughness with context budget.
deep 6--8 or all 16 Up to 6 Comprehensive review for high-risk changes (FEATURE, REDESIGN prefixes).

Periodic Triggers

Defined in the ## Periodic Triggers section of product-design/conventions.md. Periodic triggers cause the harness to surface reminders or actions at configured intervals. Pre-skill's pending-check stage displays overdue entries.

Trigger Intervals

Trigger Interval (days) Action Type Description
Periodic curation 30 periodic-curation Review product-design-as-intended.md for items ready to promote from implemented to established status.
Spec-drift check 14 spec-drift-check Run /explain drift to surface drift between design intent and as-coded state.
Git freshness check 7 check-git-freshness Compare local branches to their upstreams; surface behind/ahead counts. Invoked by check_git_freshness.py.

Thresholds

Threshold Value Description
Pending plan age escalation 30 days Days before an open implement pending entry is surfaced with the overdue banner in pre-skill's pending-check stage.
Verify-as-coded file threshold 5 files Minimum number of files changed in a plan before post-skill auto-creates a verify-as-coded pending action.
Pending age escalation 14 days Days before any pending action is flagged as overdue in pre-skill notices.
Pending auto-dismiss 90 days Days after which unaddressed pending actions are auto-dismissed by pending.py cleanup.

Architecture Description

Defined in the ## Architecture Description section of product-design/conventions.md. Describes SEJA's architectural pattern and non-negotiable conventions.

Variable Value Description
ARCHITECTURE_DESCRIPTION Rule-governed lifecycle harness for Claude Code SEJA is a governance layer, not a web application or programming framework.
ARCHITECTURE_PATTERN Skill dispatch with lifecycle hooks (pre-skill, skill, post-skill); agent delegation for specialized work Core execution pattern. Every skill invocation follows the pre-skill, skill body, post-skill sequence.
CONVENTION_1 All skills start with pre-skill and end with post-skill Lifecycle discipline is non-negotiable. Mapped to constitution principle T1.
CONVENTION_2 Human (markers) files are written only via apply_marker.py, never by direct agent prose writes Human-authored content integrity. Mapped to constitution principle T2.
CONVENTION_3 Private content never reaches public without explicit gating via check_no_private_leaks.py Leak prevention. Mapped to constitution principle S1.

Constitution Structure

The constitution file (product-design/constitution.md) defines immutable project principles. It is loaded first by pre-skill before conventions or any other reference, and its rules take precedence over everything else. The constitution template lives at .claude/references/template/constitution.md.

Sections

Section ID Prefix Count Purpose
Project Identity -- -- One-paragraph project description and primary user identification.
Technical Principles T T1--T4 Non-negotiable technical rules: lifecycle discipline (T1), human markers integrity (T2), artifact maintenance (T3), metacommunication voice (T4).
Quality Principles Q Q1--Q3 Quality commitments: design intent authority (Q1), surfacing unknowns (Q2), governable AND epistemic (Q3).
Security Invariants S S1--S2 Security rules: private/public boundary (S1), no pre-commit hook bypass (S2).
Compliance Requirements C C1--C2 Regulatory and contractual constraints: private repositories only (C1), product-design never synced to public (C2).
Enforcement -- -- How principles are loaded into agent context and verified. Violations are blocking.
Changelog -- -- Amendment history. Changes require explicit designer approval.

Principle Format

Each principle in the constitution follows a table format:

| # | Principle | Rationale |
|---|-----------|-----------|
| T1 | <principle text> | <rationale text> |

The # column contains the section prefix and number (e.g., T1, Q2, S1). The Principle column contains the non-negotiable rule. The Rationale column explains why the principle exists.

As-Intended / As-Coded Registry

Defined in the ## As-Intended / As-Coded Registry section of product-design/conventions.md. This registry is the single source of truth for /design (template generation), /explain drift (drift checking), and post-skill (DONE marker proposals).

As-Intended File Section As-Coded Counterpart
${DESIGN_INTENT} Sections 0--17: design intent + Decisions + CHANGELOG ${AS_CODED}
${DESIGN_INTENT} Section 15: designed journeys ${AS_CODED} -- Journey Maps section
${UX_RESEARCH} All (personas, problem scenarios, discovered journeys, CHANGELOG) --

Tools discriminate artifact types by ID prefix: JM-TB-NNN (designed journeys) vs. JM-E-NNN (discovered journeys). The Section column enables multi-artifact-type files where a single as-intended file maps to different sections of the as-coded counterpart.

Context Budget Tiers

Each skill declares a context_budget in its SKILL.md YAML frontmatter. Pre-skill's budget-eval stage uses this to control how much context is loaded. See Pipeline Reference for full stage details.

Tier Briefs Loading Subsequent Stages
light Skips all briefs and reference files (brief-log only). Skips ref-load and constitution stages entirely.
standard (default) Loads briefs index (${BRIEFS_INDEX_FILE}) instead of full briefs. Proceeds to orphan detection sub-step, then ref-load and constitution.
heavy Loads full ${BRIEFS_FILE} with recency windowing (first 50 entries). Also loads plan index. Proceeds to orphan detection and compaction warning sub-steps, then ref-load and constitution.

settings.json Configuration

Claude Code's settings.json files control permissions, hooks, MCP server connections, and environment variables. SEJA uses these files to enforce permission allowlists, wire lifecycle hooks, and configure runtime behavior. Unlike conventions.md (which is SEJA-specific configuration parsed by harness scripts), settings.json is a Claude Code platform file consumed directly by the Claude Code runtime.

File Locations and Precedence

Claude Code reads settings from three locations. Values merge with later sources overriding earlier ones. The project-level file is version-controlled; the local-override file is gitignored.

File Scope Version-Controlled Purpose
~/.claude/settings.json User-global No (user home directory) Baseline settings applied to all projects. Useful for org-wide defaults such as forceLoginOrgUUID.
.claude/settings.json Project-level Yes Shared team settings: permission allowlists, hooks, MCP servers, additional directories. Created by /seja-setup from the template at .claude/references/template/settings.json.
.claude/settings.local.json Local override No (gitignored) Per-developer overrides. Extra permissions, additional directories, or machine-specific MCP servers that should not be shared with the team.

Permission Allowlists

The permissions object controls which tools and commands the agent can use without prompting for confirmation. The allow array contains patterns that grant access; the deny array contains patterns that block access (deny takes precedence over allow).

Key Type Description
permissions.allow string[] Patterns granting tool access without confirmation prompts. Each entry is a tool name optionally followed by a path or command glob in parentheses. Examples: "Read(/**)" (read any file), "Bash(git commit:*)" (any git commit command), "WebSearch" (web search with no qualifier), "Skill(post-skill:*)" (invoke post-skill skill).
permissions.deny string[] Patterns that block tool access regardless of allow entries. Example: "Bash(git push*)" prevents all git push operations.
permissions.defaultMode string Default operating mode when Claude Code starts. Common values: "plan" (read-only planning), "auto" (full execution).
permissions.additionalDirectories string[] Additional directories the agent can access beyond the project root. Useful for companion workspaces, shared skill directories, or temporary output locations.

Hook Types

The hooks object defines lifecycle hooks that run at specific points during agent execution. Each hook type maps to an array of matcher-hooks pairs. When a tool use or event matches, the associated hooks execute.

Hook Type Fires When Use Case
PreToolUse Before a tool is invoked Validate or gate tool calls. Example: check Bash commands for destructive operations before execution.
PostToolUse After a tool completes Post-process tool results. Example: log file writes or validate outputs.
UserPromptSubmit When the user submits a prompt Pre-process user input. SEJA uses this to run seja_harness_hook.py on every prompt for lifecycle enforcement.
Notification When a notification is generated Handle system notifications such as subagent completion or background task results.
Stop When the agent stops responding Run cleanup or summary actions after the agent finishes a turn.

Each hook entry has the following structure:

{
  "matcher": "ToolName",
  "hooks": [
    {
      "type": "command",
      "command": "python .claude/skills/scripts/my_hook.py"
    }
  ]
}

The matcher field filters which tool invocations trigger the hook (empty string matches all). The type field is either "command" (runs a shell command; non-zero exit blocks the tool call for PreToolUse) or "prompt" (injects a prompt for the agent to evaluate; the agent decides whether to proceed based on the prompt's guidance).

MCP Server Configuration

The mcpServers object configures Model Context Protocol servers, which extend the agent with additional tools and data sources (e.g., browser automation, database access, external APIs).

Key Type Description
mcpServers.<name>.command string The command to launch the MCP server process (e.g., "npx", "python").
mcpServers.<name>.args string[] Arguments passed to the server command.
mcpServers.<name>.env object Environment variables set for the server process. Useful for API keys or configuration tokens.

Environment Variables

The env object sets environment variables for the agent's shell sessions. These are available to all Bash commands and hook scripts executed during the session. Useful for injecting API keys, feature flags, or debug toggles without modifying system environment. 

{
  "env": {
    "DEBUG": "true",
    "API_BASE_URL": "https://api.example.com"
  }
}

Other Top-Level Keys

Key Type Description
model string Default model to use (e.g., "claude-opus-4-6", "claude-sonnet-4-6"). Can be overridden per-session.
forceLoginOrgUUID string Forces authentication against a specific Anthropic organization UUID. Useful for team accounts.
