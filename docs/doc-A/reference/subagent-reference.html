Subagent Reference

Overview

SEJA delegates specialized work to 16 subagent prompts defined in .claude/agents/. Each subagent runs in an isolated context window with a focused prompt, a constrained tool set, and a well-defined input/output contract. Skills invoke subagents via the Agent tool; the calling skill handles argument parsing, interactive prompts, and lifecycle hooks while the subagent handles domain-specific analysis or generation.

Role Categories

Subagents are organized into three role categories:

Evaluator (9 agents)
Review artifacts against quality perspectives, run validation checks, or execute test suites. Evaluators consume existing artifacts and produce assessment reports. They do not modify project source code.
Generator (7 agents)
Produce self-contained artifacts from well-defined inputs -- explanation reports, documentation files, communication material, onboarding plans. Invoked by thin-skill wrappers that handle argument parsing and lifecycle hooks. Generator agents must receive the project constitution as part of their prompt for trust-boundary enforcement (except test-plan-generator).
Executor (pattern, no standalone files)
Execute plan steps in isolated context windows. Used by /implement auto mode. Not standalone prompt files -- the implement skill constructs their prompts dynamically from plan step metadata. Each executor receives the step description, file list, references, and interface contract.

Constitution Enforcement

Generator agents (except test-plan-generator) receive the project constitution (product-design/constitution.md) as part of their prompt. This ensures that generated artifacts -- documentation, communication material, onboarding plans, explanation reports -- respect the project's immutable principles (design authority, privacy invariants, lifecycle discipline, authorship voice).

Evaluator agents do not enforce the constitution directly. They read product-design/conventions.md for project-specific paths and settings, and apply their own domain-specific evaluation criteria (review perspectives, test assertions, validation scripts).

Agent Constitution Rationale
architecture-explainer Yes Explanation reports must respect privacy invariants (S1) and voice rules (T4)
communication-generator Yes Stakeholder material must not expose private content (S1, C2)
document-generator Yes Generated documentation must respect privacy and design authority (Q1, S1)
evolution-explainer Yes Historical analysis must preserve authorship voice (T4) and privacy (S1)
explanation-generator Yes Explanation reports must respect privacy invariants (S1) and voice rules (T4)
onboarding-generator Yes Onboarding plans must reflect project principles and respect privacy (S1, C2)
test-plan-generator No Test plans reference conventions only; no generated prose requiring constitution governance

Council Debate Archetypes

The council-debate agent uses a fixed set of five archetypes for every debate, supplemented by 0-2 brief-specific experts selected from a pool. This structure ensures consistent multi-perspective coverage while allowing domain-specific expertise.

Fixed Archetypes (always present)

Archetype Perspective Role in Debate
Security Advocate Threat modeling, attack surfaces, data protection Challenges proposals for security implications
DX Pragmatist Developer experience, maintainability, complexity cost Pushes for practical, buildable solutions
UX Champion User experience, accessibility, communicability Advocates for the end-user perspective
Architecture Purist System design, separation of concerns, extensibility Evaluates structural integrity and long-term implications
Product Strategist Business value, roadmap alignment, opportunity cost Grounds technical decisions in product goals

Expert Pool (0-2 selected per debate)

Expert Selected When
Agentic AI Expert Debate involves AI agent behavior, prompt engineering, or LLM integration
Data Engineer Debate involves data pipelines, storage architecture, or ETL workflows
DevOps/Platform Engineer Debate involves deployment, CI/CD, infrastructure, or observability
Domain Specialist Debate involves domain-specific knowledge not covered by fixed archetypes

Executor Pattern

Executor agents are not standalone prompt files. The /implement skill constructs executor prompts dynamically from plan step metadata:

  • Step title and self-contained description
  • File list (create/modify/delete paths)
  • Reference files to load
  • Interface contract (expected public surface from dependency-producing steps)
  • Verify condition (how to confirm the step succeeded)
  • Tests to create or update

Each executor runs in an isolated context window, receives only the information needed for its step, and returns results to the orchestrating /implement skill. In auto mode, executors iterate with the code-reviewer evaluator in a generator-critic loop until the step passes review.
