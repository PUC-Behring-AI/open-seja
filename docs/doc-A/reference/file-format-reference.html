File Format Reference

Exhaustive specification of every file format used by the SEJA harness: YAML frontmatter schemas, lifecycle marker syntax, JSONL trace formats, plan file structure, brief log format, report header conventions, roadmap files, file maintainer classification, and versioning files.

YAML Frontmatter Schemas

SKILL.md Frontmatter

Every skill definition file (.claude/skills/<name>/SKILL.md) begins with a YAML frontmatter block delimited by ---. The schema follows the agentskills.io portable spec with SEJA-specific extensions under the metadata namespace.

Core Fields (agentskills.io)

Field Required Type Description
name Yes string (1--64 chars, lowercase alphanumeric + hyphens) Unique skill identifier. Must match the directory name.
description Yes string (1--1024 chars) Human-readable purpose statement.
argument-hint No string Usage pattern for arguments (shown in /help).
user-invocable No boolean Whether the user can invoke directly. Default: true. Set to false for internal hooks (pre-skill, post-skill).
compatibility No string (<=500 chars) Runtime compatibility note (e.g., "Designed for Claude Code with the SEJA harness").

SEJA Extension Fields (metadata namespace)

Field Required Type Default Description
metadata.last-updated No datetime -- Last modification timestamp (YYYY-MM-DD HH:MM UTC).
metadata.version No semver string -- Skill version (e.g., 1.2.0).
metadata.category No enum -- Skill category. Values: utility, analysis, planning, internal.
metadata.context_budget No enum standard Context budget tier controlling how much is loaded at pre-skill. Values: light (skips refs), standard (briefs index + refs), heavy (full briefs + plan index + refs).
metadata.references No list of strings [] Reference files to load during pre-skill. Paths resolved via routing table (general/ -> .claude/references/general/, template/ -> .claude/references/template/).
metadata.eager_references No list of strings -- References loaded immediately (demand-pull mode). When present, entries in references not in this list become lazy-loaded on demand.
metadata.skip_stages No list of strings [] Pre-skill stages to skip. Valid IDs: pending-check, orphan-check, compaction-check, constitution. Only non-critical stages may be skipped.

Example

---
name: research
description: "Answer questions about the codebase."
argument-hint: "<question> [--inventory <pattern>] [--deep]"
user-invocable: true
compatibility: "Designed for Claude Code with the SEJA harness"
metadata:
  version: 1.2.0
  category: analysis
  context_budget: standard
  references:
    - general/shared-definitions.md
    - general/report-conventions.md
---

Reference File Frontmatter

All reference files in .claude/references/ begin with a YAML frontmatter block containing a single required field.

Field Required Type Description
designer_description Yes string First-person description of the file's purpose, written from the file's perspective (e.g., "When a skill uses a harness-wide concept, I'm the reference that holds the canonical definitions..."). Must not be compressed or summarized by agents.

Example

---
designer_description: "When a skill produces a report file under your
  output directory, I'm the reference that codifies the shared header
  fields, the artifact-immutability rule, and the ASCII-only character
  restrictions."
---

Lifecycle Markers

Inline markers track the lifecycle of as-intended items across registered as-intended files (declared in conventions.md As-Intended / As-Coded Registry). Agents may read markers and propose new ones via AskUserQuestion in post-skill. Agents must never remove or alter existing markers -- these are audit records.

STATUS Marker (Prose Sections)

An inline HTML comment placed immediately before the section heading. Invisible in rendered Markdown, machine-parseable by agent tooling.

Legacy Format (pre-2.8.0)

<!-- STATUS: IMPLEMENTED | plan-NNNNNN | YYYY-MM-DD -->
### Section Title

Single uppercase IMPLEMENTED, typically paired with a later ESTABLISHED stamp on promotion. A legacy marker without a plan ID is valid for items implemented outside the plan workflow.

Current Format (2.8.0+)

<!-- STATUS: proposed | plan-NNNNNN | YYYY-MM-DD -->
### Section Title

Lowercase multi-value marker with a state machine governing allowed transitions. Used by apply_marker.py and enforced by check_human_markers_only.py for Human (markers) files.

State Machine

From State To State Valid
proposed implemented Yes
implemented established Yes
established superseded Yes
established implemented No (regression)
implemented proposed No (regression)

Plan ID and date are optional for proposed (initial state) and required after. Uppercase STATUS: IMPLEMENTED markers remain valid; the widened regex detects legacy markers so a Phase 3b flip replaces rather than stacks.

ESTABLISHED Stamp

Applied when a human confirms promotion of an implemented item via /explain drift --promote or manual curation. 

<!-- ESTABLISHED: plan-NNNNNN | YYYY-MM-DD | vX.Y.Z -->
Field Required Description
plan-NNNNNN Yes Plan that implemented the item.
YYYY-MM-DD Yes Date of promotion.
vX.Y.Z No Version at promotion time. Projects without semver use date only.

IMPLEMENTED Marker (Table Rows)

For structured tables (e.g., journey map steps), a Status column carries the implementation state:

Status Value Meaning
DONE (plan-NNNNNN, YYYY-MM-DD) Implemented by the referenced plan on the given date.
- Not yet implemented.

DECISION_APPEND Marker

Appends new decision entries with auto-assigned D-NNN IDs to the ## Decisions section of product-design/product-design-as-intended.md. Written exclusively via apply_marker.py --marker DECISION_APPEND.

Decision Entry Shape (DDR)

<!-- STATUS: proposed | plan-NNNNNN | YYYY-MM-DD -->
### D-001: Use PostgreSQL as primary datastore

**Context**: ...
**Decision**: ...
**Consequences**: ...

The D-NNN namespace is orthogonal to REQ-TYPE-NNN -- separate taxonomies, never intermixed.

CHANGELOG_APPEND Marker

Appends versioned entries to changelog sections in Human (markers) files. Written via apply_marker.py --marker CHANGELOG_APPEND.

INCORPORATED Marker

Marks research findings that have been incorporated into design intent. Written via apply_marker.py --marker INCORPORATED.

Requirement ID Convention

Stable, machine-parseable identifiers for design-intent requirements, enabling spec-to-plan traceability. Each marker is an HTML comment placed immediately before the heading, table row, or bullet.

Format

<!-- REQ-TYPE-NNN -->

Type Prefix Taxonomy

Type Prefix Design-Intent Section Classification Enforcement
ENT 2. Entity Hierarchy technical advisory
PERM 4. Permission Model security blocking at preflight
VAL 10. Validation Constants security blocking at preflight
UX 8. UX Patterns ux advisory
MC 14. Per-Feature Metacomm ux advisory
JM 15. Designed User Journeys ux advisory
I18N 7. Localization cross-cutting advisory
DELTA 16--17. Deltas technical advisory

Security-classified requirements (PERM, VAL) must be traced by a plan step in the same wave. Advisory-classified requirements produce warnings but do not block. Plan steps declare satisfied requirements via the Traces metadata field. Coverage is verified by check_plan_coverage.py.

JSONL Trace Formats

conversation-trace.jsonl

Append-only conversation log stored at ${OUTPUT_DIR}/conversation-trace.jsonl. Each line is a JSON object representing one exchange event. Managed by conversation_trace.py.

Field Type Required Description
evt_id string Yes Unique event identifier (auto-generated).
session_id string Yes Claude session ID from CLAUDE_SESSION_ID env var.
timestamp ISO 8601 Yes Event timestamp in UTC.
emitter enum Yes Who produced the message. Values: user, claude.
message string Yes Content of the exchange (user utterance or 1--2 sentence agent summary).
type enum Yes Message classification. Values: question, answer, instruction.
preceding_evt_id string Yes Previous event in sequence ("null" for first event).
topic_tags list of strings No 1--3 short topic tags (agent responses only).
skill_id string No Linked skill invocation (backfilled by pre-skill).

decision-digest.jsonl

Machine-readable index of D-NNN decision entries from product-design-as-intended.md and HIGH/MEDIUM recommendations from research logs. Stored at ${OUTPUT_DIR}/decision-digest.jsonl. Generated by generate_decision_digest.py, invoked conditionally by post-skill step 7d.

telemetry.jsonl

Append-only skill execution telemetry stored at ${OUTPUT_DIR}/telemetry.jsonl. Each line is a JSON object recording one skill invocation. Prepared at post-skill step 1b, flushed at step 8b.

Field Type Required Description
skill string Yes Name of the executed skill.
id string Yes Artifact ID (e.g., plan-000123).
outcome enum Yes Skill outcome (e.g., success, partial, failed).
timestamp ISO 8601 Yes Completion timestamp in UTC.
duration_seconds number Yes Total execution duration in seconds.
git_commit_sha string No Commit SHA from step 8 (null if commit skipped).
files_changed number No Number of files in the commit (null if commit skipped).
parent_skill string No Name of the calling skill (null if top-level).
session_id string No Claude session ID from CLAUDE_SESSION_ID env var.

Plan File Structure

Header Format

# Plan NNNNNN | PREFIX-SCOPE | YYYY-MM-DD HH:MM | Short Title | Review: depth
Component Format Description
NNNNNN 6-digit zero-padded Globally unique plan ID, reserved via reserve_id.py.
PREFIX FEATURE | REDESIGN | FIX | REFACTOR | DOCUMENT | TEST | CHORE Change type classification.
SCOPE -B | -F | -X | -O Backend, Frontend, Cross-cutting, or Other.
YYYY-MM-DD HH:MM UTC datetime Plan creation timestamp.
Short Title free text Brief descriptive title.
Review: depth light | standard | deep Review depth applied during plan generation.

Plan Sections (in order)

# Section Required Description
1 ## Designer's Metacommunication Message Yes First-person I/you designer statement of intent.
2 ## User Brief Yes Verbatim user request.
3 ## Agent Interpretation Yes Structured: Problem, Approach, Alternatives rejected.
4 ## Metacomm Intention No Summary + Source (present when --framing metacomm was used).
5 ## Best Practices Yes Key practices and constraints for this plan.
6 ## Design Decisions Yes User-visible impact and trade-offs accepted.
7 ## Steps Yes Numbered steps, each following the plan step template.
8 ## Review Log Yes Phase 1 perspective triage table + Phase 2 deep-dives + execution metrics.
9 ## Outcomes Yes Expected deliverables and artifact list.
10 ## Smoke Yes true or false -- whether smoke testing is warranted.
11 ## Q&A Log No Appended by post-skill step 3 (Branch B). Uses ### Q<n> / ### A<n> format.

Plan Step Format

Each step within ## Steps must be self-contained -- executable by a subagent with no shared context from prior steps. The canonical shape is defined in .claude/references/template/plan-step.md.

Canonical Shape

### Step N: <short imperative title>
<Self-contained description of what to do.>
- **Files**: <path> (create|modify|delete), ...
- **References**: <reference-name>, ...
- **Depends on**: Step N, Step M
- **Interface**: <public surface> | N/A
- **Verify**: <success condition>
- **Tests**: <test description> | N/A
- **Docs**: <documentation changes>
- **Deploy**: <deployment config changes>
- **Traces**: REQ-xxx, REQ-yyy
- [ ] Done

Metadata Fields

Field Required When to Include Description
Files Yes Always Every path the step reads, creates, modifies, or deletes. Annotated with (create|modify|delete).
References Yes Always Only product-design/ files relevant to this step.
Depends on No When output from prior steps is needed Step numbers whose output this step requires. Omit for independent steps.
Interface Yes Always (N/A if leaf step) Expected public surface for downstream consumers within the plan.
Verify Yes Always Concrete, testable success condition. Prefer automated checks.
Tests Yes Always (N/A for doc/config steps) Required for FEATURE/FIX/REFACTOR steps with source code changes.
Docs No FEATURE/REDESIGN with user-facing code What documentation to create or update. Omit when N/A.
Deploy No When deployment config changes New env vars, ports, services, Docker/server config. Omit when N/A.
Traces No When implementing design requirements Comma-separated REQ IDs from product-design-as-intended.md.

Decomposition Guidelines

  • Each step must be completable in one subagent context window (rule of thumb: touches <=5 files).
  • Dependencies must flow forward (Step 2 depends on Step 1, not the reverse).
  • The step description must include enough context to make sense in isolation.

Brief Log Format

The briefs log (${OUTPUT_DIR}/briefs.md) records every skill invocation. Newest entries appear first (prepended by pre-skill, completed by post-skill).

STARTED Entry

STARTED | YYYY-MM-DD HH:MM UTC | skill-name | brief text

DONE Entry

DONE | YYYY-MM-DD HH:MM UTC | STARTED | YYYY-MM-DD HH:MM UTC | skill-name | brief text | PLAN | plan-id
Field Description
STARTED / DONE Entry status marker.
YYYY-MM-DD HH:MM UTC Timestamp obtained via date -u +"%Y-%m-%d %H:%M UTC".
skill-name Name of the invoked skill.
brief text Verbatim user brief (or ERROR: ... summary for error logs).
PLAN | plan-id Appended by post-skill when the skill produced a plan artifact.

Report Header Convention

When a skill produces a report file in ${OUTPUT_DIR}, the following header conventions apply. Defined in .claude/references/general/report-conventions.md.

Field Format Required Description
id 6-digit zero-padded Yes Globally unique, reserved via reserve_id.py.
datetime YYYY-MM-DD HH:MM UTC Yes Creation timestamp.
prefix FEATURE | REDESIGN | FIX | REFACTOR | DOCUMENT | TEST | CHORE When applicable Change type classification.
scope -B | -F | -X | -O When applicable Backend, Frontend, Cross-cutting, or Other.
short title free text Yes Brief descriptive title (truncated for filenames).
source source: <type>-<id> -- <motivation> No Artifact that triggered this one; motivation under 80 chars.
spawned spawned: <type>-<id>[, ...] No Artifacts created from this one (updated by post-skill).
tags lowercase kebab-case, comma-separated No Topic discovery tags (research reports only). 2--5 tags.

Additional Conventions

  • All report filenames must be lowercase.
  • All files must be saved as UTF-8 without BOM.
  • No ANSI escape sequences, no typographic characters (em-dashes, curly quotes). Use ASCII equivalents.
  • Existing artifacts in ${OUTPUT_DIR} are immutable design history -- never retroactively modify for format changes.

Roadmap File Format

Header Format

# Roadmap NNNNNN | YYYY-MM-DD HH:MM | Short Title

Sections

Section Description
## Plans Table of plans in the roadmap with IDs, titles, dependencies, and wave assignments.
## Dependencies Dependency graph between plans (which plans must complete before others).
## Timeline Wave-based execution timeline with estimated durations.

Roadmaps are generated by /plan --roadmap and stored at ${OUTPUT_DIR}/roadmaps/roadmap-NNNNNN-<slug>.md.

File Maintainer Classification

Four-value scheme applied to all reference files, principally those in product-design/. Used as the "Maintained by" column in conventions.md Key Files table.

Value Meaning Agent Rule
Human Authored and updated exclusively by humans. Agents must NOT write. May read and propose changes via AskUserQuestion.
Human (markers) Human-authored prose; agent may write fixed-format structured markers only (STATUS flags, INCORPORATED stamps, CHANGELOG append lines). Agents write only via apply_marker.py after explicit AskUserQuestion confirmation. Never write prose or modify text outside allowed marker patterns. Enforced by check_human_markers_only.py at post-skill step 6c.
Agent Auto-maintained by agents and skills (e.g., via post-skill). Agents read/write. Humans typically do not edit directly.
Human / Agent Seeded by an agent (e.g., /design), then human-owned; both may update. Also applies to harness source files. Agents may write per file's own rules. Humans are primary curators after seeding.

Versioning Files

SEJA uses three version-bearing files with distinct purposes.

File Location Purpose Maintained by When to Update
.claude/skills/VERSION Harness source Authoritative harness version (semver). Manual (developer) Bump every release.
.claude/CHANGELOG.md Harness source Human-readable release history. Manual (developer) Add ## [x.y.z] heading matching VERSION every release.
.seja-version Project root Per-project migration watermark. Automated (run_migrations.py, /seja-setup --upgrade) Written automatically; records the version a project was last migrated to.

.claude/skills/VERSION tracks what the harness IS; .seja-version tracks what a project has been UPGRADED TO. Validation: check_version_changelog_sync.py keeps VERSION and CHANGELOG in sync. Use bump_version.py to update all three files atomically.
