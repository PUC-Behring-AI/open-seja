Customization and Extension

This advanced guide is for contributors and power users who want to extend the harness itself: write a new skill, add a subagent prompt, create a custom review perspective, modify the pre-skill pipeline, or add a new periodic trigger. Each section is goal-first, and each notes the governance rule that gates the extension -- SEJA deliberately makes adding surface area cost justification.

How to Write a New Skill

A skill is a directory under .claude/skills/<name>/ containing a SKILL.md and, for user-invocable skills, a sibling SKILL-quickguide.md.

  1. Justify the skill before you write it. New skills must show their functionality cannot be a mode of an existing skill. Independent existence needs 3 of 4 criteria: (a) distinct user intent and mental model, (b) disjoint reference sets, (c) incompatible execution topology, (d) different output strategy. The 10-mode /critique is the model to follow for shared execution patterns.
    Expected output: a short justification you can defend at review.
  2. Write the frontmatter. SKILL.md opens with YAML that follows the agentskills.io spec. Top-level fields (name, description, compatibility) conform to the spec; SEJA-specific fields (context_budget, eager_references, references, skip_stages, plan_format_version, questionnaire_version) live under metadata to avoid future spec conflicts. check_skill_spec.py validates the shape.
  3. Add the mandatory Quick Guide pointer. Within the first 15 non-blank body lines, SKILL.md must carry a blockquote pointer containing the literal token SKILL-quickguide.md. The canonical form is > Overview: see [./SKILL-quickguide.md](./SKILL-quickguide.md). The quickguide-pointer-compliance scanner fails preflight if it is missing or malformed.
  4. Author the sibling Quick Guide. Put the designer-facing narrative (What / Example / When to use / Next step) in SKILL-quickguide.md. It is not added to metadata.references and pre-skill does not load it during normal stages; it is loaded on demand by --help and by /help <skill> Layer 2.
  5. Write the body and Arguments table. Keep executional instructions in SKILL.md. Templates go under .claude/references/template/; historical rationale and private citations go in an optional SKILL-rationale.md sibling (maintainer-only, never loaded at runtime).

Runtime skill generation is deferred. Agents do not create new SKILL.md files at runtime. That capability is gated on a permission-inheritance model, mandatory constitution injection, and a constrained template factory -- none of which is in place yet.

How to Add a Subagent Prompt

Subagents are prompt files in .claude/agents/, run in isolated context windows by thin-skill wrappers via the Agent tool. They come in two authored roles (a third, Executor, is constructed dynamically by /implement and is not a standalone file):

  • Evaluator -- reviews one type of artifact through one lens (e.g. code-reviewer, plan-reviewer, harness-health-evaluator).
  • Generator -- produces one type of self-contained artifact from well-defined inputs (e.g. document-generator, onboarding-generator, communication-generator).
  1. Justify single responsibility. New agents must show their domain is distinct from every existing agent. Each agent operates on one artifact type through one lens; do not merge agents or add cross-cutting responsibilities.
  2. Choose the dispatch. Use Dispatch A (wrapper → subagent) when the mode is self-contained, has a stable prompt-in / artifact-out contract, benefits from context isolation, and needs no mid-flight interaction. Otherwise keep the work inline in the wrapper (Dispatch B).
  3. Wire the wrapper. A thin skill wrapper parses arguments, runs interactive prompts, invokes the lifecycle hooks, and delegates to the agent. The wrapper -- not the agent -- owns /pre-skill and /post-skill; no dispatch fires them twice.
  4. Pass the constitution to generators. Generator agents must receive the project constitution as part of their prompt for trust boundary enforcement.

Expected output. A new prompt file under .claude/agents/ plus a wrapper that dispatches to it, keeping the single lifecycle-hook owner invariant intact.

How to Create Custom Review Perspectives

Review perspectives are the domain lenses (SEC, PERF, DB, UX, A11Y, ...) that /critique review and /critique preflight apply to code, plans, and decisions. They live under .claude/references/general/review-perspectives/, organised into Essential / Standard / Deep tiers (P0 / P1-P2 / P3-P4) with an auto-generated Essential summary.

  1. Add the perspective file in the right tier. Place a new perspective in the tier that matches how often it should run: Essential (P0) runs everywhere; Deep (P3-P4) runs only under --depth deep.
  2. Regenerate the Essential summary if you add or move a P0 perspective, so the shortlist stays consistent with the tier files.
  • Essential tier -- Recommended for a lens that must apply to every review (e.g. security-classified concerns).
  • Deep tier -- Recommended for a specialised lens that would add noise on routine reviews. NOT recommended to put a niche perspective in Essential -- it slows every preflight.

How to Modify the Pre-Skill Pipeline

Pre-skill runs as a pipeline of six composable stages -- help, brief-log, budget-eval, pending-check, ref-load, and constitution. Three are critical and always run (brief-log, budget-eval, ref-load); three are non-critical and error-isolated (help, pending-check, constitution). The orphan-check and compaction-check sub-steps now live under budget-eval, though their legacy IDs are still recognised.

A skill opts out of non-critical stages by declaring skip_stages: [stage-id, ...] in its YAML frontmatter under metadata.skip_stages. A skill can never skip pre-skill entirely -- that is a constitutional invariant.

  • Skip a non-critical stage -- Recommended when a stage's output topology does not fit the skill (e.g. a configuration skill that runs before conventions.md exists skips constitution and pending-check).
  • Keep all stages -- Recommended for lifecycle-workflow skills that produce logged _output/ artifacts and consume prior context. NOT recommended to skip critical stages -- skip_stages only affects the three non-critical ones.

The pipeline is intentionally monolithic. Pre-skill (6 stages) and post-skill (13 steps) are kept in single files so the full lifecycle is readable at once. Do not decompose them into micro-hooks; use skip_stages for per-skill overrides.

Pick a side for new skills. Lifecycle-workflow skills invoke /pre-skill as their first step; configuration and meta skills (/seja-setup, /pending, /help, and the hooks themselves) skip it. The divide is workflow versus infrastructure -- new skills should choose explicitly.

How to Add a Periodic Trigger

Periodic triggers file a pending-ledger entry at most once per interval, surfacing recurring maintenance without blocking any skill. They are declared in .claude/references/template/conventions.md (the check-git-freshness trigger is the reference example -- it files a pending entry when local branches drift from their upstreams).

  1. Declare the trigger and its interval. Add the trigger to the conventions template so seeded projects inherit it. It should file a pending entry (e.g. spec-drift-check, periodic-curation) rather than run work directly.
  2. Keep network and destructive work out of pre-skill. Triggers surface a signal; the user resolves it on demand (e.g. via /critique freshness or /explain drift). Pre-skill must stay within its fast, advisory-only budget -- no git fetch, no auto-pull, no blocking prompts.

Expected output. A trigger that, at most once per interval, files a pending item you resolve with the appropriate on-demand skill -- keeping recurring maintenance visible without taxing every skill invocation.

Common Mistakes

Mistake What happens Fix
Creating a new skill for work that is really a mode. Skill count grows without justification; the governance test fails at review. Add a mode to an existing skill unless you can meet 3 of the 4 independence criteria.
Omitting the SKILL-quickguide.md pointer. The quickguide-pointer-compliance scanner fails preflight. Add the blockquote pointer with the literal SKILL-quickguide.md token in the first 15 body lines.
Giving a subagent cross-cutting responsibilities. Violates single-responsibility; the agent-count governance test blocks it. Keep one artifact type and one lens per agent; add a new agent instead of overloading one.
Putting a niche perspective in the Essential tier. Every preflight slows down for a lens that rarely applies. Place specialised lenses in the Deep tier so they run only under --depth deep.
Trying to skip a critical pre-skill stage via skip_stages. Only the three non-critical stages are skippable; the critical ones always run. Design the skill to work with brief-log, budget-eval, and ref-load always present.
Making a periodic trigger do network or destructive work. Breaks pre-skill's fast, advisory-only budget and non-destructive default. File a pending signal; let the user resolve it with an on-demand skill.
