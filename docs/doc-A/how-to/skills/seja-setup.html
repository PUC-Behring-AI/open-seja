How to Manage the Harness with seja-setup

Goal: put the SEJA harness into a project, finalise a fresh download, stand up a companion workspace, bootstrap the demo, or upgrade an existing install to a newer release. /seja-setup is the single entry point for every harness-state operation. It inspects the current directory (via detect_setup_state.py) and routes each invocation to the correct action, preserving project-specific configuration. This guide focuses on the mechanics of the skill; for a full walkthrough of each install variant with decision trees, see the Installation and Setup chapter.

When to Use

  • You are installing SEJA into a new or existing project for the first time.
  • You cloned SEJA directly into a project folder and need to finalise it in place (--here).
  • You want a companion workspace that keeps design history out of the codebase (--workspace).
  • You want the pre-configured TaskFlow demo to explore SEJA (--demo).
  • You want to refresh harness files to the latest release without touching your project data (--upgrade).

Not for defining design intent (that is /design), or for day-to-day lifecycle work. After the first iteration you rarely run /seja-setup unless you are upgrading. It merges the former /setup and /upgrade into one unified command.

Required Inputs

The full argument pattern is [<target-directory>] [--here | --workspace | --demo | --upgrade] [--version <tag>] [--dry-run].

Argument Purpose
<target-directory> Path to the project directory to install into. Omit it for the no-argument flow, --here, or --upgrade.
--here Finalise setup in the current directory without copying harness files (after cloning SEJA directly into the project folder).
--workspace Create a separate companion workspace repository alongside a codebase.
--demo Install with the pre-configured TaskFlow demo project (pre-filled conventions, constitution, conceptual design, and walkthrough).
--upgrade Refresh harness files in an already-installed project to the latest release, preserving project-specific files.
--version <tag> Pin to a specific public seja release tag (e.g. v0.2.0) instead of the latest SemVer tag.
--dry-run Preview upgrade changes without applying them (valid with --upgrade).

Mutually exclusive. --here, --workspace, --demo, and --upgrade cannot be combined; /seja-setup rejects any invalid combination with an error.

Step by Step

  1. Pick the operation. Install into a target directory, finalise a fresh download in place, create a workspace, bootstrap the demo, or upgrade. If unsure, run /seja-setup with no arguments and let state detection route you.
    Expected output: the skill reports the detected state and the action it will take.
  2. State detection classifies the directory. detect_setup_state.py recognises six states: dev-repo-refuse (the harness dev repo -- hard abort), public-clone-soft-confirm (a clean public clone -- prompts to continue), fresh-download (harness present, no project state -- proceeds), partial-init (harness plus partial state -- proceeds with reconciliation), finalised (a full project -- offers the upgrade menu), and no-harness (nothing to finalise -- aborts).
    Expected output: a state label and matching route.
  3. Answer the Section 1 scaffolding questionnaire (install only). On first install, /seja-setup populates product-design/conventions.md with stack definitions, scaffolds CLAUDE.md and stack-flavored .claude/rules/, and (if a backend is present) smoke-test infrastructure. In brownfield projects it auto-detects the stack from dependency files and presents detected values as confirmation prompts.
    Expected output: a populated conventions.md with no unresolved {{VAR}} placeholders.
  4. Choose your stack-presence mode. The install emits only the rows and sections appropriate to your project: full-stack (backend + frontend), API-only (FRONTEND_FRAMEWORK=none), frontend-only (BACKEND_FRAMEWORK=none), or CLI / library (both none).
  5. Handle git history and cleanup (with --here). When finalising in place, the skill prompts for how to handle SEJA's git history (re-init fresh, keep history and add a project remote, or leave as-is) and presents a cleanup batch for harness-dev artefacts. Nothing is deleted without an explicit second confirmation.
    Expected output: an initial project commit and a handoff to /design.
  6. Or run an upgrade. /seja-setup --upgrade refreshes .claude/ and non-project template references to the latest SemVer tag (or --version <tag>), preserving everything under product-design/ and _output/. Add --dry-run to preview first.
    Expected output: a single reviewable upgrade commit; project-specific files untouched.

Expected Outputs

  • A populated project (or workspace) containing .claude/, product-design/conventions.md, a scaffolded CLAUDE.md, an _output/ skeleton, and a .seja-version pin.
  • For --workspace: an independent git repository with CODEBASE_DIR set by absolute path and launcher scripts (launch.sh / launch.bat); the codebase itself is never written to.
  • For --upgrade: one upgrade commit with project files preserved.
  • A handoff message directing you to run /design after a fresh install, or /critique health then /explain drift after an upgrade.

Common Mistakes

MistakeBetter approach
Combining mutually exclusive flags (e.g. --here --upgrade). Run one operation at a time; /seja-setup rejects invalid combinations.
Running /seja-setup --here or the no-arg flow inside the SEJA development repo. State detection returns dev-repo-refuse and hard-aborts. Use an explicit target directory outside the dev repo.
Expecting an upgrade to overwrite your design files. Upgrade preserves everything under product-design/ and _output/. Use --dry-run first if unsure.
Running /design before reading what setup scaffolded. Read the generated conventions.md and rule files first; entity and permission wording is hardest to change later.
Expecting source-code writes in a workspace install. Setup never writes to the codebase. Launch the agent with claude --add-dir <codebase-path> before implementing.
