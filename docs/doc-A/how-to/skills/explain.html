How to Explain Behavior or Code

Goal: understand how a part of the system works, or see and resolve the gap between your design intent and the code that implements it. The /explain skill produces explanation reports with diagrams and analogies. It has six mode types; the drift mode additionally offers an interactive workflow to realign diverged specs.

When to Use

  • You want to understand a feature's behavior, the data model, or the overall architecture.
  • You are onboarding yourself onto unfamiliar code and want a junior-friendly walkthrough.
  • You want to trace how a behavior evolved through past plans and commits.
  • You want to detect and resolve drift between product-design/product-design-as-coded.md and product-design/product-design-as-intended.md.

Not for generating artifacts someone else will read (use /document, /communicate, or /onboard). /explain answers your questions about the system.

Required Inputs

  • A mode: architecture, behavior, behavior-evolution, code, data-model, or drift.
  • A brief or target, e.g. /explain code src/auth/middleware.ts or /explain behavior What happens when a form fails validation?
  • For drift mode, populated design intent and as-coded files (the registry in conventions.md declares the pairs that are compared).

Step by Step

General modes (architecture, behavior, code, data-model, behavior-evolution)

  1. Choose the mode that matches your question. Use architecture for a system overview, behavior for a user-visible flow, code for a specific file, data-model for entity relationships, and behavior-evolution to trace change over time.
  2. Run the skill. The report is written under the matching _output/explained-* folder (for example _output/explained-architecture/).
    Expected output: an explanation report with diagrams, plain-language walkthrough, and highlighted design decisions.
  3. Follow up. These modes usually hand off to /research for deeper questions.

Drift mode

  1. Run /explain drift. It compares as-coded and as-intended specs and reports entities, permissions, and UX patterns that have diverged. Narrow the scan with conceptual-design, metacomm, or --scope since-plan plan-<id> (useful right after /implement).
    Expected output: a drift report listing divergences.
  2. Decide how to reconcile.
    • Sync now -- Recommended when the divergence is a straightforward realignment you understand.
    • Move to /plan -- Recommended when closing the drift requires real implementation work.
    • Move to /design -- Recommended when the intent itself has evolved and the spec should change, not the code.
  3. Promote as-coded reality into intent (optional). Run /explain drift --promote to generate D-NNN Decision proposals for items ready to move from as-coded to as-intended. After you have written the Decision entries, run /explain drift --promote --apply-markers plan-<id> to flip the STATUS markers (Phase 3b) via apply_marker.py.
    Expected output: draft Decision entries first; a marker flip isolated as its own audit event second.

Expected Outputs

  • An explanation report under the matching _output/explained-* folder, with diagrams and analogies.
  • In drift mode, a divergence report and -- if you promote -- draft D-NNN Decision entries, then a STATUS marker flip.

Common Mistakes

MistakeBetter approach
Using /explain to write docs for a teammate. Use /document for reader-facing artifacts; /explain is for your own understanding.
Running drift --promote --apply-markers before writing the Decision entries. Promote is two phases: generate and review the D-NNN proposals first, then apply markers so the flip is a clean, separate audit event.
Confusing drift direction: changing code when intent evolved. If the intent changed, update the spec via /design; if the code is behind the spec, plan the change via /plan.
Scanning the whole registry when you only touched one plan's files. Use --scope since-plan plan-<id> to check only the drift a specific plan introduced.
