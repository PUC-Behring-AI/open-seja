How to Make a Plan

Goal: turn an intent -- a feature, a bug fix, or a refactor -- into a reviewable, step-by-step plan before any code changes. The /plan skill produces a structured plan you approve first. It has three modes: standard (single plan, default), lightweight (--light, a quick proposal), and roadmap (--roadmap, a full product roadmap with dependency-aware execution waves).

When to Use

  • You have a clear idea of what to build or fix and want a structured plan before code changes happen.
  • You want a lightweight proposal for a small fix (use --light).
  • You want to decompose a large effort into dependency-aware waves (use --roadmap).
  • You want to preserve the user-experience perspective by framing the brief as a designer's metacommunication message (use --framing metacomm).

Required Inputs

  • A brief describing the change, e.g. /plan Add a tagging feature so users can organize tasks by topic.
  • For roadmap mode, populated design specs (the skill reads them to decompose work items), or a pre-filled spec via --from-spec.
  • Optionally a review-depth override, e.g. --review deep to force all 16 perspectives.

Step by Step

  1. Pick the mode -- or let the skill auto-detect. If you omit both --plan and --roadmap, the skill infers the best mode from your brief (roughly: three or more entities or two or more architectural layers suggests a roadmap; a single bug or file suggests a single plan) and asks you to confirm.
    • Standard single plan -- Recommended when the work is one coherent feature or fix. NOT recommended when the effort spans many independent work items.
    • Lightweight (--light) -- Recommended for small fixes that do not need full step metadata. NOT recommended when the change touches multiple files with real dependencies.
    • Roadmap (--roadmap) -- Recommended when you are building something large and want dependency-ordered waves. NOT recommended for a single, self-contained change.
  2. Run the skill with your brief. For standard mode, the skill produces a plan file under _output/plans/ with steps that each list files to change, verification criteria, and dependencies.
    Expected output: a plan-<id>-<slug>.md file plus a review log.
  3. Review the plan. The skill runs a complexity-gated review (override with --review deep). Read the steps, Best Practices, and Design Decisions before implementing.
  4. For roadmaps, review the wave structure. Roadmap mode decomposes the effort into dependency-aware waves and generates an individual plan for each work item.
    Expected output: a roadmap file under _output/roadmaps/ plus per-item plan files.

Expected Outputs

  • A plan-<id>-<slug>.md file with structured steps (Files, Verify, Depends on, Tests).
  • In roadmap mode, a roadmap summary file plus one plan per work item, grouped into execution waves.
  • An implement pending-ledger entry filed at plan completion so the work stays tracked until you execute it.

Common Mistakes

MistakeBetter approach
Implementing before reviewing the plan. The whole point of /plan is a review gate. Read the steps and Design Decisions before /implement.
Using --light for a multi-file change with dependencies. Lightweight proposals omit full step metadata. Use standard mode when dependencies matter.
Reaching for --roadmap for a single bug fix. Roadmaps are for large, multi-item efforts. A single fix is a standard or lightweight plan.
Planning intent that has not been decided yet. If the intent is still open, research it first with /research, or change the spec with /design.
