How to Critique Quality

Goal: answer any "is it OK?" question -- validation, code review, smoke tests, preflight, harness health, documentation consistency, git freshness, telemetry, test-plan generation, or semiotic inspection. The /critique skill is the unified quality gate. It has ten modes; you run one at a time.

When to Use

  • Before committing, or after making changes, to verify code quality.
  • To check overall project or harness health.
  • To get a go / no-go verdict for merging (use preflight).
  • To generate a structured manual test plan for QA (use test-plan).

Required Inputs

  • A mode: validate, review, smoke, preflight, health, docs, freshness, telemetry, test-plan, or semiotic-inspection.
  • An optional scope, e.g. /critique review src/components or /critique validate i18n.
  • An optional depth override for review and preflight: --depth light|standard|deep.

Step by Step

  1. Pick the mode that matches your question.
    • validate -- Recommended when you want a pass/fail from every project validation script. NOT recommended when you want subjective review of a diff (use review).
    • review -- Recommended when you want perspective-based review of changed code. NOT recommended when you only need script-level validation.
    • preflight -- Recommended when you want a single go / no-go verdict combining validate and review before a merge.
    • health -- Recommended when you want harness self-diagnosis across its nine built-in checks.
  2. Set depth if needed. For review and preflight, --depth deep evaluates all 16 quality perspectives; --depth light is a faster pass with fewer perspectives.
  3. Run the skill. Most modes write a timestamped check-<id> log under _output/critique-logs/. (telemetry is read-only and does not write a log.)
    Expected output: a findings report -- pass/fail per script, perspective findings, a health verdict, or a manual test plan, depending on the mode.
  4. Act on the findings. Fix findings via /plan (then /implement), or reflect on a clean pass with /reflect.

Expected Outputs

  • A check-<id> log under _output/critique-logs/ for most modes, with any Q&A appended inline.
  • For preflight, a go / no-go verdict.
  • For health, a Harness Health Report across the nine built-in checks (skill system, briefs hygiene, plans hygiene, references, conventions, constitution, spec compliance, pending ledger, and harness drift).
  • For test-plan, a structured manual test plan with scenarios, steps, expected results, and edge cases.

Common Mistakes

MistakeBetter approach
Confusing validate with review. validate runs scripts for pass/fail; review applies quality perspectives to a diff. Use the one that matches your question.
Expecting /critique to fix findings. /critique reports. Fix findings by planning and implementing the change.
Using /critique to mutate the pending ledger. Ledger mutations (add / done / snooze / dismiss) flow through /pending. /critique health only surfaces the count as a signal.
Assuming freshness pulls remote changes. freshness reports ahead/behind counts only; it never pulls automatically.
