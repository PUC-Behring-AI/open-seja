How to Generate Documentation

Goal: produce or update project documentation that someone else will read. The /document skill generates structured documentation using project templates and the documentation-quality writing guide. It has four invocation modes -- plan-driven, auto-detect, type-targeted, and bare scope -- and supports six documentation types: readme, contextual-help, api-reference, ddr, help-center, and changelog.

When to Use

  • After implementing a feature or fix that affects user-facing behavior, API contracts, or architectural decisions.
  • When a plan's Docs: fields already specify what to document (use --plan).
  • When you want a broad scan of what changed (use --auto-detect).
  • When you know exactly which type you need (use --type).

Not for stakeholder updates (use /communicate) or personalized onboarding plans (use /onboard). /document produces project documentation artifacts.

Required Inputs

  • An invocation mode and, where relevant, a target: a plan ID (--plan 000130), a doc type (--type readme), or a bare scope (/document src/auth).
  • For auto-detect, a git history to scan (optionally bounded with --since).
  • Project design and template files, which the skill reads to shape the output.

Step by Step

  1. Choose an invocation mode.
    • Plan-driven (--plan <id>) -- Recommended when documentation needs are already captured in a plan's Docs: fields.
    • Auto-detect (--auto-detect) -- Recommended when you want the skill to infer doc needs from recent git changes. NOT recommended when you already know the exact type.
    • Type-targeted (--type <type>) -- Recommended when you know precisely which doc type you need.
    • Bare scope (/document <path>) -- Recommended for ad-hoc documentation of a specific area; the skill infers the best type.
  2. Bound the scan if using auto-detect. Use --since <date>, --since last (changes since the last /document run), or --full-history.
    Expected output: matched doc types based on six heuristics (new API routes, changed models, new UI components, config changes, architectural shifts, breaking changes).
  3. Run the skill. It generates or updates the documentation in the appropriate project location using the matching template.
    Expected output: generated or updated documentation files for each identified need.
  4. Validate consistency. Run /critique docs to check the new documentation against the six consistency scanners.

Expected Outputs

  • Generated or updated documentation of one of the six supported types (readme, contextual-help, api-reference, ddr, help-center, changelog).
  • Files written to the appropriate project documentation location, following the documentation-quality writing guide.

Common Mistakes

MistakeBetter approach
Using /document for a stakeholder update. Stakeholder material is /communicate's job; onboarding plans are /onboard's.
Confusing /document with /explain. /explain is for understanding the system yourself; /document produces artifacts others read.
Running --auto-detect --full-history on a large repo by default. Bound the scan with --since last or a date so you document the recent delta, not the entire history.
Skipping /critique docs afterward. Validate the generated docs for path liveness, terminology, and structural completeness before publishing.
