Design Intent Maintenance

Design intent is the authoritative record of what you meant to build. In SEJA it lives in product-design/product-design-as-intended.md -- a unified file holding the working intent (sections §0-§17), a DDR-shaped Decisions section of D-NNN entries, and a CHANGELOG. This guide covers the day-to-day operations that keep that file honest: editing intent prose, flipping lifecycle markers, creating Decision records, running the promote workflow, and maintaining the As-Intended / As-Coded Registry.

The Maintainer Model

product-design-as-intended.md is classified Human (markers). That means:

  • Prose is human-authored. Only you write the intent narrative, sections, and Decision bodies. Agents may read and propose, but never write prose.
  • Markers are agent-written, but only through one script. Agents update fixed-format lifecycle markers exclusively via apply_marker.py, and only after an explicit confirmation prompt in the same turn.

The companion verifier check_human_markers_only.py rejects any prose mutation that slips through, and check_changelog_append_only.py keeps the CHANGELOG append-only. This split preserves the distinction between design intent (human-authored) and implementation state (agent-maintained).

How to Update the As-Intended File

To change what the project is meant to do, edit product-design/product-design-as-intended.md directly -- this is your file. Add or revise sections, refine the metacommunication message in §11, and record designed journeys (JM-TB-NNN) in §15.

First-person voice is non-negotiable for the metacommunication message. The §11 message must use first-person "I" for the designer and second-person "you" for the user -- never "the designer", "the system", "the user" (third-person), passive voice, or imperative mood. When you supply a metacommunication message as input, the agent records it exactly as written; paraphrasing distorts intent.

  • Change intent when the goal itself changes -- Recommended when what you want the system to do has shifted; run /design to reshape intent, or edit the file for small revisions.
  • Leave intent alone when only the code needs to change -- NOT recommended to touch as-intended for a pure implementation fix; go to /plan instead. Intent and implementation are separate records.

How to Apply Markers with apply_marker.py

apply_marker.py is the sole write path for Human (markers) files. It applies a lifecycle marker HTML comment or appends a CHANGELOG line, rewriting the exact target line and leaving every other word untouched. There are six marker kinds:

Marker What it does
STATUS Sets an item's lifecycle state on a prose section. Lowercase state machine: proposed → implemented → established → superseded. Regression is rejected.
ESTABLISHED Stamps an item as established (a promotion audit record). Stamp-kind marker -- no --value; requires --plan.
INCORPORATED Stamps a UX-research item as incorporated by a plan. Stamp-kind marker; requires --plan.
CHANGELOG_APPEND Appends a validated CHANGELOG line; requires --note and a recognised action value.
DECISION_APPEND Appends a new ### D-NNN: DDR-shaped Decision entry to the Decisions section with an auto-assigned ID.
REQ_TRACED_BY Annotates an existing <!-- REQ-TYPE-NNN --> marker with a traced_by link to signal pre-tracing-system requirements. Stamp-kind marker; --id is the REQ ID.

The general invocation shape is:

python .claude/skills/scripts/apply_marker.py --file <path> --id <entry-id> --marker <kind> --value <value> [--plan <plan-id>] [--date <YYYY-MM-DD>] [--note <text>] [--dry-run]

--value is required for STATUS, CHANGELOG_APPEND, and DECISION_APPEND. The stamp-kind markers (ESTABLISHED, INCORPORATED) take no --value but require --plan. Use --dry-run to print the diff without writing.

Expected output. Exactly one marker line changes; all surrounding prose is byte-identical. If the entry ID is not found or is ambiguous, the script fails with a validation error and writes nothing.

  • Preview with --dry-run first -- Recommended when you are flipping several markers or automating a batch; confirm the diff before committing.
  • Let the skill drive it -- Recommended in normal use: /pending address and the promote workflow call apply_marker.py for you with confirmation, so you rarely run it by hand.

How to Create D-NNN Decision Records

Decision entries live in the ## Decisions section of product-design-as-intended.md under ### D-NNN: Title headings, in DDR shape (Context / Decision / Consequences) with a stable ID. The D-NNN namespace is orthogonal to the REQ-TYPE-NNN requirement namespace -- never intermix them and never write REQ-D-NNN.

The usual capture mechanism is /research's decision-extract flow (step 9b): when advisory Q&A surfaces a settled decision, it offers to create a D-NNN entry via apply_marker.py --marker DECISION_APPEND, with options to create now, defer to the pending ledger, or skip. Each new Decision carries its own STATUS marker above the heading, starting at proposed.

  • Create now -- Recommended when the decision is settled and you want it recorded immediately.
  • Defer to the pending ledger -- Recommended when you want to record it but review the wording later; it files a create-decision-entry pending item.
  • Skip -- Recommended when the exchange was exploratory and captured nothing decision-worthy.

Expected output. A new ### D-NNN: entry appended to the Decisions section with an auto-assigned ID and a STATUS: proposed marker. Standalone published DDR files (via /document --type ddr) can later be sourced from these entries.

How to Run the Promote Workflow

Promotion moves an item from "implemented in code" to "established design intent". The promote workflow is /explain drift --promote, split into two phases so the designer's voice is preserved:

  1. Phase 3a -- proposal generation. Run /explain drift --promote. For items marked STATUS: implemented, it drafts DDR-shaped Decision entries from plan metadata and writes them to _output/promote-proposals/promote-proposal-plan-<id>.md. No markers are flipped and no design file is touched yet.
    Expected output: a proposal file with draft Decision entries for you to review.
  2. Review and adopt in your voice. Read the draft entries, edit them into your own wording, and copy the ones you accept into the ## Decisions section of product-design-as-intended.md.
  3. Phase 3b -- flip the markers. Run /explain drift --apply-markers plan-<id>. This flips the relevant STATUS markers from implemented to established via apply_marker.py, using a heading-only match so prose is never touched.
    Expected output: a marker flip isolated as its own audit event; check_human_markers_only.py guarantees only marker lines change.

Never remove or alter an existing established or implemented marker. These are audit records. Agents may read them and propose new markers, but the promote workflow only advances state forward; regression (e.g. established → implemented) is rejected by the state machine.

How to Maintain the As-Intended / As-Coded Registry

The As-Intended / As-Coded Registry in product-design/conventions.md declares every registered as-intended / as-coded file pair, with a Section column that lets a single file host multiple artifact types (tools discriminate by ID prefix -- for example JM-TB-NNN designed journeys versus JM-E-NNN discovered journeys). The Registry is the single source of truth for /design, /explain drift, and post-skill DONE marker proposals.

When you add a new registered design file or split an artifact type into its own section, update the Registry so the drift and promote tooling can find it. The as-intended half is Human (markers); its as-coded counterpart (product-design-as-coded.md) is Agent-maintained via post-skill and has three H2 sections: Conceptual Design, Metacommunication, and Journey Maps.

  • Register a new pair -- Recommended when you introduce a new design artifact you want drift-checked and promotable.
  • Use the Section column for multi-type files -- Recommended when several artifact types share one file; the ID prefix keeps them discriminable. NOT recommended to leave the Section column blank for a shared file -- tooling then cannot route the types.

Expected output. A Registry that lists every drift-tracked pair. Run /explain drift to confirm the new pair is picked up, and /critique health to validate conventions consistency.

Common Mistakes

Mistake What happens Fix
Editing markers by hand with a text editor. check_human_markers_only.py rejects the change, or the marker stacks incorrectly. Use apply_marker.py (directly or via the skill) as the sole write path.
Letting an agent rewrite intent prose. Violates the Human (markers) classification; the verifier blocks it. Author prose yourself; agents propose changes and write only markers after confirmation.
Copying promote proposals verbatim without editing. The Decision entries read in machine voice, not yours; intent loses nuance. Rewrite each adopted entry in your own words before pasting into the Decisions section.
Interpolating D-NNN into the REQ taxonomy (e.g. REQ-D-NNN). Namespace collision; traceability tooling misroutes the ID. Keep D-NNN Decisions and REQ-TYPE-NNN requirements strictly separate.
Writing the metacommunication message in third person or passive voice. Breaks the semiotic I/you contract; the phrasing rule is violated. Use first-person "I" for the designer and second-person "you" for the user throughout §11.
