Installation and Setup

This guide walks you through installing the SEJA harness into your project. There are four supported install variants, formed by two independent choices: whether your project is new (greenfield) or existing (brownfield), and whether the harness files live in the same repository as your source (collocated) or in a separate companion workspace repository. Every variant is driven by the single entry-point skill /seja-setup. Use the decision tree below to pick your path, then jump to the matching section.

Choosing Your Install Path

Answer two questions. The intersection selects one of four variants.

  1. Is this a new project or an existing one? A directory with no source code yet is greenfield; a directory that already holds code under version control is brownfield.
  2. Do you want the harness in the same repo, or a companion workspace? Collocated puts .claude/ and product-design/ in the same repository as your source. Workspace keeps them in a separate git repository that never writes into your codebase.
Collocated (same repo) Workspace (companion repo)
Greenfield (new project) Greenfield collocated Greenfield workspace
Brownfield (existing codebase) Brownfield collocated Brownfield workspace

The /seja-setup skill accepts these arguments; the variants below show which ones each path uses:

Argument Purpose
<target-directory> Path to the project directory to install into. Required unless you use --here, --upgrade, or the no-argument flow.
--here Finalise setup in the current directory without copying harness files (use after you cloned SEJA directly into your project folder).
--workspace Create a separate companion workspace directory alongside an existing or new codebase.
--demo Install with the pre-configured TaskFlow demo project (not covered as a primary variant here).
--upgrade Refresh harness files in an already-installed project to the latest release, preserving project-specific files.
--version <tag> Pin to a specific public seja release tag (e.g. v0.1.0). Default: latest SemVer tag.
--dry-run Preview upgrade changes without applying them (valid with --upgrade).

Tip. The full argument pattern is [<target-directory>] [--here | --workspace | --demo | --upgrade] [--version <tag>] [--dry-run]. The mutually exclusive flags (--here, --workspace, --demo, --upgrade) cannot be combined; /seja-setup rejects any invalid combination with an error.

Greenfield Collocated

Recommended when you are a solo designer or a small team starting a brand-new project from scratch and you want the harness files to live alongside your source code in one repository. NOT recommended when you must keep the harness audit trail out of the source repository (choose a workspace variant instead), or when you are layering SEJA over an existing codebase (choose a brownfield variant).

Two paths lead to the same finalised project. Pick the one that matches whether you already have a local SEJA clone on disk.

Path A: install from an existing SEJA clone

Choose this when you already have a SEJA clone on disk and want to copy the harness into a fresh target directory. From your existing SEJA clone, run /seja-setup <project-path>.

/seja-setup resolves the target version (latest SemVer tag, or the value of --version), copies harness files into <project-path>, writes .seja-version as the baseline for future /seja-setup --upgrade runs, runs the Section 1 scaffolding questionnaire to populate product-design/conventions.md, scaffolds CLAUDE.md, stack-flavored .claude/rules/, and (if a backend is present) smoke-test infrastructure, then hands off to /design.

Expected output. A populated project directory containing .claude/, product-design/conventions.md (no unresolved {{VAR}} placeholders), a scaffolded CLAUDE.md, an _output/ skeleton, and a .seja-version pin. The handoff message reports the scaffolded stack and directs you to run /design.

Path B: clone SEJA directly into the project folder

Choose this when you do not have a local SEJA clone, or when you want to explore SEJA and decide later whether to keep it. Pin to a release at clone time so setup can capture an exact-match tag: 

git clone --branch v0.1.0 --depth 1 https://github.com/simonedjb/seja my-project

Then open Claude Code in my-project/ and run /seja-setup --here. The --here flag finalises setup in place without copying harness files (the clone already provided them). If you cloned main instead of a tag, /seja-setup --here records the literal string HEAD in .seja-version and prints a warning.

/seja-setup --here first inspects the directory via detect_setup_state.py and classifies it into one of six states. The baseline clone-into command above lands in fresh-download, which proceeds directly:

State Meaning and routing
dev-repo-refuse The directory looks like the SEJA harness development repository. Hard-abort; no mutation.
public-clone-soft-confirm A clean public seja clone at the default branch. Prompts "Yes, continue" / "No, cancel" before proceeding.
finalised An already-seeded project. Offers "Upgrade instead" / "Re-run setup anyway" / "Cancel".
fresh-download Harness files present, no project state yet. Proceeds directly.
partial-init Harness files plus partial project state. Proceeds directly with reconciliation semantics (pre-existing files are logged and skipped).
no-harness No harness files found. Aborts; you are not in a SEJA download.

/seja-setup --here then asks how to handle SEJA's git history. No default is preselected -- you must pick:

  • Re-init fresh. Recommended when the project's history starts here -- SEJA's history is not yours. NOT recommended when you intend to fork and track upstream SEJA changes. A second free-text confirmation (type confirm) is required before rm -rf .git && git init runs.
  • Keep history and add a project remote. Recommended when you intend to fork and track upstream SEJA changes. NOT recommended when you do not want SEJA's history in your project repo. Prompts for your remote URL, then runs git remote rename origin upstream && git remote add origin <url>.
  • Leave as-is. Recommended when this is throwaway exploration you will not push to a remote. NOT recommended when you are setting up a long-lived project.

Warning. "Re-init fresh" permanently deletes SEJA's git history. The second free-text confirmation exists to prevent muscle-memory click-through; /seja-setup never auto-deletes .git.

After the git-history choice, /seja-setup --here presents a cleanup prompt for harness-dev artefacts (only artefacts that actually exist appear as rows). Defaults: docs/ moves to docs/seja/; SEJA's README.md and CHANGELOG.md are renamed with a SEJA- prefix; LICENSE and TRADEMARKS.md are kept in place. Nothing is silently deleted -- you submit the prompt to confirm the batch. Finally, it creates an initial commit and hands off to /design.

Expected output. A finalised project in the current directory with .seja-version pinned, an _output/ skeleton, an empty product-design/ ready for /design, and an initial commit. The handoff message confirms the pin and directs you to run /design.

Greenfield Workspace

Recommended when you are starting a brand-new project and want the harness files, design history, and generated output to live in a separate workspace repository while your source code lives in its own clean repository -- for example, a consultancy that keeps a per-engagement audit trail, or a team that must not commit design artefacts into the product repo. NOT recommended when you prefer the simplest possible layout with everything in one repo (choose greenfield collocated instead).

Run /seja-setup <workspace-path> --workspace from inside the foundational harness. Answer the prompts that ask for the codebase path; this pins the workspace to a specific source tree without copying anything into it.

In workspace mode, /seja-setup creates the workspace directory, runs git init inside it, copies .claude/ and product-design/ into it, sets CODEBASE_DIR in the workspace's product-design/conventions.md to the absolute path of the codebase, and generates launcher scripts (launch.sh / launch.bat) that start the agent with the codebase attached as an additional working directory via claude --add-dir. The codebase itself is never written to by setup.

Expected output. An independent workspace git repository containing .claude/, product-design/, _output/, and launcher scripts, with CODEBASE_DIR set by absolute path to your source tree. The source codebase directory is untouched. Change into the workspace and run /design next -- all generated design files land under the workspace's product-design/.

From there, run /design, /plan, and /implement from the workspace. When you implement, launch the agent from the workspace with claude --add-dir <codebase-path> (or use the generated launcher). Source-code changes land in the attached codebase repo; design reconciliation, plans, and briefs land in the workspace repo.

Brownfield Collocated

Recommended when you have an existing codebase and want to introduce SEJA into it without a separate workspace -- the harness files live inside the same repository as your source. NOT recommended when policy or compliance requires the harness audit trail to stay out of the product repository (choose brownfield workspace), or when the codebase is a fresh empty project (choose a greenfield variant).

The common brownfield route is to point /seja-setup <target> at your existing project root from an existing SEJA clone. Alternatively, you can clone SEJA into the codebase root and finalise in place: 

git clone https://github.com/simonedjb/seja .

Then open Claude Code in that directory and run /seja-setup --here. Unlike a greenfield project, you are laying the harness over a tree of code that is already under version control. During setup, the Section 1 questionnaire auto-detects your stack: it scans dependency files (package.json, requirements.txt, pyproject.toml, Cargo.toml, go.mod, and others) and directory structure, then presents detected values as confirmation prompts ("I detected flask; correct?") rather than open-ended entry. The same git-history and cleanup prompts described under Greenfield Collocated Path B apply.

Expected output. Your existing codebase, now carrying .claude/, a populated product-design/conventions.md pre-filled from the detected stack, a scaffolded CLAUDE.md, and an _output/ skeleton. Your source tree is otherwise unchanged. Run /design in brownfield mode next.

After setup, the recommended brownfield sequence is:

  1. Run /design. It detects that code already exists, reads the codebase to draft product-design/product-design-as-coded.md, and seeds product-design/product-design-as-intended.md with a target-state draft you refine.
    Expected output: a design spec set capturing both as-coded reality and as-intended target; product-design/constitution.md generated and Human-owned.
  2. Run /explain architecture, /explain data-model, and /explain behavior <feature> for the areas you intend to touch first.
    Expected output: analysis reports with diagrams under _output/explained-<id>/; the codebase is read-only during these passes.
  3. Run /plan <description> targeting the highest-priority gap between as-coded and as-intended. Then /implement <plan-id>, verify in the running codebase, and run /explain drift --promote.
    Expected output: draft D-NNN Decision entries under _output/explained-<id>/; no markers flipped yet.
  4. Review the draft Decisions, then run /explain drift --apply-markers plan-<id> to flip STATUS: proposed to STATUS: implemented via apply_marker.py.
    Expected output: a marker flip isolated as its own audit event; check_human_markers_only.py guarantees only marker lines change.

Brownfield Workspace

Recommended when you are a growing team or an enterprise introducing SEJA alongside an existing codebase and you want the harness files, design decisions, and audit trail to live in a workspace repository that never writes into the codebase -- the compliance-ready layout. NOT recommended when a single-repo layout is acceptable and you want the least operational overhead (choose brownfield collocated).

Run /seja-setup <workspace-path> --workspace from inside the foundational harness and answer the prompts for the existing codebase path. This creates the workspace, runs git init inside it, sets CODEBASE_DIR to the absolute path of the existing codebase, and writes launcher scripts. The codebase is only read (to validate the path exists), never written to during setup.

Expected output. An independent workspace git repository pinned to your existing codebase by absolute CODEBASE_DIR, with launcher scripts that attach the codebase via claude --add-dir. The codebase repository is untouched.

The design, explain, plan, implement, and drift-promote sequence mirrors Brownfield Collocated, with one difference: every generated artefact lands in the workspace repository, while source-code writes from /implement land in the attached codebase. Design reconciliation, plans, briefs, Decision entries, and marker flips all stay inside the workspace git history -- your decision audit trail.

To keep the workspace current as the foundational harness evolves, run /seja-setup --upgrade from the workspace periodically (or, for the scripted path, upgrade_harness.py --from <source> --target <workspace>). Upgrade refreshes .claude/ and the non-project template references while preserving everything under product-design/ and _output/.

Expected output. A single reviewable upgrade commit in the workspace git history. Project-specific files (product-design/**, .claude/settings.json, CLAUDE.md, _output/) are never overwritten. Pass --dry-run to preview the changes first.

Verifying Your Install

Regardless of variant, you can confirm a healthy install before writing any plans:

  • .seja-version exists and holds a release tag (e.g. v0.1.0), or the literal HEAD if you installed from main.
  • product-design/conventions.md exists with no unresolved {{VAR}} placeholders (greenfield and brownfield collocated, after the scaffolding questionnaire).
  • .claude/, CLAUDE.md, and an _output/ skeleton are present at the harness root (workspace root for workspace variants).
  • Run /critique health for a full harness self-diagnosis once /design has populated the design intent files.

Common Mistakes

Mistake What happens Fix
Combining mutually exclusive flags (e.g. --here --workspace). /seja-setup rejects the invocation with an error. Use --here, --workspace, --demo, and --upgrade one at a time.
Cloning main instead of a tagged release before --here. .seja-version records the literal HEAD and a warning prints; future --upgrade runs may not resolve relative deltas cleanly. Clone with --branch <tag>, or pass --version <tag> to set an explicit baseline.
Expecting "Re-init fresh" to run after one click. Nothing is deleted -- /seja-setup requires a second free-text confirm before touching .git. Type confirm exactly when prompted; any other input aborts the git action and leaves .git intact.
Running /seja-setup --here or the no-arg flow inside the SEJA development repository. State detection returns dev-repo-refuse and hard-aborts with no mutation. Run /seja-setup <target-directory> with an explicit target outside the dev repo.
Expecting source-code writes in a workspace install. Setup never writes to the codebase; without claude --add-dir, /implement cannot reach the source tree. Launch the agent from the workspace with claude --add-dir <codebase-path> (or the generated launcher) before implementing.
Running /design immediately without reading what setup scaffolded. Entity names, role labels, and permission rules are hardest to change once plans are written against them. Read the generated product-design/conventions.md and design files end to end and adjust wording before your first /plan.
