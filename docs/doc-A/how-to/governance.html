Governance Operations

This guide covers the recurring governance tasks that keep a SEJA project honest: writing and maintaining a constitution of immutable principles, managing the pending-actions ledger that tracks outstanding human work, running the harness's own quality gates before you commit, and enforcing the pre-commit hook that guards the private/public boundary. Each section is goal-first and marks its decision points.

How to Write and Maintain a Constitution

The constitution lives at product-design/constitution.md. It holds the non-negotiable commitments -- on design authority, epistemic posture, privacy, lifecycle discipline, artifact integrity, and authorship voice -- that every skill and agent must observe. It is loaded first by pre-skill, before conventions or any other reference file, so its rules take precedence over everything else. It is classified Human: agents may read and propose changes, but never write it.

/design generates the initial constitution (Interview-Driven mode derives principles from your answers). Organise principles into the template's sections: Technical, Quality, Security Invariants, Compliance Requirements, plus an Enforcement section and a Changelog. Each principle carries a stable ID (e.g. T1, Q2, S1, C1) and a rationale.

  • Derive principles by interview -- Recommended when the project is new and the design values are still being articulated; /design Mode 5 turns confirmed interview answers into principles.
  • Hand-author from an existing charter -- Recommended when you already have written values and just need them in the template shape. NOT recommended when the values are implicit -- interview mode surfaces them better.

Amending the constitution. Any change must be explicitly approved by the project lead and recorded in the file's own Changelog section. Because the file is Human- maintained, agents propose amendments via a confirmation prompt but never edit the principles directly.

Expected output. A product-design/constitution.md with identified principles, each with a rationale, plus an Enforcement section. Once present, /critique health validates its presence as one of its built-in checks.

How to Manage the Pending Ledger

The pending-actions ledger at _output/pending.jsonl is the harness's record of outstanding human work -- markers to flip, tests to run, docs to update, decisions to write. It is append-only, so you never lose history. Pre-skill surfaces open items at the top of every lifecycle skill invocation. All mutation flows through the /pending skill, which dispatches to the underlying pending.py script.

/pending exposes six subcommands: list (read-only listing with per-type advice), address (guided resolution for marker-flip types), add, done, snooze, and dismiss.

Task Command
List every open item grouped by type, each with resolution advice. /pending
Run the guided resolution workflow for one item (per-candidate marker flips with confirmation). /pending address pa-000003
File a custom reminder that pre-skill will keep surfacing. /pending add --type user-defined --source plan-000042 --description "review CSRF middleware"
Mark an item complete. /pending done pa-000003
Hide an item until a date, then resurface it. /pending snooze pa-000005 --until 2026-05-01
Dismiss an item without completing it, recording a reason. /pending dismiss pa-000007 --reason "no longer relevant after redesign"

The harness files many action types automatically -- for example mark-implemented, test-implementation, verify-as-coded, update-documentation, apply-promote-markers, spec-drift-check, periodic-curation, incorporate-research-markers, implement, review-downstream-plan, create-decision-entry, and your own user-defined reminders. Each type comes with type-specific advice on how to resolve it.

  • Address now -- Recommended when the item is a marker flip the harness can walk you through with confirmation (e.g. mark-implemented).
  • Snooze -- Recommended when the item is real but blocked on something dated; it resurfaces automatically.
  • Dismiss -- Recommended when the item is genuinely obsolete. NOT recommended as a way to silence noise you intend to do later -- snooze instead so the history stays honest.

Expected output. A curated ledger where open items reflect real outstanding work. /critique health reports the pending-ledger count as a diagnostic signal only -- it never mutates the ledger; that always flows through /pending.

How to Use the Private / Public Sync Pipeline

A SEJA project (and SEJA itself) can maintain a private working tree and a polished public distribution. Private content -- design files, research logs, plans, and the constitution -- must never reach the public repo without explicit opt-in. Two mechanisms enforce this boundary at authoring time:

  • Conditional markers for partial content. Wrap private-only fragments inside a shared file in <!-- priv-only-start --> / <!-- priv-only-end --> HTML comments. The sync tool's stripper removes everything between the markers (inclusive) when copying .md files. The markers are invisible in rendered Markdown and self-documenting in source.
  • The scripts/priv/ directory for whole files. Scripts with no public use case live in .claude/skills/scripts/priv/, which is excluded from sync entirely, so consumers never receive them.

The release itself is orchestrated by /publish, which clones the public repo into a temporary workspace, copies authored public prose, generates .claude/ with private directories excluded and markers processed, runs smoke tests, commits, and pushes. You do not hand-sync the public tree -- edit only the private sources and let the pipeline generate the public copy.

Never recreate the public .claude/ on disk. It is generated ephemerally during publish. Edit the private .claude/ and product-design/ sources; public prose (README, CHANGELOG, docs) is authored directly in the public tree.

How to Run Quality Gates

The /critique skill is the unified quality gate. It runs one mode at a time; the governance-relevant modes are:

Command What it does
/critique validate Runs all project validation scripts and reports pass/fail with details.
/critique preflight Combined validate + review in one pass -- a go / no-go verdict for merging.
/critique preflight --depth light A faster preflight with fewer perspectives.
/critique health Harness self-diagnosis across 9 built-in checks (skill system, briefs hygiene, plans hygiene, references, conventions, constitution, spec compliance, pending ledger, harness drift).
/critique docs Runs 6 documentation consistency scanners (harness integrity, path liveness, env vars, command refs, terminology, structural-completeness).

Run /critique preflight before committing anything significant. Violations discovered during a review or preflight that touch the constitution's Security Invariants are classified blocking -- they must be resolved before commit, not deferred.

  • Preflight before commit -- Recommended for changes that touch source code or design intent; it gives a single go / no-go verdict.
  • Health after an upgrade -- Recommended right after /seja-setup --upgrade to confirm the harness is internally consistent.
  • Light preflight -- Recommended when you want a fast signal on a small change. NOT recommended as the final gate before a release; use full preflight there.

Expected output. A timestamped check-NNN log under _output/ with a pass/fail verdict and per-perspective findings. A clean preflight is a good moment to move to /document or /reflect.

How to Enforce the Pre-Commit Hook

The pre-commit hook is the last line of defence for the private/public boundary. Install it once per clone by running bash .githooks/install.sh. On every commit it runs fast preflight checks and the leak gate (check_no_private_leaks.py --staged), which blocks the commit if staged content would leak private material.

Never bypass the hook. Passing --no-verify to circumvent it requires explicit designer approval recorded in a Decision entry. Hook bypass is the most common accidental path to leaking private content or shipping unvalidated code -- treat it as a governance event, not a convenience.

  • Fix the flagged content -- Recommended always: resolve what the leak gate reports, then re-commit.
  • Record an approved exception -- Recommended only when the project lead has approved it and the rationale is captured in a D-NNN Decision entry. NOT recommended as a routine unblock.

Expected output. Commits that pass the fast preflight and leak gate. The same leak scan runs again during /publish before syncing, so a passing commit is not a substitute for the publish-time gate -- it is an early, local one.

Common Mistakes

Mistake What happens Fix
Hand-editing product-design/constitution.md as an agent. The file is Human-maintained; agent writes violate the maintainer classification. Propose changes via a confirmation prompt; let the human author them and record the change in the Changelog.
Editing _output/pending.jsonl by hand. Direct edits bypass the append-only contract and can corrupt the ledger. Use /pending subcommands (add / done / snooze / dismiss) for every mutation.
Dismissing pending items you actually intend to do later. The work disappears from pre-skill's surfaced list and is lost. Snooze with --until so it resurfaces on schedule.
Recreating the public .claude/ on disk to hand-sync. There is no on-disk public mirror; hand-syncing diverges from the generated output. Edit private sources only; run /publish to generate the public copy.
Committing with --no-verify to skip the hook. The leak gate and fast preflight are skipped -- private content can slip out. Fix the flagged content; bypass only with recorded designer approval in a D-NNN entry.
