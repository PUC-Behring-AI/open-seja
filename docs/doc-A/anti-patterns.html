How Not to Use SEJA

SEJA's guarantees -- that AI-assisted development stays governable and epistemic, that design intent is preserved, that private material never leaks -- are not automatic. They hold only when the harness is used the way it was designed to be used. Each guarantee is enforced by a mechanism (a lifecycle step, a write path, a commit gate, a ledger), and each mechanism can be circumvented. When it is, the guarantee it protected silently disappears.

This page catalogs seven common anti-patterns: ways of working that look faster or more convenient in the moment but that undermine the very properties that make SEJA worth using. For each, we describe the symptom (what it looks like in practice), the consequence (why it is harmful), and the correct approach (what to do instead). If you recognize your own habits here, the fix is usually to slow down by one step and let the harness do the work it was built to do.

1. Bypassing the lifecycle

Symptom
You have a change in mind and you jump straight to /implement, skipping /research (or /explain) and /plan. The lifecycle's canonical path -- /research (or /explain) → /design | /plan → /implement → /critique → /document | /communicate → /reflect -- gets collapsed into a single implementation burst because the earlier steps feel like overhead.
Consequence
Lifecycle discipline is the core value SEJA provides; bypassing it defeats the governance model (constitution principle T1). Without a preceding /research or /explain pass you implement against an unverified mental model of the codebase, and without a /plan there is no reviewed, committed record of intent for /critique to validate against or for /reflect to learn from. The epistemic scaffolding that surfaces unknowns before you commit to a direction is simply absent.
Correct approach
Follow the canonical path. Investigate first with /research (or /explain when you need to understand existing behavior or reconcile drift), then produce a plan with /plan, and only then run /implement against that plan. Auto mode reduces clarifying questions; it does not license skipping steps. Every user-facing skill still runs pre-skill on entry and post-skill on exit, so the discipline holds even when you move quickly.

2. Hand-editing Human (markers) files

Symptom
You (or an agent acting on your behalf) open a Human (markers) file such as product-design-as-intended.md and edit its lifecycle markers directly in a text editor -- flipping a STATUS line, pasting in a decision entry, or appending a changelog line by hand -- instead of going through apply_marker.py.
Consequence
These files encode the boundary between human-authored design intent and agent-maintained lifecycle state (constitution principle T2). apply_marker.py is the sole write path for markers: it validates marker syntax, enforces the allowed status transitions, and keeps the file readable by the harness validation scripts. A hand-edited marker can use a value or transition the tools reject, desynchronize the machine-readable record, and break the very checks that keep as-intended and as-coded state aligned.
Correct approach
Write prose intent as a human designer; leave markers to the tooling. Agents apply markers only via apply_marker.py, and only after an AskUserQuestion confirmation. The script supports five marker types -- STATUS, ESTABLISHED, INCORPORATED, CHANGELOG_APPEND, and DECISION_APPEND -- so whatever the lifecycle event, there is a validated command for it rather than a manual edit.

3. Skipping pre-commit hooks

Symptom
A commit is blocked by the pre-commit hook, and instead of reading and fixing the reported problem you reach for git commit --no-verify to push the commit through unchecked.
Consequence
The pre-commit hook runs the fast preflight checks and then the pre-sync leak gate (check_no_private_leaks.py --staged) on every commit. Hook bypass is the most common accidental path to leaking private content or shipping unvalidated code (constitution invariant S2). Once private material reaches a public mirror it can be cached irreversibly (S1), so a single --no-verify can undo the whole privacy guarantee.
Correct approach
Treat a blocked commit as a signal, not an obstacle: read the hook output, fix the underlying cause, and re-run the commit so the checks pass. No plan or implementation step may circumvent the hook without explicit designer approval recorded in a D-NNN decision entry. If you have not installed the hook yet, install it once per clone so the gate runs automatically.

4. Mixing private content into public docs

Symptom
While writing public-facing documentation you paste in material that belongs only to the private workspace -- design rationale, decision records, internal research logs, plan files, or content from product-design/ -- because it happened to be the most convenient source text at hand.
Consequence
Private content (design files, research logs, plans, product-design/ files, the project constitution) must never reach the public mirror without explicit opt-in (constitution invariant S1). The product-design/ directory in particular is permanently private and is never synced. Mixing it into public docs exposes internal reasoning the designer did not choose to publish, and unlike a code bug the exposure is effectively permanent once mirrored and indexed.
Correct approach
Keep a clean separation of sources. Public prose is authored directly in the public surface; private design and workspace material stays in the private repository. When a public page needs a fact that lives in a private file, summarize or restate the fact rather than copying the private text. The leak gate (check_no_private_leaks.py --staged) is the safety net, not the plan -- author with the boundary in mind and let the gate catch mistakes.

5. Ignoring pending actions

Symptom
Outstanding human actions accumulate in the pending ledger (_output/pending.jsonl) -- implementations awaiting verification, markers awaiting a status flip, periodic curation due -- and you never run /pending to review or resolve them. The pre-skill pending notice scrolls by unread.
Consequence
SEJA is designed to surface what is not yet done or not yet verified, not only what has been decided (constitution principle Q2). The pending ledger is where deferred, human-owned follow-ups live: status markers that should have been flipped, implementations that still need verification, drift checks that are due. Ignoring it lets the machine-readable record drift out of step with reality, so the harness's confident-looking outputs quietly rest on stale state.
Correct approach
Run /pending regularly. With no argument it lists every open item grouped by type with a per-item recommendation; /pending address <id> runs the guided resolution (including marker flips through apply_marker.py after confirmation), and done, snooze, or dismiss close items you have handled or deliberately deferred. Draining the ledger keeps the record honest.

6. Treating the constitution as optional

Symptom
A plan or implementation step contradicts a constitutional principle -- overriding design intent, bypassing a security invariant, rewriting the first-person metacommunication voice -- and it is allowed to proceed on the assumption that the constitution is advisory guidance rather than a binding contract.
Consequence
The constitution holds SEJA's immutable, non-negotiable principles; it is loaded first by pre-skill, before conventions or any other reference, and its rules take precedence over everything else. Design intent is authoritative (principle Q1): no plan or implementation step may contradict the constitution without an explicit, designer-approved D-NNN decision record. Treating it as optional turns a governance failure into a silent one -- the harness keeps running while the guarantees it advertises no longer hold.
Correct approach
Read the constitution as binding. When a genuine tension arises between what a principle requires and what a task wants, do not quietly override it: surface the conflict and record an explicit D-NNN decision entry with designer approval. Violations found during /critique review or preflight are classified as blocking and must be resolved before commit -- so the cheapest path is to respect the principle up front.

7. Running /implement without a plan

Symptom
You invoke /implement with no plan in _output/plans/ to execute against, expecting the skill to improvise the work from a one-line request. This is closely related to bypassing the lifecycle, but the specific failure is the missing planning artifact rather than the skipped research pass.
Consequence
/implement is designed to execute a previously generated plan. Without one there is no reviewed statement of intent, no step decomposition, and no Verify criteria for /critique to check the result against. The pending ledger never receives the implement item that /plan files and /implement closes, so the governance trail that connects intent to execution is broken from the start.
Correct approach
Before coding, always check for an existing plan in _output/plans/. If none exists, run /plan first to produce one, review it, and then run /implement against it. Only waive the plan when the designer has explicitly chosen to -- and even then, prefer /plan --light for a lightweight proposal over no plan at all.
