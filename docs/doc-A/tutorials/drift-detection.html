Drift Detection and Alignment

Over time, the code in your project and the design intent you wrote will diverge. A feature gets added without updating the design files. A decision gets made during implementation that changes the original plan. This divergence -- called drift -- is normal and inevitable. What matters is detecting it and deciding what to do about it. This tutorial walks you through the entire drift cycle: introducing drift deliberately, detecting it, and resolving it.

Prerequisites

  • A working SEJA project with at least one implemented feature (complete Chapter 1 and Chapter 2 first)
  • The to-do app project (my-todo-app) open in your terminal

Part 1: Introduce Drift Deliberately

To learn how drift detection works, you will introduce drift on purpose. In your to-do app, the design intent says tasks have three priority levels (high, medium, low). You will now add a fourth level -- critical -- directly in the code, without updating the design intent file.

Step 1: Modify the code

Open your task model and add a fourth priority level. For example, if your Task class uses an enum, add CRITICAL = 0 before HIGH = 1. Update the CLI to accept --priority critical. Commit the change: 

git add -A
git commit -m "add critical priority level"

Step 2: Leave the design intent unchanged

Do not update product-design/product-design-as-intended.md. The design intent still says there are three priority levels. This gap between what the code does and what the design says is drift.

What just happened?

You have created a controlled divergence between two sources of truth in your project. The as-intended file (product-design/product-design-as-intended.md) describes what you designed. The as-coded state (your actual source code and product-design/product-design-as-coded.md) describes what the code actually does. When these two diverge, SEJA calls it drift.

Drift is not inherently bad. Sometimes the code evolved for good reasons during implementation, and the design intent needs to catch up. Sometimes the code drifted accidentally and needs to be brought back in line. The important thing is to know about the drift and decide what to do about it.

Part 2: Detect the Drift

Run the drift detection skill: 

/explain drift

Expected output

The agent compares your as-intended and as-coded design specs. It reads the As-Intended / As-Coded Registry in product-design/conventions.md to know which file pairs to compare, then scans each pair for divergences. The drift report looks like this: 

# Drift Report

## Conceptual Design

### Priority entity
As-intended: Three levels (high, medium, low)
As-coded:    Four levels (critical, high, medium, low)
Drift:       As-coded adds "critical" level not present in as-intended

## Summary
1 entity with drift detected
0 permissions with drift
0 UX patterns with drift

The report identifies exactly where the divergence is: the priority entity has four levels in code but only three in the design intent. The agent then asks whether you want to sync -- that is, whether you want to resolve the drift.

What just happened?

The /explain drift skill performed a structured comparison between your design intent and your implementation. Unlike a simple text diff, it understands the semantic structure of your design documents: entities, permissions, UX patterns, and journey maps. It reports not just that something changed but what the change means in design terms.

The registry in product-design/conventions.md tells the drift detector which files to compare. This registry is the single source of truth for all drift-related operations. When you add new design files, you register them here so drift detection covers them automatically.

Part 3: Resolve the Drift

There are two ways to resolve drift:

Option A: Update the design intent to match the code
If the code change was intentional and the design intent should catch up, you promote the as-coded state into the as-intended file. This is the more common resolution -- the implementation discovered something the original design missed.
Option B: Change the code to match the design intent
If the code change was accidental or undesirable, you revert the code to match the design intent. This is less common but important when implementation drifted from a deliberate design decision.

Resolving with the promote workflow

For this tutorial, the "critical" priority level was an intentional improvement. Promote it: 

/explain drift --promote

The agent generates a Decision proposal (a D-NNN entry) that documents why the design intent is changing. The proposal follows the DDR (Design Decision Record) shape: 

### D-042: Add critical priority level

Context: Users reported that "high" was not urgent enough
         for time-sensitive tasks.
Decision: Add a "critical" priority level above "high."
Trade-offs: Four levels increase cognitive load slightly,
             but the gain in urgency signaling outweighs the cost.
Status: Accepted

After you confirm the Decision entry, the agent flips the STATUS markers in your as-intended file. The priority entity in product-design/product-design-as-intended.md is updated to include four levels, and the drift is resolved.

Applying the markers

Once the Decision entry is written, apply the STATUS markers: 

/explain drift --promote --apply-markers plan-000042

Replace plan-000042 with the actual plan ID. The agent flips the STATUS: implemented markers for items covered by the plan.

What just happened?

You resolved the drift using the promote workflow, which is split into two phases:

  • Phase 3a: Generate Decision proposals. The agent creates a DDR-shaped entry (D-NNN) that captures the context, decision, and trade-offs. This entry becomes a permanent record of why the design changed.
  • Phase 3b: Apply STATUS markers. The agent flips the lifecycle markers (STATUS: implemented) for items that are now aligned.

The promote workflow connects two aspects of SEJA's governance: enforcement (the drift detector catches divergences) and epistemic awareness (the Decision entry records why the divergence happened). Drift is not just an error to fix -- it is a signal that something was learned during implementation that the original design did not anticipate. The Decision entry preserves that learning.

For a deeper exploration of how governance and epistemic awareness interact, see The Governable AND Epistemic Thesis.

When Drift Matters

Drift detection is most valuable at two moments in the lifecycle:

After implementing a plan
Run /explain drift --scope since-plan plan-000042 to check whether the implementation introduced any unintended divergence from the design intent. This scoped check is faster than a full drift scan because it only examines registry files touched by the plan.
After a reflection cycle
After /reflect closes a development cycle, run /explain drift to catch accumulated divergences across multiple features. This is the recurring governance rhythm: build, validate, document, reflect, then check for drift.

Summary

In this tutorial, you:

  1. Introduced deliberate drift by modifying code without updating design intent
  2. Detected the drift with /explain drift
  3. Resolved the drift using the promote workflow (--promote and --apply-markers)
  4. Created a Decision entry (D-NNN) documenting why the design changed

Drift detection is SEJA's mechanism for keeping design intent and implementation in sync. It treats drift as a signal, not just an error: when code and intent diverge, something was learned during implementation. The Decision entry captures that learning so future development can build on it.
