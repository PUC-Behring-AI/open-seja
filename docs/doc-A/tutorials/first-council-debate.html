Your First Council Debate

When a design decision has real trade-offs and no obvious right answer, a single perspective is not enough. SEJA's council debate convenes multiple named expert archetypes -- a Security Advocate, a DX Pragmatist, a UX Champion, an Architecture Purist, and a Product Strategist -- and runs them through structured argumentation. This tutorial walks you through running your first debate.

Prerequisites

  • A working SEJA project (complete Chapter 1 first)
  • The to-do app project (my-todo-app) open in your terminal

The Design Question

Your to-do app has been growing. A user requests shared task lists -- the ability for multiple people to collaborate on the same set of tasks. This is a high-stakes question: it changes the data model, introduces authentication, raises privacy concerns, and could fundamentally alter the product's identity as a personal task manager.

This is exactly the kind of decision that benefits from a council debate: there are genuine trade-offs, reasonable people would disagree, and the stakes are high enough that you want to hear all sides before committing.

Running the Debate

Invoke a deep research session with the council debate: 

/research --deep Should the to-do app support shared task lists?

The --deep flag activates the council debate mode instead of the standard research mode. SEJA convenes the five fixed archetypes and runs the structured debate protocol.

Expected output: Round 1 -- Position Statements

Each expert states their position in 2-3 sentences, arguing from their genuine priority:

Security Advocate
Shared lists require authentication, authorization, and access control. Today the app stores data locally in SQLite with no user identity. Adding sharing means adding a trust boundary that does not exist yet, and every shared-data feature becomes a potential data-leak surface. The risk is disproportionate to the feature's value for a personal task manager.
DX Pragmatist
Sharing would require migrating from SQLite to a networked database, adding an API layer, and building a sync mechanism. That is a 10x increase in implementation complexity for a feature that might not be the product's core value proposition. Ship the single- user experience well first; sharing can come later if demand proves real.
UX Champion
Users who asked for shared lists have a real need -- families and small teams do share tasks. But the current app's strength is its simplicity. Adding sharing risks making the common case (solo use) worse to accommodate the uncommon case (collaboration). The UX question is whether sharing can be additive without degrading the solo experience.
Architecture Purist
If sharing is on the roadmap, the data model should be designed for it now, even if the feature is not built yet. Retrofitting multi-tenancy into a single-user SQLite schema creates technical debt. The architecture-clean path is to add a user-scoped data model now and build sharing when you are ready.
Product Strategist
The feature request validates market interest, but the to-do app market is saturated with collaboration tools. Competing on sharing means competing with Todoist, Notion, and Trello. The strategic question is whether the product's identity is "personal and fast" or "collaborative and full-featured." Trying to be both risks being neither.

Expected output: Round 2 -- Cross-Examination

Each expert responds to the others' positions, surfacing genuine tensions:

Security Advocate responds
The Architecture Purist suggests designing for multi-tenancy now. That is premature from a security standpoint -- you are adding attack surface for a feature that may never ship. Design the security model when you commit to the feature, not before.
DX Pragmatist responds
The UX Champion raises a fair point about the solo experience degrading. That aligns with the implementation concern: every sharing feature adds conditional logic to every existing feature. The codebase complexity does not grow linearly; it grows combinatorially.
UX Champion responds
The Product Strategist's framing is sharp: "personal and fast" versus "collaborative and full-featured." If the product's identity is "personal and fast," then sharing is a distraction. If it is "collaborative," then the entire UX needs rethinking. You cannot bolt collaboration onto a personal tool.
Architecture Purist responds
The Security Advocate says designing for multi-tenancy early is premature. Fair point about attack surface. But the alternative is a painful migration later. A middle path exists: add a user ID column now (no auth, just a local constant), so the schema is ready without adding runtime complexity.
Product Strategist responds
The DX Pragmatist's "ship the single-user experience well first" is the right sequencing. The market signal is noted but not validated. Run a lightweight experiment (export/import of task lists as files) before committing to real-time sharing. It tests demand with minimal investment.

Expected output: Synthesis

The debate concludes with a synthesis that honestly reports where the experts agree, where they disagree, and a recommended path forward:

Consensus
All five agree that real-time sharing is premature for the current stage. The product's identity as a personal task manager should be the priority. The solo experience should be excellent before collaboration is considered.
Unresolved tensions
Architecture vs. Security: Should the data model be pre-designed for multi-tenancy (Architecture Purist) or kept minimal until the feature is committed (Security Advocate)? The core tension is future-proofing versus attack-surface minimization.
UX vs. Product Strategy: Is export/import a valid proxy for testing sharing demand (Product Strategist), or does it test the wrong thing because file sharing is not the same as real-time collaboration (UX Champion)?
Recommended path
Do not build sharing now. Instead: (1) Ship the single-user experience with excellent priority and tagging support. (2) Add a task-list export/import feature as a lightweight collaboration proxy. (3) Monitor whether users adopt export/import for sharing or request real-time collaboration. (4) If demand validates, design the multi-tenancy architecture and security model as a dedicated phase.

What just happened?

You just ran a council debate -- a structured multi-perspective argumentation protocol. Unlike a standard research query where one voice gives you a recommendation, the council debate forces five (or more) expert archetypes to argue from their genuine priorities, challenge each other's assumptions, and surface tensions that a single perspective would miss.

This connects to a key concept in SEJA's epistemic design: abductive reasoning and plural readings. SEJA does not assume there is one right answer. Instead, it generates multiple plausible interpretations (the expert positions) and evaluates them through structured debate. The synthesis does not paper over disagreement -- it names the unresolved tensions so you can make an informed decision.

The debate transcript is saved as a research log under _output/research-logs/. You can reference it in future planning sessions. For the theoretical foundation behind abductive reasoning in SEJA, see The Semiotic Engineering Foundation.

Understanding the Council

The council debate has a fixed structure designed to maximize the quality of disagreement:

The five fixed archetypes

Archetype Priority Challenges
Security Advocate Safety, data protection, worst-case scenarios Features that add attack surface
DX Pragmatist Developer productivity, simplicity, shipping speed Over-engineering and premature abstraction
UX Champion User experience, accessibility, discoverability Technical decisions that degrade the user's experience
Architecture Purist Clean boundaries, long-term maintainability Short-term expedients that create technical debt
Product Strategist Business value, time-to-market, user adoption Features that do not serve the product's identity

Brief-specific experts

Beyond the five fixed archetypes, you can add up to two domain-specific experts. For example, if your question involved data pipelines, you could include a Data Engineer. If it involved deployment strategy, you could include a DevOps/Platform Engineer. The caller selects these when invoking the debate.

The two-round structure

Round 1 (position statements) ensures every perspective is heard without interruption. Round 2 (cross-examination) forces each expert to engage with the others' arguments directly. This structure prevents the common failure mode of multi-perspective analysis: polite agreement that hides real disagreement.

When to Use a Council Debate

Not every question needs a council debate. Use it when:

  • The decision has genuine trade-offs with no obvious right answer
  • Multiple stakeholder perspectives would disagree on the approach
  • The stakes are high enough that a wrong decision is expensive to reverse
  • You suspect you are anchored on one perspective and want to stress-test it

For simpler questions (What library should I use for date parsing? Should I use camelCase or snake_case?), standard /research is faster and sufficient.
