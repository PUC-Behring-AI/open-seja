Your First SEJA Project

This tutorial walks you through creating a SEJA project from scratch. By the end, you will have a working project directory with design intent files that the harness reads on every skill invocation. The whole process takes about 15 minutes.

Prerequisites

Before you begin, make sure you have:

  • Git installed and configured on your machine
  • Claude Code (the CLI) installed and authenticated
  • A terminal or command prompt open
  • An empty parent directory where you want to create the project

What You Will Build

You will create a to-do app project called my-todo-app. The domain is personal task management. The stack is Python with SQLite. By the time you finish, your project directory will contain the harness files SEJA needs to operate and a set of design-intent files in product-design/ that capture your project's identity, standards, and trust boundaries.

Step 1: Set Up the Project

Open your terminal, navigate to the parent directory where you want your project to live, and run: 

/seja-setup my-todo-app

SEJA detects that the target directory does not exist yet and treats this as a greenfield install. It creates the my-todo-app directory, copies all harness files into .claude/, and populates .claude/references/ with the reference scaffolding the harness needs.

Expected output

You will see a series of messages as SEJA copies files. When it finishes, you will be asked a short series of questions about your project's stack. Answer them as follows:

  • Project name: my-todo-app
  • Domain: personal task management
  • Backend framework: Python (Flask)
  • Database: SQLite
  • Frontend framework: none (CLI app for now)

After answering, SEJA generates product-design/conventions.md with your stack definitions and scaffolds CLAUDE.md with stack-specific content. It then tells you to run /design next.

What just happened?

The /seja-setup command performed the bootstrap sequence: it created the project directory, copied the harness files (skills, rules, references, agent prompts, and helper scripts) into .claude/, and generated conventions.md -- the file that tells every skill where things live and what stack you are using. This file is the single source of truth for project configuration. Every skill reads it at startup.

The harness uses a state-detection system that recognizes four project states: no-harness (fresh target), fresh-download (SEJA cloned in place), partial-init (conventions exist but design intent absent), and finalised (full project). Your project is now in the partial-init state -- conventions exist, but design intent does not. That is why SEJA tells you to run /design next.

Step 2: Design the Project

Navigate into your new project and run the design skill:

cd my-todo-app
/design

SEJA detects that conventions.md exists but the design intent file does not. It skips the stack questions (already answered in Step 1) and walks you through the remaining design sections.

The design questionnaire

You will be asked questions across several design sections. For this tutorial, answer them with the to-do app in mind:

Section 0: Metacommunication message
This is a first-person statement of your design intent. Answer as the designer speaking to the user: "When you open my to-do app, I want you to see your tasks organized by priority, so you always know what to work on next. I have designed the interface to be minimal, because I believe adding a task should take less than 5 seconds."
Section 2: Conceptual design
Describe the core entities: Task (title, description, priority, due date, status), Tag (name, color), and the relationship between them (a task can have many tags).
UX Design Standards (Section 3)
For a CLI app, you can keep this minimal. Describe the command structure: todo add, todo list, todo done.
Graphic/UI Design Standards (Section 4)
Specify visual choices such as colors, typography, and spacing. For a CLI app, defaults are fine.
Engineering Standards (Sections 6--11)
Specify your testing framework (pytest), code style (PEP 8 via ruff), and any other conventions you follow. These sections cover project conventions, frontend and backend standards, testing, i18n, and security checklists. For a solo project, accept the recommended defaults.

Expected output

After the questionnaire completes, verify the generated files:

ls product-design/

You should see these files:

conventions.md
constitution.md
product-design-as-intended.md
standards.md
design-standards.md
security-checklists.md
ux-research-results.md

For a brownfield (evolving) project, you would also see product-design-as-coded.md, which captures the current implementation state.

What just happened?

The /design skill generated your project's design-intent artifacts. These files form the foundation that every other skill reads:

  • conventions.md -- your project directory layout and the harness variables the agents read at the start of every skill. Already populated in Step 1; /design may have amended it.
  • constitution.md -- immutable principles for your project. Once you approve it, agents treat it as read-only. It is the trust boundary between you and the agent.
  • product-design-as-intended.md -- your working design intent. This is the file you edit as your project evolves. Every planning session reads it first to understand what you want to build.
  • standards.md -- your engineering standards for backend, frontend, testing, and internationalization, so the agents know what "good" means in your codebase.
  • design-standards.md -- your UX patterns and graphic/visual design standards (interaction patterns, accessibility, colors, typography, spacing).
  • security-checklists.md -- security checklists and validation constants that agents enforce during implementation and review.
  • ux-research-results.md -- personas, problem scenarios, and discovered user journeys. Pre-populated from your questionnaire answers and updated as you learn more about your users.

Your project is now in the finalised state. The harness is fully configured and ready for the development lifecycle. For a deeper understanding of the metacommunication message you wrote, see The Semiotic Engineering Foundation.

Step 3: Verify the Project

Run a quick harness health check to confirm everything is in order: 

/critique health

The health check runs 9 built-in diagnostics across the skill system, briefs, plans, references, conventions, constitution, spec compliance, and the pending ledger. On a fresh project, you should see all checks pass.

Expected output

A summary table showing each check with a PASS status. If any check fails, read the diagnostic message -- it tells you exactly what is missing and how to fix it.

What just happened?

The /critique health command ran the harness's self-diagnosis suite. This is the same suite that maintainers run before releases. By running it now, you have verified that your project's harness is correctly installed and all required files are present and well-formed. You can run this check at any time to confirm the harness is healthy.

Summary

In this tutorial, you:

  1. Created a new SEJA project with /seja-setup
  2. Defined your project's design intent with /design
  3. Verified the harness health with /critique health

Your project directory now looks like this:

my-todo-app/
  .claude/
    skills/          # 17 skill definitions
    agents/          # 16 subagent prompts
    rules/           # 7 path-scoped rule files
    references/      # General, template, and project references
  product-design/
    conventions.md   # Project configuration (stack, paths, variables)
    constitution.md  # Immutable principles (trust boundary)
    product-design-as-intended.md  # Working design intent
    standards.md     # Engineering standards
    design-standards.md     # UX and visual design standards
    security-checklists.md  # Security checklists and validation
    ux-research-results.md  # Personas and user journeys
  _output/           # Plans, briefs, logs (created as you work)
  CLAUDE.md          # Agent entry point (reads this first)

You are ready to build your first feature. Continue to the next tutorial to walk through the complete development lifecycle.
