The Lifecycle in One Feature

This tutorial walks you through the complete SEJA development lifecycle by adding a single feature to the to-do app from Chapter 1. You will use five skills in sequence -- /research, /plan, /implement, /critique, and /document -- to add a "priority" field to tasks. By the end, you will understand the shape of every development cycle in SEJA.

Prerequisites

  • A working SEJA project (complete Chapter 1 first)
  • The to-do app project (my-todo-app) open in your terminal

The Feature: Task Priority

You want users to assign a priority level (high, medium, low) to each task, so they can sort and filter tasks by urgency. This is a typical small feature that touches the data model, the CLI interface, and the display logic.

Stage 1: Research

Every change after the initial setup begins with research. You ask a question, and the agent investigates your codebase before recommending an approach. Run: 

/research How should I add a priority field to tasks? Should it be an enum or a free-text field?

Expected output

The agent produces a structured report. It reads your product-design/product-design-as-intended.md to understand the existing Task entity, scans your codebase for the current data model, and evaluates the question from multiple perspectives:

  • Architecture perspective: An enum is safer -- it constrains values and makes sorting deterministic.
  • UX perspective: Three fixed levels (high, medium, low) are more discoverable than free text.
  • DX perspective: An enum integrates naturally with SQLite as an integer column with a CHECK constraint.

The report concludes with a recommendation (use an enum with three levels) and offers to continue the conversation if you have follow-up questions.

What just happened?

The /research skill is the investigation entry point for every iteration-2+ change. Before you touch any code or plan, you ask your question here. The agent does not just answer from general knowledge -- it reads your project's design intent, scans your codebase, and grounds its recommendation in your specific context. The multi-perspective analysis ensures you consider trade-offs you might have missed.

Research also serves as a routing decision: if the answer reveals that your design intent needs to change, you branch into /design. If the intent is stable and you just need to build, you branch into /plan. In this case, the intent is stable (you are adding a field, not changing the product direction), so you proceed to planning.

Stage 2: Plan

With the research recommendation in hand, create a build plan: 

/plan Add a priority field (high/medium/low enum) to tasks so users can sort by urgency

Expected output

The agent produces a numbered plan with steps like:

  1. Add priority column to the database -- Alter the tasks table to add a priority integer column with a CHECK constraint (1=high, 2=medium, 3=low). Default: 3 (low).
  2. Update the Task model -- Add a priority attribute to the Task class with validation.
  3. Update the CLI commands -- Add a --priority flag to todo add and a sort option to todo list.
  4. Add tests -- Write pytest tests for priority assignment, default values, and sort order.

Each step lists the files to create or modify, verification criteria, and dependencies on other steps. The plan also includes a review log showing which quality perspectives were evaluated.

What just happened?

The /plan skill read your design intent and the research recommendation, then decomposed the feature into concrete, ordered steps. Each step is self-contained: it names the files involved, states what to verify when done, and declares its dependencies. This plan is an artifact you can review, discuss, and revise before any code is written.

The plan also went through a quality review. Depending on the complexity of the change, the review evaluates up to 16 quality perspectives (security, performance, accessibility, architecture, and more). The plan file is saved under _output/plans/ with a unique numeric ID.

Stage 3: Implement

Review the plan. If it looks right, execute it: 

/implement 000042

Replace 000042 with the actual plan ID that /plan assigned. The agent creates a rollback branch, then executes each step in sequence.

Expected output

For each step, you will see:

  • A message indicating which step is being executed
  • The files being created or modified
  • Verification output confirming the step succeeded

After all steps complete, the agent runs a Quality Gate -- a combined validation pass, code review, and test run. If all checks pass, you see a summary of what was built.

What just happened?

The /implement skill executed your plan step by step. In auto mode (the default), each step runs in a fresh subagent with isolated context. This isolation prevents early steps from consuming the context window that later steps need. The agent also created a rollback branch before starting, so you can revert cleanly if anything goes wrong.

The Quality Gate at the end is a built-in checkpoint. It runs the same checks that /critique would run, ensuring the implementation meets your project's standards before you move on. For steps with explicit test specifications, the agent follows a test-first cycle: write the failing test, then implement until it passes.

Stage 4: Critique

The Quality Gate ran automatically, but you can also run a standalone review for deeper analysis: 

/critique review

Expected output

The agent reviews your recent changes against quality perspectives appropriate to the change complexity. For a standard feature like this, it evaluates perspectives such as:

  • Security: Are inputs validated? Can the priority value be spoofed?
  • Accessibility: Is the priority displayed in a way that does not rely on color alone?
  • Architecture: Does the priority enum follow the existing patterns?
  • DX: Is the code readable and well-documented?

Each finding is classified as Adopted (you should fix this), Deferred (noted but not blocking), or N/A (not applicable). The critique creates a log file under _output/critique-logs/.

What just happened?

The /critique skill is the validation gate. Its deliberate placement before documentation ensures you never document something that fails its own checks. The harness enforces this ordering: validate before you communicate. If the critique surfaces findings that need fixing, you would loop back to /plan to address them. In this case, the implementation is clean, so you proceed to documentation.

Stage 5: Document

Record what changed: 

/document --auto-detect

Expected output

The agent scans recent git changes and detects that you added a new model attribute, modified CLI commands, and added tests. Based on these heuristic patterns, it generates or updates the appropriate documentation: a README update describing the priority feature, and a changelog entry summarizing the change.

What just happened?

The /document skill generates documentation from your actual code changes, not from your memory of what you changed. The --auto-detect mode scans git history using six heuristic patterns (new API routes, changed models, new UI components, config changes, architectural shifts, breaking changes) and generates the documentation types that match. This ensures documentation stays synchronized with the codebase.

The Lifecycle Shape

You have now walked through the complete development lifecycle. Every feature, bug fix, and improvement follows this same path: 

# The SEJA lifecycle -- every change follows this shape

/research    # 1. Investigate: ask questions, get recommendations
     |
     v
/plan        # 2. Plan: decompose into steps with verification
     |
     v
/implement   # 3. Build: execute the plan step by step
     |
     v
/critique    # 4. Validate: review against quality perspectives
     |
     v
/document    # 5. Record: generate documentation from changes
     |
     v
/reflect     # 6. Learn: surface patterns and close the cycle

The sixth step, /reflect, was not covered in this tutorial because it works best when you have completed several cycles and have patterns to reflect on. See the How to Reflect on Your Practice guide for the full walkthrough. As you use SEJA, the reflection step becomes the cycle-closing mechanism that turns a sequence of commands into learning you can reuse.

When research reveals that your design intent needs to change (not just the code), you branch from /research into /design instead of /plan. The lifecycle accommodates both paths.

Summary

In this tutorial, you:

  1. Used /research to investigate how to add the priority field
  2. Used /plan to decompose the feature into concrete steps
  3. Used /implement to execute the plan with automatic quality checks
  4. Used /critique to validate the implementation against quality perspectives
  5. Used /document to generate documentation from actual code changes

This five-stage lifecycle (plus reflection) is the pattern for every change you make in a SEJA project. The next tutorial explores the metacommunication message -- the design-intent statement you wrote in Chapter 1 -- in more depth.
