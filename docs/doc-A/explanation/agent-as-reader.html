How the Agent Reads SEJA

Every previous chapter has treated SEJA as a message from a designer to a human user. This chapter is about SEJA's other reader: the AI agent that executes it. SEJA is unusual among design methodologies in that its primary run-time consumer is not a person but a language model. The harness is a corpus of instructions -- skill definitions, reference files, rules, a constitution -- that the agent reads into a bounded context window and acts on. Understanding how the agent reads that corpus is not a curiosity; it explains why the harness is structured the way it is, and it tells you, when you author documentation for the agent, what will actually land. This is the meta-documentation: SEJA describing how SEJA is read.

How the Agent Processes a Skill Definition

A SEJA skill is a Markdown file -- SKILL.md -- with a YAML frontmatter block and an instructional body. When you invoke a skill, the agent reads that file and follows its instructions as a procedure. There is no interpreter compiling the skill; the language model reads the prose and does what it says. This has a consequence that shapes everything about how skills are written: the instructions must be legible to a reader that follows text closely but has no execution guarantees. A skill body is imperative prose ("Read and inject the constitution," "Without asking for authorization, insert a new entry") because the agent is being asked to perform the steps, not to parse a formal grammar.

Because the agent is a probabilistic reader rather than a deterministic machine, the harness leans on a few structural habits to keep behavior reliable. Critical instructions are stated plainly and early. Verbatim invocation phrasings (like Run /pre-skill ...) are kept intact so that static tooling and the agent alike can detect them. Frontmatter carries the machine-relevant configuration -- version, category, context budget, references -- separately from the narrative body, so that the parts a tool needs to read are cleanly separable from the parts the agent needs to follow. The design assumption throughout is that the agent reads carefully but not infallibly, and that structure is what makes careful reading dependable.

Context-Window Budgets: Light, Standard, Heavy

The agent's context window is finite, and every reference file loaded into it competes for the same space with the actual task. SEJA manages this scarcity explicitly. Each skill declares a context_budget in its frontmatter -- one of three tiers -- and the pre-skill hook's budget-eval stage reads that value to decide how much to load before the skill runs. The three tiers are a direct response to the reality that not every skill needs the same context, and that loading everything for every skill would exhaust the window on ceremony.

light
The minimal tier. Pre-skill records the invocation and does essentially nothing else: it skips all briefs and all reference-file loading, and it skips the ref-load and constitution stages entirely. This tier is for skills that need almost no project context to do their job -- the ones that manage the harness itself or produce information without deep analysis. Loading design intent for them would be pure overhead.
standard (the default)
The working tier for most skills. Instead of the full briefs log, it loads a compact briefs index -- one-line summaries -- which gives the agent awareness of recent history without spending the window on full entries. It then runs orphan detection, loads the mandatory references and the skill's own references, and loads the constitution. This is the balance point: enough context to reason well, not so much that the task is crowded out.
heavy
The context-intensive tier for skills that genuinely need deep history -- planning, implementing, critiquing. It loads the full briefs log, but with recency windowing: the newest entries in full and a one-line summary standing in for the older ones, so that even "load everything" respects the window's limits. It also loads the plan index and runs an additional compaction check. The heavy tier is the harness admitting that some work is irreducibly context-hungry and budgeting for it deliberately rather than pretending otherwise.

The tiers are a governance-and-epistemics mechanism in miniature. They govern -- a skill cannot silently balloon its context footprint, because the tier is declared and the loader enforces it -- and they are epistemic, because recency windowing is an admission that the window is finite and a strategy for spending it on what is most likely to matter.

Eager vs. Lazy: Demand-Pull Reference Loading

Within the ref-load stage, SEJA supports two loading disciplines, chosen per skill by whether the skill declares an eager_references field in its frontmatter. The distinction is a direct response to the same scarcity the budget tiers address, applied at the granularity of individual reference files.

In eager-only mode (no eager_references field), the loader reads and injects every file the skill lists in references. This is the simple discipline: everything the skill might need is loaded up front, present in the window from the first step. It is the right choice when a skill's references are all likely to be used and small enough to afford.

In demand-pull mode (the eager_references field is present), the loader splits the references in two. The eager tier -- the files named in eager_references -- is loaded up front alongside the mandatory references. The lazy tier -- everything in references that is not eager -- is not loaded; instead the loader emits an "Available references" block, a compact list of the lazy files each annotated with a trigger hint ("reviewing security concerns," and the like). The agent pulls a lazy reference into context only when the work at hand calls for it. This is lazy loading in the familiar computing sense, applied to context-window management: pay the loading cost only when the reference is actually needed. It matters because a skill may declare many references that are each relevant only to a fraction of its invocations; loading all of them eagerly would waste the window on files the current task will never touch.

Agent Attention Patterns: What the Agent Prioritizes and May Miss

Loading a file into the context window is necessary but not sufficient for the agent to act on it. Attention is itself a scarce resource: a large window can hold more than the agent reliably attends to in any single step. SEJA's structure reflects a working theory of what the agent prioritizes and where it is at risk of missing content.

The agent attends most reliably to instructions that are present, recent, and unambiguous. It is at greater risk of under-weighting content that is far from the current step, buried in the middle of a long file, or phrased as background rather than instruction. This is why SEJA treats certain reference files as pinned anchors: files that must never be summarized or dropped, and must be re-injected verbatim after any context compaction. The pinned set is small and deliberate -- the constitution (dropping it would let the agent bypass governance rules), the permissions reference (dropping it would remove authorization boundaries), the constraints reference (dropping it would remove quality and safety guardrails), the active skill's own instructions, the active plan if one is being executed, and the session scratchpad. The reasoning behind the pinned set is precisely an attention-and-persistence argument: these are the files whose absence would silently corrupt the agent's behavior, so they are protected against the compaction that would otherwise quietly evict them.

Notably, the sibling facet files -- the designer-facing quick guides and the maintainer-only rationale files that live next to a pinned SKILL.md -- are not pinned, and this is intentional. They are off the agent's executional hot path: the quick guide is loaded only when a designer explicitly asks for help, and the rationale file is never loaded at run time at all. Keeping them unpinned is a deliberate attention economy: the agent's window is reserved for what it needs to act, and narrative meant for humans does not compete for that space during execution.

Path-Scoped Rules and Auto-Loading

SEJA carries a set of rule files, each scoped to a path pattern. When the agent works on a file that matches a rule's scope, that rule is auto-loaded into context. The mechanism is a targeted form of the same attention economy: rather than loading every rule for every task -- which would flood the window with guidance irrelevant to the file at hand -- the harness loads a rule exactly when the agent touches the files that rule governs. A rule about the structure of the harness loads when the agent edits harness files; a rule about a particular subsystem loads when the agent works inside it.

Path-scoping is worth pausing on as a design idea, because the alternative -- a single global rulebook always in context -- would be simpler to reason about and worse in practice. A global rulebook grows without bound as the project accumulates conventions, and every convention it holds competes for attention with every other, whether or not it is relevant to the current task. Path-scoping keeps each rule's cost local to the files it applies to, so that the guidance the agent sees is guidance it can use right now. The trade-off, examined more fully in the next chapter, is that a rule only fires when its scope is touched -- so a convention that should apply everywhere cannot be expressed as a narrowly-scoped rule.

Implications for Authoring Documentation for the Agent

The practical payoff of understanding the agent's reading model is that it changes how you write for the agent. A few implications follow directly from the mechanisms above.

Write for a bounded window. Every line of agent-facing instruction you add competes with the task for context. The harness's own constraints reference states the rule plainly: when writing or revising agent-facing instructions, be as concise as possible. Concision here is not a stylistic preference; it is context-budget hygiene. This is also why agent-facing prose is compressed while human-facing prose is not -- the two are read by different readers with different scarcities.

Put the load-bearing instruction where attention is highest. State critical directives plainly and early, not buried mid-file behind background. If a step must not be skipped, say so as an instruction, not as a note. The agent attends most reliably to the present, recent, and unambiguous, so structure the document to put what matters most in exactly those positions.

Separate what a tool parses from what the agent follows. Machine-relevant configuration belongs in frontmatter; procedure belongs in the body. Mixing them forces both readers to wade through the other's material.

Decide eager versus lazy deliberately. If you author a skill with several references, ask which the skill needs on every invocation (eager) and which only sometimes (lazy). Declaring everything eager is the easy default and the wrong one when references are large and conditionally relevant; the demand-pull discipline exists precisely so that a rarely-needed reference does not tax every invocation.

What We Are Uncertain About

The account above is a working model, not a measured one. We describe what the agent tends to prioritize and where it tends to miss, but "tends to" is doing heavy lifting: attention behavior varies across model versions, context sizes, and prompt shapes, and SEJA's structural choices are hedges against imperfect attention rather than exploits of a precisely known mechanism. The pinned-anchor set is a good example -- it is a conservative bet that certain files must survive compaction, made without a precise model of exactly when compaction would drop them or exactly how much their absence would degrade behavior. If future models attend more uniformly across a large window, some of these structural precautions would become unnecessary overhead; if they attend less reliably, the precautions would need to grow. We treat the reading model as provisional, revisable in the same abductive spirit as the rest of the harness's self-understanding.

What This Means for SEJA Users

You do not have to think about the agent's reading model to use SEJA, but knowing it demystifies several things. It explains why some skills feel instantaneous (light budget, nothing loaded) and others pause to gather context (heavy budget, full history windowed in). It explains why the harness insists on concise agent-facing prose while letting human-facing documentation breathe. And it explains why, when you extend the harness, the structure matters as much as the content: you are authoring for a reader whose attention is finite and whose window is a shared resource. The final chapter turns from how the agent reads the harness to why the harness made the specific structural choices it did -- the design decisions and the trade-offs behind them.
