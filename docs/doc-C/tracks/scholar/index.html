explanation Scholar

Load-bearing, not decorative

Most tools that invoke a design theory use it as vocabulary. The theory names things the tool already did, and removing the theory would leave the tool intact. That is the decorative case, and it is worth stating plainly because it is the default.

SEJA is structured the other way. Semiotic engineering treats software as a metacommunication act: the designer communicates to the user, through the system, about who the user is taken to be and how the system is meant to serve them. If that is true, then the designer's message is the artifact that must be preserved — and an AI collaborator that silently substitutes its own reading of the user has not made a coding error, it has broken the communication.

Every mechanism in the harness follows from taking that seriously. The reason design intent is human-authored and machine-marked rather than AI-generated is that an authored message cannot be delegated without ceasing to be authored. The reason implementation state is recorded separately from intent is that the distance between them is the measurable form of drift. The reason a constitution is loaded before every skill runs is that the message must be present when work is done, not consulted after. Remove the theory and these are arbitrary ceremony; keep it and they are the minimum the position requires.

This track is a reading route, not a second exposition. Phase 1 establishes the framework, Phase 2 maps each concept to the mechanism that carries it, and Phase 3 collects what remains open. If your question is how to use the harness, the Practitioner Track is the shorter road.

Phase 1: The Theoretical Framework

Four concept pages, in this order. The first establishes the semiotic model; the rest are the commitments that follow from it.

  1. The Sign System — the file classifications that decide who may write what, the markers that stand in for design intent, and the epistemic posture the harness takes toward its own knowledge.
  2. The Constitution — immutable principles as the highest-authority artifact, and what it means for a tool to hold a commitment it cannot revise at runtime.
  3. The Marker System — how a machine writes into a human-authored document without authoring it, and the lifecycle a marked item moves through.
  4. As-Intended and As-Coded — the two-record pattern that makes drift a measurable quantity rather than an intuition.

A full theoretical treatment — semiotic engineering's primary literature, the communicability framework, and the reflective-practice and abduction sources the harness draws on — is planned as a standalone Foundations volume and is not part of this collection yet. The four pages above are the operative subset: enough theory to read the mechanisms, not the monograph.

Phase 2: Theory into Practice

Each theoretical commitment is carried by a specific mechanism. The table names the relationship and links the page that explains it; the explanation itself lives there, not here.

Each theoretical concept and the mechanism that carries it.
Concept Mechanism The relationship
Metacommunication /design The designer's message to the user is elicited and recorded as a first-person artifact rather than inferred from the code.
Sign systems The Marker System Markers are the harness's own sign system, letting a machine annotate design intent without becoming its author.
Reflective practice /reflect Reflection is scheduled as a lifecycle phase with its own artifact, rather than left to whenever a practitioner happens to look back.
Abduction /critique Structured perspectives force plural readings of the same change, so a single plausible explanation is not mistaken for the only one.
Epistemic posture As-Intended and As-Coded Keeping intent and implementation as separate records makes the gap between them visible instead of resolvable by assertion.
