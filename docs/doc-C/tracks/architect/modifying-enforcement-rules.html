Two surfaces, two failure modes

Enforcement in the harness splits into an advisory surface and a blocking one, and extending each is a different job.

Path-scoped rules are advisory: they load context into the agent when it touches matching files, so the right questions are in front of it before it writes. Their failure mode is silence — a rule with a scope that never matches simply never fires. Check scripts are blocking: they run in the hook chain and in the validation orchestrator, and they stop a commit. Their failure mode is noise — a check that reports false positives gets bypassed, and a routinely bypassed check enforces nothing.

Path-scoped rules

A rule is a Markdown file in .claude/rules/. Its frontmatter declares the glob patterns it governs and its designer-facing description: 

---
paths:
  - "backend/**"
designer_description: "When you touch anything under backend/, I surface ..."
---

The body is deliberately thin. A rule is a router, not a manual: it names the review-perspective files whose P0 questions apply, points at the relevant section of the project's standards, and closes with a Perspective Alignment line naming the perspectives that govern it. Content that would be duplicated from a standards file belongs in that file, with the rule pointing to it.

When adding a rule, the two decisions that matter are the glob scope — narrow enough that it fires only when its questions are relevant — and the perspective alignment, which is what keeps the rule and the review checklist from drifting apart.

The check-script contract

A check script is a Python file whose name begins with check_. That prefix is the registration mechanism: the orchestrator discovers check_*.py both in .claude/skills/scripts/ and in every co-located skill subdirectory, so a check placed next to the skill it serves is picked up with no manifest entry.

The contract a check must honour:

Exit codes
0 for pass, 1 for a genuine failure, and 2 reserved for script error — a check that cannot run is not the same as a check that failed, and collapsing the two makes a broken check indistinguishable from a broken codebase.
Header block
A designer: comment in the harness's first-person voice, then a module docstring carrying the one-line purpose, Invocation:, Lifecycle:, the exit-code table, and a runnable usage example.
Self-containment
Runnable from the repository root with no arguments beyond an optional --root. Project-specific paths come from the shared project-config module, which parses the conventions file — never hardcode a directory a downstream project is free to rename.
Diagnostic output
Print the file and line for every finding. A check whose failure message does not say where forces the reader to re-derive it.

Optionally, add an entry to the check plugin registry naming the script, its display name, the stacks it applies to, its scope, and whether it is critical. The registry is what lets the orchestrator filter by stack; a script absent from it is included by default rather than skipped, so registration is about excluding your check from irrelevant stacks, not about making it run.

The commit-time hook chain

The pre-commit hook is installed once per clone with bash .githooks/install.sh and runs two gates in sequence, each blocking on failure:

  1. Fast preflight. The lightweight validation pass sized for a git hook. A non-zero exit blocks the commit.
  2. The leak gate. Scans staged shared Markdown for fingerprints and malformed private-only markers that would leak to the public repository on the next sync.

Both gates degrade gracefully: if Python or a gate script is missing the hook prints a notice and exits zero, so an older clone or a partial upgrade cannot wedge every commit. That tolerance is why an installed hook is a per-clone responsibility rather than something the repository can assume.

Choose your gate by cost. The fast preflight is the hook-time budget; the full orchestrator — which runs every discovered check and can emit JUnit XML — is the CI-time sweep. Putting an expensive check in the hook chain is the most reliable way to teach contributors to bypass it.

Bypassing the hook

No plan or implementation step may circumvent the pre-commit hook without explicit designer approval recorded in a decision entry. This is a constitutional security invariant, not a convention: hook bypass is the most common accidental path to leaking private content or shipping unvalidated code.

The practical consequence for anyone extending enforcement is that --no-verify is not an escape hatch you may design around. If a check blocks legitimate work, the fix is to correct the check, narrow its scope, or move it out of the hook chain into the CI sweep — and if the bypass is genuinely warranted, it is recorded as a decision with the designer's approval attached, not taken silently at the command line.
