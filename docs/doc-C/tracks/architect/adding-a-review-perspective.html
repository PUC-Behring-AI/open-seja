What you are adding

A review perspective is a named lens with a checklist behind it. The harness ships sixteen — eleven engineering (security, performance, database, API design, architecture, developer experience, internationalization, testability, operations, compatibility, data integrity and privacy) and five design (user experience, accessibility, visual design, responsive design, microinteractions).

Together they replace ad-hoc "simulate a council of reviewers" instructions with a structured, deterministic sweep: every applicable perspective is evaluated and recorded as Adopted (evaluated, concerns addressed), Deferred (evaluated, not addressed, with stated reason and trade-offs), or N/A (does not apply). Adding one means adding a lens that the existing sixteen genuinely do not cover — not a re-cut of an existing one.

The tier system

Each perspective file is split into three tiers, and every question inside carries a priority marker from [P0] (critical) to [P4] (informational), sorted by priority within its tier.

Essential — P0
Critical, blocking questions. Always evaluated. Loaded for a standard context budget or whenever the perspective appears in the default shortlist.
Standard — P1 to P2
Questions for a thorough review. Loaded for a heavy context budget, or when this perspective is the primary focus.
Deep — P3 to P4
Exhaustive analysis. Optional unless the perspective is the primary focus of the review.

The tiering is what makes the perspective set affordable. Under time or context pressure a reviewer works P0 and P1 first and the structure tells it where to stop — so write your P0 questions as the ones whose "no" answer should block a release, not merely inform it.

The two-stage loading protocol

No consumer bulk-loads all sixteen files. Instead:

  1. Load the compact index — tag, name, and scope for each perspective, and nothing else.
  2. Select four to six perspectives, either from the Perspective Shortcuts by Plan Prefix table or manually from the change's content.
  3. Load only the selected perspective files, and within each only the tiers the depth calls for.

This is why the index entry you write matters as much as the checklist: a scope line that does not name the concrete artifacts your perspective applies to will not get your perspective selected, and an unselected perspective is an unread one.

Writing the perspective file

Create .claude/references/general/review-perspectives/<tag>.md, where <tag> is the lowercase form of the perspective's short tag. The file opens with YAML frontmatter carrying two fields:

designer_description
First-person, designer-facing. States what the reviewer will watch for when looking through this lens and what class of failure it catches.
tier
The perspective's own baseline tier, e.g. Essential.

The body is an <h1> naming the tag and full name, followed by exactly three ## Essential, ## Standard, and ## Deep sections of priority-marked bullet questions. Keep every entry a question: the status vocabulary is an answer to a question, and a bullet phrased as an assertion has nothing for a reviewer to answer.

Registering it in three places

The file alone is inert. A perspective becomes reachable only once it is registered:

  1. The index — review-perspectives-index.md. Add a row to the Engineering or Design table with the tag, name, and scope. This is the table the two-stage protocol reads at stage one.
  2. The main reference — review-perspectives.md. Add the tag to the corresponding perspective table, linking the new file.
  3. The shortcut table — the Perspective Shortcuts by Plan Prefix section of the same file. Add your tag to the prefix-and-scope rows where it should be selected by default. A perspective absent from every shortcut row will only ever be picked manually.

Then regenerate the Essential summary. The condensed review-perspectives-essential-summary.md is generated, not hand-edited — it walks every perspective file, extracts the Essential section, and writes the combined P0 layer so a reviewer can load it as one reference instead of sixteen. Run: 

python .claude/skills/scripts/generate_essential_perspectives_summary.py

Skipping this step leaves a summary that silently omits your perspective's P0 questions from every consumer that loads the condensed layer.

Where your perspective sits in a conflict

Perspectives regularly pull a review in opposite directions, so the reference fixes the precedence rather than leaving it to the reviewer's mood. Security wins by default unless the designer explicitly accepts the risk. Accessibility is non-negotiable and is never traded against visual design or performance. Every other trade-off must be documented — both the chosen approach and the deferred concern, with rationale — and genuinely unclear conflicts are put to the designer rather than resolved silently.

When adding a perspective, decide up front whether it claims any precedence. If it does not, say so; an unstated precedence claim surfaces later as an inconsistent review.
