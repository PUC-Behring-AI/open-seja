Before you add a skill

The harness governs skill count deliberately. A new skill must first justify that its functionality cannot be a mode of an existing skill — the ten-mode /critique consolidation is the model to follow when several jobs share one execution pattern. A skill earns independent existence by meeting at least three of four criteria: distinct user intent and mental model, disjoint reference sets, incompatible execution topology, and a different output strategy.

If your candidate fails that bar, the right move is a new mode on an existing wrapper, not a new directory.

The skill directory

A skill is a directory under .claude/skills/ named after the slash command that invokes it. The directory holds three kinds of file:

SKILL.md (required)
YAML frontmatter plus the executional instructions the agent follows at runtime. This is the only file pre-skill loads on the hot path.
SKILL-quickguide.md (required for user-invocable skills)
The designer-facing narrative — What / Example / When to use / Next step. Internal lifecycle hooks have no Quick Guide and get no sibling.
SKILL-rationale.md (optional)
A maintainer-only companion holding plan and research citations and architectural-decision prose that the agent does not need at runtime. Adopt it once the body carries three or more artifact citations.

Skill-owned Python scripts live next to the SKILL.md that uses them — see the section on scripts below.

The frontmatter contract

SEJA's frontmatter follows the agentskills.io universal specification. Top-level fields conform to that spec; every SEJA-specific field is namespaced under metadata so future spec fields cannot collide with harness fields. New skills are validated against the spec by check_skill_spec.py.

Top-level fields

name
Required. Lowercase alphanumeric plus hyphens, 1–64 characters. Must match the directory name.
description
Required, non-empty, up to 1024 characters. This is what the runtime matches against a user's request, so lead with the trigger vocabulary a user would actually type.
argument-hint
The argument signature shown to the user, e.g. "<planned-item-id> [--manual] [--dry-run]". Keep it in sync with the skill's own Arguments table.
compatibility
A free-text statement of runtime assumptions. Harness skills declare "Designed for Claude Code with the SEJA harness".

Metadata fields

metadata.context_budget
light, standard, or heavy (default standard). This is the single highest-leverage field you will set: it decides how much history and how many reference files pre-skill pulls into context before your instructions run. light loads nothing but the brief log; heavy loads windowed briefs and the plan index.
metadata.references
Every reference file the skill may need. Paths beginning general/ resolve under .claude/references/general/, template/ under .claude/references/template/; anything else resolves from the repository root. Declaring this field is expected of every skill — its absence produces a pre-skill warning.
metadata.eager_references
The subset loaded upfront. Declaring this field switches pre-skill from eager-only mode (read everything in references) to demand-pull mode: eager entries are injected, and the remainder are announced as an available-references list the agent pulls on demand. An empty list is valid and means "all skill-specific refs are lazy".
metadata.skip_stages
Opts out of pre-skill's non-critical stages by ID, e.g. [pending-check, orphan-check, compaction-check, constitution]. The three critical stages cannot be skipped.
metadata.category, metadata.version, metadata.last-updated
Catalog metadata consumed by /help, the skills manifest, and the call-graph generator.
Contract-version fields
plan_format_version and questionnaire_version pin the structured-artifact format a skill produces or consumes, so a consumer can refuse an artifact it does not understand rather than misparse it.

The lifecycle contract

The harness's first technical principle is non-negotiable: every user-facing skill starts with pre-skill and ends with post-skill. A skill may opt out of non-critical pre-skill stages via skip_stages, but it may never skip pre-skill entirely. Lifecycle discipline is the core value the harness provides; bypassing it defeats the governance model.

In practice the divide is workflow versus infrastructure. Lifecycle-workflow skills — the ones that produce logged artifacts and consume prior context — invoke pre-skill as their first step. Configuration and meta skills that manipulate the harness itself, or that may run before project conventions even exist, opt out. A new skill must pick a side explicitly rather than inheriting one by accident.

One lifecycle owner per invocation. If your skill delegates work to a subagent, the wrapper keeps ownership of the hooks. No dispatch may fire pre-skill or post-skill twice.

The Quick Guide sibling

Every user-invocable skill ships a SKILL-quickguide.md alongside its SKILL.md. The sibling body is the Quick Guide — do not re-introduce a ## Quick Guide heading inside it. Designer-facing wording belongs there; executional instructions stay in SKILL.md.

The pointer back is mandatory and structurally enforced. SKILL.md must carry a blockquote line within the first fifteen non-blank body lines, outside any fenced code block, containing the literal token SKILL-quickguide.md. The canonical form is: 

> Overview: see [./SKILL-quickguide.md](./SKILL-quickguide.md)

Wording may drift within that envelope; the token and the shape may not. A missing or malformed pointer fails preflight. The asymmetry with the optional SKILL-rationale.md pointer is intentional: the Quick Guide pointer is the discoverability anchor for a contributor opening SKILL.md cold.

The sibling is never listed in metadata.references and is never loaded on the hot path. It is read only when a designer asks for it — by invoking a skill with --help, or through /help <skill> — and both paths go through one shared loader, which is the single source of truth for the file path.

Where a skill's scripts live

The harness splits Python helpers by ownership:

  • Shared utilities live in .claude/skills/scripts/. Anything more than one skill calls belongs here — ID reservation, the pending ledger, marker application, the project-config parser.
  • Skill-owned scripts live in the skill's own directory, next to its SKILL.md.

The split is not merely tidy — it is load-bearing for validation. The check orchestrator discovers check_*.py in the shared scripts directory and in every co-located skill subdirectory, so a check script placed next to its skill is picked up automatically with no registration step.

If a script carries private artifact citations, move them to a <script>-rationale.md sibling and leave one module-level pointer comment in the script. That keeps the shipped script self-contained for consumers who have no access to the private artifacts.
