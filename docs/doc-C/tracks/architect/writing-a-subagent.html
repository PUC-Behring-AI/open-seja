When a subagent is the answer

A subagent is the right shape when a unit of work is self-contained — every input is available at dispatch, no mid-flight coordination with the caller is needed — and when moving it out of the caller's context is genuinely valuable, either because the tool-call volume would bloat the parent or because several such units should run in parallel.

The counter-indication is interactivity. Work that branches on user answers mid-flight, or that loops on confirmation prompts, stays inline in the wrapper skill's own instructions. A subagent has a stable contract — prompt in, artifact or findings out — and that contract is what makes the isolation safe.

As with skills, a new agent must justify itself against the existing roster: its domain must be distinct from every agent already present. The harness does not merge agents or bolt cross-cutting responsibilities onto existing ones.

The three roles

Every agent falls into exactly one role, and the role decides both its single responsibility and how it is invoked.

Evaluator
Reviews one type of artifact through one lens — code diffs, plans, design decisions, validation scripts, test suites, migrations. An evaluator reads and reports; it does not author the artifact it judges.
Generator
Produces one type of artifact from well-defined inputs — communication material, onboarding plans, documentation, explanation reports. Generators are invoked by thin-skill wrappers, never directly by users.
Executor
Executes plan steps in an isolated context. Executors are the one role with no standalone prompt file: their prompts are constructed dynamically from plan-step metadata at dispatch time.

The single-responsibility rule is what keeps this roster legible. Two agents that both "review things" are still distinct if they review different artifacts through different lenses; an agent that reviews diffs and runs validators is one agent too few.

The prompt file

An agent is a single Markdown file in .claude/agents/, named after the agent. It opens with YAML frontmatter and continues as the agent's system prompt.

name
Matches the filename stem; this is the identifier a wrapper dispatches to.
description
Agent-facing. States what the agent reviews or produces and any behaviour that varies by input, so the dispatching runtime can route correctly.
designer_description
Human-facing, written in the first person to the designer. This is the voice the catalogs and help surfaces show; it is not a restatement of description.
tools
The explicit tool allowance, e.g. Read, Glob, Grep, Bash. Grant the minimum the role needs: evaluators typically get read and search tools only, while generators additionally get Write because producing a file is their output contract.

The body follows a consistent four-part shape:

  1. Role statement and boundary. One sentence naming what the agent is, plus — for generators — an explicit note that the agent is the generation engine and the skill is the user-facing orchestrator.
  2. Input. The named parameters the wrapper will pass, each with its type and permitted values. Optional inputs are marked as such and given a stated default.
  3. Process. Numbered steps. This is where scope-aware reference loading belongs: name the files the agent must always read and the ones it should read only when the input warrants, rather than having it bulk-load everything.
  4. Output. The exact artifact or report shape the caller will receive. An agent's final text is a return value, not a message to a human — specify it as data.

The trust boundary

Generator agents must receive the project constitution as part of their prompt. A generator authors files; the constitution is what keeps that authorship inside the designer's governance. Omitting it creates an agent that writes without constraint.

In practice the generator's prompt instructs it to read product-design/constitution.md before starting and to apply its constraints throughout generation, proceeding without it only when the file genuinely does not exist — the bootstrap case for a project that has not been configured yet.

This is the same boundary that keeps runtime skill generation deferred in the harness. Constitution injection being mandatory and unbypassable is one of the stated prerequisites before agents may ever author new skills at runtime.

Wiring a thin-wrapper skill

Delegating a mode's work to a subagent is one of the harness's two mode dispatches. The wrapper skill keeps everything the agent should not own: argument parsing, interactive prompts, result presentation, and — critically — the lifecycle hooks.

The wrapper remains the single lifecycle-hook owner. Pre-skill and post-skill are invoked by the wrapper, not by the mode and not by the agent. No dispatch fires the hooks twice.

The wrapper's job at dispatch is to assemble a self-contained prompt: the agent starts with no view of the conversation that led to it, so every path, every parameter, and every piece of project context it needs must be passed explicitly. It then waits for the agent and presents the result.

When promoting an existing inline mode to a delegated one, move the prose into the agent prompt verbatim first. Make the refactor behaviour-preserving in one commit and revise the content in a later one; a simultaneous move-and-rewrite makes any resulting regression impossible to attribute.

Agents that write files in parallel

Executor agents that run concurrently — the roadmap wave case — add one further contract on top of everything above. Each runs in its own git worktree and operates in deferred-write mode: it writes only per-plan files and commits within its own branch, skipping the lifecycle hooks entirely.

Shared mutable state is deliberately excluded from the parallel phase. The briefs log, the pending ledger, the artifact index, and telemetry are all updated afterwards by the orchestrator, serialized on the main branch, precisely because concurrent appends to a shared file are the failure mode worktree isolation cannot prevent.
