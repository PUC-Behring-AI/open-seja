Governance in depth

SEJA does not rely on a single gate to keep an AI agent inside the rules. It layers enforcement so that a lapse at one level is caught by the next. The layers run from the most abstract and unchanging — the constitution — down to concrete automated checks that either pass or fail a commit. Each layer answers a different question: what may never change, who may write where, what still needs a human, and did the last change break a rule. This page describes the four layers and how they compose.

Layer 1: the constitution (immutable)

At the top sits product-design/constitution.md, the project's immutable principles. It is a pinned anchor: it must survive any context compaction and may never be summarised or dropped. The pre-skill constitution stage reads it and injects it into every skill invocation, so its principles govern the rest of the work unconditionally. Because it is loaded first and cannot be abbreviated, an agent cannot quietly reason its way around a constitutional commitment; the principle is always present in context.

Layer 2: constraints and section boundaries

Below the constitution are two reference files that spell out concrete rules. general/permissions.md declares which actions an agent may take without asking — read any project file, run git status / log / diff, create source files, append into the output directory — and which it may never take: it must never use Edit or Write on a file classified Human (markers). general/constraints.md adds the behavioural guardrails: UTF-8 only, no invented data, no nondeterministic behaviour unless asked, no placeholder implementations, and no silent feature creep in auto or bypass mode.

These rules are path-scoped. A permission or constraint applies to a file because of what that file is — its maintainer classification, its directory, its registered section. Two kinds of scoping matter most:

Maintainer classification
Human (markers) files may be touched only through apply_marker.py; the classification, not a per-file switch, is what forbids a direct edit.
Section boundaries
The as-coded file carries several H2 domain sections, and a skill may write only to the section it owns. A section-boundary verifier rejects a hunk that reaches across into a section the invocation had no business editing.

Layer 3: the pending ledger (deferred-action tracking)

Not everything can be enforced synchronously. Some obligations must wait for a human — verify that an implementation matches its intent, run a manual test, publish a tag, flip a marker. The pending ledger (_output/pending.jsonl, driven by pending.py) is the layer that keeps those deferred actions from being dropped on the floor. It is an append-only JSONL log: skills and post-skill append records, and a last-write-wins reducer derives the current state of each action.

Each entry has a type (for example verify-as-coded, test-implementation, update-documentation, or implement) and a lifecycle: pending, snoozed, done, or dismissed. The reducer forbids illegal transitions — a dismissed or done action cannot silently return to pending. The pre-skill pending-check stage surfaces overdue actions as an informational banner at the start of the next invocation, so the backlog stays visible without ever blocking work. A periodic-curation pass ages out stale entries and dismisses orphans whose source plan has been deleted or completed.

Layer 4: guardrail scripts (automated checks)

The bottom layer is the set of scripts that turn the rules above into pass/fail checks at commit time. They are where enforcement stops being a principle and becomes a gate.

Representative guardrail scripts and the layer they enforce.
Guardrail Enforces
apply_marker.py The sole write path for Human (markers) files; validates every marker line against an allowed regex and legal state transition before touching the file.
check_human_markers_only.py Rejects any non-marker prose mutation that slips into a Human (markers) file during the post-skill commit.
check_section_boundary_writes.py Rejects a change that writes outside the H2 section an invocation is allowed to edit.
run_all_checks.py The CI-independent orchestrator that discovers and runs every check script with unified exit codes.

Together the four layers give governance in depth: the constitution states what is inviolable, constraints and boundaries scope who may write where, the pending ledger tracks what a human still owes, and the guardrail scripts verify that the last commit honoured all of it. No single layer is trusted alone.
