The canonical path

SEJA is a governance layer for Claude Code: it structures AI-assisted software work as a lifecycle, not a single free-form conversation. The canonical path runs /research (or /explain) → /design | /plan → /implement → /critique → /document | /communicate → /reflect — validate before you communicate. Each stage is a skill, and every user-facing skill shares the same shape: it opens with the pre-skill pipeline and closes with the post-skill pipeline. The skill's own work sits in between.

This uniform wrapper is the harness's core value. Skills may opt out of non-critical pipeline stages, but no skill may skip pre-skill entirely: lifecycle discipline is non-negotiable (constitution principle T1). The sections below describe the conceptual model — what the two pipelines do and why — and a matrix for choosing a skill.

Boundary. This page covers the conceptual model of the pipeline. The Reference Core sibling pipeline-stages.html is the exhaustive stage-by-stage lookup table; consult it when you need the precise behaviour, inputs, and skip rules of an individual stage.

Skill invocation: the pre-skill / skill / post-skill sandwich

A skill invocation is always three phases. Pre-skill loads the context the skill needs and logs the request; the skill does its work; post-skill records the outcome, aligns state, and commits. The designer types one command (for example /plan Add a tagging feature) and the harness runs all three phases in order.

Two internal hooks — pre-skill and post-skill — carry this out. They are not invoked directly by designers; each user-facing skill calls them at its start and end. Because the wrapper is uniform, every skill inherits the same governance guarantees: the brief is logged, the constitution is loaded, pending work is surfaced, and the result is committed.

The pre-skill pipeline: six stages

Pre-skill runs a pipeline of six composable stages. Three are critical (they always run); the rest are non-critical (error-isolated — they warn and continue on failure — and skippable when a skill lists them in its metadata.skip_stages).

The six pre-skill stages, in execution order.
Stage Criticality What it does
help Non-critical If the skill's arguments contain --help, show the skill's quick guide and stop before any other processing.
brief-log Critical Insert a STARTED entry (timestamp, skill name, brief) at the top of the briefs log, link it into the conversation trace, and persist the brief for post-skill to consume.
budget-eval Critical Read the skill's context_budget (light, standard, or heavy) and load briefs accordingly; run orphan-detection and, at the heavy tier, a compaction warning.
pending-check Non-critical Print the pending-actions banner (overdue human actions). Purely informational; never blocks the invocation.
ref-load Critical Load the mandatory references (conventions, permissions, constraints) plus the skill's declared references, eagerly or on demand.
constitution Non-critical Read and inject product-design/constitution.md so the immutable principles govern the rest of the invocation.

The tiered budget in budget-eval is how the harness keeps context lean. A light skill loads only the brief log and skips ref-load and constitution; a standard skill loads a briefs index rather than the full log; a heavy skill loads the full briefs log with recency windowing plus the plan index. The orphan-check and compaction-check legacy IDs are now sub-steps of budget-eval.

The post-skill pipeline: closing the loop

Post-skill is where the invocation's results become durable state. It marks the brief DONE, records a telemetry entry, aligns the implementation record with what was built, logs the Q&A, verifies the commit scope, regenerates indexes, and commits — then offers a contextual next-step suggestion. The pipeline is checkpointed: if it crashes partway, a checkpoint file lets a re-run resume from the step after the last completed one.

Conceptually, post-skill does four kinds of work:

  • Brief and telemetry closure. Flip the matching STARTED brief to DONE and append a telemetry record so the harness can measure its own behaviour.
  • State alignment (only after /implement). Update product-design-as-coded.md to reflect what was built, and propose flipping STATUS markers on the corresponding as-intended items — always via apply_marker.py and always after an AskUserQuestion confirmation.
  • Documentation and pending work. Offer to run /document when a plan declared documentation needs, and file pending actions (verify-as-coded, test-implementation, update-documentation) so nothing that needs a human is silently dropped.
  • Commit and hand-off. Run a git-state safety check and a commit-scope check, commit the affected files, and suggest the next skill on the canonical path.

A decision matrix: which skill next

The pipeline is the same for every skill; what varies is which skill you reach for. Match your intent to the canonical path:

Choosing a lifecycle skill by intent.
Your intent Skill Where it sits
Investigate what you are about to change; ask a question about the codebase or design /research Entry point
Understand behaviour, code, architecture, or spec drift with diagrams and analogies /explain Entry point (alternative)
Change design intent — stack, conventions, domain model, or conceptual design /design Intent branch
Decide how to build something without changing intent /plan No-intent-change branch
Execute an existing plan to add a feature, fix a bug, or refactor /implement Build
Validate: run checks, code review, smoke tests, preflight, or harness health /critique Validate (before you communicate)
Generate or update user and developer documentation /document Communicate branch
Produce tailored material for a specific stakeholder audience /communicate Communicate branch
Reflect on what was built or how you worked /reflect Close the loop

The split after the entry point is the key decision: branch into /design when the change requires intent to change, or into /plan when it does not. On the first iteration of a project, /seja-setup hands off to /design to configure the project; from the second iteration onward, start with /research (or /explain).
