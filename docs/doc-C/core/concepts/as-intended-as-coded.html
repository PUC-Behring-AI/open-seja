Two specifications, deliberately separate

SEJA keeps two design specifications side by side rather than one. The as-intended spec (product-design/product-design-as-intended.md) records what the designer means to build: the working design intent, the DDR-shaped decisions, and the changelog. The as-coded spec (product-design/product-design-as-coded.md) records what was actually built: the conceptual design, metacommunication, and journey maps as they exist in the implementation.

The two files have different owners, and that is the whole point. The as-intended file is Human (markers): its prose is authored only by the designer, and agents may touch only its lifecycle markers. The as-coded file is Agent: post-skill maintains it after each /implement run to mirror the code. Keeping intent and implementation in separate, differently-owned files means the gap between “what I wanted” and “what shipped” is always representable — it is the difference between two documents, not a hidden inconsistency inside one.

The pairing is declared in the As-Intended / As-Coded Registry in conventions.md, the single source of truth read by /design, /explain drift, and the post-skill DONE-marking proposals.

Drift reconciliation

Because intent and implementation are separate documents, they can drift apart: a feature is designed but not yet built, or built but never written into intent, or built differently than intended. The /explain drift workflow measures that gap and, optionally, reconciles it.

Drift analysis reads the registry and compares each in-scope pair section by section. For conceptual design it compares entities, permissions, UX patterns, and business rules; for metacommunication it compares feature intentions, implementation status, and stated designer intent. Each difference is classified as Added (present in as-intended but not as-coded), Removed (present in as-coded but not as-intended), or Modified (present in both but different). The result is a drift report with a summary table and a list of detailed changes.

After presenting the summary, the workflow offers an optional sync: align metacomm with the conceptual design, align the conceptual design with metacomm, or reconcile both bidirectionally. When the two files genuinely conflict, the harness never auto-resolves — it presents both sides and asks the designer to decide, then records the resolution verbatim. Drift analysis by itself is read-only; only the sync step writes.

The promote workflow

Reconciliation has a second mode aimed specifically at closing the intent-to-implementation loop: the promote workflow. Its job is to move items marked STATUS: implemented up to established — recording, in the designer's own words, that an implemented decision is now a settled part of the design.

The workflow is deliberately split into two phases so the designer owns every word of the decision prose while the harness manages only the marker lifecycle:

  • Phase 3a — proposal generation (/explain drift --promote): the harness scans registered Human (markers) files for STATUS: implemented items that lack an ESTABLISHED stamp, drafts a DDR-shaped Decision entry for each in a copy-paste-friendly proposal file, and files a pending action. It does not touch the intent file — the draft is the designer's to rewrite freely.
  • Phase 3b — marker flip (/explain drift --promote --apply-markers plan-NNNNNN): after the designer has copied the (possibly rewritten) Decision entries into the intent file, the harness confirms each D-NNN entry is present, asks per-item whether to flip its STATUS from implemented to established, and applies the change through apply_marker.py.

The two-phase shape is the key idea: the harness proposes and manages markers, but the designer authors the prose. Promotion never rewrites intent on the designer's behalf — it only records, structurally, that intent and implementation have converged.
