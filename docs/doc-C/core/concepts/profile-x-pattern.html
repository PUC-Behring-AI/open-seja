Two axes, four profiles

How SEJA installs into a project is decided by two independent questions. First: is there an existing codebase to install into (brownfield) or is this a fresh start (greenfield)? Second: should the harness live inside the codebase (collocated, or embedded) or in a separate directory alongside it (companion workspace)? The two axes give a 2×2 matrix of installation profiles, and /seja-setup routes each combination to the right flow.

Axis 1: greenfield vs brownfield

The greenfield / brownfield axis is about what already exists at the target. On a greenfield target there is no source code yet: /seja-setup creates the directory structure, runs the Section 1 basic-definitions questionnaire to populate conventions.md, and scaffolds a stack skeleton from the answers. On a brownfield target an existing codebase is present, so setup first scans the dependency files (package.json, requirements.txt, pyproject.toml, and the like) to pre-fill the questionnaire: each detected framework is presented as a confirmation prompt (“I detected flask; correct?”) rather than an open-ended entry. The two paths converge on the same populated conventions.md; brownfield simply starts from detected values.

Axis 2: collocated vs companion workspace

The collocated / workspace axis is about where the harness lives relative to the code. In the collocated (embedded) profile, .claude/ and product-design/ sit in the codebase's own root and share its git history — the simplest layout, well suited to greenfield projects and to teams comfortable with the harness in-tree. In the companion workspace profile, the harness lives in its own directory, its own git repo, with version-controlled design history kept separate from the codebase; a launcher script invokes claude --add-dir <codebase-dir> so the agent can still read and write the code. The workspace profile keeps SEJA's design history out of an existing project's repo, which is often the deciding factor for brownfield installs.

The 2×2 matrix

Reading the two axes together gives four profiles. The cells describe how /seja-setup behaves for each combination.

Installation profiles by field state and harness placement.
Collocated (embedded) Companion workspace
Greenfield Create the target, run the questionnaire, scaffold the stack, and commit — harness in-tree. Create separate workspace and codebase subdirs, git init each, redirect harness files to the workspace, and generate a launcher.
Brownfield Auto-detect the stack to pre-fill the questionnaire, then embed .claude/ in the existing codebase root. Detect any embedded harness files, offer to migrate them to a new workspace dir, git init the workspace, and generate a launcher.

/seja-setup resolves the profile by inspecting the target (via its state-detection step) and, when the layout is ambiguous, by asking — for an existing codebase it prompts “Embed SEJA in this codebase or create a separate workspace?” The same install engine handles all four cells; the profile only decides which directories are created, whether stack detection pre-fills the questionnaire, and where the harness files land.
