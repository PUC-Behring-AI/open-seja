Structured, deterministic review

SEJA reviews plans, diffs, and architectural decisions against a fixed checklist of domain lenses called perspectives. This replaces an ad-hoc “simulate a council” instruction with a structured, deterministic sweep: each applicable perspective is evaluated and recorded with an explicit status. A change is not reviewed by vibe; it is reviewed lens by lens, and the record shows which lenses were applied and what each concluded.

Boundary. This page is the conceptual overview. The exhaustive catalog of every perspective — the full per-lens question set at each priority — lives in the Reference Core sibling perspectives.html.

Two role families

The sixteen perspectives split into two families. Eleven engineering perspectives cover the build-and-run concerns; five design perspectives cover the experience concerns. Each carries a short tag used in review logs.

The two perspective families and their lenses.
Family Perspectives (tag)
Engineering (11) Security (SEC), Performance (PERF), Database (DB), API Design (API), Architecture (ARCH), Developer Experience (DX), Internationalization (I18N), Testability (TEST), Operations / DevOps (OPS), Compatibility (COMPAT), Data Integrity & Privacy (DATA)
Design (5) User Experience (UX), Accessibility (A11Y), Visual Design (VIS), Responsive Design (RESP), Microinteractions (MICRO)

Each review records a tag plus a status: Adopted (evaluated, concerns addressed), Deferred (evaluated, not addressed — with pros and cons stated), or N/A (does not apply). When two perspectives conflict, fixed rules resolve it: security wins by default unless the user accepts the risk, and accessibility is non-negotiable — never traded against visual design or performance.

Three expertise levels

Each perspective is authored at three depths, and each of its questions carries a priority from [P0] (critical, blocking) through [P4] (informational). The tiers bundle those priorities:

Essential (P0)
The critical, blocking questions. Always evaluated; loaded for standard context or the default shortlist.
Standard (P1–P2)
Questions for a thorough review; loaded for heavy context or a perspective that is a primary focus of the review.
Deep (P3–P4)
Exhaustive analysis; optional unless the perspective is the primary focus. Under time or context pressure, focus P0–P1 first.

Depth gating and two-stage loading

SEJA never bulk-loads all sixteen perspective files. Depth gating and a two-stage load protocol keep review context lean. First the review loads a compact index — tag, name, and scope for each lens — which is small enough to hold cheaply. From that index it selects four to six perspectives, either by a plan-prefix shortcut table or by the content of the change. Only the selected <tag>.md files are then loaded in full.

The plan prefix drives the default shortlist: a backend feature (FEATURE-B) pulls SEC, DB, API, ARCH, TEST, and PERF; a frontend feature (FEATURE-F) pulls UX, A11Y, VIS, RESP, I18N, TEST, and MICRO; up to two extra lenses may be added when the plan content warrants. The consumers — /plan and /critique review — follow this protocol unless the depth is Deep and every perspective is genuinely needed, in which case all sixteen load. This is how the harness gets deterministic coverage without paying the context cost of every lens on every review.
