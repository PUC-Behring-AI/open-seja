Overview

This glossary holds the canonical wording for the terms SEJA uses to describe itself and the actors it governs. The source of truth is .claude/references/general/shared-definitions.md; when the same term appears in a skill, agent, plan, or reference file it should mean exactly what it means here. The tables below are fully readable with JavaScript disabled — the in-page filter and table of contents are progressive enhancement layered on by nav.js, never a hard dependency for reading a definition.

Terminology

Core terms for how SEJA describes itself and the actors it governs. Every skill, agent, plan, and reference file should use these terms consistently.

SEJA actor and category terminology.
Term Definition
harness SEJA's category: the governance layer that constrains and shapes the model's behavior through skills, rules, references, agents, and lifecycle hooks. An agent harness is not a programming framework — it does not provide libraries, base classes, or runtime abstractions. It provides governance, constraints, and lifecycle management. The primary compound is "SEJA is an agent harness grounded in semiotic engineering."
the agent Claude — the LLM and CLI tool. Refers to the model's raw capabilities: generating code, answering questions, using tools. When a sentence describes behavior that exists without SEJA governance, use "the agent." Example: "The agent can generate code, but without governance it skips planning and review."
the harnessed agent The composite of Claude operating within the SEJA harness. When the harness shapes the agent's behavior — reading the constitution, following lifecycle skills, applying review perspectives, consulting design intent before coding — the result is the harnessed agent. Use this term when SEJA's contribution to the behavior should be visible.
subagent A specialized agent delegated to by the main agent via the Agent tool. Subagents run in isolated context windows with focused prompts (e.g., code-reviewer, document-generator, harness-health-evaluator). See .claude/agents/ for the full inventory.

Semiotic Engineering concepts

Semiotic Engineering concepts as applied in SEJA.
Term Definition
metacommunication message A designer-to-user message conveyed throughout the system and UI. Semiotic Engineering summarizes it as: "Here is my understanding of who you are, what I've learned you want or need to do, in which preferred ways, and why. This is the system that I have therefore designed for you, and this is the way you can or should use it in order to fulfill a range of purposes that fall within this vision."
phrasing rule (non-negotiable) All metacommunication messages — in templates, project files, plans, briefs, per-feature logs, and EMT answers — must use first-person "I" for the designer and second-person "you" for the user. Never use "the designer", "the system", "the user" (third-person), passive voice, or imperative mood. Example: write "I designed a postpone shortcut for you because I know you tend to over-schedule" — not "The designer provides a postpone shortcut."
verbatim rule When a user provides a metacommunication message as input (during /design, in a spec, in product-design-as-intended.md, or as a --framing metacomm brief), the agent must record it exactly as written, without summarization or editing. The designer's precise wording carries intentional nuance; paraphrasing distorts design intent.

Theoretical Foundations

SEJA is grounded in Semiotic Engineering (SemEng), a theory of HCI that treats human-computer interaction as computer-mediated human communication. The table maps SEJA concepts to their SemEng origins for intellectual traceability — skills and agents do not require users to know SemEng terminology.

Spec-drift detection (as-coded vs. as-intended) Communicability monitoring — tracking design-intent transmission [SemEng-2005, Ch. 4; SemEng-Methods-2009]

Notation Conventions

Notation and identifier conventions used across SEJA reference files.
Notation Meaning
standards.md § Backend > 6 Standards-section notation. § <Domain> identifies the H2 section (Backend, Frontend, Testing, i18n for standards.md; UX patterns, Graphic / visual design for design-standards.md) and > N identifies the H3 subsection whose heading begins with N.. Original pre-2.8.1 numbers are preserved, so backend-standards §6 maps to standards.md § Backend > 6 by direct substitution.
<!-- STATUS: … --> Inline lifecycle marker placed immediately before a section heading — invisible in rendered Markdown, machine-parseable by agent tooling. Current scheme is a lowercase multi-value marker with the state machine proposed → implemented → established → superseded; the legacy uppercase STATUS: IMPLEMENTED remains valid.
ESTABLISHED: Promotion stamp: <!-- ESTABLISHED: plan-NNNNNN | YYYY-MM-DD | vX.Y.Z -->. Applied when a human confirms promotion of an IMPLEMENTED item. The vX.Y.Z field is optional (date-only for projects without semver).
REQ-TYPE-NNN Stable, machine-parseable requirement identifier placed as an HTML comment before the heading, row, or bullet it traces. Type prefixes include ENT, PERM, VAL, UX, MC, JM, I18N, DELTA. NNN is a zero-padded 3-digit counter per type. Security-classified types (PERM, VAL) are blocking at preflight; the rest are advisory.
D-NNN Design-intent Decision entry identifier (DDR shape) under product-design-as-intended.md § Decisions. Orthogonal to REQ-TYPE-NNN — a separate taxonomy, never intermixed. Never write REQ-D-NNN collisions.
advis* (two senses) Sense A — the artifact type /research produces (formerly /advise); new writes use research. Sense B — the engineering adjective meaning non-blocking / informational (unchanged). When you encounter advis*, ask: artifact type or severity?
