Overview

SEJA reviews changes against a fixed set of sixteen domain perspectives — eleven engineering lenses and five design lenses. Each perspective is a checklist of priority-classified questions that gives structured, deterministic coverage across security, performance, architecture, accessibility, and the rest, replacing ad-hoc "simulate a council" instructions. The /plan and /critique review skills evaluate a change against each applicable perspective and record its status: Adopted (evaluated; concerns addressed), Deferred (evaluated; not addressed — with a stated rationale), or N/A (does not apply).

Boundary note. This page is the exhaustive catalog — every perspective, its tag, scope, and tiers, plus the loading protocol and conflict rules you consult while a review is running. The conceptual overview of why perspective-based review exists and how it replaces council simulation lives in the Concepts sibling Review Perspectives. Read that page for the mental model; consult this one to look up a specific lens.

The Essential / Standard / Deep tiers

Every perspective file organizes its questions into three tiers, and each perspective offers all three. The tier controls how many of a perspective's questions are evaluated, matching review depth to the context budget:

  • Essential — the [P0] critical, blocking questions. Always evaluated; loaded for a standard context budget or when the perspective is on the default shortlist.
  • Standard — the [P1]–[P2] questions for a thorough review; loaded for a heavy context budget or when the perspective is a primary focus.
  • Deep — the [P3]–[P4] exhaustive-analysis questions; optional unless the perspective is the primary focus of the review.

Questions are priority-classified [P0] (critical) through [P4] (informational) and sorted by priority; under time or context pressure, focus on P0–P1 first.

Design perspectives (5)

The five design lenses cover the human-facing concerns of a change. Accessibility (A11Y) is non-negotiable — see the conflict rules below.

Two-stage loading protocol

To avoid bulk-loading all sixteen perspective files into context, the review skills follow a two-stage protocol:

  1. Load the index. Read general/review-perspectives-index.md (under 600 tokens) — the compact tag/name/scope table for all sixteen lenses.
  2. Select 4–6 perspectives. Choose them via the Perspective Shortcuts by Plan Prefix table (default shortlists keyed on the plan prefix and scope, e.g. FEATURE-B → SEC, DB, API, ARCH, TEST, PERF), or manually by change content. Add up to two extra perspectives if the plan content warrants it.
  3. Load only the selected files. Read just the chosen review-perspectives/<tag>.md files.

/plan and /critique review both follow this protocol — unless the review depth is Deep and all sixteen perspectives are genuinely needed.

Resolving perspective conflicts

When two perspectives pull a review in opposite directions (for example PERF vs. SEC), remark the conflict and resolve it with these rules:

  1. SEC wins by default — unless the user explicitly accepts the risk.
  2. A11Y is non-negotiable — never traded against visual design or performance.
  3. Document the trade-off — record both the chosen approach and the deferred concern, with rationale.
  4. Ask when unclear — for non-default conflicts (e.g. PERF vs. DX), ask the user.
