What it does

/explain gives you a clear explanation of how something works — a feature's behavior, the data model, the overall architecture, how behavior evolved over time, how code works, or the drift between your design specs. Explanations include diagrams and analogies to make complex topics accessible.

Six mutually exclusive mode types each produce a different kind of explanation report: architecture (system architecture, component relationships, and design choices), behavior (emergent behavior from a user's perspective), behavior-evolution (current behavior and how it evolved through past plans and commits), code (how code works, aimed at junior developers), data-model (the data model with pitfalls and refactoring opportunities), and drift (the gap between as-coded and as-intended design specs). The drift mode additionally offers an interactive sync workflow to realign diverged specs, including a two-phase promote flow that drafts Decision entries and then flips STATUS markers.

When to run it

Run /explain when you want to understand how a part of the system works, need to onboard yourself on unfamiliar code, want a visual overview of the architecture, or want to see and resolve the gap between as-coded and as-intended design specs.

It answers your questions about the system — it is not for generating artifacts someone else will read (use /document, /communicate, or /onboard for that). Reach for drift mode when you need to check divergence, especially after a cycle closes.

How it fits the lifecycle

On the canonical path — /research → /design | /plan → /implement → /critique → /document | /communicate → /reflect — /explain shares the investigation entry point with /research. It is the alignment workflow you reach for when you want to understand behavior or reconcile specs before changing anything.

In its general modes (architecture, behavior, code, data-model, behavior-evolution) it most often hands off to /research for deeper follow-up questions. In drift mode it has a recurring post-/reflect role: after each cycle closes, run /explain drift to detect divergence, then branch into /plan to address it, /design if intent has evolved, or /pending to work the pending actions the check surfaced.
