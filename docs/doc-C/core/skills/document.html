What it does

/document generates or updates project documentation. It offers four invocation modes: plan-driven (--plan <id> reads the Docs: fields from a plan and produces documentation for each identified need), auto-detect (--auto-detect scans recent git changes and applies a heuristic to decide which doc types are needed), type-targeted (--type forces a specific type), and bare scope (you name a file, module, or feature and the type is inferred).

Six documentation types are supported: readme, contextual-help, api-reference, ddr, help-center, and changelog. Generation uses the project's templates and the documentation-quality writing guide, and it is carried out by document-generator agents — one per doc type, launched in parallel when a run produces several. The --since and --full-history flags tune the bounding window for auto-detect scans.

When to run it

Run /document after implementing a feature or fix that affects user-facing behavior, API contracts, or architectural decisions. Post-skill automatically suggests it for FEATURE and REDESIGN plans and for plans with non-N/A Docs: fields.

Use --plan when documentation needs are already specified in a plan, --auto-detect for a broad scan of what changed, --type when you know exactly which type you need, and bare scope for ad-hoc documentation of a specific area. /document is not for stakeholder updates (use /communicate) or personalized onboarding plans (use /onboard).

How it fits the lifecycle

On the canonical path — /research → /design | /plan → /implement → /critique → /document | /communicate → /reflect — /document sits in the delivery stage, sharing that stage with /communicate. You validate with /critique first, then document what was built for future readers.

The two delivery skills split by audience: /document produces reference and how-to material about the system itself, while /communicate produces stakeholder-facing material. After documenting, a natural follow-up is /critique docs to validate documentation consistency.

See also

  • /critique — run docs mode to validate documentation consistency.
  • /explain — understand existing system behavior, architecture, or spec drift.
