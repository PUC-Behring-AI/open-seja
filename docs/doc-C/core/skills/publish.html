What it does

/publish publishes a tagged release to the public SEJA repository. It wraps the automated publish pipeline, which handles the full release lifecycle: preflight checks, tag creation, cloning the public repo, copying prose, syncing harness files, running smoke tests, committing, pushing, and closing the pending publish entry.

You can pass an explicit version (vMAJOR.MINOR.PATCH), or omit it and let the pipeline infer the next tag from CHANGELOG.md heuristics and git tags and prompt for confirmation. --dry-run previews the full command sequence without executing any destructive actions, and --yes accepts all confirmation prompts for a non-interactive run.

When to run it

Run /publish when you are ready to cut a public release. The prerequisites are that the public CHANGELOG has content under its Unreleased heading, the working tree is clean, and the remote is reachable. Run /critique preflight beforehand if you want a quality gate before the release.

/publish is not for internal harness iteration (just commit normally), changelog authoring (edit the public CHANGELOG directly), or harness upgrades in consumer projects (use /seja-setup --upgrade).

How it fits the lifecycle

On the canonical path — /research → /design | /plan → /implement → /critique → /document | /communicate → /reflect — /publish is a release-management operation that runs after the delivery stage, once work is validated, documented, and ready to ship outward.

After a successful publish, the natural next step is to verify the release on GitHub and optionally graduate the internal changelog’s Unreleased section to a new version heading. On failure, the pipeline’s own recovery guidance is authoritative — /publish does not retry automatically.
