What it does

/implement runs a previously approved plan step by step. It creates a rollback branch before starting and ends with a Quality Gate — validation, code review, tests, and smoke tests if configured.

Three execution modes suit different situations: auto (the default) dispatches each step to a fresh subagent with isolated context and follows a TDD red-green cycle for steps that carry explicit Tests: fields, with a generator-critic loop for critical code-review findings; manual (--manual) runs steps sequentially in your current context with per-step confirmation; and roadmap (--roadmap) executes all plans in a roadmap wave by wave, pausing for review between waves. Advanced flags include --dry-run (preview without writing files), --skip-checks (skip the Quality Gate), --skip-docs (suppress the documentation prompt), and --checkpoint (control roadmap pause granularity).

When to run it

Run /implement once you have reviewed a plan created by /plan and are ready to have the agent carry it out. Use auto mode for most plans, especially those with more than six steps; use --manual for small plans or when you want per-step confirmation; and use --roadmap to execute all plans in a roadmap wave by wave without triggering each one manually.

How it fits the lifecycle

On the canonical path — /research → /design | /plan → /implement → /critique → /document | /communicate → /reflect — /implement is the build step. It takes the reviewed plan from /plan and turns it into working code.

Its end-of-run Quality Gate runs validation, review, and tests automatically unless --skip-checks was used, so /critique largely happens inline; documentation generation for qualifying plans runs automatically via post-skill unless --skip-docs was passed. After implementation, move on to /pending to review pending actions or /reflect to surface patterns across recent work.
