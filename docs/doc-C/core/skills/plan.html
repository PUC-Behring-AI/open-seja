What it does

/plan creates a step-by-step plan for your next feature, bug fix, or improvement. You describe what you want, and the agent produces a detailed plan you can review before anything changes. Each step lists the files to change, verification criteria, and dependencies.

Three modes cover different sizes of work: standard (a single plan, the default), lightweight (--light, a shorter, less formal proposal suitable for small fixes), and roadmap (--roadmap, a full product roadmap that decomposes the work into dependency-aware execution waves and generates individual plans for each item). The --framing metacomm option frames the brief as a designer's metacommunication message, preserving the user-experience perspective in the plan, and --review deep overrides the complexity-gated review depth.

When to run it

Run /plan when you have a clear idea of what you want to build or fix and want a structured plan before any code changes happen. If you omit both --light and --roadmap, the agent auto-detects the best mode from your brief and asks for confirmation before proceeding.

Use --light for quick proposals that do not need full step metadata, --roadmap for building a complete product across multiple waves, and --framing metacomm when describing the change from the user's perspective.

How it fits the lifecycle

On the canonical path — /research → /design | /plan → /implement → /critique → /document | /communicate → /reflect — /plan shares the intent-setting stage with /design. After investigating with /research or /explain, you branch into /plan when intent is already set and you just need a build plan, and into /design when the intent itself must change.

Once you have reviewed the plan, the next step is /implement to execute it (or the first roadmap item). When passed a research ID, the plan records its source so the lifecycle stays traceable.
