What it does

/design configures design intent for your project. After /seja-setup populates conventions.md with stack definitions, /design generates the remaining design-intent artifacts — product-design-as-intended, ux-research-results, standards, design-standards, security checklists, and the constitution — and amends CLAUDE.md.

Six modes cover every design lifecycle stage: an interactive questionnaire (the default), configuration from a pre-filled spec file, adding documentation templates, generating a blank spec skeleton to fill out offline, an interview-driven conversation, and updating existing design sections. Use /design update <section-slug> to jump straight to a specific section — stack, conceptual, metacomm, standards, security, testing, constitution, and more — skipping the interactive menu.

When to run it

Run /design after /seja-setup to define design intent for a new project, and anytime you want to update your project's design foundations: stack, domain model, standards, or metacommunication. Use the interview mode when you want to think out loud rather than fill in a form, and the default questionnaire when you know your stack and want speed.

It is not for topology scaffolding (use /seja-setup), planning implementation (use /plan), or checking drift between intent and code (use /explain drift).

How it fits the lifecycle

The canonical path is /research → /design | /plan → /implement → /critique → /document | /communicate → /reflect. /design shares the intent-setting stage with /plan: after investigating with /research or /explain, you branch into /design when the intent itself needs to change, and into /plan when intent is already set.

On the first iteration, /seja-setup hands off to /design to configure the project. From there, the natural next step is /plan --roadmap to generate a development roadmap from the new design, or /plan to plan your first feature.
