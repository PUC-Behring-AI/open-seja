What it does

/seja-setup is the single entry point for every harness-state transition in a project. It manages five modes: install (copy the harness into a new or existing project directory), finalise in place (--here, when SEJA was cloned directly into your project folder), companion workspace (--workspace, a separate design workspace alongside an existing codebase), demo (--demo, the pre-configured TaskFlow project), and upgrade (--upgrade, refresh harness files to the latest release).

With no arguments, it first inspects the current directory via detect_setup_state.py and routes to the right action. State detection recognises no-harness, fresh-download, partial-init, finalised, plus a dev-repo-refuse guard that hard-refuses to run inside a SEJA development repository. On a fresh install it scaffolds a bootable skeleton in one invocation: it populates product-design/conventions.md from a basic-definitions questionnaire, scaffolds a stack-dependent CLAUDE.md, writes stack-flavoured files into .claude/rules/, and adds smoke-test infrastructure when a backend is present. Four stack-presence modes — full-stack, API-only, frontend-only, and CLI / library — determine exactly what gets scaffolded.

When to run it

Run /seja-setup every time you touch SEJA’s state in a project: the first install, an in-place finalisation, companion-workspace creation, a demo bootstrap, or a later harness upgrade. After the first iteration you rarely run it again unless you are upgrading.

Reach for /seja-setup <target> to install into a new or existing directory, /seja-setup --here when you cloned SEJA straight into your project folder, /seja-setup <target> --workspace to work alongside an existing codebase, /seja-setup <target> --demo for the guided TaskFlow tour, and /seja-setup --upgrade (optionally --version <tag> or --dry-run) to refresh harness files without touching project-specific data.

How it fits the lifecycle

/seja-setup sits at the very front of the lifecycle: on the first iteration it hands off to /design to configure the project before the canonical path — /research → /design | /plan → /implement → /critique → /document | /communicate → /reflect — comes into play. Every install ends with a handoff message directing you to run /design to define entities, permissions, metacommunication, personas, and standards.

After an --upgrade, the natural next steps are /critique health to verify harness integrity and then /explain drift to catch changed conventions. The source repository is not a runtime dependency — once setup completes, all skills, rules, agents, and references live inside your project, and you work from the project rather than the source.
