Overview

/seja-setup is the single entry point into the harness. It installs SEJA into a new or existing project, finalises an in-place download, creates a companion workspace, bootstraps a demo, or upgrades an existing install. This page covers the four install modes; for refreshing an existing install see Upgrading SEJA.

The choice of mode has two axes: whether your project is new (greenfield) or existing (brownfield), and whether the harness lives collocated in the project directory or in a companion workspace beside the codebase. Those two axes give four modes.

Which mode: a decision tree

Answer two questions to land on your mode.

  1. Is your project new or existing? New (no code yet) is greenfield; an existing codebase is brownfield. For brownfield, /seja-setup auto-detects the stack from dependency files and pre-fills the scaffolding questionnaire as confirmation prompts.
  2. Same directory or companion workspace? Collocated embeds .claude/ and product-design/ in the project root. A companion workspace keeps the harness in its own git repo beside the codebase; you operate on the codebase via claude --add-dir <codebase-dir> through generated launcher scripts.
The four installation modes by project state and topology.
Collocated (embedded) Companion workspace
Greenfield (new project) greenfield-collocated. /seja-setup <target> creates the directory and copies the harness in place; the project boots with a stack-scaffolded skeleton. greenfield-workspace. /seja-setup <target> --workspace creates a workspace dir and a codebase dir, git inits each, and redirects harness files to the workspace.
Brownfield (existing codebase) brownfield-collocated. /seja-setup <target> on an existing repo offers Embed; the harness is copied into the codebase root, with brownfield stack auto-detection pre-filling conventions. brownfield-workspace. /seja-setup <target> --workspace creates a workspace alongside the codebase, offers to migrate any embedded harness files, and leaves the codebase unmodified.
Guided path. If you are unsure, run /seja-setup with no arguments in a fresh directory and choose Guide me through setup. It asks (a) greenfield or brownfield, (b) embedded or companion workspace, and (c) the target path, then routes to the right mode.

Mode 1: greenfield-collocated

A brand-new project with the harness embedded in the project root. 

/seja-setup ./my-project

The target directory does not exist yet, so /seja-setup creates it, copies the harness files (.claude/references/, all skill SKILL.md files, agents, rules, scripts, harness metadata), runs the Section 1 scaffolding questionnaire to populate product-design/conventions.md, scaffolds a stack-flavoured CLAUDE.md and .claude/rules/, adds smoke-test infrastructure when a backend is present, creates the _output/ workspace, and makes an initial commit. Then it hands off to /design to define design intent.

Mode 2: greenfield-workspace

A new project where the harness lives in its own version-controlled workspace, separate from the codebase. 

/seja-setup ./my-project --workspace

Workspace routing asks for the workspace and codebase directory names, creates both subdirectories, runs git init in each, and redirects the harness files into the workspace directory. It always generates launcher scripts (launch.sh / launch.bat) that invoke claude --add-dir <codebase-dir> so the harness can see and act on the codebase from its own directory.

Mode 3: brownfield-collocated

An existing codebase with the harness embedded directly in it. 

/seja-setup .

When the target is an existing git repo with source code, /seja-setup asks whether to embed SEJA or create a companion workspace; choosing Embed copies the harness into the codebase root. Before the Section 1 questions, brownfield stack auto-detection scans dependency files (package.json, requirements.txt, pyproject.toml, Cargo.toml, go.mod, and more) and directory structure, then presents each detected value (framework, database, test runner, directory layout) as a confirmation prompt — "I detected flask; correct?" — rather than an open-ended entry. Ambiguous or undetected fields fall back to manual entry.

Already installed? If the target already has a .claude/, /seja-setup offers Overwrite harness only (recommended for upgrades — never touches product-design/, settings, output, or CLAUDE.md), Overwrite everything (destructive, requires confirmation), or Create companion workspace.

Mode 4: brownfield-workspace

An existing codebase with the harness kept in a separate companion workspace, leaving the codebase itself unmodified. 

/seja-setup . --workspace

Brownfield workspace routing asks for the workspace directory path, detects any embedded harness files already in the codebase, offers to migrate them to the workspace, and creates and git inits the workspace directory. As with the greenfield workspace mode, it generates launch.sh / launch.bat so the harness operates on the codebase via claude --add-dir. The companion workspace is its own git repo with version-controlled design history.

Version pinning

Under the A2 release model, public SEJA ships tagged releases (vMAJOR.MINOR.PATCH). /seja-setup resolves the tag before any copy and writes it to <target>/.seja-version as the baseline for future upgrades. The resolution order is:

  1. --version <tag>, when supplied, wins;
  2. otherwise the latest SemVer tag on the remote is used;
  3. otherwise it warns and records HEAD (a pre-release fallback).

In workspace mode, .seja-version is written in the workspace directory (where .claude/ lives), not the codebase directory. Pinning a specific baseline at install time makes later /seja-setup --upgrade runs deterministic — see Upgrading SEJA.

Setup-state detection

The very first action of every /seja-setup invocation is state detection: it shells out to detect_setup_state.py --json and parses the result. The state field routes the no-argument flow to the right menu, and it also protects the harness source repo from being treated as a consumer project.

Detected setup states and how the no-argument flow responds.
State Meaning and response
no-harness No harness present. Offers "I have a target directory" or "Guide me through setup".
fresh-download SEJA files present but product-design/ and _output/ not populated. Offers to finalise here (--here) or target a different directory.
partial-init Some but not all setup artefacts exist. Offers to finalise/reconcile here or upgrade harness files.
finalised Harness plus project files exist. If .seja-version is already the latest, it reports "already up to date" and exits; otherwise offers upgrade, overwrite, or companion workspace.
public-clone-soft-confirm A clone of public SEJA with no divergence. Soft-confirms before finalising in place.
dev-repo-refuse Inside a SEJA development repo. Hard-refuses no-argument routing and --here to avoid corrupting the harness source.

Flag reference

The install-relevant flags:

--here
Finalise setup in the current directory without copying harness files — use when you ran git clone https://github.com/simonedjb/seja my-project directly into your project folder. It pins the version, scaffolds the output and project directories, runs the scaffolding questionnaire, and creates an initial commit. Incompatible with --workspace, --demo, and --upgrade.
--workspace
Create a separate companion workspace for working alongside an existing codebase, rather than embedding the harness in the codebase root. Drives the greenfield-workspace and brownfield-workspace modes.
--demo
Install and pre-fill the TaskFlow demo design files, then write a WALKTHROUGH.md guided tour. The scaffolding questionnaire is skipped; demo mode uses a pre-answered conventions file. Incompatible with --workspace and --upgrade.
Next step. After any install mode completes, open a Claude Code session in the target (or workspace) directory and run /design to define entities, permissions, metacommunication, personas, and standards.
