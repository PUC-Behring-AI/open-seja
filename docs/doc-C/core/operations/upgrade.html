Overview

Upgrading updates the project-independent parts of the harness — skills, general and template references, scripts, harness metadata — to a newer tagged release, while leaving everything you authored untouched. The upgrade runs from the target project, not the source repository, and never re-runs the scaffolding questionnaire. 

/seja-setup --upgrade

The --upgrade flag

--upgrade short-circuits state dispatch (while still honouring the dev-repo-refuse guard) and routes straight to the upgrade flow. The precondition is that the target is in the finalised state — it has .claude/, product-design/conventions.md, and a .seja-version pin (or the legacy no-pin fallback). In a finalised project, running /seja-setup with no arguments also surfaces Upgrade to latest as a menu option.

The upgrade flow, in outline:

  1. Resolve the target version (latest SemVer tag, or --version <tag>). If it already matches .seja-version, it prints "Harness already up to date" and exits.
  2. Locate the SEJA source at the resolved tag — a supplied local path, or a shallow clone of the tag.
  3. Read product-design/conventions.md for the output directory and other project paths.
  4. Run upgrade_harness.py to apply the file classification (below), writing the resolved tag to .seja-version on success.
  5. Show diffs for files that need a manual merge, offer follow-up actions, and summarise the change.

Pinning a version with --version

By default the upgrade targets the latest SemVer tag on the public SEJA remote. To pin to a specific release, pass --version <tag>: 

/seja-setup --upgrade --version v0.2.0

The resolution order mirrors install: --version <tag> wins; else the latest SemVer tag; else a warned HEAD fallback. Pinning lets you step through releases deliberately or hold a project at a known-good version rather than always chasing latest.

Previewing with --dry-run

To see what an upgrade would change without touching any files, add --dry-run: 

/seja-setup --upgrade --dry-run

Dry-run passes through to upgrade_harness.py --dry-run, which reports the same summary — files auto-updated, files needing a manual merge, new files added, the pin change — but applies nothing. Use it to review the delta before committing to the change.

.seja-version baseline tracking

.seja-version is a one-line file recording the release tag the project is currently pinned to. Install writes it first; each upgrade reads it for the "from" half of the change banner (for example v0.1.0 → v0.2.0) and overwrites it with the resolved tag on success. It is the anchor that makes upgrades deterministic and repeatable, and it is classified never overwrite only in the sense that the upgrade script — not a manual edit — owns the write.

The legacy (no .seja-version) path

Projects created before the A2 release model have no .seja-version pin. They upgrade as unknown → <target-tag> with a banner, and .seja-version is written on this first upgrade. To set a specific baseline explicitly without jumping to latest, pass --version <intended-baseline>.

Scaffolding migration. A pre-scaffolding project whose conventions.md still carries {{VAR}} placeholders keeps those placeholders through the upgrade — product-design/** is never overwritten. Run /design update stack afterwards to fill them and regenerate the downstream CLAUDE.md, rules, and smoke-test infrastructure via the named scaffolding anchors.

The preservation guarantee

The upgrade applies a file classification that decides what is safe to overwrite automatically and what is preserved. Your project definitions, settings, output, and CLAUDE.md are never overwritten.

How the upgrade treats each category of file.
Category Overwrite? Action
Skills (SKILL.md) Yes Auto-update
General references Yes Auto-update
Templates Yes Auto-update
Harness metadata (CHANGELOG, VERSION, CHEATSHEET) Yes Auto-update
Scripts Yes Auto-update
Agents Mostly Show diff, ask per file (may carry local tweaks)
Rules No Show diff, manual merge (project-specific conventions)
Project definitions (product-design/**) Never Skip
Settings Never Skip
Output directory Never Skip
CLAUDE.md Never Skip

After the run, review everything with git diff before committing. The post-upgrade summary lists the pin change, counts of files auto-updated, manually merged, and added, and the reference files it regenerated.
