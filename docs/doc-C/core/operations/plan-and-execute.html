Overview

/plan decides how to build something and produces a durable, reviewed plan artifact; /implement executes that plan. Together they are the build stretch of the canonical lifecycle: you plan without changing intent, then implement, then validate. This page covers the plan modes, the plan format, and the execution modes.

Design guard. /plan requires product-design/conventions.md to exist. If it is missing, planning stops and directs you to run /design first to define your stack, conventions, and domain model.

The /plan modes

/plan auto-detects the right mode from the brief, or you can force one with a flag.

Standard single-plan
The default for a single feature, bug fix, or refactor. Produces a full structured plan with a complexity-gated, two-phase review. Force it with --plan.
--light
A lightweight proposal for a small, surgical change — no multi-step decomposition, no multi-phase review, just an inline 2–3 perspective scan (always including SEC for code changes). For changes too small to warrant a full plan but worth tracking.
--roadmap
A full product roadmap: it decomposes conceptual design and standards into independent work items, classifies each as technical or design, and groups them into dependency-aware execution waves, generating a plan per item. Three sub-modes: auto-generate from project references (--auto), compile a pre-filled spec (--from-spec <path>), or emit a blank spec skeleton.

Auto-detection scores the brief: signals like three or more distinct entities, spanning two or more architectural layers, or multiple pages point toward a roadmap; a single bug, a specific file, or a scope that fits in twelve steps points toward a single plan. Majority wins, and the roadmap recommendation is confirmed before proceeding.

The plan format (plan_format_version 1)

A standard plan is a self-contained markdown artifact with a fixed set of sections. /implement reads the header for plan_format_version: 1; a plan without it falls back to manual execution.

  • Brief — the user brief (or the designer's verbatim metacommunication message under metacomm framing) plus the agent's interpretation: problem, approach, and — for Standard/Deep — alternatives rejected.
  • Best practices and, for Standard/Deep, design decisions (user-visible impact, trade-offs accepted, metacommunication impact).
  • Steps — the structured step list (detailed below).
  • Review Log — the perspective triage, Adopted/Deferred findings, any amendments, and the mandatory Execution Metrics table.
  • Outcomes — expected outcomes.
  • Smoke — true when any step creates or modifies API route or frontend page/component files, else false; /implement reads it to decide whether to run /critique smoke api.

Each step carries structured metadata:

The fields of a structured plan step.
Field Required? Purpose
Files Yes The files the step creates or modifies (no step touches more than five).
References Yes The specific product-design/ references the executing subagent must load.
Depends on Optional Prior steps that must complete first; absent means no dependencies.
Interface Yes (may be N/A) The type or API contract a dependency-producing step exposes.
Verify Yes How to confirm the step succeeded.
Tests Yes (may be N/A) An observable behavior to test ("when X is called with Y, returns Z"), used to write a failing test before implementation.

Review depth is complexity-gated: Light (≤6 steps and ≤4 files, Phase 1 only), Standard (7–12 steps or 5–8 files, plan-reviewer agent), or Deep (>12 steps, >8 files, or migrations/auth, all deep-dives). The --review <light|standard|deep> flag and the project's MINIMUM_REVIEW_DEPTH floor can raise the effective depth.

/implement execution

/implement <plan-id> executes a plan. The default is auto mode: each step runs in a fresh general-purpose subagent (the Ralph pattern), with state carried between steps through an append-only progress file. Auto mode follows a TDD red-green cycle per step — write a failing test from the Tests: field, implement until it passes, then confirm Verify: — and runs a bounded generator-critic loop that retries critical code-review findings up to twice before logging them as unresolved and continuing.

Manual mode (--manual) executes all steps sequentially in the current context — recommended for small plans (≤6 steps) or when you want per-step confirmation. It retains test-after ordering by design: your presence provides the oversight that the red-green cycle substitutes for in auto mode.

Both modes end with the Quality Gate — /critique validate, /critique review, the test-runner, and /critique smoke api when the plan's smoke field is true — unless --skip-checks is passed. Critical issues are fixed before the plan is marked DONE.

Roadmap execution and wave parallelism

/implement --roadmap <roadmap-id> executes every plan in a roadmap, wave by wave. Each plan runs auto mode in a fresh subagent. Wave 0 (foundation migrations) is always sequential for migration-chain safety; later waves may run in parallel when the plans' Files: lists — and their call-graph edges — do not overlap. Parallel plans run in isolated git worktrees and are merged back in a serialized merge phase.

The --checkpoint <wave|plan|none> flag sets pause granularity (default wave): wave pauses between waves so you can review what was built and revise downstream plans, plan pauses after every plan, and none runs full autopilot (failures still always pause). Roadmap runs are resumable — re-running /implement --roadmap <id> on a partially complete roadmap picks up from the first incomplete item.

The plan-to-implement lifecycle

When /plan concludes, it commits the plan as a durable git artifact and asks whether to implement now or later. The plan file persists regardless of that choice, so you can review it offline or implement it in a separate session. /implement then renames the plan to DONE on completion, closes the plan's pending entry, and — for roadmap-sourced plans — flips the roadmap's wave-summary row to done in the same commit as the rename. Validate the result with /critique before you communicate or document.
