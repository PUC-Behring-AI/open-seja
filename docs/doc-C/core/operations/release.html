Overview

A release is a tagged snapshot of the harness, cut manually when a coherent batch of changes is ready and then distributed to consumers. The /publish skill runs the whole pipeline in one step. This page covers the tag convention, the unified version namespace, the cadence and hotfix policy, and the A2 manual-sync distribution model.

Tag convention

Tags follow vMAJOR.MINOR.PATCH (SemVer), always prefixed with v. Any core-team member can cut a tag. SemVer allows gaps in the sequence, so consecutive published versions need not be numerically adjacent.

Unified version namespace

There is one version, one CHANGELOG entry, and one tag per release — no dual internal/public versioning. The harness CHANGELOG.md uses a single heading per release (e.g. ## [2.14.0]), and the same version number applies to the distributed mirror. This policy supersedes the earlier decoupled arrangement that maintained separate internal and public version streams; historical dual entries are preserved as-is for the record.

Cadence

Releases are manual: a core-team member cuts a tag when a coherent batch of changes is ready. Smaller changes are batched together, targeting at most about one release per week. A pending-ledger entry filed at tag-cut is surfaced by the pre-skill lifecycle hook on every skill invocation; if a publish entry stays unresolved for more than three days, the reminder escalates. This is the mechanism that keeps manual distribution from drifting into "cut a tag and forget."

The /publish skill

/publish [version] executes the full release pipeline: preflight, cut the tag, clone the distribution mirror, copy authored prose, sync the harness, run smoke tests, commit, and push — then close the pending publish entry. Its arguments:

  • [version] — the tag to publish (vMAJOR.MINOR.PATCH). When omitted, the pipeline infers the next tag from the CHANGELOG and git tags and prompts for confirmation.
  • --dry-run — preview the full command sequence without executing any destructive action.
  • --yes — non-interactive mode: accept all defaults at confirmation prompts.

When the resolved version has no matching harness-changelog entry, the skill generates one before proceeding. On success it reports the published version and confirms the pending entry was closed; on failure it relays the pipeline's own recovery guidance rather than retrying automatically.

Hotfix policy

The default rule is forward-fix on main: land the fix and tag the next patch version. A dedicated release branch is deferred until a real hotfix case arises — if a consumer is actively blocked on an older version, the team revisits and decides per case whether a release/<minor>.x branch is warranted.

The A2 manual-sync model

Distribution follows the A2 manual-sync model: releases are pushed to the public mirror deliberately, by running /publish, rather than on an automatic trigger. An automated CI workflow exists as a dormant fallback (dispatch-only), but the everyday path is the manual pipeline guarded by the pending-ledger reminder. A monthly consumer-path dogfooding ritual, run in a scratch consumer repo, exercises install and upgrade against a tagged release to surface experiential drift that smoke tests cannot catch.
