Overview

/critique is SEJA's validation skill. It has ten mutually exclusive modes covering everything from running validation scripts to reviewing code, smoke-testing endpoints, checking harness health, and evaluating interface communicability. One mode is required per invocation. Validate before you communicate — /critique sits between build and communicate on the canonical lifecycle.

The /critique modes

The ten /critique modes.
Mode What it does
validate Runs project validation scripts. Scope: all, i18n, auth, migrations, constants, po, coverage, tests, or spec. The standards-checker agent is the execution engine.
review Structured code review against quality perspectives via the code-reviewer agent. Scope: staged, a file, or a directory.
smoke Runtime smoke tests. Scope: all, api (Flask test client, no servers needed), or ui (Playwright).
preflight Combined validate + review in one pass — a pre-merge checkpoint. Scope: staged, all, or a directory.
health Harness self-diagnosis: nine built-in checks via the harness-health-evaluator agent. --source enables the drift check.
test-plan Generates a structured manual test plan from a brief and recent DONE plans.
docs Documentation consistency check via check_docs.py plugin scanners (paths, env vars, command refs, terminology).
freshness Compares local branches to their upstreams for the configured repos. Advisory only — never pulls.
telemetry Usage analytics and skill-invocation statistics from telemetry.jsonl. Read-only: reserves no ID and files no critique log.
semiotic-inspection SIM-based communicability evaluation via the semiotic-inspector agent. Scope: a feature, page, flow, or all.

Stack filtering via conventions.md

The validate and preflight modes filter which checks run to your project's stack. They read BACKEND_FRAMEWORK and FRONTEND_FRAMEWORK from product-design/conventions.md (via project_config.py), then load the plugin registry and keep each plugin whose stack.backend and stack.frontend are either empty (stack-agnostic) or contain your project's value. Only the matching scripts run; non-matching ones are skipped silently.

Legacy fallback. If conventions.md has no stack variables and they cannot be inferred from the codebase, /critique runs all scripts and includes a warning advising you to add BACKEND_FRAMEWORK and FRONTEND_FRAMEWORK to enable filtering.

The --depth override

The global --depth <light|standard|deep> flag overrides review depth for the review and preflight modes. The effective depth resolves as max(floor, flag), where floor is MINIMUM_REVIEW_DEPTH from product-design/conventions.md (default light). With no --depth flag, the code-reviewer agent evaluates all sixteen perspectives — equivalent to deep. Lighter depths use the two-stage loading protocol to select four to six relevant perspectives from the content of the change.

The preflight checkpoint pattern

preflight is the pre-merge checkpoint: it combines validate and review into a single pass and produces a go/no-go verdict. It resolves a scope (staged validates all and reviews staged; all reviews everything modified; a directory reviews that directory), applies stack filtering, then fans out — standards-checker, code-reviewer, and the smoke test (when the plan's smoke field is true) run as concurrent agents, each writing its own section. If one check fails, the others still produce results; preflight does not abort.

The verdict is conservative: READY only when all validation checks pass and there are no HIGH-severity review issues; otherwise NOT READY. Run preflight before merging so a single command gives you the full validate-plus-review picture.
