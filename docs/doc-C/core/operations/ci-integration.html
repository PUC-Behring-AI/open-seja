Overview

SEJA ships two orchestrators for running its validation scripts, sized for two different jobs. run_preflight_fast.py is the fast gate — a curated subset that finishes in under ten seconds and returns a single pass/fail verdict, so it can run on every commit without becoming the reason you stop running it. run_all_checks.py is the full-coverage orchestrator — it discovers every registered check_*.py script, runs them in turn, and can emit a JUnit XML report for a CI dashboard. The same fast gate backs the local pre-commit hook, the post-skill lifecycle step, and the GitHub Actions fast gate.

The run_preflight_fast.py entry point

run_preflight_fast.py is the single entry point for the fast gate. It is invoked from three contexts:

  • Local hook — .githooks/pre-commit calls it, blocking, before every commit.
  • Post-skill — the post-skill lifecycle step runs it advisorily after a skill completes.
  • GitHub Actions — the CI fast gate runs it, blocking, on push.

It runs a curated list of fast checks in order — conventions, retired-tokens, skill-system, secrets, skills-manifest, skill-spec, version-changelog-sync, design-output, plan-coverage, human-markers, changelog-append-only, section-boundary-writes, the three check_docs.py documentation scanners (harness-reference-coverage, docs-frontmatter, mantra-banner-consistency), and skill-graph-sync — printing one PASS/FAIL line per check. Three priv-only checks (the private-leak gate, plus the call-graph and harness-reference freshness checks) are appended only when their script files exist on disk, so a public consumer repo silently omits them. Deliberately excluded from this hot path is lifecycle-fact-uniqueness: its O(N²) comparison can produce false positives during transitional doc states, so it runs only under /critique docs and run_all_checks.py.

Exit codes. 0 = all checks pass, 1 = one or more checks failed, 2 = script error. The same code convention is honored by run_all_checks.py.

Two flags tune the run. --verbose streams each check's detailed output instead of capturing it. --ci appends the harness unit-test suite (pytest) to the run — the fast gate skips pytest by default to stay under its time budget, and the --ci flag opts into full test inclusion where the extra seconds are acceptable.

The pre-commit hook and installer

.githooks/pre-commit is a thin bash wrapper: it locates a Python interpreter, resolves the repo root, and runs run_preflight_fast.py. If the fast gate fails, the commit is blocked with guidance to fix the issues or bypass with git commit --no-verify (used sparingly). After the fast gate passes, the hook runs a second, priv-only stage — the pre-sync leak gate (check_no_private_leaks.py --staged) — but only when that script exists, so upgrades and public clones stay safe. If either stage fails, the commit is blocked.

The hook is not active until you point Git at it. .githooks/install.sh does this in one step: it runs git config core.hooksPath .githooks, after which the pre-commit checks run on every commit. Run it once per clone (bash .githooks/install.sh); uninstall with git config --unset core.hooksPath.

The run_all_checks.py orchestrator

run_all_checks.py is the CI-independent, full-coverage orchestrator. It discovers every check_*.py script in the scripts directory and in co-located skill subdirectories, runs each in turn, and rolls the results into a per-check summary table plus a single pass/fail verdict. It accepts --root to set the repository root, --filter <stack> to keep only checks matching a stack keyword via the plugin registry, and --verbose to stream child output. Its exit codes match the fast gate: 0 pass, 1 failure, 2 orchestrator error.

For CI dashboards, --junit <path> writes a JUnit XML report — a <testsuite> with one <testcase> per script, carrying per-check durations and embedding captured output inside <failure> or <error> elements. This is the preferred orchestrator for CI pipelines that need full coverage and a machine-readable report, while run_preflight_fast.py remains the lighter-weight option for git hooks and quick local validation.

Fast gate vs. full orchestrator

How the two orchestrators differ.
Aspect Scope Speed Output format Invocation context
run_preflight_fast.py Curated subset of fast checks (plus --ci pytest opt-in) Under ~10s One PASS/FAIL line per check + verdict Pre-commit hook, post-skill, GitHub Actions fast gate
run_all_checks.py Every discovered check_*.py script (optional stack filter) Slower — full sweep Summary table + optional JUnit XML (--junit) CI pipelines needing full coverage and machine-readable reports
