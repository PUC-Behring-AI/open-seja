Quickstart

The fastest path from zero to a working SEJA project. This chapter walks you through clone, setup, and your first lifecycle cycle with concrete commands and expected outputs. By the end you will have a configured project with a plan and its implementation.

Prerequisites

Before you begin, make sure you have:

  • Git -- any recent version. You will need it to clone the SEJA repository and to manage your project history.
  • Claude Code CLI -- the official Anthropic CLI for Claude, installed and authenticated. SEJA runs as a governance layer on top of Claude Code, so the CLI must be available in your terminal.
  • Python 3.10+ -- SEJA uses Python scripts for state detection, index generation, validation checks, and other harness utilities. Python must be on your PATH.

Tip: You do not need any particular application stack to follow this tutorial. SEJA governs how the AI agent works, not what you build with it. The setup questionnaire will ask about your stack and adapt accordingly.

Clone and Setup

There are two ways to start a SEJA project: clone the public repository and finalise in place, or copy the harness into an existing project directory. We will cover the clone-and-finalise path first, then note the alternative.

Option A: Clone and Finalise In Place

Clone the SEJA repository directly into your project folder, then tell the harness to finalise setup around the files already present: 

# Clone SEJA into a new directory
git clone https://github.com/simonedjb/seja my-project
cd my-project

# Install the pre-commit hook (fast preflight checks on every commit)
bash .githooks/install.sh

Now open Claude Code in the project directory and run the setup skill: 

/seja-setup --here

The --here flag tells the harness that the SEJA files are already in the current directory (from the clone) and it should finalise setup without copying anything. The harness will:

  1. Detect the project state (it sees a fresh SEJA download and routes accordingly).
  2. Pin the version tag to .seja-version for future upgrades.
  3. Create the output directory (_output/) with subdirectories for plans, advisory logs, QA logs, and check logs.
  4. Run the Section 1 scaffolding questionnaire -- a short sequence of questions about your project name, description, backend framework, frontend framework, database, and test tooling. Your answers populate product-design/conventions.md.
  5. Scaffold CLAUDE.md, stack-flavored rule files in .claude/rules/, and smoke-test infrastructure (when a backend is present) -- all derived from your questionnaire answers.
  6. Offer git-history handling (re-initialise fresh, keep and add a project remote, or leave as-is) and cleanup of harness-dev artefacts you do not need.
  7. Create an initial commit.

When setup completes, you will see a summary like: 

Your SEJA setup has been finalised in `/path/to/my-project`.
Stack scaffolded (flask + react).

Next steps:
1. Run /design to define entities, permissions, metacommunication,
   personas, and standards.
2. Once /design completes, you are ready to run /research, /plan,
   /implement, and the other SEJA skills.
3. .seja-version is pinned to 0.9.1 -- /seja-setup --upgrade will
   use this as the baseline next time you want to refresh harness
   files.

Option B: Copy Harness Into an Existing Project

If you already have a project directory with source code and a git history you want to keep, use the install mode instead: 

# From any directory, point SEJA at your existing project
/seja-setup /path/to/my-existing-project

This copies the harness files into the target directory without touching your existing source code. The same scaffolding questionnaire runs, and you end up with the same result: a project directory containing both your code and the SEJA harness, ready for /design.

Tip: If your existing project already has a .claude/ directory (from a prior SEJA install), the setup skill detects this and offers options: overwrite harness only, overwrite everything, create a companion workspace, or abort.

First Lifecycle Cycle

With setup complete, you are ready to run through a minimal lifecycle cycle: design your project, plan a small feature, and implement it. Each step uses a SEJA skill -- a slash command that the harness intercepts and governs.

Step 1: Design

The /design skill defines your project's design intent: domain entities, permissions, metacommunication message, personas, standards, and the project constitution. Since /seja-setup already populated product-design/conventions.md with your stack answers, /design detects the partial-design state and skips the stack questions. It picks up from the metacommunication message and walks you through the remaining design sections. 

/design

You will be asked about:

  • Metacommunication message -- a short statement of your design intent, written in first/second person ("I, the designer, am telling you, the user...").
  • Domain entities -- the core concepts your application manages (e.g., Task, Category, User).
  • Permissions and access control -- who can do what.
  • Design standards -- UX patterns, backend conventions, frontend conventions, and testing standards.
  • Constitution -- immutable project principles (e.g., "accessibility first," "every change must have a test").

When /design finishes, you will have several new files under product-design/: 

# Expected files after /design
product-design/
  conventions.md              # stack and directory layout (from setup)
  product-design-as-intended.md  # domain model, entities, metacomm
  standards.md                # backend, frontend, testing, i18n standards
  design-standards.md         # UX and visual design standards
  ux-research-results.md      # personas, scenarios, discovered journeys
  constitution.md             # immutable project principles

These files are the designer's voice -- the reference material that the harness loads into every subsequent skill invocation via the pre-skill hook. From this point on, the AI agent works accountable to your stated intent.

Step 2: Plan a Small Feature

Now plan something concrete. Give /plan a brief describing a small feature: 

/plan add a health-check endpoint that returns the app version

The /plan skill verifies that product-design/conventions.md exists (its design guard), then:

  1. Reserves a 6-digit plan ID (e.g., 000042).
  2. Investigates the codebase to understand the current state.
  3. Writes a step-by-step plan file at _output/plans/plan-000042-health-check-endpoint.md.
  4. Runs a complexity-gated review (light, standard, or deep) against engineering and design perspectives.

Expected output: 

Plan 000042 saved to _output/plans/plan-000042-health-check-endpoint.md
Review: 3 steps, estimated complexity: low
Ready to implement with: /implement 000042

Step 3: Implement the Plan

Execute the plan by passing its ID to /implement: 

/implement 000042

By default, /implement runs in auto mode: it creates a rollback branch, spawns subagents for each plan step, and tracks progress in _output/plans/plan-000042-progress.md. Each step reads the plan file, executes it, and marks it done. After all steps complete, the skill runs a quality gate (validation checks and code review) unless you pass --skip-checks.

When implementation finishes, you will see a summary of what was created or modified, and the plan file's to-do list will show all steps checked off.

Tip: If you prefer to execute each step yourself rather than delegating to subagents, pass the --manual flag: /implement 000042 --manual.

You now have a working SEJA project with a design foundation, one completed plan, and its implementation. The harness tracked every step: the brief log in _output/briefs.md records each skill invocation, and the plan file documents the full execution history.

What Just Happened

The three commands you just ran -- /seja-setup, /design, and /plan followed by /implement -- traced the opening segment of the SEJA canonical lifecycle path: 

/research > /design > /plan > /implement > /critique > /document > /reflect

Here is how each step maps to the lifecycle:

/seja-setup -- Harness Installation
Not a lifecycle skill per se, but the prerequisite for everything else. It scaffolds the project topology: directory layout, CLAUDE.md, stack-flavored rules, and the output directory. After setup, the harness is operational.
/design -- Design Intent
Defines what the project is and why it exists. Populates the product-design/ directory with the designer's domain model, metacommunication message, standards, and constitution. Every subsequent skill invocation loads these files via the pre-skill hook, ensuring the AI agent stays aligned with your intent.
/plan -- Planning
Defines how to build a feature and why those implementation choices are appropriate. Produces a numbered plan file under _output/plans/ with step-by-step instructions, a review log, and a to-do checklist for execution.
/implement -- Execution
Carries out the plan. In auto mode, subagents handle each step in isolated context windows. A quality gate runs afterward to validate the result against engineering and design perspectives.

The Skills You Did Not Use Yet

The lifecycle continues beyond implementation. The remaining skills complete the feedback loop:

/research (or /explain)
Investigate questions about the codebase, architecture, or design decisions. Typically the starting point from iteration 2 onward, before you decide whether to branch into /design (when intent needs to change) or /plan (when it does not).
/critique
Run validation checks, code review, smoke tests, preflight analysis, or harness health diagnostics. The quality-assurance counterpart to implementation.
/document
Generate or update project documentation -- READMEs, API references, contextual help, changelogs -- based on what changed in the most recent plan.
/communicate
Generate tailored communication material for a specific audience: evaluators, clients, end-users, or academics.
/reflect
On-demand reflection anchored on a specific plan or artifact. Records your observations about either the product (what was built) or your practice (how you worked).
