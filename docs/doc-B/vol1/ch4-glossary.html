Glossary and Shared Definitions

This chapter collects the terms you will encounter throughout the SEJA documentation, organized into three conceptual domains: core harness concepts, semiotic engineering theory, and operational lifecycle vocabulary. Each entry provides a designer-facing definition and a cross-reference to the chapter that covers the concept in depth.

Core Terms

As-Intended / As-Coded
Two complementary views of a project's design state. The as-intended view (recorded in product-design/product-design-as-intended.md) captures what the designer means the product to be: its purpose, entity model, permission rules, UX patterns, and metacommunication vision. The as-coded view (recorded in product-design/product-design-as-coded.md) captures what the codebase actually implements at any given moment. SEJA treats the gap between these two views as the primary signal for design drift -- when they diverge, something was lost in translation. See Design Intent Files (Vol. 2) and Maintenance and Drift (Vol. 4).
Brief
A short, structured summary of a completed skill invocation, logged automatically by the post-skill pipeline into _output/briefs.md. Briefs serve as the project's institutional memory: they let any future skill invocation understand what has already been done, what decisions were made, and what questions remain open -- without requiring the agent to re-read every plan and advisory. See The Lifecycle Pipeline.
Constitution
A set of immutable principles that define a project's non-negotiable boundaries -- values, constraints, and quality commitments that no plan, skill, or agent may override. Stored in product-design/constitution.md, the constitution is loaded into every subagent's context to enforce trust boundaries. It is the designer's way of saying: "These things are true about my project regardless of what you are asked to build." See Constitution Guide (Vol. 2).
Design Intent
The designer's explicit statement of what a product should be and why, captured before any code is written. In SEJA, design intent is recorded in the as-intended file and the metacommunication message, then carried forward through plans and implementation. Every code change is measured against design intent to detect drift. This is the central idea behind SEJA's governance: the designer's vision is not implicit knowledge that fades over time but an explicit artifact that can be compared against reality. See What SEJA Is (and Is Not).
Marker
An inline HTML comment embedded in design-intent files to track the lifecycle state of individual requirements or decisions. Markers follow a state machine (proposed -> implemented -> established -> superseded) and carry a plan ID and date for traceability. They are the mechanism by which SEJA connects "what was designed" to "what was built" at the granularity of individual items, not just whole files. See Plans and Implementation.
Metacommunication Message
The designer-to-user message that a product conveys through its entire interface. Semiotic engineering summarizes it as: "Here is my understanding of who you are, what I have learned you want or need to do, in which preferred ways, and why. This is the system that I have therefore designed for you, and this is the way you can or should use it in order to fulfill a range of purposes that fall within this vision." In SEJA, this message is written in first-person ("I designed...") to preserve the designer's personal voice and recorded in product-design/product-design-as-intended.md. It is the north star that every implementation decision should serve. See Metacommunication (Vol. 2) and Extended Metacommunication (Vol. 5).
Plan
A structured implementation blueprint generated by the /plan skill before any code is written. Each plan receives a unique numeric ID (e.g., plan-000701), contains ordered steps with file targets and trace links to design-intent requirements, and undergoes a multi-perspective review before execution. Plans are the mechanism that prevents the agent from jumping straight to code -- they force a design checkpoint between intent and implementation. See Plans and Implementation.
Roadmap
A higher-level planning artifact that organizes multiple plans into a sequenced development strategy. Generated by /plan --roadmap, a roadmap defines waves (groups of plans that can execute in parallel), dependencies between them, and the overall trajectory from current state to a target state. While a plan answers "how do I build this feature?", a roadmap answers "in what order should I build everything?". See Plans and Implementation.
Skill
A governed capability within the SEJA harness, invoked via a slash command (e.g., /plan, /implement, /critique). Each skill follows a defined protocol: pre-skill hooks load context and check constraints, the skill body executes its task, and post-skill hooks log the result, update briefs, and propose next steps. Skills are not arbitrary chat commands -- they are lifecycle-aware actions that maintain the project's audit trail. See Skills In Depth.
Subagent
A specialized agent delegated to by the main agent via Claude's Agent tool. Subagents run in isolated context windows with focused prompts tailored to a specific role (e.g., code reviewer, plan reviewer, document generator). Isolation is deliberate: it prevents a reviewer from being biased by the same context that produced the code, and it lets SEJA parallelize independent work. Subagent prompt files live in .claude/agents/. See Subagent Delegation.

Semiotic Engineering Terms

SEJA is grounded in semiotic engineering, a theory of human-computer interaction developed by Clarisse Sieckenius de Souza. The terms below are theoretical concepts from that foundation. You do not need to master semiotic engineering to use SEJA effectively, but understanding these terms will help you see why the harness is shaped the way it is.

Abduction
A form of reasoning that generates the best available explanation for an observed phenomenon, even when that explanation is not certain. Unlike deduction (which guarantees truth) or induction (which generalizes from patterns), abduction produces plausible hypotheses. In semiotic engineering, users engage in abduction whenever they interpret an interface: they see a button, a layout, an error message, and form a hypothesis about what the designer intended. SEJA's council-debate agent formalizes this process by having multiple expert perspectives generate competing interpretations of a design decision. See Abduction and Plural Readings (Vol. 5).
Communicability
The quality of a system's ability to convey its designer's intent to users through the interface. A system with high communicability makes it easy for users to understand what it does, why it was designed that way, and how they should interact with it. A system with low communicability leaves users guessing, confused, or forming incorrect mental models. SEJA's review perspectives and spec-drift detection are mechanisms for evaluating and maintaining communicability across the development lifecycle. See Sign Systems (Vol. 5).
Dynamic Sign
An interface element whose meaning emerges through interaction over time -- its significance is revealed by what happens when a user acts on it. Examples include a button that triggers a state change, a drag-and-drop interaction that reorders items, or a progressive-disclosure pattern that reveals content on click. Dynamic signs cannot be fully understood by looking at a static screenshot; they require experiencing the interaction. Together with static signs and metalinguistic signs, they form the three classes of interface signs in semiotic engineering. See Sign Systems (Vol. 5).
Metacommunication
Communication about communication. In semiotic engineering, every software interface is an act of metacommunication: the designer is communicating to the user (through the interface) about how the user should communicate with the system. The designer cannot be present at use-time, so the interface must carry the full message on the designer's behalf. This is the theoretical foundation for SEJA's metacommunication message and the first-person phrasing rule -- they make the implicit designer-to-user conversation explicit and auditable. See Metacommunication (Vol. 2) and Software as Communication (Vol. 5).
Metalinguistic Sign
An interface element that explains other interface elements -- it is a sign about signs. Examples include tooltips, help text, onboarding walkthroughs, error messages, and placeholder text in form fields. Metalinguistic signs are the interface's built-in explanation layer: they tell the user how to interpret the rest of the interface. When metalinguistic signs are unclear or missing, users must rely more heavily on abduction to figure out what the designer intended. See Sign Systems (Vol. 5).
Sign
Anything that stands for something else to someone. In semiotic engineering, every element of a software interface -- a button label, a color, an animation, a menu structure -- is a sign that carries meaning from the designer to the user. The designer chooses signs to express intent; the user interprets those signs to form an understanding. When the user's interpretation matches the designer's intent, communication succeeds. When it does not, there is a communicability breakdown. See Sign Systems (Vol. 5).
Sign System
The organized collection of signs and the rules governing their combination within a software interface. A sign system is not a random assortment of interface elements but a structured language: it has a vocabulary (the individual signs), a grammar (the rules for combining them), and conventions (the patterns users learn to expect). In SEJA, the project's conventions file (product-design/conventions.md) and design standards collectively define the sign system that the product's interface should express. See Sign Systems (Vol. 5).
Static Sign
An interface element whose meaning can be understood from its appearance alone, without any interaction. Examples include labels, icons, colors, layout structure, and typography choices. A user can look at a static sign in a screenshot and derive its intended meaning. Static signs form the "first impression" layer of an interface's communicability. See Sign Systems (Vol. 5).

Lifecycle Terms

These terms describe the operational mechanisms that SEJA uses to govern the agent's behavior across skill invocations and project evolution.

Checkpoint
A quality gate within the lifecycle that requires explicit verification before proceeding. Checkpoints appear at plan review (where a multi-perspective review must pass before implementation begins), at implementation completion (where a quality gate validates the changes), and at promotion time (where a human confirms that an implemented item matches its design intent). Checkpoints are the points where SEJA slows the agent down deliberately, preventing it from racing ahead without verification. See Quality and Critique.
Council Debate
A structured deliberation process in which multiple expert perspectives evaluate a high-stakes design decision. Five fixed archetypes (plus up to two brief-specific experts) stake out positions, cross-examine each other, and surface trade-offs that a single viewpoint would miss. The council-debate agent formalizes the abductive reasoning that semiotic engineering describes: rather than accepting one interpretation, it generates competing hypotheses and lets the designer choose. See Subagent Delegation (Vol. 3) and Abduction and Plural Readings (Vol. 5).
Drift
The divergence between design intent (as-intended) and actual implementation (as-coded). Drift is natural and inevitable -- implementation always reveals things the design did not anticipate. What matters is detecting drift and deciding whether to update the intent, fix the code, or accept the deviation. SEJA's /explain drift command compares the as-intended and as-coded files to surface these gaps systematically. Undetected drift is how projects lose coherence over time. See Maintenance and Drift (Vol. 4).
Human (markers) Classification
A file-maintainer classification indicating that a file is human-authored prose where the agent may only write fixed-format structured markers (STATUS flags, INCORPORATED stamps, CHANGELOG lines) -- never modify prose or free-text content. This classification protects the designer's voice: the agent can record that a section has been implemented, but it cannot rewrite what the designer said. Write access is enforced through apply_marker.py and validated by check_human_markers_only.py. See Marker System (Vol. 2) and Enforcement Architecture (Vol. 4).
Pending Action
An outstanding item that requires human attention, tracked in the pending-actions ledger (_output/pending.jsonl). Pending actions are filed automatically by the lifecycle (e.g., when a plan completes, an implement action is filed; when a plan changes at least five files, a verify-as-coded action is filed) and addressed through the /pending skill. They are SEJA's mechanism for ensuring that nothing falls through the cracks between skill invocations. See The Lifecycle Pipeline.
Post-Skill
The lifecycle hook that executes after every skill invocation. It logs a brief summarizing what was done, updates the briefs index, proposes marker flips for implemented items, runs periodic housekeeping checks, and suggests the next logical step in the lifecycle. Post-skill is how SEJA maintains institutional memory -- without it, each skill invocation would be an isolated event with no connection to what came before. See The Lifecycle Pipeline.
Pre-Skill
The lifecycle hook that executes before every skill invocation. It runs as a pipeline of composable stages: loading the project constitution, evaluating context budget, checking for pending actions, loading relevant references, and logging the brief. Pre-skill ensures that every skill starts with the right context loaded and the right constraints enforced, regardless of what the agent's context window currently contains. See The Lifecycle Pipeline.
Reflection Register
A structured record of a designer's reflections on completed work, captured by the /reflect skill. Reflections can focus on the product (what was built and whether it matches intent) or on practice (how the work process went and what could improve). The register preserves the designer's own words verbatim, anchored to specific plans or artifacts, creating a qualitative history that complements the quantitative audit trail of briefs and markers. See Reflective Practice (Vol. 5).
