What SEJA Is (and Is Not)

Before diving into quickstart steps or skill references, it helps to understand what SEJA actually is -- and, just as importantly, what it is not. This chapter positions SEJA as an agent harness, distinguishes "the agent" from "the harnessed agent," and previews the two properties that make the harness distinctive.

What SEJA Is

SEJA (Software Engineering with AI) is a governance layer for Claude Code, grounded in semiotic engineering theory. It structures the entire lifecycle of AI-assisted software development -- from research and design through planning, implementation, critique, documentation, communication, and reflection -- so that the AI stays aligned with the designer's intent at every step.

An Agent Harness, Not a Framework

SEJA is not a library you import, a framework that scaffolds your application code, or a platform that hosts your services. It is a harness: a set of skills, rules, reference files, and lifecycle hooks that sit between you (the human designer) and the AI agent (Claude). The harness does not replace the agent or constrain what it can do at the language level. Instead, it governs how the agent works -- what it reads before acting, what steps it follows, what checks it performs afterward, and what artifacts it produces along the way.

The Agent vs. the Harnessed Agent

This distinction matters throughout the documentation:

The agent (Claude, the raw LLM)
A general-purpose language model that can generate code, answer questions, and follow instructions. Without governance, it works from whatever context is in its prompt window. It has no persistent design memory, no lifecycle discipline, and no mechanism to surface what it does not know.
The harnessed agent (Claude running under SEJA)
The same model, but operating within a structured governance layer. Before every skill invocation, the harness loads the project constitution, the designer's conventions, and any relevant reference files (via the pre-skill hook). After every skill invocation, the harness marks the work as done, commits artifacts, and flushes decision records (via the post-skill hook). The agent's output is now accountable to the designer's stated intent -- not to the model's own heuristics.

What the Harness Provides

Three capabilities distinguish a SEJA-governed project from an ungoverned Claude Code session:

Lifecycle discipline
Every user-facing skill follows a mandatory pipeline: pre-skill (brief log, budget evaluation, pending check, reference load, constitution load) followed by the skill's own work, followed by post-skill (DONE marking, git commit, decision flush). Skills may opt out of non-critical stages, but no skill may skip pre-skill entirely. This pipeline is defined in .claude/skills/scripts/ and enforced by the harness's hook system.
Design-intent alignment
The designer's metacommunication message -- a first-person statement of who the user is, what the designer has learned they need, and how the system is designed to serve them -- is the highest-authority artifact in a SEJA project. It lives in product-design/product-design-as-intended.md, and the harness loads it (along with the project constitution in product-design/constitution.md) into every agent context. Plans must serve design intent. Implementations must serve plans. Critiques evaluate against design intent, not against the AI's own judgment.
Epistemic scaffolding
SEJA is designed to surface what is not yet known, not only what has been decided. Gap detection in product topology flags objectives without supporting tasks. Research logs label heuristic inferences with explicit confidence indicators. Pending actions surface unincorporated research and unverified implementations. The designer's epistemic posture -- knowing what you don't know -- is mirrored in the harness's tooling.

Tip: If you have used Claude Code without SEJA, the difference is not what the AI can do -- it is what the AI must do. The harness adds structure and accountability around the same underlying model.

What SEJA Is Not

Positioning SEJA clearly requires ruling out common misconceptions. Each of the following describes something SEJA is frequently confused with but is not.

Not a CI/CD Pipeline

SEJA includes validation scripts and a pre-commit hook, but it is not a continuous integration system. It does not build your application, run your test suite, or deploy your code. The harness operates at the designer-to-agent layer -- it governs how the AI plans and implements, not how the resulting code reaches production. Your existing CI/CD pipeline remains separate and unchanged.

Not a Testing Framework

The /critique skill validates implementation against design intent, and the harness runs preflight checks before commits. But these are governance checks, not unit tests, integration tests, or end-to-end tests. SEJA does not replace pytest, vitest, or any other testing tool. It operates at a different level of concern: whether the work aligns with what the designer intended, not whether individual functions return correct values.

Not a Prompt Library

SEJA's skills are structured instructions for the AI agent, and the harness does load reference files into the agent's context. But SEJA is not a collection of reusable prompts that you copy into your own workflows. The skills are bound to a lifecycle -- each one has a pre-skill phase, a post-skill phase, and dependencies on the artifacts produced by earlier skills. Extracting a single skill's prompt text and using it outside the harness would lose the governance structure that gives it meaning.

Not a Code Generator

Claude generates code; SEJA does not. The harness governs the process by which code is planned, implemented, and reviewed -- but the code itself comes from the underlying language model. SEJA adds no code-generation capabilities beyond what Claude already provides. What it adds is the discipline around when and how that generation happens: after a plan has been approved, under the constraints of the constitution, with a critique step to follow.

Not a Replacement for the Designer

SEJA enforces that the designer's intent is authoritative. The metacommunication message, the constitution, and the design-intent files are all human-authored -- classified as Human (markers), meaning the agent may write only lifecycle markers into them, never prose. The harness cannot author design intent on the designer's behalf. It can surface gaps, flag drift, and structure the development process, but the design decisions remain the human designer's responsibility.

The Dual Thesis Preview

SEJA rests on two complementary properties. Neither is sufficient alone; together they define what makes the harness distinctive. This section previews both theses without developing them fully -- for the complete argument, see The Dual Thesis in Vol. 5.

Governable

The designer controls the agent's behavior through explicit, inspectable mechanisms. The project constitution in product-design/constitution.md defines immutable principles that no plan or implementation step may contradict without a recorded decision. Lifecycle hooks enforce that every skill invocation follows the pre-skill/post-skill pipeline. Permissions are declared in .claude/settings.json and .claude/references/general/permissions.md, not inferred by the model. The Human (markers) file classification prevents the agent from overwriting human-authored design prose. At every point, the designer can inspect what the agent was given, what it did, and why -- because the harness makes the governance structure visible, not hidden inside opaque prompts.

Epistemic

The harness does not merely execute instructions -- it surfaces what is not yet known and makes uncertainty visible. Gap detection flags design objectives that lack supporting implementation tasks. Research logs label claims with confidence indicators rather than presenting all inferences as equally certain. The pending ledger tracks unincorporated research findings and unverified implementations, ensuring that open questions do not silently disappear. The designer's epistemic posture -- "I am aware of what I have learned about my users and equally aware of what I have not yet learned" -- is not just a philosophical stance; it is encoded in the harness's tooling and surfaced in its outputs.

Why Both Are Required

Governance without epistemic support produces brittleness: the agent follows rules precisely but cannot flag that the rules themselves may be based on incomplete understanding. Epistemic support without governance produces drift: the agent surfaces uncertainties but has no mechanism to ensure they are addressed before implementation proceeds. SEJA requires both axes. The governance layer ensures that decisions are traceable and accountable; the epistemic layer ensures that the basis for those decisions is honest about its own limitations.
