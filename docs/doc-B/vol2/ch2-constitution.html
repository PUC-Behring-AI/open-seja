The Constitution

If the metacommunication message is the apex of the design layer, the constitution is its bedrock. It is the one file whose contents the agent is never permitted to override, work around, or quietly reinterpret. Where design-intent files evolve as understanding deepens, the constitution holds a small set of principles fixed: the non-negotiable commitments on architecture, quality, security, and compliance that every skill and every subagent must observe. This chapter documents what a constitution contains, how you write and maintain one over the life of a project, and why immutability -- anchored by the constitution's place in the pre-skill load order -- is the property that makes it worth having at all.

The live file lives at product-design/constitution.md. New projects start from the template at .claude/references/template/constitution.md, which /seja-setup copies into place and /design instantiates with project-specific principles.

What a Constitution Contains

A SEJA constitution is a short Markdown file with a fixed section structure. The template defines the sections; a project fills them in. The document is deliberately small -- it should change rarely, and every row in it is a hard rule rather than an aspiration.

Section Structure

The template and the live SEJA constitution share the same skeleton. From top to bottom:

Section Column headings What it records
Project Identity (prose) A one-sentence mission statement and, optionally, the primary users or audience. No table -- just the project's name and reason to exist.
Technical Principles #, Principle, Rationale Non-negotiable architectural decisions, numbered T1, T2, ... Hard rules, not preferences.
Quality Principles #, Principle, Rationale Quality gates that cannot be bypassed, numbered Q1, Q2, ...
Security Invariants #, Invariant, Rationale Security rules that must never be relaxed without explicit sign-off, numbered S1, S2, ...
Compliance Requirements #, Requirement, Regulation/Contract Regulatory, contractual, or policy obligations, numbered C1, C2, ... Left empty if none apply.
Enforcement (prose) How the principles are loaded and checked, and the rule for amending the document.
Changelog (prose) Versioned amendment history. Because the constitution changes rarely, this section stays short.

Each principle carries its own ID prefix -- T for technical, Q for quality, S for security, C for compliance -- so that a plan, a critique finding, or a decision record can cite the exact principle it engages (for example, "blocked by S1"). Every row except the compliance table pairs the rule with a Rationale: the reason the line exists. The compliance table records the governing Regulation or Contract in place of a free-form rationale.

The designer_description Header

The file opens with a YAML front-matter block containing a single designer_description field written in the designer's first-person voice. It is a human-facing narrative -- the file introducing itself -- not a machine field, and it is preserved verbatim (never compressed) through any maintenance pass.

A Worked Example

SEJA's own constitution is private to seja-priv and instantiates this structure with eleven principles. A few representative rows show the shape:

ID Section Principle (abbreviated) Rationale (abbreviated) Cites
T1 Technical Every user-facing skill starts with pre-skill and ends with post-skill; skills may opt out of non-critical stages but never skip pre-skill entirely. Lifecycle discipline is the core value SEJA provides; bypassing it defeats the governance model. Lifecycle
Q1 Quality Design intent is authoritative; no plan or implementation step may contradict the metacommunication message or constitution without an explicit D-NNN decision record. A plan that silently overrides design intent is a governance failure. Design authority
S1 Security Private seja-priv content must never reach seja-public without explicit opt-in; the pre-commit hook runs check_no_private_leaks.py --staged on every commit. Accidental exposure is irreversible once cached by search engines or CI logs. Privacy
C1 Compliance GitHub repositories created via SEJA tooling must always use --private. Regulation/Contract: the "Private repositories only" global rule. Policy

Notice what these rows have in common: each is testable, each is a line that a proposal could cross, and each carries the reason it exists. That is the bar for constitution content. A rule you cannot picture a plan violating does not belong here -- it belongs in conventions or design intent, where the agent has room to decide.

Writing and Maintaining One

You do not author a constitution from a blank page. You start from the template, fill in only the principles that are genuinely immutable for your project, and then let the document accrete slowly -- one amendment at a time, each justified by a decision record.

Starting from the Template

  1. Confirm the template has been copied to product-design/constitution.md. /seja-setup does this for new projects; if the file is missing, copy .claude/references/template/constitution.md into place yourself.
  2. Replace the identity placeholder. Fill {{PROJECT_NAME}} and the one-sentence mission, and add a sentence about primary users if it clarifies scope.
  3. Fill each principle table. The template ships example rows as HTML comments (<!-- Example: ... -->) and placeholder rows marked with {{...}}. Replace the placeholders with your real rules, delete unused rows, and delete the example comments once you have written your own.
  4. Leave sections empty where they do not apply. A project with no regulatory obligations leaves the Compliance Requirements table empty rather than inventing rows to fill it.
  5. Write the first changelog entry. The template's ### v1 -- {{YYYY-MM-DD HH:MM UTC}} stub records that the constitution was created; replace the timestamp with a real one and note how the principles were derived.

In practice /design drives this interactively. SEJA's own constitution, for instance, was created via /design in interview-driven mode, with its principles derived from a confirmed interview exchange and mapped onto the template's Technical / Quality / Security / Compliance sections -- exactly the workflow above, run as a conversation rather than by hand.

Iterating Through Decision Records

Once written, the constitution should change rarely -- but "rarely" is not "never." When a genuine need arises to add, remove, or reword a principle, the change does not happen inline and unannounced. It goes through the amendment discipline the Enforcement section itself declares:

  1. Record the decision. Capture the reasoning as a D-NNN decision record in product-design/product-design-as-intended.md, written via apply_marker.py with a DECISION_APPEND marker. The decision explains why the immutable line is moving.
  2. Get explicit approval. The Enforcement section requires that any amendment be explicitly approved by the project lead -- the constitution is not something the agent may revise on its own initiative.
  3. Amend the file and the changelog. Make the edit, then add a new versioned entry to the Changelog section recording what changed and when.

The same D-NNN mechanism has a second role: it is the only sanctioned way to proceed when a plan or implementation would otherwise contradict a principle. Rather than silently overriding Q1 or bypassing a security invariant, the designer records an approved decision that authorizes the specific exception. Without that record, the contradiction is a blocking violation.

Tip: Keep the constitution shorter than you think it needs to be. Every principle you add is a line the agent must check against on every relevant proposal. A tight constitution of a handful of load-bearing rules is easier to honour -- and easier to trust -- than a sprawling one where the genuinely immutable commitments are lost among conveniences.

Common mistakes. Two failure modes recur when authoring a constitution:

  • Putting mutable conventions in the constitution. Naming schemes, formatting choices, directory layouts, and tooling preferences change as a project matures. If you freeze them here, every routine adjustment becomes a constitutional amendment. Mutable conventions belong in product-design/conventions.md; evolving intent belongs in the design-intent files (see Ch. 3: Design Intent Files). The constitution holds only what must not change.
  • Writing principles without rationale. A rule with no stated reason cannot be reasoned about. When a future proposal presses against it, no one can tell whether the rule still serves its purpose or has outlived it -- so it either gets cargo-culted forever or discarded on a whim. Every principle row pairs the rule with the reason it exists; treat the Rationale column as mandatory, not decorative.

Why Immutability Matters

An immutable file is only as strong as the guarantee that it is actually consulted -- and consulted first, before the agent has formed any competing intention. The constitution earns its authority from where it sits in the lifecycle, not merely from a sentence claiming it is authoritative.

Loaded into Every Context, Ahead of Everything Else

The constitution's own opening line states the arrangement plainly: "The constitution is loaded first by pre-skill, before conventions or any other reference file. Rules here take precedence over everything else." In the pre-skill pipeline the constitution is loaded as a dedicated stage and injected into the agent's context for every skill invocation running at the standard or heavy budget tier. Its principles are therefore present before the skill does any of its own reasoning -- the immutable ground is in place first, and everything the skill subsequently proposes is measured against it. For the full pre-skill ordering and how the constitution stage fits among the six stages, see Vol. 3, Ch. 1: The Lifecycle Pipeline.

Precedence is the second half of the guarantee. Being loaded is not enough; the constitution must win when it conflicts with anything else in context. The Enforcement section makes this concrete: no plan or implementation step may contradict the constitution without a recorded decision, and /critique validate checks conformance against the agent-facing constraints derived from the document. Violations surfaced during /critique review or /critique preflight are classified as blocking -- they must be resolved before commit, not deferred.

Extending the Boundary to Delegated Work

The trust boundary does not stop at the main agent. When a skill delegates to a generator subagent, that subagent receives the project constitution as part of its prompt, so a delegated task cannot escape a principle simply by running in an isolated context window. The immutable ground travels with the work.

Why "Immutable" Is a Feature, Not a Limitation

It is tempting to read immutability as rigidity -- a constraint that gets in the way. The opposite is true. The value of a constitution is precisely that the agent cannot talk itself out of it mid-task. A conventions file can be revised in passing when a proposal finds it inconvenient; a principle in the constitution cannot. That asymmetry is deliberate. It concentrates the project's genuinely non-negotiable commitments in one small, highly visible file and puts a deliberate, human-approved amendment process between those commitments and any change to them.

This is why the boundary between the constitution and the rest of the design layer matters so much. Everything that should evolve -- intent, conventions, research findings -- lives elsewhere, free to change as understanding deepens. Everything that must not evolve without ceremony lives here, protected by load order, precedence, and the amendment discipline. Get that division right and the constitution becomes the stable point the whole design layer can pivot around.
