Design Intent Files

Below the metacommunication message and the constitution sits the pair of files that carry the working detail of a SEJA project's design layer: product-design/product-design-as-intended.md (the target state -- what you intend the system to be) and product-design/product-design-as-coded.md (the current state -- what the system actually is). The first is authored by you, the designer; the second is maintained by the harnessed agent as code ships. The gap between them is where design intent lives or dies -- and this chapter documents both files, the workflow that keeps them honest, and the markers that track the lifecycle of every item they contain.

This chapter mixes three registers. The reference sections walk the real section layout of each file so you can navigate them without guessing. The explanation section makes the case for maintaining two files instead of one. The how-to section is the maintenance workflow you follow as the project evolves.

Inside product-design-as-intended.md

product-design/product-design-as-intended.md is the unified working-intent artifact. It is classified Human (markers): the prose is authored by you and you alone, while the harnessed agent may write only fixed-format lifecycle markers (STATUS flags, DECISION_APPEND, CHANGELOG_APPEND) through apply_marker.py after an explicit AskUserQuestion confirmation. A direct agent prose write is rejected by check_human_markers_only.py during post-skill. The mechanics of that classification -- and the markers that make it work -- are the subject of The Marker System.

The numbered sections (§0--§17)

The file opens with a header block that records its classification and the stable-ID conventions it uses, then proceeds through eighteen numbered sections grouped into three parts.

§0. Planned Changes is a forward-looking table of changes targeted at future versions, each with a change summary and a motivation column. It sits before the numbered domain sections because it describes where the design intent is heading, not where it is.

Part I -- Conceptual Design (§1--§10) carries the domain model:

Section Heading What it captures
§1Platform PurposeWhat the platform is for, plus a Design Philosophy subsection
§2Entity HierarchyThe artifacts the harness produces and manages, as an ASCII tree with per-entity prose
§3Domain-Specific ConceptsMetacommunication, lifecycle governance, Human (markers) classification, epistemic posture, and the SPO
§4Permission ModelSystem-level roles and resource-level access tables
§5Content Authoring and AttributionThe Human/Agent authoring boundary and marker attribution
§6Content Import and ExportMarked "Not applicable" for the harness
§7User Community and LocalizationTarget community and localization design
§8User Experience Patterns (Domain-Driven)Skill dispatch, AskUserQuestion at decision points, transparency of reasoning
§9Administrative DomainActivity logging, backup and restore, design governance
§10Validation Constants (Domain)Marked "Not applicable" for the harness

Part II -- Metacommunication (§11--§15) holds the metacommunication artifacts proper:

Section Heading What it captures
§11Global Metacommunication VisionThe canonical first-person message: who you understand your user to be, what you have learned they need, and how you designed the system to serve them
§12Extended Metacommunication Template Guiding QuestionsThe EMT: structured "what I know / what I don't yet know" answers across Analysis, Design, Prototyping, and post-deployment stages
§13Solution RepresentationsSolution scenarios (SS-NNN) tying personas, goals, and problem scenarios to designed flows
§14Per-Feature Metacommunication IntentionsA table of per-feature designer intent, implementation status, source, and last-updated date
§15Designed User JourneysThe designed journey maps (JM-TB-NNN), each with steps, touchpoints, pain points, and outcomes

Part III -- Delta from As-Coded (§16--§17) records how the intent has moved since the last as-coded update: §16 (Conceptual Design Delta) and §17 (Delta Rationale). Both are placeholder sections until the first /implement run populates them via post-skill and /explain drift.

Note: §11 is the metacommunication message itself -- the highest-authority artifact in the whole design layer, written in first-person "I" (the designer) addressing second-person "you" (the user). It is documented in full in The Metacommunication Message. Everything else in the file is accountable to it.

The Decisions section (D-NNN)

After the numbered sections comes ## Decisions -- a run of DDR-shaped decision records under ### D-NNN: Title headings. Each record has four fields: Context, Decision, Consequences, and Rejected Alternatives, usually closed with a source line (Source: from research-000586, for example). IDs are auto-assigned in sequence (D-001, D-002, ...), and the D-NNN namespace is orthogonal to the REQ-TYPE-NNN requirement namespace -- the two are never intermixed.

A decision record moves through a lifecycle of proposed → implemented → established → superseded, tracked by the STATUS marker that sits immediately above its heading. Entries are appended only through apply_marker.py --marker DECISION_APPEND after AskUserQuestion confirmation -- never hand-inserted by the agent. This is where the rationale behind consequential architectural choices lives, so that a future designer can understand not just what was decided but what was rejected and why.

The CHANGELOG section

The file closes with ## CHANGELOG: an append-only table of Date / Action / Source rows recording each marker flip and each significant change to the file. The agent writes to it only through apply_marker.py --marker CHANGELOG_APPEND. Because it is append-only, the CHANGELOG is a chronological audit trail: nothing is ever rewritten or removed.

Inside product-design-as-coded.md

product-design/product-design-as-coded.md is the unified implementation-state artifact. Its classification is Agent: it is written by post-skill after each plan execution and is never hand-edited. You read it to understand what the codebase currently implements; post-skill mirrors the target structure of the as-intended file into it as code ships. Where the as-intended file has eighteen numbered sections, the as-coded file collapses them into three H2 domain sections, each holding the numbered material as H3-and-deeper subsections.

H2 section Mirrors Contents
## Conceptual Design As-intended §1--§10 The domain model as built -- platform purpose, entity hierarchy, domain concepts, permission model, authoring, and validation, each as an H3 subsection numbered to match its as-intended counterpart
## Metacommunication As-intended §11--§14 The as-coded metacommunication chains: the global summary, the EMT answers, the implemented solution representations (with an Implementation Status of Implemented / Partial per scenario), the per-feature metacommunication log, and a per-section changelog
## Journey Maps As-intended §15 The implemented journey maps (JM-TB-NNN) with per-step "Implemented" flags, a Delta from As-Intended block listing not-yet-implemented steps, and a changelog

Two disciplines are worth calling out. First, post-skill writes target exactly one H2 domain section at a time; the check_section_boundary_writes.py validator (preflight step 6c) rejects any contiguous write region that spans two or more H2 sections, so a conceptual-design edit can never accidentally reach into the metacommunication section. Second, the file carries a designer_description in its YAML frontmatter and a classification header identifying itself as the as-coded mirror -- both orient a reader who lands in the file without context.

The as-coded file is where implementation reality is recorded plainly. Its solution-representation entries, for instance, may carry a status of Partial where the as-intended file describes a fully designed flow -- an honest admission that part of the designed journey (a planned feature, say) has not yet shipped. That honesty is the entire point of maintaining the file separately, which the next section explains.

Why the As-Intended / As-Coded Split Exists

It would be simpler to keep one file. SEJA keeps two, deliberately, because the target state and the current state answer different questions and are owned by different authors.

Two questions, two authors

The as-intended file answers what should the system be? It is yours -- Human (markers)-classified, authored in your voice, the place where design intent is declared. The as-coded file answers what is the system, right now? It is the agent's -- written by post-skill, derived mechanically from what plans actually implemented. Collapsing the two would force one author to overwrite the other: either the agent would have to edit your design intent to keep it "current" (which the Human (markers) classification forbids for exactly this reason), or you would have to hand-maintain an implementation record that the harness can generate for you.

The gap is the signal

Keeping the two files apart makes the gap between them a first-class, inspectable object. That gap is the subject of /explain drift: the skill compares product-design-as-intended.md against product-design-as-coded.md and surfaces every place where the implementation has diverged from the intent. Some divergences are sanctioned -- captured by a D-NNN decision record that deliberately changed the approach. Others are unintended drift, the kind that is invisible until it becomes expensive to fix. A single merged file would erase the very distance that lets drift be measured.

The pattern is not unique to this file pair. SEJA maintains an as-intended / as-coded pair for each registered design domain, and the As-Intended / As-Coded Registry in product-design/conventions.md is the single source of truth for which pairs exist. It is what /design, /explain drift, and post-skill's DONE-marker proposals all consult to know which files pair with which.

How as-coded stays in step with the codebase

The as-coded file does not drift into staleness because it is not hand-maintained -- it is regenerated by the lifecycle pipeline. When /implement executes a plan, post-skill's as-coded alignment step updates product-design-as-coded.md to reflect what was actually built: it edits the ## Conceptual Design section for new or changed entities, updates the ## Metacommunication section when the plan carried metacommunication framing, and cross-references implemented features against the journey maps. Each write stays within a single H2 boundary, and the section-boundary validator enforces that at preflight. The full post-skill mechanics -- which steps run, in what order, and under what conditions -- are documented in The Lifecycle Pipeline.

Tip: Because post-skill only runs as-coded alignment when the parent skill is /implement, the as-coded file reflects shipped work, not planned work. A plan that has been written but not yet implemented does not move the as-coded file at all. That is by design: the as-coded file tracks the codebase, not the backlog.

REQ Markers and the STATUS Lifecycle

Two marker families give the design-intent files their machine-readable spine: REQ markers that identify individual requirements, and STATUS markers that track each item's lifecycle. Both are defined canonically in .claude/references/general/shared-definitions.md; the mechanics of how they are written and read are covered in The Marker System. This section documents what they mean.

REQ markers

A REQ marker is a stable, machine-parseable identifier for a design-intent requirement, written as an HTML comment placed immediately before the heading, table row, or bullet it applies to. Its format is <!-- REQ-TYPE-NNN -->, where NNN is a zero-padded three-digit counter per type, starting at 001. The type prefix ties the requirement to the as-intended section it lives in:

Type prefix Design-intent section Classification Enforcement
ENT§2. Entity Hierarchytechnicaladvisory
PERM§4. Permission Modelsecurityblocking at preflight
VAL§10. Validation Constantssecurityblocking at preflight
UX§8. UX Patternsuxadvisory
MC§14. Per-Feature Metacommuxadvisory
JM§15. Designed User Journeysuxadvisory
I18N§7. Localizationcross-cuttingadvisory
DELTA§16--17. Deltastechnicaladvisory

Security-classified requirements (PERM, VAL) must be traced by a plan step in the same wave as their parent entity; advisory-classified requirements produce warnings but do not block. Plan steps declare the requirements they satisfy through a Traces metadata field (for example, Traces: REQ-ENT-001, REQ-PERM-003), and coverage is verified by check_plan_coverage.py. The /design skill auto-assigns REQ IDs during verification. As noted above, the D-NNN decision namespace is orthogonal to REQ-TYPE-NNN: never interpolate a D-NNN into the REQ taxonomy, and never write a REQ-D-NNN collision.

The STATUS lifecycle

A STATUS marker is an inline HTML comment placed immediately before a prose section heading (or above a D-NNN heading). Two schemes coexist on disk. The current scheme (SEJA 2.8.0 and later, used by apply_marker.py) is a lowercase multi-value marker driven by a state machine: 

<!-- STATUS: proposed | plan-NNNNNN | YYYY-MM-DD -->
### Section Title

The state machine has five legal transitions, validated against the human-markers registry:

  • proposed → implemented
  • proposed → superseded
  • implemented → established
  • implemented → superseded
  • established → superseded

Regression (for example established → implemented) is rejected. The plan ID and date are optional for the initial proposed state and required after it. The legacy scheme (pre-2.8.0, still supported) uses a single uppercase STATUS: IMPLEMENTED marker, typically paired with a later ESTABLISHED stamp on promotion; a legacy marker without a plan ID is valid for items implemented outside the plan workflow (source manual). New and consolidated files use the lowercase scheme, and product-design/product-design-as-intended.md is the canonical lowercase-primary Human (markers) file.

Tip: STATUS markers are audit records. The agent may read them and propose new ones, but must never remove or alter an existing implemented or established marker. When a promotion flips a marker, the tooling replaces the existing marker rather than stacking a second one on top of it.

Maintaining the Design Intent Files

The two files are maintained on different cadences by different actors. This section is the practical workflow for keeping them healthy as the project evolves.

Updating an as-intended section

When your understanding of the design changes -- a revised domain model, a new UX pattern, an updated metacommunication intention -- edit the prose of product-design-as-intended.md directly. This is your file to author. Prefer running /design, which knows the section structure, auto-assigns REQ IDs during verification, and keeps the numbering consistent, rather than hand-editing in a way that the tooling later has to reconcile. Do not ask the agent to write prose into the file on your behalf: check_human_markers_only.py will flag the mutation at post-skill step 6c and recommend aborting the commit.

Recording a decision

When a design decision worth preserving is reached -- most often during /research, whose step 9b detects decisions in the Q&A and offers to capture them -- record it as a D-NNN entry rather than burying it in prose. The entry is appended via apply_marker.py --marker DECISION_APPEND after an AskUserQuestion confirmation, with an auto-assigned ID and the DDR shape (Context, Decision, Consequences, Rejected Alternatives). You can create the entry now, defer it to the pending ledger, or skip it. The same apply_marker.py path handles CHANGELOG appends, so the audit trail stays intact.

Letting as-coded catch up

You do not maintain product-design-as-coded.md by hand -- post-skill does it for you when /implement runs. After an implementation, post-skill updates the as-coded section that changed and proposes any DONE markers on the as-intended items the plan satisfied. Accept or defer those proposals through the AskUserQuestion gate; the flip from proposed/implemented is written by apply_marker.py, never by direct edit.

Promoting implemented intent to established

Once an intent item has shipped and settled, promote it from implemented to established with the promote workflow, which runs in two phases:

  1. Phase 3a -- draft decision entries. /explain drift --promote reads plan metadata and drafts DDR-shaped entries for items marked STATUS: implemented, writing them to _output/promote-proposals/promote-proposal-plan-<id>.md. You review each draft, edit it into your own voice, and copy the entries into the ## Decisions section of the as-intended file. The agent never writes the decision prose for you.
  2. Phase 3b -- flip the markers. /explain drift --promote --apply-markers plan-<id> then flips the STATUS markers from implemented to established via apply_marker.py, using a heading-only match to verify each entry's presence without touching the surrounding designer-authored prose.

Checking for drift periodically

On a regular cadence -- and whenever a spec-drift-check pending action comes due -- run /explain drift to compare the two files. Triage each surfaced divergence: if it reflects a deliberate change, capture it as a D-NNN entry (or confirm it is already covered by one); if it is unintended drift, either fix the implementation to match the intent or update the intent to match reality, and record a pending action for the work if it cannot be done on the spot.

Tip: The golden rule for both files: your prose is yours to write, and the agent's markers are the agent's to write -- but only through apply_marker.py, only after AskUserQuestion. If you ever find yourself about to hand-edit the as-coded file, or about to let the agent draft as-intended prose, stop -- you are working against the classification, and the post-skill verifier will catch it.
