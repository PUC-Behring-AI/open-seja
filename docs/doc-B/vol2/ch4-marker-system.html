The Marker System

A design-intent file is a shared document. The designer writes prose into it; the agent needs to record, later, that a given item was built, promoted, or superseded. Those two hands must never collide. The marker system is how SEJA keeps them separate: a small vocabulary of fixed-format HTML comments that the agent may write into otherwise human-owned files, applied through a single controlled tool (apply_marker.py) and verified by a companion checker. This chapter documents the marker types, the tool that applies them, the classification scheme that decides who may touch which file, and the deeper reason the whole arrangement is a designed signification system rather than an ad-hoc convention.

Marker Types

SEJA defines six marker kinds. Three are lifecycle stamps that live immediately above a heading or entry (STATUS, ESTABLISHED, INCORPORATED); two are append operations that add a new line or entry to a dedicated section (CHANGELOG_APPEND, DECISION_APPEND); and one annotates an existing requirement marker in place with the plan that traced it (REQ_TRACED_BY). Every one of them is a machine-parseable HTML comment or structured line -- invisible in rendered Markdown, but readable by the harness tooling. The canonical definitions live in .claude/references/general/shared-definitions.md; the allowed values and regexes are enforced by human_markers_registry.ALLOWED_MARKERS.

STATUS

The STATUS marker tracks where an as-intended item sits in its lifecycle. It is an HTML comment placed on the line immediately before the section heading (or decision entry) it governs. The current scheme (SEJA 2.8.0+) uses lowercase values driven by a state machine: 

<!-- STATUS: proposed | plan-NNNNNN | YYYY-MM-DD -->
### Section Title

The allowed values are proposed, implemented, established, and superseded. Transitions are validated -- the five legal transitions are proposed → implemented, proposed → superseded, implemented → established, implemented → superseded, and established → superseded (the two → superseded shortcuts cover early abandonment). Regression (for example established → implemented) is rejected. The plan ID and date are optional for the initial proposed state and required thereafter. A legacy uppercase STATUS: IMPLEMENTED marker (pre-2.8.0) remains valid; the tool normalizes it to implemented so that a promotion replaces the legacy line rather than stacking a new marker above it.

ESTABLISHED

The ESTABLISHED stamp records that a human has confirmed the promotion of an implemented item -- an audit record that the designer, not the agent, owns the decision to establish. It carries a required plan ID and a date, with an optional semantic version: 

<!-- ESTABLISHED: plan-NNNNNN | YYYY-MM-DD | vX.Y.Z -->

Projects without semver use the date-only form (<!-- ESTABLISHED: plan-000178 | 2026-04-02 -->). An ESTABLISHED stamp, once written, must never be removed or altered by an agent -- it is a permanent audit trace.

INCORPORATED

The INCORPORATED stamp records that an item's content has been absorbed into a downstream artifact by a specific plan. Like ESTABLISHED, it is a stamp kind: it requires a plan ID, accepts an optional --date argument (the emitted marker always carries a date), and is inserted above the target heading rather than replacing an existing marker. 

<!-- INCORPORATED: plan-NNNNNN | YYYY-MM-DD -->

CHANGELOG_APPEND

CHANGELOG_APPEND adds a single audit line to the file's ## CHANGELOG section. The action value must be one of added, revised, revoked, or superseded, and a note is required. The appended line has the shape: 

YYYY-MM-DD | <entry-id> | <action> | <plan-id or -> | <note>

If no plan ID is supplied, the plan token defaults to -. The line is appended after the last non-empty line of the ## CHANGELOG section, leaving all surrounding prose untouched.

DECISION_APPEND

DECISION_APPEND adds a new DDR-shaped decision entry to the ## Decisions section of the design-intent file. The --id argument is ignored for this marker: the next D-NNN identifier is auto-assigned by scanning existing ### D-NNN: headings within the ## Decisions section. The --value carries the full entry text -- its first line becomes the decision title and the remainder becomes the body (Context, Decision, Consequences). An optional --note appends a source attribution line. The D-NNN namespace is orthogonal to the REQ-TYPE-NNN taxonomy; the two are never intermixed.

Marker Kind Requires plan Requires value Effect
STATUS Stamp (replaces) Optional (required after proposed) Yes Sets lifecycle state above a heading; validated transitions
ESTABLISHED Stamp (inserts) Yes No Audit record of human-confirmed promotion
INCORPORATED Stamp (inserts) Yes No Records absorption of an item by a plan
CHANGELOG_APPEND Append line Optional Yes (action) Adds an audit line to ## CHANGELOG
DECISION_APPEND Append entry Optional Yes (entry text) Adds a ### D-NNN: entry to ## Decisions

Tip: Agents may read markers and propose new implemented STATUS markers (via AskUserQuestion during post-skill). Agents must never remove or alter an existing ESTABLISHED stamp or an established/implemented marker on their own -- these are audit records, and the designer owns the promotion decision.

Applying Markers with apply_marker.py

apply_marker.py is the sole write path for Human (markers) files. When the agent needs to update a lifecycle marker, it must go through this script rather than using Edit or Write on the file directly. The script rewrites the exact marker line and leaves every other word untouched; the companion verifier check_human_markers_only.py rejects any prose mutation that slips past it.

General invocation

The script lives at .claude/skills/scripts/apply_marker.py. Its general form is: 

python .claude/skills/scripts/apply_marker.py \
    --file <path> --id <entry-id> --marker <kind> --value <value> \
    [--plan <plan-id>] [--date YYYY-MM-DD] [--note <text>] [--dry-run]

The arguments are:

--file (required)
The target file, repo-relative. It must resolve to a file that is classified as Human (markers); the script refuses to write otherwise.
--id (required)
The entry ID whose heading the marker attaches to (for example a requirement ID or a D-NNN decision ID). Ignored for DECISION_APPEND, which auto-assigns the next ID.
--marker (required)
The marker kind. One of STATUS, ESTABLISHED, INCORPORATED, CHANGELOG_APPEND, DECISION_APPEND, or REQ_TRACED_BY (the choices are drawn from the registry of allowed markers).
--value
The marker value. Required for STATUS, CHANGELOG_APPEND, and DECISION_APPEND; ignored by the stamp kinds ESTABLISHED and INCORPORATED.
--plan
The plan ID. Accepts the fully-qualified form plan-NNNNNN, a bare 6-digit ID (auto-prefixed with plan-), or the literal manual for human-initiated changes outside the plan workflow.
--date
Overrides the date (YYYY-MM-DD). Defaults to today's UTC date.
--note
The changelog note text. Required for CHANGELOG_APPEND; optional source attribution for DECISION_APPEND.
--dry-run
Prints a unified diff of the intended change without writing the file. Always the safe first step.

Example: flip a STATUS marker to implemented

Preview the change first, then apply it: 

python .claude/skills/scripts/apply_marker.py \
    --file product-design/product-design-as-intended.md \
    --id D-001 --marker STATUS --value implemented \
    --plan plan-000178 --dry-run

On success (exit code 0) the script prints, for example, applied STATUS=implemented to product-design/product-design-as-intended.md:42. Drop --dry-run to write the change.

Example: stamp ESTABLISHED on promotion

python .claude/skills/scripts/apply_marker.py \
    --file product-design/product-design-as-intended.md \
    --id D-001 --marker ESTABLISHED --plan plan-000178

The stamp kinds take no --value but require --plan; omitting the plan fails with a validation error.

Example: append a CHANGELOG line

python .claude/skills/scripts/apply_marker.py \
    --file product-design/product-design-as-intended.md \
    --id D-001 --marker CHANGELOG_APPEND --value revised \
    --plan plan-000178 --note "Reworded consequences after review"

Exit codes

The script returns 0 on success, 1 on validation failure (unknown marker, disallowed transition, unregistered file, missing required argument), and 2 on a runtime error (for example an unreadable or unwritable file). A disallowed STATUS transition, a missing ## Decisions or ## CHANGELOG section, or an ambiguous entry ID all surface as validation failures with a clear message.

Markers as a Designed Signification System

It is tempting to read the marker system as mere bookkeeping -- a set of HTML comments that some scripts happen to parse. But look at what it actually is: a small, closed vocabulary of expressions (STATUS, ESTABLISHED, INCORPORATED, and the two append operations), each paired with a precise content (a lifecycle state, an audit fact, a decision), and each governed by rules about who may produce it and how it may change. That is the definition of a signification system: a conventionalized set of expression-content pairs. The marker vocabulary is a designed code, and every marker written into a file is a sign.

The design choices are not incidental. The lowercase state machine (proposed → implemented → established → superseded) encodes a grammar for the code: not every expression may follow every other. The refusal to let an agent regress or overwrite an ESTABLISHED stamp is a rule about who holds authorship of which signs -- the designer signs off on establishment; the agent may only propose. And the fact that markers are HTML comments, invisible in the rendered document, means the same file carries two layers of communication at once: the prose the designer writes for a human reader, and the marker layer the agent reads and writes for the tooling. The file is a single surface with two audiences.

This is why the marker system belongs in the design layer and not merely in the toolchain. It is the mechanism by which design intent stays legible over time: a reader (human or agent) can look at any entry and read, from its marker, exactly how far it has travelled from proposal to established fact, and which plan carried it there. The markers make the lifecycle of intent communicable -- readable as a message, not reconstructed by guesswork.

Tip: For the full semiotic-engineering account of why a conventionalized expression-content code is a sign system -- and how communicability lets a reader recover intent from such signs -- see Vol. 5, Ch. 2: Sign Systems and Communicability.

File Maintainer Classification

The marker system exists because some files are owned by humans but must still carry agent-written state. The File Maintainer Classification is the four-value scheme that decides, per file, who may write what. It is applied to reference files in product-design/ and surfaced as the "Maintained by" column of the Key Files table in product-design/conventions.md. The pivotal value for this chapter is Human (markers): human-authored prose that the agent may annotate only through the fixed-format markers described above, and only via apply_marker.py.

Value Meaning Agent rule Enforcement Example file
Human Authored and updated exclusively by humans. Agents must not write. May read and propose changes via AskUserQuestion. Convention; agent self-restraint. constitution.md
Human (markers) Human-authored prose; agent may write fixed-format structured markers only (STATUS flags, ESTABLISHED / INCORPORATED stamps, CHANGELOG / DECISION appends). Agents write only via apply_marker.py after explicit AskUserQuestion confirmation in the same turn. Never prose, never text outside the allowed marker patterns. check_human_markers_only.py during post-skill step 6c. product-design-as-intended.md, ux-research-results.md
Agent Auto-maintained by agents and skills (e.g., via post-skill). Agents read and write freely. Humans typically do not edit directly. Section-boundary checks where applicable. product-design-as-coded.md
Human / Agent Seeded by an agent (e.g., /design), then human-owned; both may update. Also applies to harness source files. Agents may write per the file's own rules; humans are primary curators after seeding. Per-file rules. conventions.md

The classification is what makes the marker system enforceable rather than merely advisory. apply_marker.py checks the target file against the Human (markers) allowlist before it does anything else -- a write to any file not on that list is refused outright. This closes the loop: only registered files accept markers, and those files accept only markers.

Common Mistakes

Warning: hand-editing Human (markers) files. The most common mistake is having the agent open a Human (markers) file -- such as product-design/product-design-as-intended.md or product-design/ux-research-results.md -- and write or flip a marker with Edit or Write directly, instead of going through apply_marker.py.

Consequence: a direct edit bypasses the state-machine validation (it can stack a duplicate marker, write a disallowed transition, or silently corrupt the prose around the heading). Post-skill step 6c runs check_human_markers_only.py on the staged changes and catches the prose mutation, recommending that the commit be aborted; if the commit proceeds anyway, the pre-commit hook may also flag it.

Avoidance: always route marker writes through apply_marker.py, and preview with --dry-run first. The script is the only hand allowed to touch these files: it rewrites the exact marker line, validates the transition, and leaves every other word untouched.

Two related pitfalls: forgetting that ESTABLISHED and INCORPORATED are stamp kinds that require --plan but ignore --value; and forgetting that CHANGELOG_APPEND requires --note. Both surface as clean validation failures (exit code 1) rather than silent corruption -- another reason to prefer the tool over a hand edit.
