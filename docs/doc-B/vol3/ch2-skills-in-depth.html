Skills In Depth

This chapter provides a per-skill reference for all 15 user-facing skills and the 2 internal lifecycle hooks. Each skill section follows a consistent template: purpose, parameters, prerequisites, workflow summary, subagent delegations, reference file loads, expected outputs, and common mistakes. For the lifecycle pipeline that wraps every skill invocation, see The Lifecycle Pipeline. For subagent details, see Subagent Delegation.

Skill System Overview

SEJA organizes all agent behavior into skills -- self-contained instruction sets that the agent executes when invoked by a slash command. The harness ships 17 skills: 15 user-facing skills and 2 internal lifecycle hooks (/pre-skill and /post-skill) that bracket every invocation.

The Canonical Lifecycle Path

Skills are designed to be invoked in a particular order. The canonical lifecycle path is: 

/research (or /explain)
  > /design | /plan
  > /implement
  > /critique
  > /document | /communicate
  > /reflect

On the first iteration of a new project, /seja-setup hands off to /design to configure the project. From iteration 2 onward, the entry point is typically /research (or /explain) to investigate what you are about to change. From there, branch into /design when design intent needs to change, or /plan when intent is set and you need a build plan. The key rule: validate before you communicate -- /critique always runs before /document or /communicate.

Skill Dispatch

Each skill is defined by a SKILL.md file in .claude/skills/<name>/. The file's YAML frontmatter declares the skill's metadata: name, description, argument-hint (the parameters it accepts), category, context budget, and the reference files it may load. A companion SKILL-quickguide.md provides a designer-friendly summary with examples and usage scenarios. When a user types a slash command, the harness loads the corresponding SKILL.md and follows its instructions.

Context Budget Tiers

Every skill declares a context_budget in its frontmatter, which governs how many reference files the pre-skill hook loads into the agent's context window. Three tiers exist:

Tier Reference Load Typical Skills
Light Minimal references; quick operations with low context cost /pending, /help, /qa-log
Standard Typical reference set; most analysis and explanation work /research, /explain, /design, /reflect
Heavy Full reference loads; planning, implementation, and quality checks /plan, /implement, /critique

The budget tier determines which pre-skill stages run and how aggressively references are loaded. Heavy-budget skills eagerly load design-intent files, coding standards, and review perspectives to ensure the agent has full project context before acting. For details on the pre-skill stages and post-skill steps, see The Lifecycle Pipeline.

/research

Answers questions about the codebase, architecture, or design decisions, logging Q&A pairs in a structured report. Two modes: research (default, question-driven investigation with perspective analysis) and inventory (--inventory, catalogs codebase elements matching a pattern). An optional --deep flag activates a structured expert council debate for high-stakes decisions.

Parameters

Argument Required Description
<question or topic> Yes The question or topic to investigate
--inventory <pattern> No Switch to inventory mode: catalog codebase elements matching the pattern
--deep No Activate structured expert council debate for high-stakes decisions

Prerequisites

The project should exist (a product-design/conventions.md file is expected for reference loading). For --deep mode, the question should involve a genuinely high-stakes design decision -- the council debate engages 5-7 named expert archetypes and consumes significant context budget.

Workflow Summary

  1. Run pre-skill, reserve a global ID, and load references on demand (design specs when comparing current vs. target, shared definitions when terminology is ambiguous).
  2. Research the question thoroughly -- read the codebase, search the web, interview the user about goals and constraints.
  3. Run expert analysis: in standard mode, launch the research-reviewer agent for multi-perspective evaluation; in --deep mode, launch the council-debate agent for a 2-round structured debate.
  4. Synthesize perspectives, save a report with Q&A log and recommendations summary, and run post-skill.
  5. If design decisions were detected, offer a decision-extract proposal flow (create a D-NNN entry now, defer, or skip). Present next-step options: execute now, plan only, refine, or save.

Subagent Delegations

  • research-reviewer -- standard mode perspective evaluation (see Subagent Delegation)
  • council-debate -- --deep mode structured expert debate

Reference Files Loaded

  • product-design/product-design-as-coded.md (eager)
  • product-design/product-design-as-intended.md (on demand)
  • .claude/references/general/shared-definitions.md
  • .claude/references/general/report-conventions.md
  • .claude/references/general/review-perspectives.md
  • .claude/references/template/docs/ddr.md

Expected Outputs

A research report at _output/research-logs/research-<id>-<slug>.md containing the Q&A log (verbatim), perspective analysis, and a recommendations summary with HIGH/MEDIUM/LOW priority levels. Inventory mode produces _output/inventories/inventory-<id>-<slug>.md.

Common Mistakes

Using --deep for routine questions
The council debate engages 5-7 expert archetypes in a 2-round structured debate. Reserve it for genuinely high-stakes decisions (architecture changes, technology migrations, governance shifts). Standard mode with its research-reviewer agent is sufficient for most questions.
Forgetting to follow up on HIGH-priority recommendations
Research produces recommendations but does not act on them. Use /plan to turn HIGH-priority recommendations into actionable plans, passing the research ID so the plan records its provenance.
Skipping the decision-extract proposal for design decisions
When research resolves a design question, the decision-extract flow (step 9b) offers to create a structured D-NNN entry. Skipping this means the decision is buried in a research report rather than tracked in the design-intent file where /explain drift can find it.

/explain

Produces clear explanations of how things work -- a feature's behavior, the data model, the overall architecture, how behavior evolved over time, how code works for developers being onboarded, or the drift between design specs. Six mutually exclusive modes, each delegated to a specialized subagent (except drift, which runs inline). Includes diagrams and analogies.

Parameters

Argument Required Description
architecture [brief] One type required (mutually exclusive) System architecture, component relationships, design choices
behavior [brief] Emergent behavior from a user's perspective
behavior-evolution [brief] Current behavior and how it evolved over time
code [brief] How code works, aimed at junior developers
data-model [brief] Data model, pitfalls, refactoring opportunities
drift [scope] Compare as-coded and as-intended specs; optional sync. Scopes: all, conceptual-design, metacomm, --promote, --scope since-plan plan-NNNNNN

Prerequisites

Project source files for the scope being explained. For drift mode, both product-design/product-design-as-intended.md and product-design/product-design-as-coded.md should exist (drift analysis compares them section by section).

Workflow Summary

  1. Run pre-skill, reserve a global ID, and determine the explanation mode from the first argument.
  2. For general modes (behavior, code, data-model, architecture, behavior-evolution): delegate to the appropriate subagent, which reads the codebase, produces diagrams and analogies, and writes the report.
  3. For drift: compare as-coded vs. as-intended sections (entities, permissions, UX patterns, metacommunication), compile a drift summary table, and present sync options (align in either direction, bidirectional, promote implemented items, or skip).
  4. Save the report and run post-skill.

Subagent Delegations

  • explanation-generator -- behavior, code, data-model modes
  • evolution-explainer -- behavior-evolution mode
  • architecture-explainer -- architecture mode
  • Drift runs inline (no subagent)

Reference Files Loaded

  • .claude/references/general/shared-definitions.md (eager)
  • .claude/references/general/report-conventions.md (eager)
  • product-design/product-design-as-coded.md (on demand)
  • product-design/product-design-as-intended.md (on demand)

Expected Outputs

Mode-specific reports in dedicated output directories: _output/explained-behaviors/, _output/explained-code/, _output/explained-data-model/, _output/explained-architecture/, _output/behavior-evolution/. Drift mode produces a research report at _output/research-logs/research-<id>-<slug>.md with a drift summary table. The promote workflow (Phase 3a) writes decision proposals to _output/promote-proposals/.

Common Mistakes

Using /explain for prescriptive recommendations
/explain answers "how does this work?" -- it describes, it does not prescribe. For recommendations and trade-off analysis, use /research instead.
Running drift without a design-intent file
Drift analysis requires both product-design/product-design-as-intended.md and product-design/product-design-as-coded.md. If design has not been configured yet, run /design first.
Confusing /explain with /document
/explain generates explanations for your own understanding. /document generates artifacts for others to read (READMEs, changelogs, API references). See the audience routing in Vol. 4: Governance.

/design

Defines or updates the project's design foundations -- stack choices, conventions, domain model (entity hierarchy, permissions), metacommunication message, standards (backend, frontend, testing, UX, security, i18n), and constitution. Serves both the initial post-setup configuration and ongoing design evolution. Six modes cover every design lifecycle stage.

Parameters

Argument Required Description
[spec-file-path] No Path to a pre-filled spec file for automated configuration (Mode 2)
--mode interview No Conversational intake instead of fixed questionnaire (Mode 5)
--generate-spec No Generate a blank spec skeleton to fill out offline (Mode 4)
--add-docs No Add documentation templates to a configured project (Mode 3)
update <section-slug> No Jump directly to a specific section update. Slugs: stack, conceptual, metacomm, backend-standards, frontend-standards, ux-standards, ui-standards, i18n, security, testing, constitution, full

Prerequisites

For initial design: /seja-setup must have run first so that product-design/conventions.md exists with stack definitions. For design updates: product-design/product-design-as-intended.md must exist.

Workflow Summary

  1. Detection: examine arguments and project state to determine the active mode -- interactive questionnaire (Mode 1), spec file (Mode 2), add-docs (Mode 3), generate-spec (Mode 4), interview (Mode 5), or design update.
  2. Gather input: walk the user through the questionnaire (Sections 0-5+: metacommunication, conceptual design, UX/visual design, standards, docs) or conduct an open-ended interview (Mode 5). For brownfield projects, auto-detect entities, permissions, and validation from existing code.
  3. Instantiate templates: copy .claude/references/template/* into product-design/, substituting questionnaire answers. Amend CLAUDE.md with design-intent references.
  4. Verify and finalize: run a verification pass checking semantic fidelity between spec input and generated files, assign requirement IDs (REQ markers), run secrets check, and present a summary with next-step options.

Subagent Delegations

None -- /design runs entirely inline.

Reference Files Loaded

  • .claude/references/general/report-conventions.md
  • .claude/references/general/review-perspectives.md
  • .claude/references/general/shared-definitions.md

Expected Outputs

  • product-design/product-design-as-intended.md -- unified working intent with Decisions section and CHANGELOG
  • product-design/constitution.md -- immutable project principles
  • product-design/standards.md -- backend, frontend, testing, i18n standards
  • product-design/design-standards.md -- UX patterns and graphic/visual design
  • product-design/security-checklists.md -- security checklists and validation constants
  • product-design/ux-research-results.md -- personas, problem scenarios, journey maps

Common Mistakes

Running /design before /seja-setup
On a new project, /seja-setup must run first to scaffold the harness and populate conventions.md with stack definitions. /design builds on that foundation. Without it, /design enters a legacy fallback path.
Skipping the metacommunication message
Section 0 of the questionnaire asks for the designer's metacommunication message -- the first-person statement of who the user is and what the system is designed to do for them. This message anchors all downstream design intent. Skipping it leaves the harness without its highest-authority alignment artifact.
Confusing /design with /plan
/design defines what and why (entities, permissions, metacommunication, standards). /plan defines how to build it. /seja-setup scaffolds the project topology. These three skills serve distinct concerns. See Plans and Implementation for the planning workflow.

/plan

Creates a structured, step-by-step plan for a feature, bug fix, or refactor. Each plan step carries metadata (files, verification criteria, test specifications, dependencies) that /implement uses to execute reliably. Three modes: standard (default single plan), lightweight (--light, quick proposal), and roadmap (--roadmap, full product roadmap with dependency-aware execution waves). See Plans and Implementation for the full plan lifecycle.

Parameters

Argument Required Description
<brief> Yes Description of the task to plan
--light No Generate a lightweight proposal instead of a full plan
--roadmap No Generate a full product roadmap with dependency-aware waves
--framing metacomm No Frame the brief as a designer's metacommunication message (I/you phrasing)
--review <light|standard|deep> No Override complexity-gated review depth
--auto No Auto-generate roadmap from project references (use with --roadmap)
--only-unimplemented No Scope roadmap to REQ items lacking a STATUS marker (use with --roadmap --auto)

Prerequisites

Design guard: product-design/conventions.md must exist. If missing, the skill stops and directs the user to run /design first.

Workflow Summary

  1. Mode detection: explicit flags (--light, --roadmap, --plan) override auto-detection. Without flags, the brief is scored against signals (entity count, architectural layers, scope) to choose between roadmap and single plan.
  2. Generate the plan: create a structured artifact with user brief, agent interpretation, best practices, design decisions, and a step list. Each step follows the format defined in .claude/references/template/plan-step.md with Files, Verify, Tests, Interface, and other metadata fields.
  3. Complexity-gated review: Phase 1 triages 3-6 relevant perspectives from the 16 available and scans for issues. Phase 2 (Standard/Deep only) runs targeted deep-dives via the plan-reviewer agent, iterating up to 3 times until convergence.
  4. Finalize: save the plan, run post-skill to commit, and ask whether to implement now or defer.

Subagent Delegations

  • plan-reviewer -- Standard and Deep review (Phase 2 deep-dives, conflict checks, iterations)

Reference Files Loaded

  • product-design/product-design-as-coded.md (eager)
  • product-design/product-design-as-intended.md (eager)
  • .claude/references/general/report-conventions.md (eager)
  • .claude/references/general/coding-standards.md (eager)
  • .claude/references/general/review-perspectives-index.md (eager)
  • product-design/conventions.md, product-design/standards.md, product-design/security-checklists.md, product-design/design-standards.md (on demand)

Expected Outputs

  • Standard: _output/plans/plan-<id>-<slug>.md with structured steps, review log, and outcomes
  • Lightweight: _output/proposals/proposal-<id>-<slug>.md
  • Roadmap: _output/roadmaps/roadmap-<id>-<slug>.md with wave summary table plus generated plans per work item

Common Mistakes

Writing vague step descriptions
Each plan step must be self-contained -- a subagent executing it should understand what to do without reading other steps. Include specific file paths, the exact changes needed, and clear verification criteria.
Skipping the Verify field
/implement uses the Verify field to confirm each step succeeded. Without it, the executor has no way to distinguish success from failure. Every step needs an observable verification criterion.
Forcing --roadmap for single-feature work
Auto-detection handles mode selection well. If your brief describes a single bug or touches fewer than 5 files, a standard single plan is appropriate. Roadmap mode's wave decomposition adds overhead that small tasks do not need.

/implement

Executes a previously approved plan step by step. The default auto mode dispatches each step to a fresh subagent with isolated context, preventing context degradation across many steps. Manual mode (--manual) runs sequentially in the current context with per-step confirmation. Roadmap mode (--roadmap) executes all plans in a roadmap wave by wave. A pending mode (--pending) clears all pending implement entries at once. See Plans and Implementation for the full execution lifecycle.

Parameters

Argument Required Description
<planned-item-id> Yes The 6-digit ID of the plan to execute
--manual No Execute sequentially in current context (default: auto mode with subagents)
--roadmap <roadmap-id> No Execute all plans in a roadmap, wave by wave
--pending No Execute all pending plans via auto-generated roadmap
--max-iterations N No Cap auto-mode iterations (default: 20)
--skip-checks No Skip the final Quality Gate
--skip-docs No Skip automatic documentation generation at post-skill

Prerequisites

A plan file must exist for the given ID, and its plan_format_version must be 1. Plans without version metadata trigger a fallback to manual mode.

Workflow Summary

  1. Setup: run pre-skill, read the plan, create a rollback branch (pre-plan-<id>), and build the execution queue from incomplete steps in dependency order. Create the progress file for cross-iteration learnings.
  2. Execute steps: for each step, spawn a fresh general-purpose subagent with the step's full description, Files, Verify, Tests, and progress-file content. Auto mode follows TDD red-green: write a failing test first (when Tests is non-N/A), then implement until the test passes.
  3. Process results: SUCCESS marks the step done; PARTIAL indicates a blocker (logged in the progress file); FAILED pauses for user guidance. After 2 consecutive PARTIAL/FAILED results, the executor pauses automatically.
  4. Quality Gate: run validation, code review, tests, and smoke tests (if configured). A generator-critic loop retries critical findings up to 2 times.
  5. Finalize: mark the plan DONE, update any associated roadmap, append a summary, and run post-skill.

Subagent Delegations

  • general-purpose -- one per step in auto mode (executor subagents)
  • test-runner -- Quality Gate test execution
  • code-reviewer -- Quality Gate code review
  • standards-checker -- Quality Gate validation

Reference Files Loaded

  • product-design/product-design-as-coded.md (eager)
  • product-design/product-design-as-intended.md (eager)
  • .claude/references/general/report-conventions.md (eager)
  • .claude/references/general/coding-standards.md (eager)
  • product-design/standards.md, product-design/security-checklists.md (on demand per step)

Expected Outputs

  • Modified source files per the plan's step specifications
  • _output/plans/plan-<id>-progress.md -- append-only progress file with cross-iteration learnings and codebase patterns
  • Updated plan file with DONE marker, step checkboxes, and aggregated summary

Common Mistakes

Running /implement without reviewing the plan
Always read the plan before executing it. Auto mode will faithfully execute every step -- including ones that are wrong. The plan is your checkpoint; review it before committing to execution.
Using --manual for large plans
Plans with more than 6 steps benefit from auto mode, where each step runs in a fresh subagent with isolated context. Manual mode accumulates context across all steps, risking degradation and confusion in later steps.
Ignoring PARTIAL results
A PARTIAL result means the step hit a blocker. The blocker is documented in the progress file. Ignoring it may cause downstream steps to fail or produce incorrect results. Review the progress file and address blockers before continuing.

/critique

Unified quality gate for all "is it OK?" questions. Ten mutually exclusive modes cover validation scripts, code review, smoke tests, preflight checks, harness health diagnostics, test-plan generation, documentation consistency, git freshness, telemetry analysis, and semiotic inspection. See Quality and Critique for the full quality system.

Parameters

Mode Description
validate [scope] Run project validation scripts. Scopes: all, i18n, auth, migrations, constants, po, coverage, tests, spec
review [scope] Structured code review against quality perspectives. Scopes: staged, file path, directory path
smoke [scope] Runtime smoke tests. Scopes: all, api, ui
preflight [scope] Combined validate + review in one pass (pre-merge checkpoint)
health Harness self-diagnosis with 9 built-in checks
test-plan [brief] Generate a structured manual test plan
docs Documentation consistency check via plugin scanners
freshness Git branch freshness check (advisory; never pulls)
telemetry Usage analytics from telemetry.jsonl (read-only)
semiotic-inspection [scope] SIM-based communicability evaluation

Global flag: --depth <light|standard|deep> overrides review depth for review and preflight modes.

Prerequisites

The project must exist. Smoke tests require smoke_test_registry.json and a running backend. Semiotic inspection requires product-design/ files with metacommunication content. Stack filtering for validate and preflight reads BACKEND_FRAMEWORK and FRONTEND_FRAMEWORK from product-design/conventions.md.

Workflow Summary

  1. Dispatch: run pre-skill, parse the mode from the first argument, and determine scope.
  2. Execute: each mode delegates to the appropriate agent or script -- standards-checker for validate, code-reviewer for review, harness-health-evaluator for health, etc. Preflight runs validate + review + smoke in parallel.
  3. Report: save a critique report at _output/critique-logs/critique-<id>-<slug>.md with mode-specific content (exception: telemetry is read-only and does not produce a report file).
  4. Present and close: show the summary with severity-highlighted findings and run post-skill.

Subagent Delegations

  • standards-checker -- validate mode
  • code-reviewer -- review mode
  • migration-validator -- validate migrations scope
  • test-runner -- validate tests scope
  • harness-health-evaluator -- health mode (9 built-in checks)
  • test-plan-generator -- test-plan mode
  • semiotic-inspector -- semiotic-inspection mode

Reference Files Loaded

  • .claude/references/general/report-conventions.md
  • product-design/standards.md
  • product-design/design-standards.md
  • product-design/security-checklists.md
  • .claude/references/general/review-perspectives.md
  • .claude/references/general/review-perspectives-index.md
  • .claude/references/general/review-log-template.md

Expected Outputs

A critique report at _output/critique-logs/critique-<id>-<slug>.md with mode-specific content: validation pass/fail table (validate), perspective evaluation table with prioritized issues (review), API/UI test results (smoke), go/no-go verdict (preflight), 9-check diagnostic report (health), manual test scenarios (test-plan), documentation scan results (docs), ahead/behind counts (freshness), or SIM communicability report (semiotic-inspection). Exception: telemetry mode displays output directly without saving a report file.

Common Mistakes

Reviewing the entire codebase instead of scoping
/critique review defaults to staged changes. Reviewing an entire directory or the whole codebase without scoping consumes heavy budget. Scope to the files you changed: /critique review staged or /critique review src/auth/.
Treating advisory findings as blocking
Only critical findings (security vulnerabilities, correctness bugs, failing tests) require immediate attention. Advisory findings are informational -- defer them to a future plan unless they affect the current change.
Skipping preflight before merge
Preflight combines validation and review in a single pass and produces a clear go/no-go verdict. Running validate and review separately may miss the integration check. Use /critique preflight as the pre-merge checkpoint.

/reflect

Supports on-demand reflection anchored on specific artifacts. The designer picks what to reflect on, chooses a lens (product or practice), and writes their reflection in their own words. /reflect is strictly non-prescriptive -- it writes observations and the user's own words, never recommendations. Three modes: conversational (default), deep (--deep, visualization-backed practice evolution), and telemetry (--telemetry, statistical pattern mining).

Parameters

Argument Required Description
--deep No Deep reflection mode with event matrix, transition graph, and practice narrative
--telemetry No Statistical telemetry mining mode (5 analysis primitives)
--scope <keyword> No Free-text scope filter for --deep mode
--since <duration> No Time window (ISO datetime or Nd suffix). Default: 30d
--skill <name> No Filter telemetry to a single skill
--dry-run No Print report to stdout without writing to disk (telemetry mode)

Prerequisites

For conversational mode: artifacts to reflect on (plans, research reports, etc.) should exist. For --telemetry and --deep modes: _output/telemetry.jsonl must contain data within the time window.

Workflow Summary

  1. Scope selection (conversational): ask the user what to reflect on -- recent plans, recent research, a specific artifact by ID, a time window, or free-form. Resolve the selection to artifact IDs.
  2. Summarize and present: run summarize_artifacts.py to produce narrative summaries of the chosen artifacts, so the designer can see what they are reflecting on.
  3. Lens and reflection: ask which lens the designer is reflecting through -- product (what was built), practice (how they worked), or both. Ask the corresponding open-ended question and capture the response verbatim.
  4. Write and close: save the reflection report with the designer's words recorded verbatim, and run post-skill.

Deep mode reads telemetry and briefs within a time window, produces an event matrix visualization (Vega-Lite), a transition graph (Graphviz DOT), and a past-tense practice evolution narrative. Telemetry mode runs 5 analysis primitives: sequence mining, duration anomalies, revision rate, stuck loops, and decision reversals.

Subagent Delegations

None -- /reflect runs entirely inline.

Reference Files Loaded

  • product-design/conventions.md (eager)
  • .claude/references/general/constraints.md (eager)
  • .claude/references/general/shared-definitions.md
  • .claude/references/general/skill-graph.md
  • .claude/references/general/coding-standards.md

Expected Outputs

  • _output/reflections/reflection-<id>-<slug>.md -- reflection report with lens, artifact summaries, and the designer's words verbatim
  • Deep mode adds companion visualization files: event matrix (.vl.json, .svg, .html) and transition graph (.dot, .svg, .html)

Common Mistakes

Expecting /reflect to give recommendations
/reflect is strictly non-prescriptive -- it writes observations and the designer's own words, never "you should" or "consider changing." For prescriptive follow-up on patterns surfaced during reflection, use /research.
Reflecting before implementing
Reflection is most valuable when there is something concrete to examine. Reflecting on a plan before it has been implemented is a planning activity, not reflection. Wait until after /implement and /critique to reflect on outcomes.
Using --telemetry with very short time windows
The 5 analysis primitives (sequence mining, duration anomalies, stuck loops, etc.) need volume to detect meaningful patterns. Windows shorter than 7 days rarely contain enough data points for useful analysis. The default 30-day window is a good starting point.

/document

Generates or updates project documentation based on plan Docs: fields, auto-detection of recent changes, or explicit type selection. Supports six documentation types (readme, contextual-help, api-reference, ddr, help-center, changelog) and can produce multiple types in parallel when driven by a plan or auto-detection. Sits at the output end of the canonical lifecycle -- run it after /critique confirms the implementation is sound. For the full lifecycle context, see The Lifecycle Pipeline.

Parameters

Argument Required Description
<scope> Yes (unless --plan or --auto-detect) What to document: a file path, module, feature name, or general topic
--plan <id> No Read Docs: fields from a plan file and generate documentation for each identified need
--auto-detect No Detect documentation needs from recent git changes using heuristics
--type <type> No Force a specific documentation type: readme, contextual-help, api-reference, ddr, help-center, or changelog
--since <ref> No Override auto-detect bounding window. Accepts a date, git SHA, or last (since last /document run)
--full-history No Ignore per-doc-type bounding windows and scan the full recent git history

Prerequisites

The project must have been through at least one implementation cycle so there is code to document. For --plan mode, the referenced plan must exist and contain non-N/A Docs: fields in its steps. For --auto-detect, recent git history must contain changes that match one of the detection heuristics.

Workflow Summary

  1. Run /pre-skill and determine the mode from arguments: --plan, --auto-detect, --type, or bare scope (inferred type).
  2. For --auto-detect: compute per-doc-type bounding windows from the briefs index (each doc type tracks when it was last generated, so only new changes are evaluated).
  3. Resolve the template path for each documentation type: check product-design/docs/<type>.md first, then fall back to .claude/references/template/docs/<type>.md.
  4. Launch one document-generator agent per doc type (parallel when multiple types are needed). Each agent receives the doc type, scope, template path, quality guide, project context, and output path.
  5. Record document run metadata (HEAD SHA, generated types) in the briefs file, then run /post-skill.

Subagent Delegations

  • document-generator -- produces the documentation artifact for a single doc type. Multiple agents run in parallel when --plan or --auto-detect identifies several needs. See Subagent Delegation.

Reference Files Loaded

  • .claude/references/general/documentation-quality.md
  • .claude/references/general/report-conventions.md
  • product-design/conventions.md
  • product-design/product-design-as-coded.md

Expected Outputs

One or more documentation files in project-appropriate locations, determined by the doc type: READMEs at project root, API references alongside route files, DDRs in _output/, changelogs at project root, and help-center articles in the configured documentation directory. The briefs index records the HEAD SHA and generated types for future bounding-window calculations.

Common Mistakes

Running /document before /critique
Documentation should describe validated behavior. Documenting an implementation that has not passed /critique risks capturing bugs or incomplete features as intended behavior. The canonical path places /critique before /document for this reason.
Ignoring auto-detect bounding windows
By default, --auto-detect only evaluates changes since the last /document run of each type. Using --full-history bypasses these windows and scans all recent history, which can regenerate documentation that is already up to date. Use --full-history only when you want a clean-slate rescan.
Using bare scope when --plan is available
When a plan exists with Docs: fields, use --plan <id> instead of manually specifying scope and type. The plan mode extracts documentation needs that were identified during planning, ensuring nothing is missed.

Communicating before validating

Using the wrong audience tag

Not using --source when reformatting existing content

Parameters

Argument Required Description
<role-family> Yes (unless batch mode) Role family: builder / shaper / guardian (or tags BLD / SHP / GRD). Combinations allowed (e.g., builder+guardian)

The project must have completed initial setup and design so that product-design/conventions.md and product-design/product-design-as-coded.md exist. The onboarding plan is tailored to the project's actual stack, conventions, and domain -- without these files, the plan would be generic and unhelpful.

  1. Run /pre-skill, parse arguments, and resolve role tags and expertise level. Map aliases to canonical tags (e.g., senior maps to L2). If arguments are missing, present an interactive menu.

  • .claude/references/general/onboarding/<level>.md
  • product-design/product-design-as-coded.md

Common Mistakes

Generating onboarding plans before /design completes
Onboarding plans are tailored to the project's domain model, stack, and conventions. Running /onboard before /design produces generic plans that do not reflect the project's actual architecture or design decisions.
Using --all when only one combination is needed
--all generates 9 plans (3 roles x 3 levels), which is useful for comprehensive onboarding documentation but wasteful when you only need a plan for a specific team member. Use the targeted single-plan invocation with the member's role and level.
Confusing role families with job titles
Role families describe how someone interacts with the harness, not their job title. A "tech lead" is typically Builder+Guardian, not just Builder. A "PM who writes prompts" is Shaper+Builder. Choose the combination that matches the person's actual workflow with the harness.

/pending

Lists and addresses outstanding human actions from the pending ledger (_output/pending.jsonl). The pending ledger tracks work that the harness has identified but cannot complete autonomously: plans to implement, markers to flip, tests to run, documentation to generate, and user-defined tasks. This skill provides five subcommands: list, address, add, done, snooze, and dismiss. Uses the light context budget tier -- it can run at any point in a session without risking context exhaustion.

Parameters

Argument Required Description
(none, or list) No List all pending items with per-item resolution steps
address <id> No Run the guided resolution workflow for a specific item (marker flips, confirmation prompts)
add --type <type> --source <id> --description "<text>" No Append a new pending action directly
done <id> No Mark a pending item as completed
snooze <id> --until <YYYY-MM-DD> No Snooze an item until a future date
dismiss <id> [--reason <text>] No Dismiss an item without completing it

Prerequisites

The project must be set up with an output directory containing pending.jsonl. For the address subcommand, the referenced item must exist and have pending status. No design or implementation prerequisites -- /pending can be run at any point in the lifecycle to triage outstanding work.

Workflow Summary

  1. Run /pre-skill (with pending-check skipped to avoid recursion -- the skill itself walks the ledger).
  2. For list: run pending.py list --status pending --json, group items by type, and render each with its type-specific resolution steps (the exact commands needed to close the item).
  3. For address: dispatch by item type. mark-implemented and incorporate-research-markers run interactive marker-flip workflows via apply_marker.py. All other types print the full resolution steps with resolved file paths and command arguments.
  4. For add, done, snooze, dismiss: forward arguments to pending.py and report the result.
  5. Run /post-skill.

Subagent Delegations

None. /pending runs entirely inline in the current context. All state transitions go through the pending.py script; the skill never writes to pending.jsonl directly.

Reference Files Loaded

  • .claude/references/general/shared-definitions.md

Expected Outputs

No artifact files are produced. The skill modifies _output/pending.jsonl via the pending.py script (state transitions: pending to done, snoozed, or dismissed). The list subcommand produces a formatted summary displayed to the user. Marker flips via the address subcommand modify the referenced Human (markers) files through apply_marker.py.

Common Mistakes

Dismissing items without verifying in the codebase
Before dismissing a pending item, verify that the referenced artifact still exists and is still relevant. Pattern-matching from memory can lead to dismissing items that are genuinely pending -- always check the actual files.
Not running /pending list before starting new work
The pending ledger may contain items from previous iterations that should be addressed before starting new features. The /pre-skill pipeline surfaces pending items automatically, but running /pending list at the start of a session gives you a complete view of outstanding work and helps you prioritize.
Manually editing pending.jsonl
All state transitions must go through the pending.py script to maintain ledger integrity. The script handles uniqueness invariants, orphan cleanup, and source-based shortcuts. Direct edits bypass these safeguards and can corrupt the ledger.

/qa-log

Logs the current question-and-answer conversation to a file for future reference. In standalone mode it writes to _output/qa-logs/ with a reserved ID and a slug-based filename (qa-<id>-<slug>.md); the log captures the full Q&A exchange from the session and derives a title from the conversation topic or a supplied argument. The same skill also runs in companion mode from /post-skill, producing a QA log collocated next to the parent artifact. Uses the light context budget tier -- it can run at any point in a session without risking context exhaustion.

Parameters

Argument Required Description

[title] No Use the provided text as the log title (and filename slug) instead of an inferred one

Prerequisites

  1. Run /pre-skill.
  2. Reserve an ID via reserve_id.py --type qa and derive a filename slug from the supplied title or the conversation topic.
  3. Collect the full set of Q&A exchanges from the current session, including the brief that opened it.

A single Markdown log file: _output/qa-logs/qa-<id>-<slug>.md in standalone mode, or a collocated companion QA log next to the parent artifact when invoked from /post-skill. The file records the brief and every numbered Q&A exchange from the session.

Common Mistakes

Treating the QA log as design intent
A QA log is a captured conversation, not an authoritative design artifact. Decisions worth preserving should be promoted to a Decision entry (D-NNN) or the design-intent files -- the log itself is a reference record, not a source of truth.
Running it inside an active skill that already captures Q&A
Skills such as /research, /plan, /implement, and /critique already embed their Q&A inline (or via post-skill companion capture). Invoking /qa-log separately mid-skill duplicates that record.

/publish

Publishes a tagged release to the public SEJA repository via the automated publish pipeline. Handles the full 8-step release lifecycle: preflight checks, tag creation, public repo clone, prose copy, harness sync, smoke test, commit, and push. Supports version inference from CHANGELOG.md and git tags, dry-run preview, and non-interactive mode. Uses the light context budget tier. This skill is specific to SEJA harness maintenance and is not part of the typical project lifecycle.

Parameters

Argument Required Description
[version] No Version tag to publish (vMAJOR.MINOR.PATCH). When omitted, inferred from CHANGELOG.md + git tags
--dry-run No Preview the full command sequence without executing any destructive actions
--yes No Non-interactive mode: accept all defaults at confirmation prompts

Prerequisites

.claude/CHANGELOG.md must have an entry for the target version (the skill auto-generates one if missing via the document-generator agent). The preflight check must pass (or the user must explicitly accept remaining warnings). The working tree must be clean, and the user must have push access to the public SEJA repository.

Workflow Summary

  1. Run /pre-skill and resolve the target version (user-specified or inferred from CHANGELOG.md heuristic: Breaking changes -> major, Added -> minor, else -> patch).
  2. Run the preflight check (publish.py --preflight-only --json). If the harness changelog entry is missing, auto-generate it via the document-generator agent, commit, and re-run preflight.
  3. Present any remaining preflight issues to the user with fix commands. Offer: address now, proceed anyway (warnings only), or abort (errors present).
  4. Execute publish.py [version] [--dry-run] [--yes], which handles the full 8-step lifecycle internally.
  5. Report the outcome: published version on success, or error message with recovery instructions on failure. Run /post-skill.

Subagent Delegations

  • document-generator -- generates a harness changelog entry when the preflight check detects one is missing (step 2 auto-update). Not always invoked.

Reference Files Loaded

No eager references. /publish operates with the light context budget and loads no reference files beyond what the publish script needs internally.

Expected Outputs

  • A new git tag (vMAJOR.MINOR.PATCH) on the private repository.
  • Updated .claude/CHANGELOG.md (if auto-generated).
  • Updated .claude/skills/VERSION (auto-bumped if major version matches).
  • A commit and push to the public SEJA repository with synced harness files and prose.

Common Mistakes

Publishing without running preflight
The skill runs preflight automatically, but if you bypass the skill and run publish.py directly, you skip the changelog auto-generation and issue triage steps. Always use /publish rather than the script directly.
Force-accepting errors in preflight
Preflight issues with severity "error" indicate the release will likely fail or produce a bad artifact. Proceeding anyway is possible but strongly discouraged. Only warnings are safe to accept without investigation.

/seja-setup

Manages the SEJA harness lifecycle in a project: installs into a new or existing codebase, finalises an in-place download (--here), creates a companion workspace (--workspace), bootstraps a demo project (--demo), and upgrades harness files to the latest release (--upgrade). State-driven dispatch inspects the current directory via detect_setup_state.py and routes each invocation to the correct action. This is the single entry point into the harness -- on the first iteration, it hands off to /design for design-intent configuration.

Parameters

Argument Required Description
<target-directory> Yes (unless --here, --upgrade, or no-arg flow) Path to the target project directory
--here No Finalise setup in the current directory without copying harness files (use when SEJA was cloned directly into the project)
--workspace No Create a separate workspace directory for working alongside an existing codebase
--demo No Set up with the pre-configured TaskFlow demo project
--upgrade No Upgrade harness files to the latest release (or --version <tag>). Preserves project-specific files
--version <tag> No Pin to a specific public release tag (e.g., v0.1.0). Default: latest SemVer tag
--dry-run No Preview upgrade changes without applying them (with --upgrade)

Prerequisites

For install mode: a target directory (existing or to be created). For --here: the current directory must contain SEJA files from a direct clone. For --upgrade: the project must be in finalised state with .claude/ and product-design/conventions.md present. The skill refuses to run in the SEJA development repository itself (dev-repo-refuse state) to prevent corrupting the harness source.

Workflow Summary

  1. State detection: run detect_setup_state.py --json to determine the project state (no-harness, fresh-download, partial-init, finalised, dev-repo-refuse, or public-clone-soft-confirm). Route to the appropriate flow based on state and flags.
  2. Standard install: create directory structure, copy harness files, run the scaffolding questionnaire (Section 1 basic-definitions) to populate product-design/conventions.md with stack choices, scaffold CLAUDE.md, .claude/rules/, and smoke-test infrastructure conditionally based on the declared stack.
  3. Version pinning: resolve the target tag (latest SemVer tag on the public repository, or --version) and write to .seja-version.
  4. Upgrade: classify files (auto-update vs. manual merge vs. never overwrite), run upgrade_harness.py, show diffs for manual-merge files, and offer follow-up actions for new convention variables or stale references.
  5. Create initial commit and hand off to /design.

Subagent Delegations

None. /seja-setup runs entirely inline in the current context. The scaffolding questionnaire, file copying, and upgrade logic are all handled within the skill.

Reference Files Loaded

  • .claude/references/general/shared-definitions.md
  • .claude/references/template/questionnaire.md
  • .claude/references/template/conventions.md

Expected Outputs

  • Install: a fully scaffolded project directory with .claude/, product-design/, _output/, populated conventions.md, stack-flavored CLAUDE.md, .claude/rules/, and (when backend is present) smoke-test infrastructure.
  • Upgrade: updated skill files, general references, templates, scripts, and harness metadata. Project definitions, settings, output, and CLAUDE.md are preserved. A diff summary for manual-merge files (agents, rules).
  • .seja-version file recording the pinned release tag.

Common Mistakes

Running /seja-setup inside the SEJA development repository
The skill hard-refuses in the dev-repo-refuse state. If you want to work on the harness itself, use standard development workflows. To set up a consumer project, provide an explicit target directory outside the dev repo.
Using --upgrade expecting the questionnaire to re-run
Upgrade mode never re-runs the Section 1 scaffolding questionnaire. It preserves your existing conventions.md unchanged. If you need to update stack choices, run /design update stack after upgrading.
Combining incompatible flags
--here cannot be combined with --workspace, --demo, or --upgrade. --demo is incompatible with --workspace and --upgrade. The skill rejects these combinations with a clear error message.

Uses the light context budget tier.

Parameters

Argument Required Description
[skill-name] No Show full details for a specific skill (quick guide, arguments, category, related skills)
--browse No Interactive category browser with skill graph. Lets you pick a category, then a skill to run

Prerequisites

Reading /help output as authoritative documentation
/help provides a curated summary for quick orientation. The authoritative specification for each skill is its SKILL.md file. For detailed behavior, edge cases, and mode-specific logic, read the SKILL.md directly.
Not using /help --browse for discovery
New users often type /help repeatedly for individual skills. The --browse mode provides an interactive overview of all skills with their relationships, making it easier to discover what is available and how skills connect.

Common Mistakes Across Skills

Beyond the per-skill pitfalls documented above, several cross-cutting mistakes affect skill usage in general. These apply regardless of which skill you are running.

Running skills out of lifecycle order
The canonical path (/research or /explain > /design | /plan > /implement > /critique > /document | /communicate > /reflect) exists because each skill builds on the outputs of the previous one. Running /implement before /plan means there is no structured plan to execute. Running /document before /critique means you may document buggy behavior. Running /communicate before /critique means you may promise broken features to stakeholders. The path is a guideline -- you can skip or revisit steps -- but deviations should be conscious choices, not oversights. See The Lifecycle Pipeline for the full pipeline mechanics.
Misunderstanding context budget tiers
Every skill declares a context budget tier (light, standard, or heavy) that controls how many reference files are loaded. Heavy skills like /plan, /implement, and /critique load the full reference set and can exhaust the context window in a long session. Running a heavy skill after several other skills in the same session risks context degradation -- compaction warnings from /pre-skill's budget-eval stage indicate this is happening. Consider starting a fresh session before running heavy skills, or use /implement in auto mode (which delegates each step to a fresh subagent with its own context window).
Not checking the pending ledger before starting new work
The pending ledger (_output/pending.jsonl) accumulates actions that need human attention: plans to implement, markers to flip, tests to verify, documentation to generate. Starting a new feature without checking the ledger can lead to forgotten work, duplicated effort, or drift between design intent and implementation. Run /pending list at the start of each session -- or rely on the /pre-skill pending-check stage to surface outstanding items automatically.
Skipping /critique before /document or /communicate
/document captures the current state of the implementation as reference material. /communicate presents project status to stakeholders. Both assume the implementation is correct. If /critique has not run, bugs, standards violations, or incomplete features may be captured as intended behavior in documentation or communicated as completed work to stakeholders. The canonical lifecycle places /critique before both output skills specifically to prevent this. See Quality and Critique for details on available critique modes.
