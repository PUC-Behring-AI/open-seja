The Lifecycle Pipeline

Every SEJA skill invocation follows a three-phase pipeline: pre-skill (6 stages that load context and log the brief), skill execution (the skill's own work), and post-skill (13 steps that commit artifacts, update indexes, and flush telemetry). This chapter documents the pipeline end-to-end: the canonical ordering of skills, the internal mechanics of each lifecycle phase, the enforcement mechanisms that make the pipeline mandatory, and the variations that adapt it to different task shapes.

The Canonical Path

The lifecycle defines a recommended ordering for skill invocations. This ordering is not arbitrary -- it mirrors the natural sequence of software development activities, ensuring that each skill has the context it needs from the skills that preceded it.

The Ordered Sequence

The canonical path, as declared in CLAUDE.md, is: 

/research (or /explain)
  > /design | /plan
    > /implement
      > /critique
        > /document | /communicate
          > /reflect

Each arrow represents a dependency: /plan needs the understanding that /research produces; /implement needs a plan to execute; /critique needs implementation artifacts to evaluate. The rule is: validate before you communicate -- a critique must precede documentation or stakeholder communication so that what you share has been checked against design intent.

First Iteration vs. Subsequent Iterations

On the first iteration of a new project, the path begins with /seja-setup, which hands off to /design to configure project-specific files (conventions, constitution, design intent). From iteration 2 onward, the path starts with /research (or /explain) to investigate what you are about to change. The investigation step branches:

  • Into /design when the designer's intent needs to change (new feature direction, revised domain model, updated metacommunication message).
  • Into /plan when the intent is stable and the work is an implementation of existing design.

When to Deviate

The canonical path is a recommendation, not a strait-jacket. Legitimate deviations include:

Skipping /research for trivial changes
A one-line bug fix or typo correction does not require a research phase. The designer may go directly to /plan (even with --light for a lightweight proposal).
Repeating /critique after rework
If a critique surfaces issues that require implementation changes, the path loops back: /implement (rework) followed by /critique again. This loop may repeat until the critique passes.
Running /explain drift as an alignment workflow
The /explain drift mode reconciles design specs with as-coded state. It can be invoked at any point when spec drift is suspected, without following the full canonical sequence.
Parallel /document and /communicate
These two skills address different audiences (developers vs. stakeholders) and can run in either order or in parallel, as long as both follow a successful /critique.

Tip: The skill graph in .claude/references/general/skill-graph.md encodes the valid transitions. Post-skill step 12 reads this file to suggest contextually appropriate next skills after each invocation.

Pre-Skill Stages

Pre-skill is the first phase of every skill invocation. It runs 6 stages in a fixed order, loading the context that the skill needs to operate under governance. Three stages are critical (they always run and cannot be skipped); three are non-critical (they are error-isolated and can be skipped via the calling skill's metadata.skip_stages YAML field). If a non-critical stage fails, pre-skill logs a warning and continues to the next stage.

The pre-skill pipeline is defined in .claude/skills/pre-skill/SKILL.md.

Order Stage Critical Purpose
1 help No Intercept --help flag; display quickguide and stop
2 brief-log Yes Log a STARTED entry to the briefs file
3 budget-eval Yes Determine context budget tier and load briefs accordingly
4 pending-check No Surface overdue pending actions (informational only)
5 ref-load Yes Load reference files (conventions, permissions, constraints, skill-specific refs)
6 constitution No Load the project constitution (immutable design principles)

Stage 1: help

Before any other processing, pre-skill checks whether the calling skill's arguments contain --help. If so, it reads and displays SKILL-quickguide.md from the skill's directory (falling back to the description field in the skill's YAML frontmatter if no quickguide exists). Pre-skill then stops -- no further stages run, and the calling skill does not execute. This allows any skill invocation to double as a help query: /plan --help, /critique --help, etc.

Stage 2: brief-log Critical

The brief-log stage creates a timestamped STARTED entry in the project's briefs file. The entry records the skill name and the user's brief (what they asked the skill to do). Format: 

STARTED | 2026-03-19 21:00 UTC | plan | Add user profile page

The timestamp comes from date -u, never estimated. The entry is written immediately (before continuing to later stages) so that if the system crashes, the briefs file records that a skill invocation was attempted. Post-skill later prepends DONE to mark completion.

After logging the brief, pre-skill also performs conversation trace linkage: it calls conversation_trace.py backfill-skill to annotate the most recent conversation trace entry with the skill invocation that followed it. This links non-skill Q&A exchanges to the skill they led to.

Stage 3: budget-eval Critical

Budget evaluation determines how much context to load for this skill invocation. Each skill declares a context_budget tier in its YAML frontmatter -- light, standard (default), or heavy. The tier controls what is loaded:

Tier Loads Then
light Skips all briefs and reference files (brief-log only) Skip ref-load and constitution stages
standard Briefs index (compact summary, not full file) Proceed to orphan detection, then ref-load
heavy Full briefs file with recency windowing (first 50 entries); also plan index Proceed to orphan detection and compaction warning, then ref-load

Budget-eval contains two sub-steps, which correspond to legacy stage IDs still recognized by skip_stages:

Orphan detection (legacy ID: orphan-check)
Scans for STARTED entries with no matching DONE. Warns the user about potential crashed sessions and lists the 5 most recent orphaned entries. Runs on standard and heavy tiers.
Compaction warning (legacy ID: compaction-check)
Counts skill invocations in the last 2 hours. If the count exceeds the threshold (default: 8), warns that context may be getting heavy and suggests starting a fresh conversation. Runs on heavy tier only. Advisory, never blocking.

Stage 4: pending-check

Runs pending.py status --overdue-days 14 --format banner and prints any output verbatim. This surfaces overdue pending actions (unverified implementations, unflipped markers, deferred documentation) so the user is aware of outstanding work. The stage is purely informational -- it never blocks skill execution.

Stage 5: ref-load Critical

Reference loading injects the files that the skill needs to operate under governance. Three files are always loaded regardless of the skill:

  • product-design/conventions.md (or the template fallback) -- project paths, naming conventions, registry
  • .claude/references/general/permissions.md -- what the agent may and may not do
  • .claude/references/general/constraints.md -- harness-wide constraints and decision-point rationale conventions

Beyond the mandatory files, ref-load operates in one of two modes depending on whether the calling skill declares eager_references in its YAML frontmatter:

Mode 1: Eager-only (no eager_references field)
All files listed in metadata.references are read and injected into context immediately. This is the legacy behavior -- simple but potentially heavy for skills with many references.
Mode 2: Demand-pull (eager_references present)
Files in eager_references are loaded immediately. Files in metadata.references that are not in eager_references become lazy -- they are listed in an "Available references" block with trigger hints (e.g., "when reviewing security concerns") but not read until the skill actually needs them. This keeps context lean for skills that have many references but only use a subset per invocation.

Stage 6: constitution

Reads and injects product-design/constitution.md, the project's immutable design principles. The constitution is the highest-authority reference file -- no plan or implementation step may contradict it without a recorded decision. If the file does not exist (e.g., in projects that predate the constitution feature), the stage skips silently.

Post-Skill Steps

Post-skill runs after every skill completes. Its 13 steps handle artifact finalization, as-coded alignment, quality assurance logging, index regeneration, and git commit. The step numbering uses sub-labels (1b, 2b, 2c, 2d, 6b, 6c, 7e, 8b) for steps added after the original design -- these are not optional variants but full steps in the pipeline.

The post-skill pipeline is defined in .claude/skills/post-skill/SKILL.md with static schemas in .claude/skills/post-skill/SKILL-reference.md.

Step 0: Checkpoint Recovery

If a .post-skill-checkpoint file exists in the output directory, post-skill reads it to determine where a previous run was interrupted. The checkpoint format is <step> | <datetime> | <skill-id>. If the skill ID matches the current invocation, post-skill resumes from the step after the checkpointed one. If the skill ID does not match (stale checkpoint from a different skill), the file is deleted and post-skill starts from the beginning. Each major step writes a checkpoint before proceeding, so the pipeline is resilient to crashes at any point.

Step 1: Brief DONE

Marks the STARTED entry (written by pre-skill stage 2) as DONE by running mark_brief_done.py. The DONE entry includes the completion timestamp and, when applicable, the plan ID. This closes the brief's lifecycle -- any STARTED entry without a matching DONE is flagged as an orphan by subsequent pre-skill orphan detection.

Step 1b: Telemetry Recording

Prepares a telemetry record in memory. The record captures skill name, ID, duration, outcome, brief text, context budget tier, Q&A interaction type, and decision points. Three fields (git_commit_sha, files_changed, parent_skill) are left null at this point -- they depend on the commit at step 8 and are filled at step 8b.

Step 2: As-Coded Alignment

Runs only when the parent skill is /implement (skipped for /plan, which has no code yet). Updates the project's as-coded state in product-design/product-design-as-coded.md to reflect what was actually implemented. This step has multiple sub-phases:

2a. Conceptual design update
Incrementally edits the ## Conceptual Design section: adds new entities, updates modified ones, removes deleted ones. Uses anchor-based Edit on H3 subsections. Appends a changelog entry to product-design-changelog.md.
2b. Documentation auto-run
Collects non-N/A Docs: fields from the plan. If any are found, presents an AskUserQuestion: "Auto-run now" (run /document immediately) or "Skip" (defer to the pending ledger). The --skip-docs flag on the parent /implement invocation bypasses this prompt entirely.
2c. Metacommunication update
If the plan carried metacommunication framing, updates the ## Metacommunication section with implementation status, designer intent, and changelog entries. All text uses first-person ("I" for designer, "you" for user).
2d. Journey maps update
Cross-references implemented features against designed journeys (JM-TB-NNN) and discovered journeys (JM-E-NNN). Updates status and delta from as-intended.
2e. DONE marker proposal
Scans as-intended files for items that appear to have been implemented by this plan. Presents three options: Apply now (flip STATUS markers immediately), Defer (add to pending ledger), or Skip.
2g. Pending action creation
Files pending actions based on plan metadata: verify-as-coded (when many files changed), test-implementation (when the plan has a test plan), update-documentation (when docs were skipped). Also closes the implement pending entry filed at /plan completion.

Step 2c: Design Intent Curation Reminder

Informational only -- outputs a reminder that design intent from the plan has been implemented and suggests promoting items to established status via /explain drift --promote. Post-skill does not perform the promotion itself (the designer owns every word of Decision entries).

Step 2d: Eager Implement Entry

Runs only when the parent skill is /plan. Files an implement pending entry so the user is reminded to execute the plan later. Uses --if-absent for idempotency under checkpoint recovery.

Step 3: QA Log

Captures the Q&A exchanges from the skill session. Three branches, evaluated in order:

Branch A: Skip
If the parent passed skip_qa_log: true. Currently only /research uses this (its transcript is the artifact itself).
Branch B: Inline in artifact
For plan, implement, roadmap, and critique artifacts: Q&A is appended directly to the artifact file under a ## Q&A Log section with numbered ### Q1 / ### A1 entries.
Branch C: Companion file
For all other artifact types: creates a sibling file (e.g., advisory-000012-qa-token-rotation.md) collocated with the parent artifact.

Steps 4-6: Commit Preparation

Step 4: Commit message
Creates an appropriate commit message including the skill name and artifact ID.
Step 5: Git-state safety check
Verifies no rebase is in progress, no unmerged conflicts exist, and HEAD is not detached. If on main/master, warns and asks for confirmation. If any blocker is detected, outputs the commit message for manual use.
Step 6: Commit scope verification
Runs verify_commit_scope.py to check staged files against expected paths for this skill type. Unexpected pre-staged files trigger a warning and manual commit fallback.

Steps 6b-6c: Safety Gates

Step 6b: Fast preflight gate
Runs run_preflight_fast.py. Exit 0 proceeds silently; non-zero displays failures but is advisory (the pre-commit hook is the hard gate).
Step 6c: Human markers verifier
Runs check_human_markers_only.py --staged. Detects unauthorized prose mutations in Human (markers) files. Violations prompt an abort/proceed decision; the default recommendation is to abort (unauthorized edits should go through apply_marker.py).

Step 7: Index Regeneration

Refreshes all project indexes to reflect the new artifacts:

7a. Briefs index
generate_briefs_index.py -- compact index of briefs for efficient pre-skill loading.
7b. Macro index
generate_macro_index.py -- the output directory's INDEX.md with all artifacts.
7c. Cross-reference update
update_cross_refs.py -- reads the produced artifact's source: header and updates the spawned: field on the source artifact.
7d. Decision digest
generate_decision_digest.py -- regenerates the decision digest when /research produced HIGH/MEDIUM recommendations or a plan applied DECISION_APPEND markers.

After index regeneration, post-skill captures the current HEAD SHA as <pre-commit-sha> for comparison at step 8b.

Step 7e: Deferred-Artifact Generation

Runs only for /implement parent skills. Generates artifacts that depend on the completed implementation:

Manual Actions section
If any plan step requires manual operator action after deployment (database migration, environment variable, service restart), maintains a ## Manual Actions section in the plan file.
deploy.html
Scans plan steps for non-N/A Deploy: fields. If found, generates or updates _output/docs/deploy.html -- a self-contained deployment guide with Docker, Linux, and Windows sections, a highlighted "Changed in plan" banner, and a reverse- chronological change history.

Step 8: Commit

Stages all affected files (artifacts, regenerated indexes, as-coded updates, deferred artifacts) and commits using the message from step 4. Writes a final checkpoint, then deletes the checkpoint file on success -- the pipeline has completed.

Step 8b: Telemetry Flush

Enriches the step 1b telemetry record with commit-dependent fields (git_commit_sha, files_changed, parent_skill) and writes it via build_telemetry.py. The telemetry record is committed as a separate trailing commit (e.g., telemetry: plan 000042) to avoid amend-after-push divergence. If step 8 produced no commit (HEAD unchanged), the telemetry record is dropped.

Steps 9-12: Wrap-Up

Step 9: Surprise output
Reports any unexpected events during skill execution, their resolution, and status (resolved or pending).
Step 10: Artifact link
Outputs a link to the generated artifact file within the output directory.
Step 11: Completion banner
Emits the standardized completion banner: --- SKILL COMPLETE: <skill> <type> <id> ---.
Step 12: Contextual next-step suggestions
Reads skill-graph.md to look up valid transitions from the completed skill. Presents at most 3 suggestions (plus "End"), each with a reason from the graph and a note on when the suggestion would be wrong. Suppresses suggestions for checks already run (6b/6c), documentation already offered (2b), and low-value reflections (CHORE/DOCUMENT briefs).

Tip: Post-skill also supports a --deferred mode for roadmap parallel-wave execution. In deferred mode, the orchestrator handles wave-level briefs, QA, and commits; post-skill runs only the per-plan state alignment steps (0, 1b, 2, 2c, 7, 2g, 8b). See Skills In Depth for the roadmap orchestration model.

Enforcement Mechanisms

The lifecycle pipeline is not merely documented -- it is enforced through four complementary mechanisms. Together, they form a defense-in-depth strategy: if one mechanism is bypassed (or the agent fails to follow a rule), another catches the violation before it reaches the repository.

CLAUDE.md Rules

The project's CLAUDE.md file is the primary governance mechanism. Claude Code reads this file at the start of every conversation, making its rules the baseline context for all agent behavior. CLAUDE.md declares:

  • The canonical lifecycle path and its skill ordering
  • The conversation trace logging protocol (for non-skill exchanges)
  • Key workflows and their entry points
  • Global rules (private repositories, no hand-syncing of public harness files)

Because CLAUDE.md is injected into the agent's context window, its rules are effectively instructions that the model follows. This is a soft enforcement mechanism -- it depends on the model's instruction-following capability rather than code-level constraints. The harder mechanisms below compensate.

Pre-Commit Hooks

The pre-commit hook in .githooks/pre-commit (installed via bash .githooks/install.sh) runs automatically on every git commit. It executes fast preflight checks and the pre-sync leak gate (check_no_private_leaks.py --staged). The hook is a hard gate: if any check fails, the commit is rejected. This catches violations that the agent's instruction-following missed -- for example, staging a file with private-only content that should not be committed.

Validation Scripts

The harness includes a suite of validation scripts in .claude/skills/scripts/ that enforce specific constraints:

verify_commit_scope.py
Post-skill step 6. Checks that staged files match expected paths for the skill type. Flags unexpected files that may have been staged by accident.
run_preflight_fast.py
Post-skill step 6b. Runs a battery of fast checks including call-graph freshness validation. Advisory at post-skill time, but the pre-commit hook is the hard gate.
check_human_markers_only.py
Post-skill step 6c. Detects prose mutations in Human (markers) files -- files where the agent may write only lifecycle markers (STATUS, ESTABLISHED, INCORPORATED), never prose content.
run_all_checks.py
CI-independent validation orchestrator. Discovers and runs all check scripts with unified exit codes and JUnit XML output. Invoked by /critique validate and by CI workflows.
check_section_boundary_writes.py
Enforces that agent edits to product-design-as-coded.md stay within the correct H2 section boundary. Prevents a conceptual design edit from accidentally modifying the metacommunication section, for example.

Constitution Loading

The project constitution (product-design/constitution.md) contains immutable design principles that no plan or implementation step may contradict. Pre-skill stage 6 loads this file into the agent's context for every skill invocation (at standard and heavy budget tiers). Generator subagents also receive the constitution as part of their prompt, extending trust boundary enforcement to delegated work. The constitution is not a suggestion -- it is a hard constraint. /critique health validates that the file exists (Check 7), and its absence is flagged as a health issue for new projects.

Lifecycle Variations

The canonical path assumes a feature-development workflow, but not all tasks are feature development. The lifecycle adapts to three common variations by adjusting which steps run and which are skipped.

Bug Fixes

A bug fix typically starts from /research (to understand the root cause) or skips directly to /plan when the cause is already known. The plan carries a FIX prefix rather than FEATURE. The key lifecycle differences:

  • /research may be skipped for obvious bugs (one-liner fixes, typo corrections).
  • /plan --light is appropriate for small fixes that do not warrant a full plan.
  • Post-skill step 2b (documentation auto-run) triggers only when the plan has non-N/A Docs: fields -- most bug fixes do not, so documentation is skipped automatically.
  • Post-skill step 2e (DONE marker proposal) is unlikely to fire because bug fixes rarely implement new as-intended items.

Documentation-Only Tasks

When the task is purely documentation (updating a README, writing a new guide, refreshing API docs), the plan carries a DOCUMENT prefix. The lifecycle contracts:

  • /design is skipped (no intent change).
  • /implement executes the plan as usual, but the implementation is prose, not code.
  • Post-skill step 2 (as-coded alignment) is skipped because the parent skill is /implement but the plan prefix signals no conceptual-model change.
  • Post-skill step 12 suppresses /reflect as a next-step suggestion (low-value reflection target for DOCUMENT briefs).

Refactoring

Refactoring preserves external behavior while restructuring internal code. The plan carries a CHORE prefix. The lifecycle adapts:

  • /research or /explain is important to understand the current architecture before restructuring.
  • /critique after implementation focuses on whether the refactoring preserved behavior (regression risk) rather than design-intent alignment.
  • Post-skill step 2b (documentation auto-run) may or may not trigger depending on whether the refactoring changed user-facing behavior or API surfaces.
  • Post-skill step 12 suppresses /reflect (low-value for CHORE briefs).

Tip: The plan prefix (FEATURE, FIX, CHORE, DOCUMENT, REDESIGN) is the primary signal that controls lifecycle variation. The prefix is set at /plan time and propagates through /implement and post-skill automatically. See Skills In Depth for the full prefix taxonomy.

Conversation Trace Integration

Not all user-agent exchanges happen inside skill invocations. The user might ask a question, discuss an approach, or give an instruction outside any /skill call. These non-skill exchanges are captured by the conversation trace -- a JSONL file at _output/conversation-trace.jsonl that records every utterance in the session.

The Logging Protocol

After responding to any user message that is not within an active skill invocation, the agent logs two entries to the conversation trace:

  1. Get preceding event ID: call conversation_trace.py last-evt-id to find the most recent entry for this session.
  2. Log user utterance: call conversation_trace.py append with --emitter user, the user's message, and an inferred type (question, answer, or instruction).
  3. Log agent response: call conversation_trace.py append with --emitter claude, a 1-2 sentence summary of the response, and optional --topic-tags.

Entry Schema

Each conversation trace entry is a JSON object with these fields:

Field Type Description
timestamp ISO 8601 UTC timestamp of the entry
session_id string CLAUDE_SESSION_ID env var value
evt_id string Sequential event ID (qa-NNNNNN)
preceding_evt_id string evt_id of the preceding entry (or "null")
emitter string "user" or "claude"
message string Utterance text (may contain [MASKED:...] replacements)
type string "question", "answer", or "instruction"
led_to_skill string | null Skill invocation that followed this entry (backfilled by pre-skill)
topic_tags string[] | null 0-3 short topic tags

Linkage to Skills

When a user's non-skill question leads to a skill invocation (e.g., asking "How should we handle auth?" followed by /plan add-token-rotation), pre-skill stage 2 (brief-log) backfills the led_to_skill field on the most recent conversation trace entry. This creates a traceable chain: the question that motivated the skill invocation is linked to the skill that addressed it.

Sensitivity Masking

The conversation_trace.py append command may apply sensitivity masking to messages, replacing sensitive content with [MASKED:<pattern-name>] tokens. If masking is applied (exit code 2), the agent shows the masked message to the user and asks for confirmation before persisting. This prevents accidental logging of credentials, API keys, or other sensitive data.

Common Mistakes

The following mistakes are frequently encountered when working with the SEJA lifecycle. Each entry describes the mistake, its consequence, and how to avoid it.

Skipping lifecycle steps
Mistake: Jumping from /research directly to /implement, skipping /plan. Or implementing without running /critique afterward.
Consequence: Implementation proceeds without a recorded plan, making it impossible to trace design decisions back to their rationale. Without critique, design-intent drift goes undetected until much later.
Avoidance: Follow the canonical path. If you believe a step is unnecessary for a particular task, use the appropriate shortcut (/plan --light for small changes) rather than skipping the step entirely.
Confusing pre-skill with post-skill
Mistake: Expecting pre-skill to commit artifacts, or expecting post-skill to load reference files.
Consequence: Debugging incorrect lifecycle behavior by looking in the wrong pipeline phase.
Avoidance: Remember the separation of concerns: pre-skill loads context (references, constitution, briefs); post-skill finalizes output (commits, indexes, telemetry). The skill itself does the actual work in between.
Running /implement without a plan
Mistake: Invoking /implement without a corresponding plan file in _output/plans/.
Consequence: The implementation has no recorded scope, no step-by-step breakdown, and no Docs: or Deploy: metadata for post-skill to act on. As-coded alignment (step 2) has no plan to read from. Post-skill's documentation auto-run and deferred-artifact generation have nothing to process.
Avoidance: Always run /plan first. For trivial changes, use /plan --light to produce a lightweight proposal. The CLAUDE.md rules instruct the agent to check for an existing plan before implementing.
Forgetting to commit
Mistake: Manually interrupting post-skill before step 8, leaving artifacts uncommitted.
Consequence: Work is done but not persisted in version control. The briefs file shows DONE but the artifacts exist only in the working tree. A subsequent skill invocation may overwrite or conflict with the uncommitted changes.
Avoidance: Let post-skill run to completion. If you must interrupt, use the checkpoint recovery mechanism (step 0) -- re-invoking post-skill with the same skill ID resumes from where it left off. If you have already interrupted past the point of recovery, stage and commit manually using the commit message that post-skill prepared at step 4.
Editing Human (markers) files directly
Mistake: Having the agent write prose content into files classified as Human (markers), such as product-design-as-intended.md or ux-research-results.md.
Consequence: Post-skill step 6c (check_human_markers_only.py) catches the violation and recommends aborting the commit. If the commit proceeds anyway, the pre-commit hook may also flag it.
Avoidance: Use apply_marker.py for all writes to Human (markers) files. This script supports STATUS, ESTABLISHED, INCORPORATED, CHANGELOG_APPEND, DECISION_APPEND, and REQ_TRACED_BY marker types -- the only write operations permitted on these files.
