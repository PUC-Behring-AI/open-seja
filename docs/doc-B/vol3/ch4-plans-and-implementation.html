Plans and Implementation

Every non-trivial change in a SEJA-governed project passes through a plan before reaching code. The /plan skill generates structured, self-contained plan files; the /implement skill executes them step by step. This chapter covers the anatomy of a plan file, the three planning modes, the generation and review workflow, the implementation executor, progress tracking, and the traceability chain that connects each implementation step back to design intent.

Plan File Structure

A plan file is a Markdown document stored in the project's plans directory (typically _output/plans/). It follows plan_format_version: 1 and contains a structured header, interpretive sections, a step list, and optional review and Q&A appendices. The file name follows the convention plan-NNNNNN-slug.md, where the six-digit ID is reserved by reserve_id.py.

Header

The first line carries the plan's identity and classification: 

# Plan 000701 | DOCUMENT-X | 2026-07-14 20:32 | Phase 1 content authoring | Review: standard
plan_format_version: 1
source: roadmap-000665 -- SEJA Documentation Collection (Wave 1)

The header fields are:

Field Content
Kind + ID Plan NNNNNN -- the reserved numeric identifier
Prefix + Scope A category tag such as FEATURE-X, FIX-O, CHORE-O, DOCUMENT-X. Prefixes follow the plan-prefix convention from general/report-conventions.md
Datetime Creation timestamp in UTC
Short title Human-readable summary of the plan's purpose
Review depth Review: light, standard, or deep -- determined by the complexity gate

The plan_format_version: 1 line enables the /implement executor to parse step metadata. Plans without this version marker fall back to manual mode. An optional source: line traces the plan back to a roadmap or advisory that spawned it.

Interpretive Sections

Between the header and the steps, a plan contains several interpretive blocks:

User Brief
The designer's original task description, recorded verbatim. For metacomm-framed plans, this is the designer's first-person metacommunication message.
Agent Interpretation
The agent's understanding of the brief, structured as: Problem (what this plan solves), Approach (chosen strategy and rationale), and for standard/deep reviews, Alternatives rejected and Selection rationale (disposition of source recommendations).
Files
A master list of all files the plan will create, modify, or read. Each entry notes the operation: (create), (modify), (delete), or (read).
Best Practices
Engineering practices that apply across the plan. Sourced from the project's coding standards, conventions, and any domain-specific constraints.
Design Decisions (standard/deep only)
User-visible impact, trade-offs accepted, and metacommunication impact (when the plan changes what the system communicates to users).

Step Format

Each step in the ## Steps section follows a canonical shape defined in .claude/references/template/plan-step.md. The format ensures that every step is self-contained -- executable by a fresh subagent with no shared context from prior steps. 

### Step 1: <short imperative title>
<What to do -- a self-contained description that a subagent
can execute without reading other steps.>
- **Files**: path/to/file.py (create), path/to/other.py (modify)
- **References**: product-design/standards.md § Backend
- **Depends on**: Step 2, Step 3
- **Interface**: exports UserService with find_by_id(id: str) -> User | None
- **Verify**: tests pass; endpoint returns 200
- **Tests**: Add unit tests for new service method
- **Docs**: Update API reference
- **Deploy**: Add DATABASE_URL env var; update docker-compose.yml
- **Traces**: REQ-ENT-001, REQ-PERM-003
- [ ] Done

Step Metadata Fields

Field Required Purpose
Files Yes Every path the step reads, creates, modifies, or deletes. Existing files must be verified on disk during planning. Each step should touch no more than 5 files; split if larger.
References Yes Only the product-design/ files relevant to this step. Subagents load these on demand rather than ingesting all references at once.
Depends on No Step numbers whose output this step requires. Absent means no dependencies. Dependencies must flow forward (no circular or backward references).
Interface Yes (may be N/A) Expected public surface for dependency-producing steps: function names, class names, exported types with signatures. N/A for leaf steps. Used by auto-mode subagents as the type contract when writing TDD failing tests.
Verify Yes A concrete, testable condition that confirms the step succeeded. Prefer automated checks ("tests pass", "migration runs forward and backward") over subjective assessments.
Tests Yes (may be N/A) What tests to create or update. Required for steps that create or modify source code. N/A for migrations, configuration, pure refactors with existing coverage, and framework-only steps. Test descriptions must express observable behavior ("when X is called with Y, returns Z"), not structural assertions.
Docs No Documentation to create or update. Present for steps that create or modify user-facing code or public APIs. Omit entirely when not applicable.
Deploy No Deployment configuration changes: new environment variables (name + expected value shape), changed ports, new services, container changes. Covers Docker and standalone (Windows/Linux) where they differ. Omit entirely when the step has no deployment impact.
Traces No Comma-separated REQ IDs from product-design/product-design-as-intended.md that this step implements. Links implementation work back to design requirements. Omit when no REQ markers exist or the step does not trace to one.

Appendix Sections

After the steps, a plan file may accumulate several appendix sections over its lifetime:

Review Log
Appended during the plan review phase. Contains perspective scan results, amendments, execution metrics, and any Phase 2 deep-dive findings.
Outcomes
Expected outcomes of the plan, stated upfront during generation.
Smoke
true if any step creates or modifies API route files or frontend components; false otherwise. Consumed by /implement to decide whether to run /critique smoke api after execution.
Q&A Log
Numbered Q&A exchanges appended during planning and implementation. When /implement runs against the same plan, its Q&A is appended with a separator comment.
Reflection
Optional dated bullets appended by the post-skill reflection loop. Absent by default; created on first use.

Three Plan Modes

The /plan skill supports three distinct modes, each designed for a different scale of work. Mode selection happens either explicitly via flags or automatically based on the brief's scope.

Standard Single-Plan Mode

The default mode. Generates a full plan with structured steps, metadata fields, a complexity-gated review, and a post-plan commit. Suitable for features, bug fixes, and refactors that fit comfortably within 12 steps.

Aspect Detail
Flag --plan (or no flag, if auto-detection resolves to single plan)
Output A single plan file in _output/plans/
Review Complexity-gated: Light, Standard, or Deep
Scope A single bug, fix, refactor, or feature that references a specific file, component, or endpoint

Lightweight Proposal Mode

A minimal change proposal for small, surgical modifications. No multi-step decomposition, no multi-phase review. The proposal uses an abbreviated format (defined in .claude/references/template/proposal.md) with an inline 2-3 perspective scan. If the user approves, the change is executed immediately in the current context -- no subagent orchestration.

Aspect Detail
Flag --light
Output A proposal file in the proposals directory
Review Inline light review (2-3 perspectives; always includes SEC for code changes)
Scope Changes too small to warrant a full plan but worth tracking

Roadmap Mode

For work that spans multiple entities, architectural layers, or user flows. Decomposes the brief into independent work items, classifies each as technical or design, groups them into dependency-aware execution waves, and optionally generates plans for each item. Three sub-modes control how the roadmap is sourced:

Mode 1: Auto-generate from project references
Reads product-design/product-design-as-intended.md and product-design/product-design-as-coded.md, computes the delta between intended and coded state, and decomposes work items across four layers: Foundation (models + migrations), Service + API, Frontend, and Cross-cutting. Items are classified as technical or design and grouped into waves (Wave 0 through Wave 4). The --only-unimplemented flag scopes extraction to open items only by filtering out REQ markers that carry a STATUS: implemented marker.
Mode 2: From spec file
Parses a pre-filled roadmap-spec.md file with themes, work items, constraints, and wave groupings. Validates required fields and dependency graphs before generating the roadmap.
Mode 3: Generate blank spec
Creates a roadmap-spec skeleton for offline editing. The user fills it in manually, then runs /plan --roadmap --from-spec <path> (Mode 2) to compile it.
Aspect Detail
Flag --roadmap (with optional --auto, --from-spec)
Output A roadmap summary file plus zero or more plan files
Review Delegated to generated per-item plans
Scope 3+ entities, 2+ architectural layers, or multiple user flows

Mode Detection

When the user provides neither --plan, --light, nor --roadmap, the skill auto-detects the appropriate mode by scoring the brief against signals:

Signal Points toward
Brief mentions 3+ distinct entities, resources, or features Roadmap
Brief spans 2+ architectural layers (model + API + UI) Roadmap
Brief describes a single bug, fix, or refactor Single plan
Brief references a specific file, component, or endpoint Single plan
Brief scope fits in 12 or fewer steps Single plan

If auto-detection recommends a roadmap, the skill presents a confirmation gate before proceeding. Single-plan detection proceeds without asking.

Plan Generation Workflow

This section walks through the end-to-end workflow of /plan in standard single-plan mode, from the designer's brief to a committed plan artifact.

Step 1: Design Guard

Before any planning begins, the skill verifies that product-design/conventions.md exists. This file is created by /design and contains the project's stack, directory structure, and coding conventions. If it is missing, the skill stops immediately: 

No project design found. Run /design first to define your
project's stack, conventions, and domain model.

The design guard ensures that plans are always grounded in a declared project structure, not in the agent's assumptions about how the project is organized.

Step 2: Pre-Skill and Reference Loading

The /pre-skill pipeline runs its six stages: help detection, brief logging, budget evaluation, pending check, reference loading, and constitution loading. References are loaded eagerly from the plan skill's YAML frontmatter (design intent files, report conventions, coding standards, review perspectives index) and lazily on demand based on what the plan touches:

Condition Reference loaded
--framing metacomm flag product-design/product-design-as-intended.md
Plan touches backend, frontend, testing, or i18n files product-design/standards.md
Plan involves auth, validation, or sensitive data product-design/security-checklists.md
Plan involves UX flows or visual design product-design/design-standards.md

Step 3: ID Reservation and Plan Generation

The skill reserves a six-digit numeric ID via reserve_id.py --type plan, then generates the plan file. The generation process creates the header, records the user brief verbatim (or the metacommunication message if --framing metacomm is active), writes the agent interpretation, lists files, documents best practices and design decisions, and decomposes the work into structured steps.

Step decomposition follows the guidelines in .claude/references/template/plan-step.md:

  • Each step must be completable in one subagent context window (rule of thumb: touches 5 or fewer files).
  • Every file path the step reads, creates, modifies, or deletes must be listed in the Files field.
  • Existing file paths must be verified on disk during planning.
  • Dependencies must flow forward -- Step 2 may depend on Step 1, never the reverse.
  • Each step description must be self-contained: it should make sense to a subagent that has not read any other step.

Step 4: Metacomm Framing (When Active)

When --framing metacomm is passed, the plan treats the brief as a designer's metacommunication message using "I" (designer) / "you" (user) phrasing. The brief is recorded verbatim, and the agent checks for contradictions against existing intentions in product-design/product-design-as-intended.md. A ## Metacomm Intention section is appended to the plan, summarizing the metacommunication message the plan implements. This section is consumed by /explain drift and /post-skill to keep the design-intent file in sync.

Step 5: Coverage Check

If the as-intended file contains REQ markers (<!-- REQ-*-NNN -->), the skill runs check_plan_coverage.py --mode advisory and includes the coverage summary in the plan. This check verifies that the plan's steps collectively address the design requirements they claim to trace to. The check is advisory -- it does not block plan generation.

Step 6: Review, Commit, and Next Steps

The plan undergoes the complexity-gated review process described in the next section. After review, the plan is saved and committed via /post-skill. The plan is now a durable git artifact. The designer is then presented with options: implement now (via /implement <id>) or end the session and implement later.

Tip: The plan is committed to git before the implement question is asked. This means you can safely close the session and return to implement later -- the plan file is already versioned and findable via its ID.

Plan Review and Critique

Every standard plan undergoes a structured review before implementation. The review process is complexity-gated: smaller plans get lighter scrutiny, while larger or higher-risk plans receive multi-phase evaluation from multiple engineering perspectives.

Step Metadata Validation

Before the perspective review begins, the skill validates step metadata:

  • Every step has all required fields (Files, References, Interface, Verify, Tests, checkbox).
  • Interface is required but may be N/A -- omitting it entirely is a validation error.
  • Optional fields (Depends on, Docs, Deploy, Traces) may be omitted entirely.
  • Non-N/A Tests entries must express observable behavior ("when X is called with Y, returns Z"), not structural assertions ("module exports class Z").
  • File paths for existing files are verified on disk.
  • Dependencies flow forward with no circular references.
  • No step touches more than 5 files.
  • Each step description is self-contained.

Any issues found at this stage are fixed before the perspective review proceeds.

Complexity Gate

The review depth is determined by the plan's size and risk profile:

Depth Criteria Phases
Light 6 or fewer action steps AND touches 4 or fewer files Phase 1 only
Standard 7-12 action steps OR touches 5-8 files Phase 1; Phase 2 eligible
Deep More than 12 steps OR more than 8 files OR involves migrations, auth, or cross-scope changes Phase 1 + Phase 2 for all Deferred concerns

The --review <level> flag can override the auto-detected depth. The effective depth is max(auto, floor, flag) where floor comes from MINIMUM_REVIEW_DEPTH in product-design/conventions.md (defaults to light).

Phase 1: Perspective Triage and Scan

Phase 1 runs inline (no subagents) using a two-stage loading protocol:

  1. Load .claude/references/general/review-perspectives-index.md to see all 16 perspectives.
  2. Identify a default shortlist of 3-6 perspectives using the Perspective Shortcuts by Plan Prefix table.
  3. Optionally add up to 2 more with a one-line justification.
  4. Load only the selected review-perspectives/<tag>.md files.

Each selected perspective is evaluated and marked as Adopted (issue found and addressed) or Deferred (concern noted for later) with a one-line description. Perspectives not in the shortlist are marked N/A. For Light-depth reviews, the process stops here.

Phase 2: Targeted Deep-Dives

Phase 2 triggers only for Standard and Deep reviews. The plan-reviewer agent is launched with the plan text, file path, and depth level. The agent performs deep-dive analysis on Deferred perspectives whose concerns could cause regression, production incidents, or standards violations.

For Deep reviews, additive-improvement Deferred concerns also trigger deep-dives. Cosmetic or out-of-scope concerns never trigger Phase 2.

Amendments and Convergence

When Phase 2 produces recommendations that change the plan:

  1. A ### Plan Amendment (iteration N) section is appended (additive -- existing text is never modified).
  2. The Steps section is updated in place (the only section allowed to change, since it is a living checklist).
  3. Perspectives whose steps were modified are re-evaluated, along with any still Deferred.
  4. If all Phase 2 findings are "no change needed," the loop terminates immediately.
  5. Otherwise the loop repeats until all perspectives are Adopted or Deferred-with-rationale, or 3 iterations are reached, or the deep-dive budget (6) is exhausted.

After each iteration that produces recommendations, a conflict check runs to detect contradictions between perspectives. Conflicts are resolved per the rules in general/review-perspectives.md and logged in the review log.

Execution Metrics

Every review log ends with a mandatory Execution Metrics table: 

| Metric                            | Value       |
|-----------------------------------|-------------|
| Perspectives shortlisted          | 5           |
| Perspectives Adopted              | 5           |
| Perspectives Deferred             | 0           |
| Deep-dives used                   | 0/6         |
| Iterations completed              | 1/3         |
| Convergence reason                | all resolved |

The /implement Executor

The /implement skill takes a plan ID and executes it. It supports four execution modes and includes quality controls that run after implementation completes.

Execution Modes

Mode Flag When to use Topology
Auto (default) Most plans, especially those with more than 6 steps where context degradation is a risk Each step runs in a fresh general-purpose subagent; state shared via the progress file
Manual --manual Small plans (6 or fewer steps) or when per-step confirmation is needed Sequential in the current context
Roadmap --roadmap <id> Executing every plan in a roadmap without per-plan invocation Each plan runs auto mode in a fresh subagent; pauses between waves per --checkpoint
Pending --pending Clearing all pending implement entries in one go Generates a lightweight roadmap from pending entries, then dispatches to roadmap mode

Auto Mode Workflow

Auto mode is the default and most common execution path. It operates in three phases:

Phase 0: Setup
Runs /pre-skill, reads the plan file, parses the Steps section, creates the progress file (if missing), builds the execution queue from incomplete steps in dependency order, creates a rollback branch (pre-plan-<id>) from current HEAD, and informs the user of the iteration count.
Phase 1: Iteration Loop
For each step in the execution queue (up to --max-iterations, default 20): picks the next eligible step (all dependencies complete), builds a self-contained subagent prompt, spawns a general-purpose subagent, and processes the result. The subagent receives the step's full description, Files, Verify, Tests, Interface, and the progress file content. It also reads the project conventions and coding standards. Each subagent commits with message plan-<id> step <N>: <step title>.
Phase 2: Wrap-up
Runs the quality gate (unless --skip-checks), marks the plan as DONE, appends an aggregated summary, updates roadmap status if applicable, and runs /post-skill.

TDD in Auto Mode

When a step has a non-N/A Tests field, auto-mode subagents follow the TDD red-green cycle:

  1. Red: Write a failing test per the Tests description. If an Interface field is present, use it as the type contract. If the test passes before any implementation, report PARTIAL with a note about possible scope overlap.
  2. Green: Implement the step until the test passes.
  3. Verify: Run test commands from product-design/conventions.md to confirm the Verify condition. On failure, retry the green phase up to 3 times before returning PARTIAL.

Manual mode retains test-after ordering by design. The user's presence provides the quality oversight that the TDD cycle substitutes for in auto mode.

Subagent Result Handling

Each subagent returns one of three statuses:

Result Plan checkbox Action
SUCCESS - [x] Done Save plan file; continue to next step.
PARTIAL - [~] Partial Read the progress-file blocker. If addressable (missing file or fixture), proceed -- a later step may unblock. After 2 consecutive PARTIAL or FAILED results, pause and ask the user.
FAILED - [!] Failed Read the progress-file failure. Pause and ask the user: skip, retry, or abort.

Quality Gate

After all steps complete (or after each step in manual mode), the executor runs the quality gate (skipped with --skip-checks):

  1. Run /critique validate -- validation scripts and structural checks.
  2. Run /critique review -- code review against engineering perspectives.
  3. Launch the test-runner agent with scope "all".
  4. If the plan's smoke field is true, run /critique smoke api.
  5. Critical issues (failing tests, security findings, blocking validation errors) must be fixed before proceeding; non-critical issues become deferred items.

Generator-Critic Loop

Auto mode runs a bounded retry loop for critical code-review findings after Quality Gate step 2. The loop classifies each finding as critical (security, correctness, failing tests) or advisory (non-blocking), then iterates up to 2 times: for each critical finding, a general-purpose subagent receives a fix prompt with the finding description, file/line, and plan context. After fixing, /critique review re-runs on changed files only.

If the retry cap (2 iterations) is reached with critical findings remaining, they are logged as unresolved in the plan summary and execution continues. Manual mode treats all review findings as advisory -- the user decides what to fix.

Roadmap Execution

When --roadmap <id> is used, the executor parses the roadmap's wave summary, filters to incomplete items, and executes plans wave by wave. Wave 0 always runs sequentially (migration chain safety). Subsequent waves may run in parallel when plans' Files lists do not overlap and no call-graph edges connect their files. Parallel execution uses worktree isolation: each plan runs in a separate git worktree, and results are merged back in plan-ID order during a serialized merge phase.

Between waves, checkpoints pause for user review (configurable via --checkpoint wave|plan|none). The executor prompts the user to verify that the next wave's plan assumptions still hold after the previous wave's implementation.

Progress Tracking

Auto mode maintains a progress file alongside the plan file. This file serves as the shared-memory channel between subagents that execute individual steps.

Progress File Format

The progress file is created at the start of auto mode and follows a fixed structure: 

# Progress -- Plan <id>

Append-only cross-iteration learnings. Each subagent reads
this file at the start and appends findings at the end.

## Codebase Patterns
<!-- Subagents consolidate reusable patterns here -->

## Iteration Log

The file has two sections:

Codebase Patterns
Reusable patterns discovered during execution. When a subagent finds an existing pattern in the codebase (naming convention, error handling approach, test structure), it promotes the pattern to this section. Later subagents read these patterns and follow them, ensuring consistency across steps even though each subagent starts with a fresh context.
Iteration Log
A chronological log of what each step did, what it discovered, and any blockers it encountered. Each entry records the step number, date, files modified, source files read, key content decisions, and notable patterns used.

Checkpoint Recovery

Because the plan file's step checkboxes and the progress file are both updated after each step, execution is resumable. If a session is interrupted:

  1. Re-run /implement <id> in a new session.
  2. The executor reads the plan file and finds which steps are already checked as [x] Done or [~] Partial.
  3. The execution queue is rebuilt from incomplete steps only.
  4. The progress file provides the new subagents with context about what prior steps accomplished, so they do not duplicate work or contradict earlier decisions.

Roadmap execution is similarly resumable: re-running /implement --roadmap <id> on a partially complete roadmap picks up from the first incomplete item. Completed plans are not re-executed.

Rollback

Before execution begins, the executor creates a rollback branch from the current HEAD: 

git branch pre-plan-<id>

For roadmap execution, both a roadmap-level and per-wave rollback branch are created: 

git branch pre-roadmap-<id>         # roadmap-level rollback
git branch pre-wave-<N>-<id>     # per-wave rollback

The user can undo all changes for a plan via git checkout pre-plan-<id>, or undo a specific wave via git checkout pre-wave-<N>-<id>.

Design-Intent Traceability

SEJA maintains a traceability chain from design requirements through plans to implementation. This chain ensures that every code change can be traced back to a design decision, and conversely, that every design requirement can be traced forward to the code that implements it.

The Traces Field

The Traces field in each plan step connects implementation work to design requirements. Each entry is a REQ ID from product-design/product-design-as-intended.md, following the format REQ-<TYPE>-NNN:

Prefix Classification Example
REQ-ENT Entity / domain model REQ-ENT-001 (User entity)
REQ-PERM Security / permissions REQ-PERM-003 (Admin role)
REQ-VAL Validation REQ-VAL-005 (Email format)
REQ-UX User experience REQ-UX-010 (Dashboard layout)
REQ-MC Metacommunication REQ-MC-002 (Error message tone)
REQ-I18N Internationalization REQ-I18N-001 (Locale setup)
REQ-DELTA Technical delta REQ-DELTA-004 (API migration)
REQ-JM Journey map REQ-JM-001 (Onboarding flow)

Coverage Check

During plan generation, if the as-intended file contains REQ markers, the skill runs a coverage check (check_plan_coverage.py --mode advisory) that verifies: which REQ IDs the plan's steps collectively claim to trace to, which REQ IDs in the as-intended file are not addressed by any step, and which steps claim traces that do not correspond to actual REQ markers. The check is advisory -- it surfaces gaps without blocking.

For roadmaps, a broader coverage check (check_plan_coverage.py --mode advisory) runs after all plans are generated, verifying coverage across the entire roadmap.

STATUS Marker Lifecycle

REQ markers in the as-intended file progress through a defined lifecycle via STATUS markers:

No STATUS marker (open)
The requirement exists in the design but has not yet been implemented. It is eligible for inclusion in plans and roadmaps. The --only-unimplemented flag on /plan --roadmap --auto scopes extraction to these open items.
<!-- STATUS: implemented | plan-NNNNNN | YYYY-MM-DD -->
The requirement has been implemented by the referenced plan. Applied by /explain drift --apply-markers plan-<id> via the apply_marker.py script. The legacy uppercase form (STATUS: IMPLEMENTED) is also recognized.
<!-- STATUS: established | plan-NNNNNN | YYYY-MM-DD -->
The implementation has been verified and promoted to established status. Applied during the promote workflow (/explain drift --promote). Established items have been confirmed to match the as-coded state.

The promote workflow is split into two phases: Phase 3a generates decision entry proposals for each promoted item, and Phase 3b flips the STATUS markers via apply_marker.py. Decision entries follow a DDR-shaped format with stable D-NNN IDs in a namespace orthogonal to REQ IDs.

End-to-End Traceability

The full traceability chain connects five layers:

  1. Design intent: REQ markers in product-design/product-design-as-intended.md.
  2. Plan: Traces fields in plan steps reference specific REQ IDs.
  3. Implementation: Each plan step produces committed code with a plan-referencing commit message.
  4. Verification: /explain drift compares as-intended with as-coded state and proposes STATUS marker updates.
  5. Decision record: Promoted items generate D-NNN decision entries that document why the implementation took the form it did.

This chain ensures that no design requirement silently disappears and no implementation exists without a traced rationale.

Common Mistakes

Writing vague step descriptions
Each step must be self-contained -- executable by a subagent that has not read any other step. Descriptions like "finish the API" or "update the tests" lack the context a fresh subagent needs. Include what the code should do, which file to edit and why, and what the expected outcome looks like. The rule of thumb: if a colleague who has never seen the plan could execute the step from its description alone, it is specific enough.
Skipping the Verify field
The Verify field is required on every step. It defines the concrete condition that confirms the step succeeded. Without it, neither the auto-mode subagent nor the manual-mode designer has an objective way to know when the step is done. Prefer automated checks ("tests pass", "migration runs forward and backward", "endpoint returns 200") over subjective ones ("looks correct"). A missing or vague Verify field will be caught by the step metadata validation during plan review.
Not checking file existence during planning
The Files field must list every path the step reads, creates, modifies, or deletes. For existing files, those paths must be verified on disk during planning -- not assumed. A plan that references a file path that does not exist will cause the implementing subagent to fail or create files in the wrong location. The plan review's step metadata validation checks existing-file paths, but only if they are listed. Unlisted files are invisible to the validator.
Implementing without a plan
The SEJA lifecycle requires a plan before implementation. The design guard in /plan verifies that project design exists; CLAUDE.md instructs the agent to check for existing plans before coding. Skipping the plan means losing the review process, the traceability chain, the progress file's cross-iteration context, and the rollback branch. For trivially small changes, use /plan --light (lightweight proposal) rather than skipping planning entirely.
Not committing the plan before implementing
The plan must be a committed git artifact before /implement runs. The /plan skill handles this automatically via /post-skill, but if you interrupt the plan generation after saving but before the post-skill commit, the plan file exists on disk but is not versioned. If the session is lost, the plan may be lost too. Always let the post-skill step complete before closing the session.
Confusing the five-file rule with a hard limit
The decomposition guideline says each step should touch "5 or fewer files." This is a rule of thumb for staying within a subagent's context window, not a validation error. Steps that read 6 files but modify only 2 are typically fine. Steps that modify 8 files should be split. The plan review flags steps that touch more than 5 files, but the planner can override with justification.
Setting Traces fields for steps that do not implement requirements
The Traces field links a step to specific REQ IDs from the as-intended file. Not every step traces to a requirement -- infrastructure setup, test configuration, and refactoring steps often have no REQ connection. Adding incorrect Traces values pollutes the coverage check and creates false traceability. When no requirement applies, omit the Traces field entirely rather than guessing.
