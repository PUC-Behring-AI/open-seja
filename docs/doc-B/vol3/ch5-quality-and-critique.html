Quality and Critique

The /critique skill is SEJA's unified quality gate -- ten modes covering validation, code review, smoke tests, preflight checks, harness health, test plan generation, documentation consistency, git freshness, telemetry analysis, and semiotic inspection. This chapter explains the critique system's role in the lifecycle, documents each mode and the review perspectives they use, and shows how to interpret and act on results.

The Critique System

In SEJA's canonical lifecycle -- /research or /explain, then /design or /plan, then /implement, then /critique, then /document or /communicate, and finally /reflect -- critique occupies a gatekeeping position between implementation and outward-facing artifacts. The principle is simple: validate before you communicate. No documentation should be generated, no stakeholder material produced, and no release cut until the work has passed through one or more critique modes.

Why Critique Is a Separate Skill

Critique is not embedded in /implement because evaluation and construction are distinct cognitive activities with different concerns. Implementation asks "does this code do what the plan says?" Critique asks a broader set of questions: does the implementation conform to the project's validation rules? Does it introduce security vulnerabilities, accessibility regressions, or performance hazards? Is the harness itself healthy? Are the project's branches up to date with their upstreams? Separating these concerns into a dedicated skill with ten specialized modes allows each mode to apply focused expertise without overloading the implementation context.

Ten Modes, One Skill

All ten modes share a common execution pattern: pre-skill invocation loads the project context, the mode-specific logic runs its analysis, and the results are saved to the critique logs directory (with one exception: telemetry is read-only and produces no log file). The modes are mutually exclusive -- each invocation runs exactly one mode. Here is the full inventory:

Mode Purpose Saves Log
validate Run project validation scripts against code standards Yes
review Structured code review against 16 quality perspectives Yes
smoke Runtime smoke tests for API and UI Yes
preflight Combined validate + review as a pre-merge checkpoint Yes
health Harness self-diagnosis across 9 built-in checks Yes
test-plan Generate a structured manual test plan Yes
docs Documentation consistency check via plugin scanners Yes
freshness Compare local branches to upstreams; advisory-only Yes
telemetry Usage analytics from telemetry data No
semiotic-inspection SIM-based communicability evaluation of interfaces Yes

Shared Execution Pattern

Every mode follows three common steps (with minor variations noted per mode):

C1. Pre-skill
Invokes /pre-skill "critique" with the mode and scope arguments to load references, check the budget, and establish the project context in the agent's working memory.
C3. Reserve ID and save report
Reserves a globally unique ID via reserve_id.py, then writes the critique report to the critique logs directory with a standardized header and mode-specific body.
C4. Present and post-skill
Presents the summary to the user, highlighting failures and high-severity findings, then runs /post-skill for lifecycle completion (DONE marking, git commit, decision flush).

Two modes add a stack-filtering step (C2) between C1 and C3: validate and preflight read the project's backend and frontend framework settings from product-design/conventions.md and run only the validation scripts that match the project's stack.

Critique Modes

Each mode is invoked as /critique <mode> [scope] [flags]. This section documents every mode's purpose, scope options, what it checks, and what it produces.

validate

Runs project validation scripts and aggregates results into a compliance report.

AspectDetail
Scope options all (default), i18n, auth, migrations, constants, po, coverage, tests, spec
What it checks Dispatches to the standards-checker agent, which runs all applicable check scripts from the plugin registry. Stack filtering (C2) ensures only scripts matching the project's backend/frontend frameworks execute. The migrations scope additionally launches the migration-validator agent for deep inspection and idempotency checks. The tests scope launches the test-runner agent. The spec scope runs spec conformance checking directly.
Output Validation report with a summary table (check name, status PASS/FAIL/INFO, error count, warning count), per-failure details, and an overall "X/Y checks passed" verdict.

review

Structured code review against quality perspectives, with depth-gated evaluation.

AspectDetail
Scope options staged (default -- reviews git diff --cached), a file path, or a directory path
Depth flag --depth <light|standard|deep>. At light and standard, the reviewer selects 4-6 relevant perspectives via the two-stage loading protocol. At deep, all 16 perspectives are evaluated. The effective depth is max(floor, flag) where the floor comes from MINIMUM_REVIEW_DEPTH in product-design/conventions.md. With no --depth flag, all 16 perspectives are evaluated (equivalent to deep).
What it checks Launches the code-reviewer agent, which follows the two-stage loading protocol: loads the perspective index, selects relevant perspectives based on change content, loads only those perspective files, and evaluates the diff against each one. See Review Perspectives and The Two-Phase Review Process below.
Output Code review report with a perspective evaluation table (each perspective marked Adopted, Deferred, or N/A), prioritized issues (severity, perspective tag, description, file:line), and recommendations.

smoke

Runtime smoke tests that exercise API endpoints and UI pages to catch basic functionality regressions.

AspectDetail
Scope options all (default), api, ui
What it checks API: runs smoke_test_api.py against in-memory SQLite via the Flask test client -- no servers required. Endpoints are driven by .claude/skills/scripts/smoke_test_registry.json. UI: runs e2e/smoke.spec.ts via Playwright (requires backend on port 5000 and frontend on port 3000). All: runs API first (faster, independent), then UI if the E2E spec exists.
Output Smoke test report with API results table and/or UI results table, captured errors, and an overall PASS/FAIL verdict. On failure, offers to investigate and fix, create a plan, or dismiss.

preflight

Combined validate + review in a single pre-merge checkpoint. The go/no-go verdict tells you whether the branch is ready to merge.

AspectDetail
Scope options staged (default -- validate all + review staged), all (validate all + review all modified), or a directory path (validate all + review files in that directory)
What it checks Parallel fan-out: launches standards-checker (validation, stack-filtered), code-reviewer (review at the resolved scope), and optionally smoke tests (if the plan's smoke flag is true) as concurrent operations. If one check fails, the others still complete -- preflight never aborts early.
Output Preflight report with validation summary table, code review perspective table, merged issues prioritized by severity, and an overall status: READY only if all validation checks pass and no HIGH-severity review issues exist; otherwise NOT READY.

health

Harness self-diagnosis that verifies the integrity of the SEJA installation itself.

AspectDetail
Scope options None (runs all 9 checks). Supports --verbose for detailed output and --source <path> to enable harness drift detection against a canonical source directory.
What it checks 9 built-in diagnostic checks: (1) skill system integrity, (2) orphaned briefs, (3) stale plans, (4) reference file completeness, (5) conventions completeness, (6) constitution presence, (7) skill spec compliance, (8) pending ledger summary, (9) harness drift (when --source is provided).
Output Harness health report with per-check PASS/FAIL/WARN status, details for each failing check, and an overall health summary.

test-plan

Generates a structured manual test plan from a brief or from recently completed plans.

AspectDetail
Scope options A text brief describing what to test. If omitted, the skill asks the user.
What it produces Launches the test-plan-generator agent, which reads completed plans, carries unchecked items forward from prior test plans, and produces a test plan with scenarios, step-by-step instructions, expected results, and edge cases. Each to-do is phrased as a command to the user.
Output Test plan file saved to the user-tests directory with a usertest-NNN ID.

docs

Documentation consistency checker powered by plugin-based scanners.

AspectDetail
Scope options --plugins LIST (default: all), --verbose (show passing and detail), --filter SEVERITY (error, warning, or info; default info)
What it checks Runs check_docs.py, whose plugin scanners include harness-integrity, path-liveness, env-vars, command-refs, terminology, and structural-completeness. Each plugin scans documentation files for specific consistency issues.
Output Documentation consistency report with error/warning/info counts, per-plugin findings grouped by severity, and an overall PASS or ISSUES FOUND status.

freshness

Compares local branches to their upstream counterparts. Advisory only -- it never pulls or pushes automatically.

AspectDetail
Scope options Implicit (configured repos): the workspace root plus the codebase directory when it is absolute and distinct.
What it checks Runs check_git_freshness.py --json and parses per-repo data: branch name, upstream, ahead/behind counts, and fetch status. Suggests appropriate next actions (pull, push, or rebase) based on divergence state.
Output Git freshness report with per-repo sections showing branch status, ahead/behind counts, and suggested actions. Includes the raw JSON payload for downstream tooling.

telemetry

Read-only usage analytics. The only mode that does not reserve an ID or write a critique log file.

AspectDetail
Scope options None.
What it checks Runs generate_telemetry_report.py and displays the resulting markdown directly. Reports skill invocation counts, usage patterns, and session statistics from telemetry.jsonl.
Output Markdown displayed to the user. No file saved, no post-skill invoked.

semiotic-inspection

Conducts a Semiotic Inspection Method (SIM) evaluation of an interface's communicability -- how effectively the designer's intent is communicated to users through the interface.

AspectDetail
Scope options A feature name, page, user flow, or all. If omitted, the skill asks the user.
What it checks Launches the semiotic-inspector agent, which reconstructs the designer's metacommunication message across three sign classes: metalinguistic signs (explicit help text, labels, tooltips), static signs (layout, visual hierarchy, affordances at rest), and dynamic signs (responses to user interaction, state transitions, feedback). The agent collates these three partial messages, applies 5 scaffold questions and 4 SigniFYIng Interaction dimensions, and produces a communicability judgment.
Output Semiotic inspection report with per-sign-class analysis, collated metacommunication message, communicability risks, and recommended improvements.

Review Perspectives

The review and preflight modes evaluate code changes against 16 perspectives organized into two groups (engineering and design) and classified into tiers that determine when they are loaded into the review context.

The Sixteen Perspectives

SEJA defines sixteen review perspectives -- eleven engineering and five design lenses. A review does not evaluate all sixteen every time: the two-stage loading protocol selects a shortlist (typically three to six) from the Perspective Shortcuts by Plan Prefix table, adding others when the change content warrants. Selection is driven by the change at hand, not by a fixed ranking of the perspectives themselves. Within each selected perspective, the questions are tiered by priority -- Essential (P0), Standard (P1-P2), and Deep (P3-P4) -- as the next section details: at standard depth reviewers focus the Essential and Standard questions, escalating to the Deep questions for exhaustive analysis.

Tag Name Group Scope
SEC Security Engineering Auth, input validation, secrets, dependency vulnerabilities
ARCH Architecture Engineering Layer boundaries, separation of concerns, dependency direction
DB Database Engineering Schema migrations, backward compatibility, idempotency
DX Developer Experience Engineering Readability, conventions, documentation, error messages
I18N Internationalization Engineering i18n keys, locale support, pluralization, RTL, date/number formats
TEST Testability Engineering Test coverage, mocking strategy, test isolation
UX User Experience Design User flows, feedback, error handling, navigation, discoverability
A11Y Accessibility Design WCAG AAA, contrast, keyboard nav, screen readers, focus management
PERF Performance Engineering N+1 queries, unbounded loops, indexes, caching, bundle size
API API Design Engineering RESTful conventions, route consistency, request/response contracts
OPS Operations / DevOps Engineering Environment parity, logging, monitoring, deployment, config management
COMPAT Compatibility Engineering API contract stability, schema evolution, browser/version support
DATA Data Integrity and Privacy Engineering PII handling, GDPR compliance, validation, audit trails
VIS Visual Design Design Design system consistency, CSS conventions, spacing, typography
RESP Responsive Design Design Mobile/tablet/desktop breakpoints, fluid layouts, touch targets
MICRO Microinteractions Design Hover/focus/active states, transitions, loading indicators, animations

Priority Levels Within Perspectives

Each perspective file contains questions classified by priority. Under time or context pressure, reviewers focus on P0-P1 first:

[P0] Critical
Blocking questions -- these must be addressed before merging. A P0 finding at HIGH severity in a preflight check produces a NOT READY verdict.
[P1] Important
Should be addressed in this iteration. Deferral requires documented rationale.
[P2] Standard
Good-practice checks. May be deferred with brief justification.
[P3] Beneficial
Nice-to-have improvements. Typically deferred unless the perspective is the primary focus of the review.
[P4] Informational
Advisory observations. No action required.

Perspective Status Vocabulary

When reporting on each perspective, the reviewer assigns one of three statuses:

Adopted
The perspective was evaluated and all concerns were addressed (or no concerns were found).
Deferred
The perspective was evaluated but one or more concerns were not addressed in this iteration. The review states why and notes the trade-off.
N/A
The perspective does not apply to this change (e.g., a backend-only change marks RESP and MICRO as N/A).

The Two-Phase Review Process

Loading all 16 perspective files into context for every review would consume significant token budget without proportional benefit -- a database migration does not need the Microinteractions checklist. The two-phase review process keeps context lean while ensuring thorough coverage.

Phase 1: Perspective Triage and Scan

The reviewer loads the compact perspective index (under 600 tokens) and selects 4-6 perspectives relevant to the change. Selection can follow two paths:

Prefix-based shortlists
Plans carry a prefix-scope code (such as FEATURE-B for a backend feature or FIX-F for a frontend fix) that maps to a default set of perspectives. The reviewer loads the shortlisted perspectives and may add up to 2 additional ones if the change content warrants it.
Content-based selection
When no plan prefix is available (e.g., reviewing an ad-hoc diff), the reviewer inspects the change content -- which files are touched, what patterns appear -- and selects perspectives accordingly. A change touching backend/auth/ and backend/models/ would naturally pull in SEC, DB, and ARCH.

After selecting perspectives, the reviewer loads only those perspective files from .claude/references/general/review-perspectives/ and scans the diff against each one's Essential (P0) questions.

Phase 2: Targeted Deep-Dives

When the Phase 1 scan identifies a concern, the reviewer examines the Standard (P1-P2) and Deep (P3-P4) questions for that perspective. This is targeted -- the reviewer does not deep-dive into all selected perspectives, only those where the P0 scan raised a flag or where the change content warrants closer examination.

At --depth deep (or when the reviewer runs without a depth flag), all 16 perspectives are loaded and their full question sets are evaluated. This is the most thorough mode but also the most context-intensive.

Convergence

The review converges when all selected perspectives have been evaluated and each has a status (Adopted, Deferred, or N/A). The final report lists all perspectives in a table, followed by a prioritized list of findings (HIGH first, then MEDIUM, then LOW). Each finding names the responsible perspective, the file and line, and a description of the concern.

Conflict Resolution

Perspectives can conflict -- a performance optimization might weaken security, or a visual-design choice might harm accessibility. The review framework defines a priority order for resolving these tensions:

SEC wins by default
Security concerns take priority over all other perspectives unless the user explicitly accepts the risk.
A11Y is non-negotiable
Accessibility is never traded against visual design or performance. A change that improves aesthetics but degrades keyboard navigation is not acceptable.
Document the trade-off
When a conflict is resolved, the review records both the chosen approach and the deferred concern with rationale.
Ask when unclear
For non-default conflicts (e.g., PERF vs DX where neither has automatic priority), the reviewer asks the user to decide.

Interpreting Results

Critique reports follow consistent formatting across modes. Here is how to read the most common output types and decide what to act on.

Reading Validation Output

A /critique validate report contains a summary table where each row is one check script. Look at the status column first:

PASS
The check ran successfully with no issues. No action needed.
FAIL
The check found violations. Scroll to the per-failure details section to see the specific file, line, and rule that was violated. These should be fixed before merging.
INFO
The check produced advisory information that does not block the build. Read it for awareness, but no immediate action is required.

The overall verdict ("X/Y checks passed") tells you at a glance whether the validation gate is clear.

Reading Review Logs

A /critique review report has two main sections:

Perspective evaluation table
Scan for any Deferred entries -- these are perspectives where a concern was identified but not addressed. The "Notes" column explains why. If the deferral reason is "out of scope for this change," that is typically acceptable. If it is "needs architectural discussion," consider filing a follow-up plan.
Findings list
Findings are prioritized by severity. Focus on HIGH findings first -- these indicate risks that should be resolved before merging. MEDIUM findings are significant but may be deferred with documented rationale. LOW findings are advisory.

Reading Preflight Reports

A /critique preflight report merges validation and review results. The overall status tells you the answer:

READY
All validation checks passed and no HIGH-severity review findings exist. The branch is safe to merge.
NOT READY
Either a validation check failed or a HIGH-severity review finding exists. Read the merged findings section to understand what needs fixing.

What to Fix vs. What to Defer

Not every finding requires immediate action. Use this decision framework:

Fix now
HIGH-severity findings, any FAIL in validation, and any SEC or A11Y concern regardless of severity. These block a clean merge.
Fix in this iteration
MEDIUM-severity findings where the fix is straightforward and contained. Addressing them now avoids technical debt.
Defer with a plan
MEDIUM findings that require architectural changes or cross-cutting work. File a follow-up plan with /plan so the deferral is tracked.
Accept as advisory
LOW-severity findings and informational observations. Read them for awareness. If a pattern of LOW findings accumulates across multiple reviews, consider a cleanup pass.

Common Mistakes

Running review without reading the diff
Launching /critique review and reading only the summary verdict misses the point. The perspective evaluation table and the individual findings carry the actionable detail. Before running review, look at the diff yourself (git diff --cached for staged changes) so you can evaluate whether the review's findings match your own understanding. A review is a conversation partner, not an oracle.
Ignoring Deferred findings
When a perspective is marked Deferred, it means a concern was identified and deliberately not addressed. If you treat Deferred the same as N/A -- skipping the notes column entirely -- you lose track of known technical debt. Deferred findings should be either filed as follow-up plans (via /plan) or explicitly accepted with rationale in the review record. A pattern of silently deferred findings across multiple reviews signals that the review depth may be too ambitious for the project's current pace.
Skipping preflight before merge
Relying on /critique validate alone before merging misses the review half of the quality gate. /critique preflight exists precisely to combine both validation and review in a single pass. The extra time it takes (a few minutes) is far less than the time spent debugging an issue that a review perspective would have caught. Make preflight the default pre-merge checkpoint.
Treating advisory findings as blocking
LOW-severity findings and INFO-level validation results are advisory -- they surface patterns worth knowing about but do not indicate defects. Treating every advisory finding as a blocker leads to over-engineering and slows iteration. Conversely, a single HIGH finding is blocking, even if every other perspective shows Adopted. Calibrate your response to the severity level, not to the count of findings.
Running critique without a plan
If you run /critique review on changes that were not guided by a plan, the review has no plan prefix to use for perspective shortlisting and no design intent to evaluate against. The review still works -- it falls back to content-based perspective selection -- but it lacks the anchor that makes findings actionable. Whenever possible, follow the lifecycle: plan first, implement, then critique.
Confusing health with validate
/critique health checks the harness itself -- whether skills are intact, references are complete, and the constitution is present. /critique validate checks your project's code against its own validation rules. They answer different questions. Running health when you meant validate (or vice versa) wastes time and produces irrelevant results. Health is about harness integrity; validate is about code compliance.
