Subagent Delegation

This chapter documents how skills delegate work to specialized subagents, provides a per-agent reference for all 16 agents (9 evaluators and 7 generators), and explains how to write custom subagents.

The Delegation Model

Skills in the SEJA harness follow a delegation pattern: when a skill needs specialized analysis or content generation, it launches a subagent rather than performing the work inline. The skill acts as an orchestrator -- it parses arguments, manages lifecycle hooks, and presents results -- while the subagent does the deep, focused work. This separation keeps the orchestrator lean and lets the subagent concentrate entirely on its domain without the overhead of lifecycle management.

Why Delegate

Delegation solves two problems at once. First, specialized agents can focus deeply on one task -- reviewing code against 16 engineering perspectives, generating a stakeholder communication, or running a structured council debate -- without their context window being consumed by lifecycle hooks, argument parsing, pending-ledger checks, and other orchestration concerns. Second, the main conversation context stays clean: the detailed intermediate analysis (raw diff parsing, per-perspective evaluation notes, codebase scanning) lives in the subagent's context window and never pollutes the caller's. Only the final result -- a structured report, a generated document, or a pass/fail verdict -- flows back.

The Trust Boundary

Each subagent operates in a fresh context window with no inherited state from the calling skill. The subagent does not see the conversation history, does not know what the user said before the skill was invoked, and does not have access to any variables or in-memory structures from the orchestrator. This is a trust boundary: the subagent can only act on what the skill explicitly passes in its prompt.

This boundary is intentional. It ensures that subagent behavior is reproducible (the same prompt produces the same analysis regardless of conversation history) and that the subagent cannot accidentally leak context from unrelated parts of the session. It also means that the skill must be disciplined about what it includes in the prompt -- everything the subagent needs must be there, because nothing else will be.

Prompt Construction

When a skill delegates to a subagent, it constructs a self-contained prompt that includes everything the subagent needs to do its work. The prompt typically contains:

  • The agent's role and instructions (read from its prompt file in .claude/agents/)
  • The specific inputs for this invocation (e.g., the diff to review, the question to research, the audience segment to generate for)
  • File paths the agent should read for context (project conventions, design files, review perspectives)
  • The output path where the agent should write its result
  • Any configuration parameters (review depth, output format, scope constraints)

The skill uses the Agent tool to launch the subagent, specifying the subagent_type parameter to select the appropriate agent definition. The agent prompt file (in .claude/agents/) becomes the agent's system-level instructions, and the skill's constructed prompt provides the task-specific context.

Result Processing

When the subagent completes, the skill reads the agent's output -- typically a structured report written to a file path the skill specified. The skill then integrates this result into the broader workflow: presenting it to the user, appending it to a plan file, feeding it into subsequent lifecycle steps, or using it to gate further actions (e.g., the quality gate in /implement uses the code-reviewer's findings to decide whether to proceed).

The skill does not blindly trust the subagent's output. It validates that the expected output file was created, checks for expected structure, and handles failure cases (agent error, timeout, missing output) gracefully -- typically by reporting the failure and continuing with the remaining checks.

Agent Prompt Files

Every subagent in the harness is defined by a Markdown prompt file in the .claude/agents/ directory. These files are the single source of truth for what each agent does, how it behaves, and what tools it has access to.

File Format

Each agent prompt file follows a consistent structure:

  1. YAML frontmatter -- metadata enclosed in --- delimiters, containing the agent's name, description, designer description, and available tools.
  2. Markdown body -- the agent's full instructions, including its role definition, input specification, process steps, and output format.

The YAML frontmatter fields are:

Field Purpose
name The agent's identifier, matching the filename without the .md extension (e.g., code-reviewer).
description A concise, agent-facing summary of the agent's role (used in tool listings and dispatch).
designer_description A human-facing narrative explaining what the agent does and why, written in second person ("When you hand me a diff...").
tools Comma-separated list of tools the agent may use (e.g., Read, Bash, Glob, Grep).

The Markdown body typically contains these sections:

  • Role statement -- a one-sentence declaration of the agent's purpose (e.g., "You are a code reviewer.").
  • Input -- what the invoking skill passes and in what format.
  • Process -- the step-by-step procedure the agent follows.
  • Output Format -- the expected structure of the agent's result.

Location and Naming

All 16 agent prompt files live in .claude/agents/. The filename is the agent's kebab-case name with a .md extension. The harness organizes agents into two categories:

  • Evaluator agents (9 files) -- review artifacts against quality perspectives and return structured findings.
  • Generator agents (7 files) -- produce self-contained artifacts (documents, reports, plans) from well-defined inputs.

There is also a third pattern -- executor agents -- used by /implement in auto mode. These are not standalone prompt files; the implement skill constructs their prompts dynamically from plan step metadata. See Plans and Implementation for details.

Evaluator Agents

Evaluator agents review artifacts -- code changes, plans, research questions, migration chains, harness configuration -- against quality perspectives and return structured findings. They read, analyze, and judge; they do not create new project artifacts. All 9 evaluator agents are invoked by the /critique skill (in its various modes), and some are also invoked by /plan, /research, and /implement. See Skills In Depth for which skills invoke each agent and under what conditions.

code-reviewer

Reviews code changes against engineering and design perspectives, reporting findings with Adopted/Deferred/N/A status per perspective.

Inputs A file path, directory, the word "staged" (for git diff --cached), or raw diff output; an optional review depth (light, standard, or deep).
Outputs A structured review report with a per-perspective evaluation table (Adopted/Deferred/N/A per perspective), categorized findings with severity (HIGH/MEDIUM/LOW), file paths, and line numbers.
Invoked by /critique review, /critique preflight (parallel fan-out).

The code-reviewer uses a two-stage loading protocol for review perspectives: it reads the perspective index first, selects 4-6 relevant perspectives based on the change content, then loads only those perspective files. In deep mode, all 16 perspectives are evaluated. A vulnerability pre-scan checks for dangerous patterns (injection, XSS, deserialization, template injection) before the full perspective pass.

council-debate

Runs a structured expert council debate for high-stakes design decisions, surfacing trade-offs through position statements and cross-examination.

Inputs The question or decision to debate; optional council members from the brief-specific pool (0-2); optional context pointers (file paths, design docs, prior analysis).
Outputs A debate transcript with position statements from 5-7 expert archetypes, cross-examination exchanges, areas of agreement and tension, and a recommended path that names the trade-offs.
Invoked by /research --deep.

The council always includes five fixed archetypes (Security Advocate, DX Pragmatist, UX Champion, Architecture Purist, Product Strategist) plus 0-2 brief-specific experts selected by the caller (Agentic AI Expert, Data Engineer, DevOps/Platform Engineer, or Domain Specialist).

harness-health-evaluator

Runs 9 built-in harness self-diagnosis checks and produces a Harness Health Report with PASS/WARN/FAIL status per check.

Inputs A reserved check-NNN ID; the target output path; an optional verbose flag; an optional source path for the harness drift check.
Outputs A Harness Health Report with a nine-row status table (PASS/WARN/FAIL per check) and an overall N/9 tally. Checks cover: skill system integrity, orphaned briefs, stale plans, reference file completeness, conventions completeness, constitution presence, skill spec compliance, pending ledger summary, and harness drift.
Invoked by /critique health.

When the source input is provided, the drift check compares the canonical harness root against the target project. When omitted, the drift check reports INFO status and does not count toward the pass/total tally (N/8+1 instead of N/9).

migration-validator

Validates Alembic migration chain integrity, checks for idempotency issues, PostgreSQL syntax problems, and common migration pitfalls.

Inputs all (full chain validation), a specific migration file path, or recent (migrations since last tagged release).
Outputs A validation report covering chain integrity (broken links, cycles, orphaned migrations, multiple heads) and per-file inspection (non-idempotent operations, syntax issues, foreign-key type mismatches, data-loss risks in downgrade paths). Findings are separated into must-fix, warnings, and best-practice suggestions.
Invoked by /critique validate (with migrations scope).

The migration-validator reads project conventions to locate the migrations directory, ORM model definitions, and the chain validation script. It performs both automated chain checking (via the script) and deep file-by-file inspection.

plan-reviewer

Reviews a plan against engineering and design perspectives using the complexity-gated two-phase review process.

Inputs The full plan text (header, actions, and to-do); the plan file path; the review depth (Light, Standard, or Deep).
Outputs A review log with Adopted/Deferred/N/A status per perspective, one-line concerns, and any concrete amendments the plan should absorb before implementation.
Invoked by /plan (Standard and Deep complexity).

The plan-reviewer uses the same two-stage perspective loading protocol as the code-reviewer. Phase 1 performs a triage scan across the shortlisted perspectives. For Light reviews, it stops there. For Standard and Deep reviews, Phase 2 performs targeted deep-dives on deferred concerns that could cause regressions or incidents.

research-reviewer

Evaluates design decisions, open-ended questions, and trade-offs against engineering and design perspectives.

Inputs The question, decision, or trade-off to evaluate; optional context file paths; an optional review depth (light, standard, or deep).
Outputs A structured analysis with a per-perspective status table, detailed evaluation per perspective, and prioritized recommendations with trade-offs.
Invoked by /research (standard mode, without --deep).

Unlike the code-reviewer (which operates on diffs) and the plan-reviewer (which operates on structured plans), the research-reviewer handles open-ended questions and recommendations that do not have a fixed artifact structure.

semiotic-inspector

Conducts a Semiotic Inspection Method (SIM) evaluation of a project's interface communicability across metalinguistic, static, and dynamic sign classes.

Inputs A scope string (feature name, page, user flow, or all); a reserved check-NNN ID; the target output path.
Outputs A SIM report with per-sign-class analysis (metalinguistic, static, dynamic), independent metacommunication reconstructions, collation of agreements and contradictions, and a communicability judgment.
Invoked by /critique semiotic-inspection.

The semiotic-inspector reads the project's metacommunication files to establish the designer's intended message, constructs inspection scenarios from user personas and goal-directed activities, then analyzes each sign class independently before collating the findings. This agent implements the formal SIM methodology from semiotic engineering research.

standards-checker

Runs all project validation scripts and aggregates results into a unified compliance report.

Inputs all (run every validation script) or a specific check name matching an entry in the project's Validation Scripts table (e.g., i18n, auth, migrations, constants).
Outputs A unified compliance report with a pass/fail summary table across all checks, error and warning counts, and specific issues with file and line references.
Invoked by /critique validate, /critique preflight (parallel fan-out).

The standards-checker reads the Validation Scripts table from product-design/conventions.md to discover which scripts to run. It executes each script, captures stdout and stderr, strips ANSI escape codes, and parses the output for pass/fail status, error counts, and specific issues.

test-runner

Runs backend and frontend test suites and reports failures with actionable context.

Inputs all (both suites), backend, frontend, integration, or a specific test file path.
Outputs A test summary with pass/fail/skip counts and, for each failure, the file, test name, error message, classification (test bug, source bug, environment issue, or flaky), and a suggested next step.
Invoked by /critique smoke, /implement (quality gate).

The test-runner reads test commands from product-design/conventions.md (variables like BACKEND_TEST_CMD, FRONTEND_TEST_CMD) and dispatches to the appropriate runner (pytest for backend, vitest for frontend). It classifies each failure to help the developer prioritize fixes.

Generator Agents

Generator agents produce self-contained artifacts -- documents, reports, onboarding plans, communication material -- from well-defined inputs. Unlike evaluator agents, which judge existing artifacts, generator agents create new ones. All generator agents receive the project constitution as part of their prompt to enforce trust boundary constraints during generation. See Skills In Depth for the skills that invoke each generator and their full workflow context.

communication-generator

Generates tailored stakeholder communication material for a specific audience segment.

Inputs An audience tag (EVL, CLT, USR, or ACD); the audience reference file path; the Diataxis mapping file path; project context paths (conceptual design, conventions, communication style); output path and ID; format (md, html, or both); a deep flag; an optional source file to reformat.
Outputs A Markdown and/or HTML communication document tailored to the target audience's tone, register, and content expectations. No meta-commentary or internal notes.
Invoked by /communicate.

The communication-generator loads the audience-specific content guidance (tone, depth, vocabulary), the project's identity and value proposition from the conceptual design, and the communication style overrides. It produces material that speaks in the register the target audience expects.

onboarding-generator

Generates tailored onboarding plans for new team members based on role family and expertise level.

Inputs Role tags (BLD, SHP, and/or GRD); expertise level (L1- L3); optional member name and focus area; role and level file paths; project context paths; output path and ID; format.
Outputs A personalized onboarding plan with a welcome, a day-one universal foundation, role- and level-specific weekly milestones, a 30-60-90 day timeline, and a prioritized reading list referencing actual project files.
Invoked by /onboard.

The onboarding-generator scans the actual codebase (using the backend and frontend directories from conventions) to provide concrete file references rather than generic advice. It supports three role families (Builders, Shapers, Guardians) and three expertise levels (Contributor, Expert, Leader).

document-generator

Generates or updates project documentation for a specific documentation type.

Inputs A doc type (readme, contextual-help, api-reference, ddr, help-center, changelog); scope (file path, module, feature name); template path; quality guide path; project context paths; output path; optional plan context.
Outputs A documentation artifact matching the target doc type's template, Diataxis classification, and quality standards. Content is sourced from the actual codebase, not generic filler.
Invoked by /document, /publish (for changelog auto-generation).

The document-generator reads the appropriate template from .claude/references/template/docs/, the documentation quality writing guide, and the project's conventions and conceptual design. It supports parallel generation when multiple doc types are requested.

test-plan-generator

Generates structured manual test plans from a user-supplied brief and the most recent completed plans.

Inputs A test brief string; a reserved usertest-NNN ID; the target output path; optional overrides for plan and user test directories.
Outputs A manual test plan with a header, user brief, agent interpretation, and a to-do enumeration of plan steps phrased as imperative commands with expected outcomes. Carries forward unchecked items from prior test reports.
Invoked by /critique test-plan.

The test-plan-generator reads the global artifact index to find recently completed plans relevant to the brief, then phrases each step as a command the user can walk through by hand (e.g., "Navigate to X; do A, check B. The expected outcome is O").

explanation-generator

Generates explanation reports for the behavior, code, and data-model modes of the /explain skill.

Inputs A mode (behavior, code, or data-model); the user's brief or scope description; the output path; the reserved artifact ID.
Outputs An ID-stamped explanation report. Behavior and data-model reports use a conversational, user-centered voice with roles, goals, activities, and analogies. Code reports target junior developers learning the stack.
Invoked by /explain behavior, /explain code, /explain data-model.

The explanation-generator dispatches on the mode to determine the output directory, filename convention, header label, and voice. It reads the project constitution and applies its constraints throughout generation.

architecture-explainer

Generates architecture explanation reports covering system structure, component boundaries, communication patterns, and design trade-offs.

Inputs The user's brief or scope description; the output path; the reserved artifact ID; an optional scope to focus on a specific component or subsystem.
Outputs An architecture explanation report aimed at onboarding developers, focusing on the "why" behind architectural decisions. Covers the full system when unscoped, or a specific component and its dependencies when scoped.
Invoked by /explain architecture.

The architecture-explainer uses a multi-phase workflow: survey the system (read CLAUDE.md, conventions, scan directories), identify major components and their relationships, then write the report with trade-offs and multiple analogies for complex concepts.

evolution-explainer

Generates behavior-evolution explanation reports tracing how a feature reached its current state through plan history.

Inputs The user's brief (the feature area to trace); the output path; the reserved artifact ID.
Outputs A behavior-evolution report with a current behavior snapshot and a full evolution timeline showing waves of change, design rationale, and how the feature morphed across plans.
Invoked by /explain behavior-evolution.

The evolution-explainer mines the plan history by reading the global artifact index, filtering plan IDs whose title or prefix-scope touches the feature area, reading the full plan files, sorting chronologically, and building a timeline that tells the story of how the feature evolved.

Writing Custom Subagents

You can extend the harness with custom subagents by adding new prompt files to .claude/agents/. Each file defines a new agent type that skills can delegate to.

Step 1: Create the Prompt File

Create a new Markdown file in .claude/agents/ with a descriptive kebab-case name (e.g., .claude/agents/my-custom-agent.md). The filename (without extension) becomes the agent's identifier.

Step 2: Write the Frontmatter

Add YAML frontmatter with the required fields: 

---
name: my-custom-agent
description: One-line summary of what this agent does.
designer_description: "When you hand me X, I do Y and return Z."
tools: Read, Glob, Grep
---

Choose the minimal set of tools the agent needs. Common combinations:

  • Read, Glob, Grep -- read-only analysis agents
  • Read, Glob, Grep, Bash -- agents that run scripts or commands
  • Read, Glob, Grep, Write -- agents that produce output files
  • Read, Bash, Glob, Grep, Write -- agents that both run commands and write output

Step 3: Write the Body

The Markdown body defines the agent's behavior. Follow this structure: 

# My Custom Agent

You are a [role]. Your task is to [purpose].

## Input

You will receive:
- **item_a**: description of first input
- **item_b**: description of second input

## Process

1. [First step]
2. [Second step]
3. [Third step]

## Output Format

[Describe the expected output structure]

Step 4: Invoke from a Skill

To use the new agent, the invoking skill launches it via the Agent tool with subagent_type set to the agent's name: 

Agent({
  subagent_type: "my-custom-agent",
  prompt: "[self-contained prompt with all needed context]"
})

The agent prompt file content becomes the agent's system-level instructions. The prompt parameter provides the task-specific inputs. Remember: the agent starts with a fresh context window, so the prompt must include everything the agent needs -- file paths to read, scope constraints, output expectations.

Tip: Before creating a new agent, check whether an existing agent already covers your use case. The 16 built-in agents cover most common patterns. A new agent is warranted when you need a fundamentally different analysis workflow or output format that the existing agents cannot accommodate.

Common Mistakes

Passing too little context to a subagent
Mistake: Assuming the subagent can see the conversation history or infer context from prior interactions.
Consequence: The subagent produces generic or incorrect output because it lacks the project-specific information it needs.
Avoidance: Treat every subagent prompt as self-contained. Include the file paths to read, the scope of the task, the output format, and any constraints. The prompt is the agent's entire world.
Expecting subagents to share state
Mistake: Launching two subagents in sequence and expecting the second to build on what the first discovered.
Consequence: The second agent starts fresh with no knowledge of the first agent's findings, leading to duplicated work or inconsistent results.
Avoidance: If two tasks depend on each other, the orchestrating skill must read the first agent's output and pass the relevant findings to the second agent's prompt. Alternatively, combine both tasks into a single agent if the dependency is tight.
Using subagents for simple tasks
Mistake: Delegating a task that could be done in a few lines of inline work (reading one file, running one command) to a full subagent.
Consequence: The context setup overhead (reading the agent prompt file, constructing the self-contained prompt, launching a fresh context window, processing the result) exceeds the cost of doing the work inline.
Avoidance: Delegate when the task requires deep, focused analysis across many files or perspectives. Keep simple lookups, single-file reads, and straightforward commands inline in the orchestrating skill.
Not reading the subagent's result before proceeding
Mistake: Launching a subagent and continuing the workflow without checking whether the agent produced its expected output.
Consequence: The workflow proceeds with missing or malformed data, potentially producing invalid artifacts or skipping quality gates.
Avoidance: After a subagent completes, verify that the output file exists and contains the expected structure before using the results. Handle failure cases (missing output, agent error, timeout) gracefully by reporting the failure rather than silently continuing.
