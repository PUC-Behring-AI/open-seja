Output Artifacts

Everything SEJA produces lands in one place: the _output/ directory. Plans, research logs, reflections, critique reports, generated documentation, roadmaps, and the audit trail that records every skill invocation all live here, organized into a fixed set of typed subdirectories. This chapter is the reference map for that tree: what each subdirectory holds, which skill creates artifacts there, how each artifact type is named and retired, and how the briefs log and conversation trace together record the full history of the workspace. It closes with the governing rule that makes the whole tree trustworthy -- generated artifacts are agent-maintained and never hand-edited.

The Output Directory Tree

The output root is defined by the OUTPUT_DIR convention variable in product-design/conventions.md and resolves to _output/. Beneath it, each artifact-producing skill writes to its own typed subdirectory. The tree grows lazily: a subdirectory is created the first time a skill needs to write there, so a fresh workspace may show fewer directories than a long-lived one. The subdirectories currently present in this workspace are enumerated below. 

_output/

  check-logs/                 # preflight / review check logs
  communication/              # stakeholder communication material
  critique-logs/              # critique / validation / review reports
  docs/                        # generated documentation (HTML/Markdown)
  explained-architecture/     # architecture explanations
  generated-scripts/          # skill-generated helper scripts
  inventories/                # codebase element inventories
  onboarding-plans/           # role-tailored onboarding plans
  perspective-council-review/ # expert council debate outputs
  plans/                       # plan and implement artifacts
  presentations/              # generated presentation material
  promote-proposals/          # design-intent promotion proposals
  proposals/                  # lightweight change proposals
  qa-logs/                    # companion Q&A log files

The table below documents each subdirectory: its purpose, the skill (or lifecycle step) that creates artifacts there, and its lifecycle -- how long its contents persist. Not every convention variable in conventions.md has a directory on disk yet (several, such as user-tests/ or explained-code/, are reserved but unpopulated); the table lists only the directories that currently exist.

Subdirectory Purpose Created by Lifecycle

Alongside the subdirectories, the output root holds a handful of top-level files that are not artifacts per se but indexes and logs: INDEX.md (the global artifact index), briefs.md and briefs-index.md (the execution log and its compact index), conversation-trace.jsonl, decision-digest.jsonl, pending.jsonl, and telemetry.jsonl. The briefs log and the conversation trace are covered under The Audit Trail below.

Tip: The mapping from skill to output directory is declared as *_DIR variables in the "Directory Structure" table of product-design/conventions.md. When a skill needs to resolve its output path, it reads that variable rather than hard-coding a folder name -- which is how a downstream project can relocate the entire tree by changing one value.

Artifact Types and Their Lifecycle

Each artifact type follows a consistent lifecycle: it is created by a skill, named using a monotonic ID convention, and eventually retired -- either superseded by regeneration, consumed once acted upon, or retained permanently as a historical record. Most artifact filenames share the shape <type>-<NNNNNN>-<slug>.<ext>, where the six-digit ID is drawn from a shared monotonic counter so that IDs are globally ordered across all artifact types.

Artifact type Created by Naming convention Retirement
Plan /plan <prefix>-NNNNNN-<slug>.md (e.g. implement-000187-...); prefix reflects the plan class. Retained; marked DONE after implementation. Progress files are consumed during execution.
Research log /research research-NNNNNN-<slug>.md Retained -- the log is the artifact.
Reflection /reflect reflection-NNNNNN-<slug>.md (with optional companion HTML). Retained permanently; append-only practice record.
Proposal /plan --light proposal-NNNNNN-<slug>.md Retained; may graduate into a full plan.
Promote proposal /explain drift --promote promote-proposal-plan-NNNNNN.md Consumed once the designer applies or dismisses it.
Roadmap /plan (roadmap) roadmap-NNNNNN-<slug>.md Long-lived; updated wave by wave.
Advisory log Legacy advisory flow advisory-NNNNNN-<slug>.md Retained for history; superseded by proposals/critiques.
Inventory /research --inventory inventory-NNNNNN-<slug>.md Snapshot; superseded by regeneration.
Critique / check log /critique critique-NNNNNN-<slug>.md / check-NNNNNN-<slug>.md Retained per invocation as an audit record.
Documentation /document Type-specific paths under docs/ (HTML/Markdown). Long-lived; regenerated in place.
Explanation /explain <mode>-NNNNNN-<slug>.md (e.g. architecture-000489-...). Retained per report; regenerated on request.
Onboarding plan /onboard onboarding-NNNNNN-<slug>.md (often date-foldered). Retained; regenerated per new team member.
Communication /communicate communication-NNNNNN-<slug> (Markdown and/or HTML). Retained; regenerated when messaging changes.
Q&A log Post-skill step 3, /qa-log Inlined in the parent artifact, or <parent>-qa-<slug>.md companion. Lives and dies with its parent artifact.

The ID is assigned at creation time and never reused: once 000489 is spent, the next artifact of any type takes the next free number. This gives every artifact a stable, globally unique handle that indexes, cross-references, and the briefs log can point at unambiguously. Many artifacts also carry a source: header naming the artifact that spawned them; post-skill's cross-reference step (7c) uses this to maintain a spawned: back-link on the source, so the lineage of an artifact is traceable in both directions.

Note: Retirement rarely means deletion. Most artifact types are retained even when superseded -- an outdated research log or a completed plan is history, not clutter. Only genuinely ephemeral content (the tmp/ tree, consumed progress files) is safe to discard. When in doubt, prefer marking an artifact superseded over removing it, so the audit trail stays intact.

The Audit Trail

The output tree records not just what was produced but every action that produced it. Two append-only logs at the output root form the audit trail: the briefs log captures every skill invocation, and the conversation trace captures every non-skill exchange. Between them, no user-agent interaction goes unrecorded.

The Briefs Log

The briefs log (_output/briefs.md, BRIEFS_FILE) is the execution log of all skill invocations. It is written across the lifecycle in two halves, giving each skill invocation a STARTED / DONE lifecycle:

  • STARTED is written by pre-skill (stage 2, brief-log) the moment a skill begins, before any work runs. The entry records a UTC timestamp, the skill name, and the brief -- what the user asked the skill to do.
  • DONE is written by post-skill (step 1) when the skill completes, marking the STARTED entry closed and recording the completion timestamp and, where applicable, the plan ID. 
STARTED | 2026-07-15 09:12 UTC | plan | Add output-artifacts chapter
DONE    | 2026-07-15 09:24 UTC | plan | plan-000676

Because STARTED is written first, a crash mid-skill leaves a STARTED with no matching DONE. Subsequent pre-skill runs detect these orphans and warn the user, so an interrupted invocation never silently vanishes. The compact briefs-index.md is regenerated from this log for efficient loading during pre-skill.

The Conversation Trace

Not every exchange happens inside a skill. When the user asks a question, discusses an approach, or gives an instruction outside any /skill call, the briefs log would not capture it. The conversation trace (_output/conversation-trace.jsonl, CONVERSATION_TRACE_FILE) fills that gap: an append-only JSONL log where, after every non-skill response, the agent records two entries -- the user's utterance and a short summary of its own reply -- each with a sequential event ID and a link to the preceding entry.

The two logs are stitched together at the seam where a conversation leads into a skill. When a non-skill question is followed by a skill invocation, pre-skill's brief-log stage backfills a led_to_skill link onto the most recent trace entry. The result is a single traceable chain: the question that motivated a skill is linked to the skill that answered it, which is linked through its brief to the artifact it produced.

Tip: The briefs STARTED/DONE lifecycle and the conversation trace are complementary halves of the same audit record. Reach for the briefs log to answer "what skills ran and did they finish?"; reach for the conversation trace to answer "what was discussed, and what led to that skill running?"

Artifact Immutability

Every generated artifact in the output tree carries an implicit contract: it is agent-maintained and never hand-edited. In the "Key Files" registry of product-design/conventions.md, a Maintained by column marks each file as Agent, Human, or Human (markers). Nearly everything under _output/ -- briefs, indexes, the decision digest, the conversation trace, as-coded state -- is Agent-maintained: the skills that write these files own their contents end to end.

The reason is trust. The output tree is only useful as an audit trail if it faithfully reflects what the harness actually did. If a human quietly edits a research log, retimes a brief, or rewrites a plan after the fact, the record no longer matches reality and the trail can no longer be trusted. Keeping generated artifacts agent-only preserves the invariant that the output tree is a record of execution, not a document that anyone may revise. Conceptually this mirrors the constitution's traceability principle: what the harness records must trace back to what the harness did, without undocumented mutation.

The rule is not merely a convention -- it is enforced. Files classified Human (markers) may only be changed through the marker mechanism (via apply_marker.py), which permits lifecycle markers like STATUS or ESTABLISHED but never free-form prose rewrites; post-skill and the pre-commit hook run verifiers that reject unauthorized prose mutations to those files. The practical consequence for anyone working in the tree: to change a generated artifact, re-run the skill that produced it. Do not hand-edit the file. Regeneration keeps the artifact, its indexes, and its audit trail in sync; a manual edit silently breaks that alignment.

Warning: Hand-editing an agent-maintained artifact does not just risk a merge conflict -- it corrupts the audit trail. The next regeneration will overwrite your changes, and in the meantime the indexes and cross-references still point at the version the harness believes it wrote. If an artifact is wrong, fix the inputs and re-run the skill; never patch the output by hand.
