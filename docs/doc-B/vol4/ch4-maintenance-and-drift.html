Maintenance and Drift

A SEJA project accumulates two kinds of state that must stay in alignment: design intent (what the designer meant to build) and as-coded reality (what was actually built). Over time, these diverge -- code changes, documentation ages, and implemented items linger without being promoted to established status. SEJA counters this drift with two mechanisms: freshness policies that flag stale artifacts, and periodic triggers that fire maintenance work at configured intervals. This chapter documents both mechanisms as reference, then walks through the two workflows a designer uses to resolve drift: /explain drift (comparing intent against reality and promoting implemented items) and the spec-drift-check periodic trigger.

Freshness Policies

A freshness policy is a contract that declares how long an artifact can go without review before it is considered stale. SEJA carries freshness contracts in two places: git branch state and documentation metadata.

Git Freshness

The check_git_freshness.py script compares local branches to their upstreams for both the codebase (seja-priv) and the companion workspace, surfacing behind/ahead counts. It never pulls -- it only reports how far each branch has drifted from its remote so the designer can decide whether to sync. The script is invoked by /critique freshness and by the check-git-freshness periodic trigger (see the next section). A branch that is many commits behind its upstream is the git-level analogue of a stale document: the local working state no longer reflects the shared source of truth.

Documentation Freshness

Documentation templates and generated pages carry two classification fields in their YAML frontmatter:

Field Purpose
freshness Declares the per-type review interval for the document. When the document has not been reviewed within its interval, it is flagged as stale by the documentation quality checks.
diataxis Declares the Diataxis type of the document (tutorial, how-to, reference, or explanation). For system-isomorphic volumes, classification moves to the section level via data-diataxis attributes and the file-level diataxis meta tag is set to mixed.

The freshness standard is defined in .claude/references/general/documentation-quality.md. Its core principle is that documentation updates should be possible without heroic effort -- automated validation (path liveness, terminology, structural completeness) plus per-type freshness policies keep the documentation set honest without requiring a full manual audit.

Which Files Carry Freshness Contracts

Not every file in a SEJA project carries a freshness contract. The files that do fall into two groups:

  • Documentation templates and pages (template/docs/*.md and generated _output/docs/ content) -- via the freshness and diataxis frontmatter fields.
  • Git branches (codebase and workspace) -- via the check_git_freshness.py behind/ahead comparison, which treats divergence from upstream as a staleness signal.

Tip: Freshness is a soft signal, not a hard gate. A stale document or a behind branch produces a notice, not a blocked commit. The designer decides whether to act. This keeps freshness advisory -- it informs maintenance decisions without forcing them.

Periodic Triggers

A periodic trigger is a maintenance action that should recur at a fixed interval rather than in response to a specific event. SEJA configures three periodic triggers in product-design/conventions.md under the Periodic Triggers heading. Each trigger has an interval in days, an action type, and a description.

The Configured Triggers

Trigger Interval Action type What it does
Periodic curation 30 days periodic-curation Review product-design-as-intended.md for items ready to promote from implemented to established.
Spec-drift check 14 days spec-drift-check Run /explain drift to surface drift between design intent and as-coded state.
Git freshness check 7 days check-git-freshness Compare seja-priv and seja-public to their upstreams; surface behind/ahead counts.

How Triggers Are Configured

The intervals above are not hard-coded in a script -- they are read from the conventions table. This makes them project-configurable: a project that wants a tighter drift-check cadence edits the Interval (days) column rather than modifying harness code. The project_config.py module parses conventions.md and supplies these values to the tools that act on them.

How Triggers Fire

Periodic triggers surface through the pending ledger (_output/pending.jsonl) and the pre-skill pending-check stage. When a trigger's interval elapses, an entry of the matching action type (periodic-curation, spec-drift-check, or check-git-freshness) becomes due. Pre-skill's pending-check stage runs at the start of every skill invocation and prints a banner of due and overdue actions, so the designer is reminded of periodic maintenance without having to track intervals manually. The /pending skill then lists and addresses these actions.

Threshold Configuration

Alongside the interval-based triggers, conventions.md defines a set of thresholds that govern how pending actions escalate and expire, and when post-skill files certain actions automatically:

Threshold Value What it controls
Pending plan age escalation 30 days Days before an open implement pending entry is surfaced with the overdue banner.
Verify-as-coded file threshold 5 files Minimum files changed before post-skill auto-creates a verify-as-coded pending action.
Pending age escalation 14 days Days before a pending action is flagged overdue in pre-skill notices.
Pending auto-dismiss 90 days Days after which unaddressed pending actions are auto-dismissed by pending.py cleanup.

Tip: The escalation and dismissal thresholds form a lifecycle: a pending action is filed, surfaced at 14 days (or 30 days for plan-implement entries), and auto-dismissed at 90 days if never addressed. This prevents the ledger from growing without bound while still giving the designer a long window to act.

The /explain drift Workflow

The /explain drift workflow compares as-intended design specs against as-coded reality, reports the differences, and optionally syncs or promotes implemented items. This section is a how-to: it walks through running a drift analysis and promoting implemented items to established status.

Running a Drift Analysis

Invoke /explain drift with an optional scope argument: 

/explain drift # scope: all (default)
/explain drift conceptual-design
/explain drift metacomm
/explain drift --scope since-plan plan-000676

Drift analysis (Step A) reads the As-Intended / As-Coded Registry from conventions.md, then compares each in-scope pair section by section:

  • Conceptual Design drift compares product-design-as-coded.md § Conceptual Design against the design-intent file across entities, permissions, UX patterns, and business rules.
  • Metacomm drift compares the § Metacommunication sections for feature intentions, implementation status, and designer intent.

Each difference is classified as Added (in as-intended, not as-coded), Removed (in as-coded, not as-intended), or Modified (in both, different). The analysis also scans for STATUS: implemented markers lacking an ESTABLISHED: stamp and collects them as pending promotion items. The result is a drift report with a summary table and a detailed change list, presented to the designer.

The Sync Prompt

After presenting the report, /explain drift offers a sync prompt (Step B). The designer may align metacomm with conceptual design (or the reverse), reconcile both directions, promote implemented items, or skip. Conflicts are never auto-resolved -- when the two files disagree, the workflow presents both sides and asks the designer to choose.

The Promote Workflow

Promotion is split into two phases so that the designer owns every word of the Decision prose while the harness manages the STATUS lifecycle structurally:

Phase 3a -- Decision-entry proposal (/explain drift --promote)
Scans registered Human (markers) files for STATUS: implemented markers lacking ESTABLISHED:, groups candidates by plan ID, and drafts DDR-shaped Decision entries (Context, Decision, Consequences) with auto-assigned D-NNN IDs. The drafts are written to _output/promote-proposals/promote-proposal-plan-<id>.md in copy-paste-friendly fenced blocks. This phase does not modify product-design-as-intended.md -- it only produces a designer-owned draft and files an apply-promote-markers pending action. The designer reviews the draft, edits it to their voice, and copies the entries into product-design-as-intended.md § Decisions.
Phase 3b -- Marker flip (/explain drift --promote --apply-markers plan-NNNNNN)
Verifies that the ### D-NNN: entries were added to the intent file using a heading-only grep (^###\s+D-NNN) so that the designer's rewritten prose is never matched. For each present entry, it runs a per-item AskUserQuestion confirmation, then invokes apply_marker.py to flip the STATUS marker. Post-skill's check_human_markers_only.py verifies that the flip did not bleed prose into the Human (markers) file.

The STATUS Marker Lifecycle

The promote workflow advances an as-intended item along the STATUS state machine. The relevant transition is implemented -> established: 

proposed -> implemented -> established -> superseded

An item enters implemented when a plan implements it (proposed by post-skill's DONE marker step). Promotion to established is the human-confirmed acknowledgement that the item has proven itself and become part of the settled design. The marker itself is an inline HTML comment above the item's heading: 

<!-- STATUS: established | plan-000676 | 2026-07-15 -->
### Section Title

Legacy uppercase STATUS: IMPLEMENTED markers are detected by the widened marker regex and replaced (not stacked) by the lowercase form during a Phase 3b flip. Agents may propose new implemented markers but must never remove or alter an existing established marker -- these are audit records.

Tip: The two-phase split exists because Decision entries are Human (markers) content -- the designer's precise wording carries intentional nuance. Phase 3a produces a draft outside the intent file; only after the designer copies and edits the entries does Phase 3b touch the markers. This preserves designer voice while letting the harness manage the structural lifecycle.

The Spec-Drift-Check Workflow

The spec-drift-check periodic trigger (14-day interval) is the scheduled counterpart to running /explain drift on demand. It ensures that intent-versus-reality divergence is reviewed on a regular cadence, not only when the designer happens to suspect drift. This section walks through how the trigger surfaces drift and how the designer resolves it.

How the Trigger Surfaces Drift

  1. When 14 days have elapsed since the last spec-drift check, a spec-drift-check action becomes due in the pending ledger.
  2. At the start of the next skill invocation, pre-skill's pending-check stage prints a banner listing the due spec-drift-check action (flagged overdue after the 14-day pending age-escalation threshold).
  3. The designer sees the reminder and knows a drift review is due.

How the Designer Resolves It

  1. Run /pending to list outstanding actions, or invoke /explain drift directly.
  2. /explain drift produces the drift report (Step A) and presents the summary and detailed changes.
  3. Review the report. If drift is found, choose a resolution at the sync prompt (Step B): align the two files in one direction, reconcile both, or promote implemented items. If no drift is found, skip the sync.
  4. Once the review is complete, the spec-drift-check action is marked done, resetting the 14-day interval for the next cycle.

Tip: A spec-drift check that finds no drift is still valuable -- it confirms that intent and reality remain aligned and resets the interval. The goal is not to force changes every 14 days but to guarantee that unnoticed divergence never accumulates for longer than one interval.
