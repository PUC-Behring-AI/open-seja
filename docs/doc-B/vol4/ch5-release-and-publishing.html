Release and Publishing

SEJA is developed in a private repository and distributed through a separate public mirror. Publishing is the one-way process that turns a coherent batch of private work into a tagged public release: a maintainer records the changes in a changelog, cuts a version tag, regenerates the public tree from the private source, runs a smoke gate, and pushes. This chapter documents that pipeline end-to-end -- the /publish workflow as a step-by-step procedure, the tag naming and cadence conventions, and the ephemeral publish workspace that makes the private-to-public sync safe by construction.

The /publish Pipeline

The /publish skill is a thin wrapper around the tools/publish.py orchestrator. The skill handles version resolution and the preflight decision, then hands off to the script, which runs the full release lifecycle: preflight, cut tag, clone the public repo into an ephemeral workspace, copy authored prose, regenerate the harness tree, smoke test, commit, and push. This section walks through a release from an unreleased changelog entry to a pushed tag.

Maintainers only. Publishing is a core-team activity. If you consume SEJA in your own project via /seja-setup (install and --upgrade), you do not run this pipeline -- you simply upgrade to a tagged release.

Step 1: Record the change in the changelog

Before publishing, the changes to ship must be described in the public changelog's Unreleased section. This is the human-authored record of what the release contains. The publish preflight also checks that a harness changelog entry exists for the target version; if it is missing, the pipeline can auto-generate one from git history before continuing.

Step 2: Preview with --dry-run

Always preview first. A dry run prints the full command sequence and the inferred version without executing any destructive action (no tag, no push): 

/publish --dry-run

Under the hood this constructs a call to the orchestrator with the dry-run flag: 

# Preview only -- no tag is cut, nothing is pushed
python tools/publish.py --dry-run

Step 3: Resolve the version

If you pass a version, it is used verbatim. If you omit it, publish.py infers the next tag from the changelog and the existing git tags, then asks you to confirm. The inference heuristic reads the changelog bump hint:

Changelog signal Version bump
Breaking changes present Major
Added (new features) Minor
Otherwise (fixes, chores) Patch

To let the heuristic decide, run /publish with no version and accept the inferred tag. To override it, pass the tag explicitly: 

# Let publish.py infer the next version from CHANGELOG.md + tags
/publish

# Or specify the exact tag
/publish v0.3.0

Step 4: Clear the preflight gate

The pipeline runs a preflight check that returns a JSON list of issues, each with a severity and (where available) a fix command. Errors indicate the release will likely fail or produce a bad artifact; warnings are advisory. Address any errors before continuing. If only warnings remain, you may consciously proceed. 

# Run preflight in isolation to inspect issues
python tools/publish.py --preflight-only --json v0.3.0

Step 5: Execute the release

Once the version is resolved and preflight is clean (or its remaining warnings are accepted), run the release for real. The orchestrator performs the destructive steps in order:

  1. Cut the tag via cut_tag.py -- creates an annotated vMAJOR.MINOR.PATCH tag and files a PUBLISH: entry in the pending ledger. The two actions are coupled: if either fails, the other is rolled back.
  2. Clone the public repo into an ephemeral publish workspace.
  3. Copy authored prose (changelog, README, consumer-facing docs) from the public-authored sources.
  4. Regenerate the harness tree via sync_to_public.py, which strips private-only sections and excludes private-only directories.
  5. Smoke test the candidate via pre_publish_smoke.py as a pre-push gate.
  6. Commit and push the release to the public seja repository, then close the PUBLISH: pending entry.
# Full release -- cuts the tag and pushes the public mirror
python tools/publish.py v0.3.0

# Non-interactive: accept all confirmation defaults
python tools/publish.py v0.3.0 --yes

Tip: The pre-commit hook enforces a leak gate (check_no_private_leaks.py --staged) on every commit, independently of the publish pipeline. Even if a private-only detail slipped past the sync step, the leak gate is a hard barrier that rejects the commit before it can reach the public repository. Install the hook once per clone with bash .githooks/install.sh.

Step 6: Report and resolve

On success the pipeline reports the published version and confirms the PUBLISH: pending entry was closed. On failure it relays the error and the script's recovery guidance -- do not retry blindly; the script's recovery instructions are authoritative.

Tag Conventions

Releases are named with a single unified version namespace: one version, one changelog entry, one tag. The conventions below are the authoritative reference; the canonical source is tools/release-process.md.

Aspect Convention
Format vMAJOR.MINOR.PATCH (SemVer), always prefixed with v
Starting version v0.1.0 -- the leading 0. signals the harness contract is still evolving
Who cuts tags Any core-team member
Cadence Manual, when a coherent batch is ready; target at most about one release per week, batching smaller changes together

Version namespace

A unified policy governs versioning: the harness changelog uses one heading per release (for example ## [2.14.0]), and the public changelog uses the same version number. Because SemVer allows gaps, the public repository can jump forward to the internal version; a gap note above the affected entry explains the jump for consumers.

Hotfix policy

Hotfix branching is deferred until the first hotfix case arises. The default rule is to forward-fix on main and tag the next patch version. If a consumer is actively blocked on an older version, the team revisits per-case whether a release/<minor>.x branch is warranted.

The Ephemeral Publish Workspace

The most important idea in SEJA's release model is that the public harness tree is never stored on disk in the private repository. There is no checked-in copy of the public .claude/ to hand-edit. Instead, the public tree is generated on demand, into a temporary workspace, only during a publish -- and discarded afterward. Understanding why this design was chosen explains most of the project's authoring rules.

One source, one direction

The private repository is the single source of truth for the harness. Maintainers edit only two things: .claude/ (the harness itself) and product-design/ (project configuration). Public-only prose -- the changelog, README, and consumer docs -- is authored directly in the public-authored sources. Everything else in the public repository is derived, never original.

The sync flows in exactly one direction: private to public. During a publish, sync_to_public.py reads the private .claude/, strips private-only sections (the parts marked off in each file), excludes private-only directories, and writes the sanitized result into the ephemeral workspace. Nothing flows back from public to private. 

# Conceptual data flow during a publish
seja-priv/.claude/  # source of truth (edited here)
    # |  sync_to_public.py: strip priv-only sections, exclude priv dirs
    # v  (one-way, generated on demand)
ephemeral workspace/.claude/  # built during publish, then discarded
    # |  commit + push
    # v
public seja repository

Why generated and not stored

SEJA is not open-sourced, and the public face must show only polished evolution -- not the private iteration history. Two designs were considered. Storing a checked-in public copy would mean two trees to keep in sync by hand, an endless source of drift and accidental leaks. Full automation was rejected for a small-team cadence because it would either leak private history or demand heavy sanitization tooling. The chosen model -- generate ephemerally, publish manually -- keeps privacy correct by construction: there is simply no persistent public tree to leak from, because it does not exist between releases.

Do not recreate the public tree on disk. A common mistake is to try to hand-sync a seja-public/.claude/ directory. That directory does not exist on disk and must not be recreated -- it is generated ephemerally by the publish pipeline into a temporary clone. Editing it by hand would defeat the one-way sync model. Edit only .claude/ and product-design/ in the private repository.

Release discipline and the sync runbook

Because the release path is manual, the harness has a built-in safeguard against "cut tag and forget." When cut_tag.py cuts a tag, it files a PUBLISH: entry in the pending ledger. The pre-skill lifecycle hook's pending-check stage surfaces that entry on every skill invocation, and if it stays unresolved for more than three days the reminder escalates to the top of the output with stronger wording. The ledger entry is the forcing function that keeps the manual path reliable -- it remains until the maintainer completes the sync or explicitly dismisses it.

The /publish pipeline automates what was historically a manual runbook. That runbook's seven steps are still a useful mental model of what the pipeline does on your behalf:

  1. Update the public changelog's Unreleased section with the changes to publish.
  2. Cut the tag via cut_tag.py, which creates the annotated tag and files the PUBLISH: ledger entry.
  3. Regenerate the public tree via sync_to_public.py (strip private-only sections, exclude private-only directories).
  4. Run pre_publish_smoke.py as the pre-push gate.
  5. Inspect the diff against the last published state.
  6. Push to the public seja repository.
  7. Resolve the PUBLISH: pending ledger entry.

A monthly consumer-path dogfooding ritual runs in a scratch consumer repository (never in the private repo). It exercises /seja-setup (install and --upgrade) against a tagged release to surface experiential drift -- misleading prompts, stale how-to instructions, broken cross-links -- that CI smoke tests cannot catch.
