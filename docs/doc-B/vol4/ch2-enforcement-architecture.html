Enforcement Architecture

Governance in SEJA is not a matter of good intentions -- it is enforced. This chapter documents the machinery that makes the lifecycle mandatory rather than merely recommended: the multi-layer defense-in-depth model, the file-maintainer classification that controls who may write what, the leak-prevention gate that guards the private/public boundary, and the structural split between what stays private and what syncs to the public seja repository. It closes with an Anti-patterns catalog of the mistakes that this architecture exists to prevent. For the theoretical grounding of why enforcement is framed as making the harness governable and epistemic, see Vol. 5 Ch. 6.

Multi-Layer Enforcement

SEJA enforces its governance through defense in depth: no single mechanism is trusted to catch every violation. Instead, three layers sit in series, each catching a different class of failure that the previous layer let through. Because the agent's compliance rests partly on instruction-following -- a soft, probabilistic behavior -- the harder, code-level gates below it exist precisely to compensate when instruction-following slips.

Layer Mechanism Posture Catches
1 Post-skill advisory checks Advisory (warns, may prompt) Scope and marker violations at the moment they are staged, before the commit is attempted
2 Pre-commit hook Blocking (rejects commit) Anything the advisory layer surfaced but the operator overrode, plus private-content leaks
3 Continuous integration Blocking (rejects merge) Full-coverage checks too slow for the fast local gate; violations from clones without the hook installed

Layer 1: Post-Skill Advisory Checks

During the post-skill pipeline, several steps run validation scripts against the staged changes and report their findings before the commit is made. Step 6 runs verify_commit_scope.py to flag files staged outside the expected paths for the skill type. Step 6b runs run_preflight_fast.py, a battery of fast checks. Step 6c runs check_human_markers_only.py --staged to detect unauthorized prose mutations in Human (markers) files. These checks are advisory: a non-zero result displays the failures and, for the marker verifier, prompts an abort/proceed decision, but the operator can still choose to continue. The value of this layer is early feedback -- the violation is named at the moment it is introduced, when the fix is cheapest.

Layer 2: The Pre-Commit Hook (Blocking Gate)

The pre-commit hook in .githooks/pre-commit (installed once per clone via bash .githooks/install.sh) runs automatically on every git commit. Unlike the advisory layer, it is a hard gate: it runs the fast preflight checks and the pre-sync leak gate (check_no_private_leaks.py --staged), and if any check fails the commit is rejected outright. This is the layer that catches what the advisory layer merely warned about -- if an operator overrode a step 6c prompt, or if the agent skipped post-skill entirely, the hook still stands between the working tree and the repository.

Warning: The hook only protects clones where it has been installed. bash .githooks/install.sh is a per-clone step -- a fresh clone has no active hook until it is run. This is why Layer 3 (CI) exists: it enforces the same checks on the server side, where no local installation is required.

Layer 3: Continuous Integration (Full Coverage)

CI runs the complete validation suite via run_all_checks.py, the CI-independent orchestrator that discovers and runs every check script with unified exit codes and JUnit XML output. This is the backstop for two gaps the earlier layers leave open: checks too slow to belong in the fast local preflight, and commits that arrived from a clone without the pre-commit hook installed. Because CI runs regardless of local configuration, it is the layer of last resort -- a violation that slipped past both the advisory checks and an uninstalled hook is still caught before it can be merged.

Tip: The three layers are intentionally redundant, not wasteful. Each catches what the previous missed: advisory checks catch it early but can be overridden; the hook blocks it locally but only where installed; CI blocks it centrally regardless of local state. Removing any one layer opens a path that the others were relied upon to close.

File-Maintainer Classification

Enforcement needs to know not just what may change but who may change it. SEJA answers this with a file-maintainer classification: a scheme that assigns each governed file a maintainer type, recorded in the "Maintained by" column of the Key Files table in product-design/conventions.md and summarized in .claude/references/general/harness-governance.md. Three of the four values matter most for enforcement.

Value Meaning Agent write rule
Human Authored and updated exclusively by humans. The agent must not write. It may read and propose changes via AskUserQuestion.
Human (markers) Human-authored prose; the agent may write fixed-format structured markers only. The agent writes only via apply_marker.py, after explicit confirmation. Never prose.
Agent Auto-maintained by agents and skills (e.g., via post-skill). The agent reads and writes freely. Humans typically do not edit directly.

The "Human (markers)" Boundary

The middle classification is the subtle one. Files such as product-design/product-design-as-intended.md and product-design/ux-research-results.md hold design intent and research findings whose prose is the designer's own -- their precise wording carries intentional nuance that paraphrasing would distort. But these same files also carry machine-parseable lifecycle markers (STATUS flags, ESTABLISHED stamps, CHANGELOG append lines) that the agent legitimately needs to update as work progresses.

The rule that resolves this tension is strict: on a Human (markers) file, the agent may write only the fixed-format markers, and only through apply_marker.py -- never the prose. The script is the sole sanctioned write path; it supports the STATUS, ESTABLISHED, INCORPORATED, CHANGELOG_APPEND, DECISION_APPEND, and REQ_TRACED_BY marker types and nothing else. Any prose mutation the agent introduces is a violation, caught by check_human_markers_only.py at post-skill step 6c and, if it reaches the commit, by the pre-commit hook.

Tip: When you need to flip a STATUS marker, record an ESTABLISHED stamp, or append a changelog line to a Human (markers) file, reach for apply_marker.py rather than editing the file directly. Editing by hand is exactly the pattern the marker verifier is designed to reject.

Leak Prevention

The most consequential thing the pre-commit hook does is prevent private content from leaking into a commit that could later be synced to the public repository. The gate is check_no_private_leaks.py, run in --staged mode by the hook and again by /publish before the public sync. This section shows how to run it and what it blocks.

Running the Leak Gate

The pre-commit hook runs the staged-mode scan automatically, so in normal work you never invoke it by hand -- a failing commit is your signal. To run the same scan manually against your staged changes (for example, to check before you attempt a commit): 

# Scan the currently staged changes for private leaks
python .claude/skills/scripts/priv/check_no_private_leaks.py --staged

# Scan an explicit list of files instead of the staged set
python .claude/skills/scripts/priv/check_no_private_leaks.py --files path/to/file.md

Exit code 0 means the staged content is clean and the commit may proceed. A non-zero exit lists the offending files and patterns; the pre-commit hook translates that into a rejected commit.

What It Blocks

The gate blocks staged content that belongs only in the private workspace from reaching a commit destined for -- or synced into -- the public tree. In practice this means:

  • References to private-only artifacts and workspace paths that have no public counterpart.
  • Content that would appear in public-facing prose but originates in the private half of the repository.
  • Private-only fragments that escaped their conditional markers and would otherwise survive the public sync.

Because the same script runs both at commit time (--staged) and again during /publish, a leak has to defeat the check twice to reach the public repository -- another instance of the defense-in-depth pattern.

The Priv/Public Boundary

seja-priv is both a codebase (it authors the harness) and a workspace (it hosts the harness's own design artifacts). The leak gate above only makes sense against this structural split: some content is meant to propagate to the public seja repository, and some is meant to stay private. Knowing which half you are editing is the contributor's core responsibility, because edits to the codebase half reach downstream consumers while edits to the workspace half do not.

What Syncs to Public

The codebase half propagates outward. It comprises the harness source under .claude/ -- skills, rules, agents, scripts, and the general and template reference directories -- which consumers receive via /seja-setup and its --upgrade mode. Alongside it, a set of public-facing prose files (the changelog, README, license, and public docs) are authored directly in the public tree and copied during release. Publication is orchestrated by /publish, which generates the public .claude/ ephemerally into a temp clone via the sync tool rather than from any on-disk mirror.

What Stays Private

The workspace half stays inside seja-priv. This is SEJA's own iteration history and strategic context:

  • The product-design/ design configuration for this project.
  • The _output/ workspace -- plans, roadmaps, research logs, reflections, the pending ledger, and the other artifacts a working session produces.
  • Private-only tooling under .claude/skills/scripts/priv/, excluded from sync entirely.
  • Private-only fragments embedded inside otherwise-shared files, guarded by conditional markers that the sync tool strips.

The boundary is structural: it is defined by where a file lives and by the markers around a fragment, not by ad-hoc judgment at commit time. When in doubt about which side a change falls on, the reliable test is to check whether the file would appear in the public tree after a dry-run of the sync tool. The two-role split and its rationale are documented in .claude/references/general/harness-governance.md under "Codebase and workspace".

Tip: Editing the codebase half affects downstream consumers at the next release; editing the workspace half is visible only inside seja-priv and is safe to iterate on freely. The leak gate and the priv/public markers exist so that this distinction is enforced mechanically, not left to memory.

Anti-patterns

The enforcement architecture exists to prevent a specific set of recurring mistakes. Each entry below describes the mistake, its consequence, and how to avoid it -- and, where relevant, which enforcement layer catches it if you do not.

Bypassing the lifecycle
Mistake: Skipping the pre-skill or post-skill phases -- for example, doing a skill's work directly without invoking /pre-skill to load context, or interrupting before /post-skill finalizes and commits the output.
Consequence: References and the constitution are never loaded, so the work proceeds without governance context. On the exit side, artifacts are produced but not committed, indexes go stale, and telemetry is never flushed -- the briefs file may show work as DONE while nothing is persisted.
Avoidance: Let the lifecycle run end to end. Lifecycle-workflow skills invoke /pre-skill as their first step and /post-skill as their last; do not short-circuit either. If post-skill is interrupted, re-invoke it with the same skill ID so checkpoint recovery resumes from where it stopped.
Hand-editing Human (markers) files directly
Mistake: Writing prose or markers into a Human (markers) file -- such as product-design-as-intended.md or ux-research-results.md -- by editing the file directly instead of going through apply_marker.py.
Consequence: Post-skill step 6c (check_human_markers_only.py --staged) detects the unauthorized mutation and recommends aborting the commit. If the commit proceeds anyway, the pre-commit hook is the next gate. Prose edits corrupt the designer-voice guarantee these files exist to protect.
Avoidance: Use apply_marker.py for every write to a Human (markers) file. It is the only sanctioned write path and supports exactly the marker types these files permit (STATUS, ESTABLISHED, INCORPORATED, CHANGELOG_APPEND, DECISION_APPEND, REQ_TRACED_BY). Leave the prose to the human author.
Skipping pre-commit hooks
Mistake: Committing with git commit --no-verify to bypass the pre-commit hook, or working in a clone where bash .githooks/install.sh was never run.
Consequence: The blocking layer is removed. Fast preflight failures and, critically, the private-leak gate are never evaluated, so a commit containing private content or a preflight regression can reach the branch. It will only be caught later, by CI -- if at all.
Avoidance: Run bash .githooks/install.sh once per clone and let the hook run on every commit. Do not use --no-verify to work around a failing check; fix the underlying violation instead. Treat a hook failure as information, not an obstacle.
Mixing private content into public documentation
Mistake: Writing private-only details -- workspace-only artifact references, or internal strategic context -- into files that sync to the public seja repository, or into public-facing prose authored in the public tree.
Consequence: The leak reaches the public distribution, exposing content that was meant to stay private. The check_no_private_leaks.py gate exists precisely to block this at commit time and again at /publish, but a leak that is written carelessly still forces an abort and a rewrite.
Avoidance: Keep private content in the workspace half (_output/, product-design/, scripts/priv/) or, for fragments inside shared files, wrap it in the conditional priv-only markers that the sync tool strips. When unsure, run a dry-run of the sync tool to see whether a file would appear in the public tree.
Running implementations without a plan
Mistake: Invoking /implement (or simply writing code) without a corresponding plan file in _output/plans/.
Consequence: The implementation has no recorded scope, no step-by-step breakdown, and no Docs: or Deploy: metadata for post-skill to act on. As-coded alignment has no plan to read from, and the documentation auto-run and deferred-artifact generation have nothing to process. Design decisions cannot be traced back to their rationale.
Avoidance: Always run /plan first; for trivial changes, /plan --light produces a lightweight proposal. The CLAUDE.md rules instruct the agent to check for an existing plan before implementing -- honor that check rather than working around it.

Tip: Every anti-pattern here maps to a layer of the enforcement architecture that will catch it. That is the point: the safest way to work is to treat the lifecycle, the marker script, the hook, and the plan requirement as the intended path rather than as obstacles to route around.
