Software as Designed Communication

SEJA rests on a claim that is easy to state and consequential to take seriously: software is a message. It is a message about how to communicate that a designer sends to a user, and every interface element, default, error string, and interaction path is a fragment of that message. This chapter sets out the theoretical source of that claim — the Semiotic Engineering of Clarisse Sieckenius de Souza (2005) — and shows how SEJA turns it into a concrete, mandatory design artifact. It also does the harder work: it marks where the "software as message" framing is strongest, where it strains, and what it leaves unexplained. Later chapters in this volume build on the vocabulary introduced here; this one establishes the ground.

The Designer's Deputy

Semiotic Engineering (de Souza, 2005) reframes human-computer interaction as a species of communication rather than as a species of cognition. Where cognitive approaches to HCI ask how a user forms a mental model of a system and executes actions against it, Semiotic Engineering asks a different question: what is the system saying, who is saying it, and to whom? Its answer is that an interactive system is a message from its designers to its users about how the system can and should be used to achieve a range of purposes.

The theory's central device for making this precise is the designer's deputy. The designer is not present at use time; the user interacts with software that was authored weeks, months, or years earlier. Yet the designer's communicative intent must reach the user somehow. In Semiotic Engineering, the system's interface is the designer's proxy at runtime — a deputy that speaks on the designer's behalf. Every affordance the user encounters, every message the system emits, every constraint that channels behaviour, is an utterance of this deputy. The deputy does not merely enable interaction; it conducts, on the designer's behalf, an ongoing act of communication.

De Souza (2005) frames this as a deliberately unusual answer to the question "who communicates with the user?" The naive answer is "the system." The semiotic answer is "the designer, through the system." This shift has teeth. It means an interface is accountable in the way an authored text is accountable: it can be coherent or incoherent, honest or misleading, complete or evasive about its own intentions. It means usability problems are, at root, communication failures — breakdowns in the designer's message — not merely mismatches between a user's mental model and a system's state model.

Tip: The designer's deputy is a role, not a person. In a conventional product the deputy is dispersed across the running interface. In SEJA, as the final section of this chapter argues, the deputy role is occupied by an unusually explicit agent — which is exactly why the framing repays being made precise.

Metacommunication and the Two Registers

If the interface is a message, what kind of message is it? Here Semiotic Engineering introduces its defining concept: metacommunication. The prefix meta is load-bearing. The designer's message is not communication within the system — it is communication about communication: a message that tells the user how to communicate with the system in order to accomplish their goals. It is a communication whose content is a communicative system.

De Souza (2005) gives the metacommunication message a canonical paraphrase, a template the designer is understood to be uttering through the deputy:

"Here is my understanding of who you are, what I've learned you want or need to do, in which preferred ways, and why. This is the system that I have therefore designed for you, and this is the way you can or should use it in order to fulfil a range of purposes that fall within this vision."

Read closely, this is a first-person message. The "I" is the designer; the "you" is the user. It carries the designer's model of the user ("who you are"), the designer's model of the user's needs ("what I've learned you want"), a justification ("and why"), a claim about the artifact ("the system that I have therefore designed"), and a set of usage prescriptions ("the way you can or should use it"). Every one of these is a design decision made visible. Metacommunication is thus not decoration on top of a system — it is the semantic content the system was built to convey.

Two Registers: System-Level and Meta-Level

Because the message is about communication, Semiotic Engineering distinguishes two registers operating simultaneously in any interaction (de Souza, 2005, Ch. 3):

The system-level register (interaction)
The moment-to-moment exchange between user and system: the user clicks, the system responds; the user types a query, the system returns results. This is communication with the deputy — the running dialogue of use. It is what most usability work observes and measures.
The meta-level register (metacommunication)
The single, global message the designer sends through the totality of the system-level interaction. Every system-level exchange is also a fragment of this larger message — a piece of evidence about who the designer thinks the user is and how the designer intends the system to be used. The meta-level message is not uttered in any one screen; it is the emergent utterance of all of them together.

The relationship between the two registers is the crux. Each individual system-level exchange (a button press, a validation error) is legible on its own. But it is also a sample of the meta-level message: from the pattern of what the system allows, forbids, defaults to, and explains, the user reconstructs the designer's vision. When those samples are consistent, the user receives a coherent message and interaction feels intelligible. When they conflict — when the system's defaults imply one model of the user and its error messages imply another — the meta-level message fractures, and the user cannot tell what the designer meant. Semiotic Engineering's central quality criterion, communicability (the subject of Chapter 2), is precisely the degree to which the meta-level message comes through clearly across the system-level register.

This two-register analysis is what distinguishes Semiotic Engineering from a merely metaphorical use of "communication." The theory does not just say interfaces are like messages; it identifies a specific structure — a global authored message delivered through, and reconstructable from, a stream of local interactions — and makes that structure the object of design and evaluation.

How SEJA Operationalizes Metacommunication

SEJA does not treat the metacommunication message as a background metaphor. It elevates the message to a first-class, captured design artifact and makes the harness the machinery that keeps that message coherent across the lifecycle. Two operational commitments carry this.

The Message as the Canonical Top-Level Artifact

When a project is configured through the /design skill, the metacommunication message is elicited directly from the designer and recorded as the Global Metacommunication Vision — section 11 of product-design/product-design-as-intended.md. This is not an optional field. The /design skill classifies the metacommunication message among its required conceptual design inputs: it is prompted at question 0.1 (or at the questionnaire's Final Step) and cannot be satisfied by a default. The message the designer writes is the seed from which project-specific per-feature intentions (section 14) and the Extended Metacommunication Template guiding questions (section 12) are developed.

Two properties of this capture are worth stating precisely, because they follow from the theory rather than from convenience. First, the message is recorded in the designer's first person: the template for section 11 instructs the author to "use 'I' as the designer and 'you' as the user — never third-person or passive voice." This is the theory made literal — the artifact is written as the utterance the deputy will deliver, not as a third-party description of it. Second, when a designer supplies a message, the harness records it verbatim. The shared-definitions rule is explicit that a user-provided metacommunication message must be recorded "exactly as written, without summarization or editing," because "the designer's precise wording carries intentional nuance; paraphrasing distorts design intent." In Semiotic Engineering terms: the artifact is the message, so editing the artifact edits what the designer says to the user.

The canonical framing string SEJA uses to scaffold section 11 is de Souza's own paraphrase, carried through the harness in .claude/references/general/shared-definitions.md and echoed in the section-11 template guidance. The theory's paraphrase and the project's authoring prompt are, deliberately, the same words. The full extended treatment of this message — its slot structure, the section-12 guiding questions, and how it decomposes into per-feature intentions — is the subject of Volume 2, Chapter 1; this chapter is concerned only with the why.

Verified against live harness: the claim that the metacommunication message is the canonical, required top-level design artifact is checked against .claude/skills/design/SKILL.md (Field Classification: metacommunication message under "Required conceptual design"; Mode 1 Final Step capture) and the section-11 template in product-design/product-design-as-intended.md. The verbatim and first-person rules are from .claude/references/general/shared-definitions.md.

The Deputy Is the Agent

SEJA's second commitment is the one that makes it an unusually literal instance of the theory. In a conventional product the designer's deputy is the interface — the message is delivered through pixels, controls, and copy. In SEJA the designer is a human working through an agent, and it is the agent that plans, implements, documents, and communicates the system. The metacommunication message is loaded into the agent's governing context: the constitution and design-intent artifacts — section 11 among them — are injected at every skill invocation (this is the pre-skill reference-load and constitution stages, detailed in Volume 3, Chapter 1). The agent thereby becomes the deputy that delivers and defends the designer's message across the build. The message is the content; the agent is the channel through which the designer's intent reaches the artifact — and, ultimately, the user.

This is why the harness invests so heavily in keeping the message coherent. The whole point of the two-register analysis is that local decisions must remain consistent with the global message. In SEJA, drift between what was intended (section 11 and its decomposition) and what was built (the as-coded metacommunication section) is exactly the fracturing of the meta-level message that Semiotic Engineering warns against — and the harness makes that drift detectable and reconcilable rather than invisible. Chapter 7 takes up how the agent, as deputy, reads and re-delivers the harness's own metacommunication.

Critical Counter-Reading: Where the One-Shot Message Strains

Intellectual honesty requires marking the limits of the framing SEJA adopts. The "software as a single authored message" model is strongest for the class of systems Semiotic Engineering was first developed against: authored, editorially controlled artifacts with an identifiable design authority and a broadly one-directional communicative posture. For such systems the model is illuminating and the coherence criterion is exactly right. But the model was articulated as a one-shot message — a single global utterance fixed at design time — and several system classes strain that reading.

Interactive and Adaptive Systems

A recommender, a personalized feed, or an ML-driven interface does not deliver a fixed message. What the user encounters is generated at runtime and differs per user and per session; the "message" is co-produced by the designer's intent, a model's learned behaviour, and the user's own history. Semiotic Engineering accommodates interaction as the system-level register, but the theory's image of a single designer-authored meta-level message fits awkwardly when the meta-level content is itself partly emergent and not fully known to the designer in advance. The designer can author the policy that generates behaviour, but the policy is a weaker sense of "message" than the paraphrase in section 2 suggests. SEJA's artifact captures designer intent well; it is a less complete account of systems whose runtime message is substantially machine-authored.

Multi-Designer and Long-Lived Products

The theory speaks of "the designer" in the singular, but real products are authored by many hands over years, with turnover, acquisitions, and competing internal factions. There may be no single coherent "I" behind the message — the meta-level utterance a user reconstructs may be the uneasy composite of several designers' partly incompatible visions. This is not fatal to the theory (a composite author is still an author), but it does undercut the tidy first-person paraphrase, and it raises a question the model does not answer on its own: whose message wins when designers disagree? SEJA's answer is partly procedural — the constitution and the recorded design intent are meant to hold a single coherent authority — but that is a governance commitment layered on top of the theory, not a consequence of it.

The Risk of Over- and Under-Engineering

Two failure modes bracket SEJA's operationalization. It can over-engineer: for a small, single-author tool with an obvious purpose, eliciting a full first-person metacommunication message, an extended template, and per-feature intentions may cost more ceremony than the coherence it buys. And it can under-engineer: capturing the message once, at design time, does not by itself guarantee the running system still speaks it — the artifact can become a museum piece that the code has quietly outgrown. SEJA mitigates the latter with drift detection and reconciliation, but the mitigation is only as good as the discipline of running it. The framing tells you what coherence is; it does not, by itself, keep a codebase coherent.

Open Questions

Some tensions the framing raises are not resolved by SEJA and are worth naming as open:

  • Emergent meta-messages. When runtime behaviour is machine-generated, how should a designer's intended message be reconciled with the message the system actually delivers in aggregate — and which one is the object of "communicability"?
  • The user as author. Semiotic Engineering casts the user primarily as a recipient and interpreter of the designer's message. In deeply configurable, user-scripted, or collaborative systems, users co-author the message. The model has resources for this (users as interpreters who talk back through interaction) but does not foreground it, and SEJA's artifact does not yet capture user-side authorship.
  • Agent as author vs. deputy. SEJA places an agent in the deputy role. But an agent that generates code and copy is not a neutral conduit — it introduces its own regularities into the message. How much of the delivered meta-message is the human designer's, and how much is the agent's, is a question the "deputy" metaphor tends to hide rather than surface. Chapter 6 returns to the governance side of this.

None of these undercut the value of the framing; they mark its edges. SEJA adopts Semiotic Engineering because, for the systems it is built to help design, treating software as designed communication yields a sharper design object — the message — and a clearer failure mode — incoherence — than the alternatives. Knowing where the model strains is part of using it well.
