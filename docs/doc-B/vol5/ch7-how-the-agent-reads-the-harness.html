How the Agent Reads the Harness

The preceding six chapters treat the harness as a message: software as designed communication, the sign systems that carry it, the metacommunication template that structures it, the reflective and abductive practices it disciplines, and the twin claims that it is at once governable and epistemic. This closing chapter turns that lens around. If the harness is a message, then there is a reader on the other end of it -- and that reader is not the human designer but the agent: Claude, the model reading skill files, reference files, rules, and markers as its instructions for how to behave.

This is meta-documentation of an unusual kind: documentation about how the reader of the documentation actually reads. It is unique to a harness because in ordinary software the runtime executes bytes deterministically; here the "runtime" is a language model that interprets prose, and interpretation is fallible, budgeted, and order-sensitive. Understanding how the agent reads the harness is therefore not idle introspection. It explains why the harness is shaped the way it is -- why frontmatter fields sit where they sit, why some references load eagerly and others lazily, why the harness spends a designer_description on files whose primary reader is a machine. And it comes with a caution the rest of the volume has earned: everything here is a reading of a reader whose interior we cannot see.

The Skill File as a Sign to Be Read

A SEJA skill is a single Markdown file, SKILL.md, living in .claude/skills/<name>/. Structurally it is two parts: a block of YAML frontmatter between --- fences, followed by a Markdown body. The frontmatter conforms to the agentskills.io portable skill specification -- name, description, optional compatibility, and an extensible metadata block where SEJA-specific fields live. The body is prose: the instructions the agent follows once the skill is invoked.

The division is not cosmetic. The frontmatter is data about the skill -- read and parsed by tooling and by the pre-skill pipeline before the body ever runs. The body is instruction to the agent -- read as the operative procedure. When the user types /plan add-token-rotation, the harness does not simply hand the body to the model and step back. It first routes the invocation through pre-skill, which reads the calling skill's SKILL.md, parses its frontmatter, and uses those fields to decide what else to load into the context window before the skill's own instructions take effect.

So the skill file is a sign in the semiotic sense developed earlier in this volume: an expression (the file's text) paired with a content (the behavior it is meant to produce in the agent). But the agent does not read the whole harness at once. It reads what the pre-skill pipeline places in front of it, in the order the pipeline places it, within a budget the frontmatter declares. The rest of this chapter is an account of that reading process and its consequences for anyone who authors harness files.

Tip: The full mechanics of the pre-skill loading stages -- help, brief-log, budget-eval, pending-check, ref-load, constitution -- are documented in Vol. 3, Ch. 1: The Lifecycle Pipeline. This chapter reads those same stages through the question they raise for authoring: given that the agent reads only what the pipeline loads, how should the harness be written so the right things get read?

Context-Window Budgets

The context window is finite. Every token spent loading a reference file is a token unavailable for the skill's actual work and, more subtly, one more token competing for the model's attention. SEJA treats context as a budget to be spent deliberately, and it lets each skill declare how much it wants to spend through a single frontmatter field: metadata.context_budget. The pre-skill budget-eval stage reads this field and loads accordingly. The field takes one of three tiers; standard is the default when the field is absent.

Tier What budget-eval loads Downstream effect
light Nothing beyond the brief-log entry -- no briefs, no reference files. The ref-load and constitution stages are skipped entirely. The agent runs on the skill body and its own priors, nothing else.
standard (default) The briefs index -- a compact generated summary -- rather than the full briefs file. Proceeds to orphan detection, then ref-load. Mandatory references plus skill-declared references are loaded.
heavy The full briefs file with recency windowing (the first 50 entries, newest first, with older ones summarized as a count) and the plan index. Proceeds to orphan detection and the compaction warning, then ref-load.

The tiers are chosen to match a skill's genuine need for history. A skill that reasons over the arc of the project -- /plan, /implement, /critique -- carries context_budget: heavy, because prior briefs and the plan index are the material it works from. A skill that produces a bounded artifact from a fresh prompt -- /design, /document, /communicate -- carries standard, loading a compact briefs index rather than the full log. The light tier is the austere case: brief-log only, no references, no constitution. It exists for invocations where loading governance context would cost more than it returns.

A budget is a governance decision, not just a performance knob. The light tier skips the constitution stage. A skill declaring light therefore runs without the project's immutable principles in context. That is acceptable only for invocations that cannot violate those principles -- a help lookup, a trivial query. Raising a skill to heavy to "be safe" is not free either: it crowds the window with history the skill may never consult, diluting attention on the instructions that matter. The tier is a claim about what the skill needs to read well.

Note that the pre-skill pipeline itself is an ordinary skill in this respect. Its own SKILL.md declares context_budget: standard and references: [] -- it loads the mandatory triad but no skill-specific references, because its job is to load context for other skills, not to reason from a reference set of its own.

Eager and Lazy Reference Loading

The budget tier decides how much history to load. A second, orthogonal decision governs how the skill's reference files load: all at once, or on demand. This is the eager-versus-lazy distinction, and it turns on whether the skill's frontmatter declares an eager_references field alongside its references list. The pre-skill ref-load stage reads both fields and chooses a mode.

Mode 1 -- Eager-only (no eager_references field)
Every file listed in metadata.references is read and injected into context immediately, before the skill body runs. This is the legacy behavior: simple, predictable, and appropriate when a skill's references are few and used on nearly every invocation. An empty references: [] is valid and means the skill intentionally loads no skill-specific references at all.
Mode 2 -- Demand-pull (eager_references present)
The files listed in eager_references are loaded immediately, alongside the mandatory triad. Any file in references that is not also in eager_references becomes lazy: it is not read at load time. Instead, pre-skill emits an "Available references" block -- a compact numbered list naming each lazy file with a trigger hint derived from its name -- and the agent reads a lazy file only when the work in front of it actually calls for that reference. An empty eager_references: [] is also valid: it makes every skill-specific reference lazy, loading only the mandatory triad upfront.

The mandatory triad is loaded in both modes regardless of budget (at standard and heavy): the project's conventions.md, permissions.md, and constraints.md. Everything past that triad is what the eager/lazy machinery governs.

A concrete example makes the mechanism legible. The /implement skill declares context_budget: heavy and a demand-pull reference set: 

metadata:
  context_budget: heavy
  eager_references:
    - product-design/product-design-as-coded.md
    - product-design/product-design-as-intended.md
    - general/report-conventions.md
    - general/coding-standards.md
  references:
    - product-design/product-design-as-coded.md
    - product-design/product-design-as-intended.md
    - general/report-conventions.md
    - general/coding-standards.md
    - product-design/standards.md
    - product-design/security-checklists.md
    - general/review-perspectives.md

The four files in eager_references load upfront: they are needed on essentially every implementation step, so paying for them eagerly is justified. The three files in references that are not repeated in eager_references -- standards.md, security-checklists.md, and review-perspectives.md -- stay lazy. A step that touches backend code pulls standards.md; a step touching authentication pulls security-checklists.md; the quality gate pulls review-perspectives.md. A step that touches none of these pays for none of them. The design keeps a history-heavy, reference-rich skill from loading its entire reference set on every single step.

Demand-pull is, in the vocabulary of this volume, a bet about the model reader. It assumes the agent can recognize, from a trigger hint and the shape of the work, when a lazy reference is relevant -- and will pull it. That bet is usually sound and occasionally not, which the counter-reading below takes up.

Attention, Ordering, and What the Agent Sees First

Loading a file into the context window is necessary but not sufficient for the agent to act on it. A language model distributes attention unevenly across its context, and that distribution is shaped by position, salience, and repetition. Two instructions that are both present in the window are not thereby equal: the one that appears earlier, or is stated more explicitly, or is repeated, tends to exert more pull on the model's output. This is the practical reality behind SEJA's authoring conventions, and it is worth stating plainly because it is easy to forget when writing harness prose.

Why frontmatter order matters

Because frontmatter is parsed by tooling, one might assume field order is irrelevant -- a YAML mapping is unordered by the standard. But the frontmatter is also read by the agent as the first thing it encounters in a skill file, and the same is true of the body that follows. Ordering matters wherever a human or the model reads top-to-bottom rather than by key lookup. The name and description fields lead because they are the skill's identity and its one-line self-description -- what the agent sees first when deciding what this skill is for. The operative instructions in the body are sequenced so that the most binding constraints and the canonical procedure appear early, before the variations and edge cases. An instruction buried below three screens of exception-handling competes for less attention than one stated at the top.

What the agent can miss

The corollary is that the agent can miss things that are present. A constraint stated once, late, in a subordinate clause, inside a reference file that loaded lazily and was pulled reluctantly, is a constraint the model may not weight. SEJA's defenses against this are deliberate redundancy where redundancy is cheap and enforcement where it is not: the mandatory triad is loaded on every non-light invocation so that permissions and constraints are never merely "available"; the constitution is re-injected every standard/heavy invocation rather than trusted to persist; and hard limits are backed by validation scripts and pre-commit hooks rather than by instruction-following alone. The lifecycle chapter calls this defense-in-depth. Read from the agent's side, it is an admission that reading is fallible and that important constraints cannot rest on the hope that the model attended to them.

Why designer_description exists

A striking piece of evidence that the harness takes its own reading seriously is the designer_description field. It appears in the frontmatter of reference files, agents, and rules, and it is governed by its own authoring rubric, general/designer-copy-voice.md. Its purpose is specifically not to instruct the agent at load time. It is a human-facing paragraph, written in first person ("I", the file speaking) addressed to "you" (the designer), that is surfaced in the call-graph viewer's side panel -- a rendered explanation of what a node is for, in the harness's own voice, so the whole viewer reads as one system speaking rather than a patchwork of machine docstrings.

Why does a field whose reader is a human belong in a chapter about how the agent reads? Because it marks the boundary the harness draws between the two audiences. The description field is terse, machine-oriented, and load-bearing at invocation time; the designer_description is narrative, human-oriented, and load-bearing only in the viewer. The harness maintains both deliberately, and its marker governance (see below) forbids collapsing the human-facing narrative into the machine-facing terse form during conciseness passes. The existence of two descriptions, held apart by rule, is the harness acknowledging that it is read by two very different readers and refusing to let either reading degrade the other.

Tip: The governance of designer_description and the other markers the agent reads and (narrowly) writes -- STATUS, ESTABLISHED, the File Maintainer Classification that decides who may edit what -- is the subject of Vol. 2, Ch. 4: The Marker System. This chapter treats markers only as signs the agent parses; that chapter treats them as a governed writing surface.

Critical Counter-Reading: The Limits of Reading a Reader

Everything in this chapter is written in the confident register of mechanism -- "the agent sees this first," "attention favors earlier tokens," "demand-pull assumes the model will recognize relevance." That register earns a warning. The harness reasons about the agent's "attention" from the outside, and reasoning about a model's interior from the outside is exactly the kind of inference this volume has elsewhere urged caution about.

Attention is a metaphor, not an observation

We do not observe the model attending. We observe outputs and retrofit an account of attention that would explain them. The statement "an instruction stated early exerts more pull" is a serviceable heuristic derived from aggregate behavior, not a measured property of a specific invocation. Model architectures change; the positional and salience effects that hold today may weaken or invert with the next model. SEJA's ordering conventions are therefore defensive heuristics against a moving target, not exploits of a fixed mechanism. Authors should hold them as good practice with an expiry date, not as laws.

The harness cannot verify that a reference was read

Loading a file into the context window guarantees the file is present; it guarantees nothing about whether the model conditioned on it. A lazy reference emitted in the "Available references" block may go unpulled when it was needed, and no stage of the pipeline can detect the omission -- the pipeline knows what it offered, not what the agent used. This is why the harness leans on out-of-band enforcement (validation scripts, hooks, the human in the loop at decision points) for anything it cannot afford to have missed. The honest position is that the eager/lazy machinery optimizes availability, and availability is a necessary but not sufficient condition for correct behavior.

Where SEJA may over- or under-engineer

The budget tiers and eager/lazy split are a real cost paid against a benefit that is hard to measure. It is plausible that the harness over-engineers here: three tiers and a two-list reference scheme add cognitive load for authors and surface area for misconfiguration, in service of context savings that a larger context window or a more capable model might render moot. It is equally plausible that it under-engineers: the scheme still treats reference relevance as something the author declares in advance and the model recognizes at runtime, when a more principled approach might retrieve references by semantic match to the task at hand. SEJA's current design is a defensible middle position, chosen for legibility and auditability over sophistication -- but it is a position, and this volume does not present it as the settled answer.

Open questions

Three questions remain genuinely open, and naming them is more honest than papering over them:

  • Read-verification. Is there any reliable signal, short of behavioral inference, that a loaded reference actually shaped an output? Without one, the harness's reasoning about its own reading stays a well-motivated guess.
  • Tier stability across models. The light/standard/heavy tiers were calibrated against particular model behaviors. How much of that calibration survives a model change, and who re-calibrates it?
  • The authoring burden of ordering conventions. If "put binding constraints early" is a heuristic against a moving target, how much author effort should be spent optimizing order versus investing in enforcement that does not depend on the model attending at all?

The chapter closes the volume by turning its theory on the harness's own reader, and it ends by conceding that this reader is the one thing in the whole account we cannot read directly. That concession is not a failure of the theory; it is the theory being consistent with itself. A harness grounded in the claim that meaning must cross a gap between communicators has no license to pretend the gap between itself and its agent has been closed.
