Skills In Depth

Skill System Overview

SEJA organizes agent capabilities into 17 skills: 15 user-facing skills invoked via slash commands, plus 2 internal lifecycle hooks (pre-skill and post-skill) that run automatically before and after every user-facing skill invocation. Skills are the fundamental unit of work in the harness.

The Canonical Lifecycle Path

Skills are designed to be invoked in a specific order that moves work from understanding through design, implementation, validation, and reflection. The canonical lifecycle path is: 

/research (or /explain)
    |
    v
/design  |  /plan
    |
    v
/implement
    |
    v
/critique
    |
    v
/document  |  /communicate
    |
    v
/reflect

On the first iteration, /seja-setup hands off to /design to configure the project. From iteration 2 onward, start with /research (or /explain) to investigate what you are about to change, then branch into /design when intent needs to change or into /plan when it does not.

Skill Dispatch Mechanism

Every skill invocation follows the same dispatch sequence:

  1. The user invokes a slash command (e.g., /plan Add user auth).
  2. The skill's SKILL.md file is read and its YAML frontmatter parsed for metadata: name, description, argument hints, context budget tier, and reference file lists.
  3. pre-skill runs its 6-stage pipeline (help, brief-log, budget-eval, pending-check, ref-load, constitution) to set up context.
  4. The skill body executes its mode-specific logic.
  5. post-skill runs its 13-step pipeline (brief completion, as-coded alignment, QA log, commit, index regeneration, telemetry, next-step suggestions) to close out the invocation.

Context Budget Tiers

Each skill declares a context budget tier in its YAML frontmatter that controls how much project state is loaded into the agent's context window during pre-skill:

Tier Loads Used by
light Brief-log only. Skips all reference files, briefs index, and constitution. Skills that need minimal context (e.g., /help, /pending)
standard Briefs index (not full briefs), mandatory references (conventions.md, permissions.md, constraints.md), skill-specific references (eager and lazy), and constitution. Most skills (/research, /explain, /design, /reflect)
heavy Full briefs with recency windowing (first 50 entries), plan index, mandatory references, skill-specific references, and constitution. Skills that need broad project awareness (/plan, /implement, /critique)

Within the standard and heavy tiers, skills can further control reference loading via eager vs. lazy declarations. Eager references are loaded immediately during pre-skill; lazy references are listed as available but only loaded on demand when the skill needs them.

/research

Purpose

Investigates the codebase, architecture, or design decisions and produces actionable recommendations. Use /research when you need guidance on a design decision, want to understand trade-offs, or need an overview of what exists. Two modes: research (default, question-driven Q&A with perspective analysis) and inventory (--inventory, codebase element catalog). From iteration 2 onward, /research is the usual lifecycle entry point.

Parameters

ParameterDescription
<question or topic>The question or topic to research (required)
--inventory <pattern>Switch to inventory mode: catalog codebase elements matching the pattern
--deepActivate structured expert council debate for high-stakes decisions

Prerequisites

No strict prerequisites. Works on any project with or without design files. When product-design/product-design-as-coded.md exists, it is loaded eagerly to provide design context.

Workflow

  1. Pre-skill runs and loads references (as-coded file eagerly; as-intended, shared definitions, report conventions, review perspectives on demand).
  2. The agent researches the question thoroughly, reading codebase files, design docs, and searching the web as needed.
  3. Expert analysis runs: in standard mode, the research-reviewer agent evaluates from multiple perspectives; in --deep mode, the council-debate agent convenes a 5-7 member expert council.
  4. A structured report is saved with Q&A log, perspective synthesis, and prioritized recommendations (HIGH/MEDIUM/LOW).
  5. If design decisions are detected, a decision-extract proposal flow offers to create structured D-NNN entries.

Subagent Delegations

research-reviewer
Standard mode: evaluates the question against applicable review perspectives and returns prioritized recommendations.
council-debate
--deep mode: runs a 2-round structured debate across a 5-7 member expert council with named archetypes.

Reference Files Loaded

Eager: product-design/product-design-as-coded.md. Lazy: product-design/product-design-as-intended.md, general/shared-definitions.md, general/report-conventions.md, general/review-perspectives.md, template/docs/ddr.md.

Expected Outputs

Research mode: _output/research-logs/research-<id>-<slug>.md with header, tags, Q&A log, and recommendations summary. Inventory mode: _output/inventories/inventory-<id>-<slug>.md with a structured catalog of matched elements.

Common Mistakes

Skipping /research and going straight to /plan
Leads to plans that miss architectural context or existing patterns. Research first to understand the landscape, especially from iteration 2 onward.
Using standard mode for high-stakes architectural decisions
Standard mode uses a single reviewer agent. For decisions with significant trade-offs (e.g., framework migration, data model redesign), use --deep to activate the expert council debate.
Not following up on decision-extract proposals
When the skill detects design decisions and offers D-NNN entries, deferring them is fine, but skipping them entirely loses the design rationale while it is fresh.

/explain

Purpose

Produces clear explanations of how parts of the system work, with visual diagrams and analogies. Six mode types cover different explanation needs: architecture (system structure and design choices), behavior (emergent behavior from the user's perspective), behavior-evolution (how behavior changed over time), code (how code works, aimed at junior developers), data-model (entity relationships and refactoring opportunities), and drift (compare as-coded and as-intended design specs with optional sync).

Parameters

ParameterDescription
architecture [brief]Explain system architecture, component relationships, and design choices
behavior [brief]Explain emergent behavior from a user's perspective
behavior-evolution [brief]Explain current behavior AND how it evolved over time
code [brief]Explain how code works, aimed at junior developers
data-model [brief]Explain data model, pitfalls, and refactoring opportunities
drift [scope]Compare as-coded and as-intended specs. Scope: all, conceptual-design, metacomm, --promote, --scope since-plan plan-NNNNNN

Prerequisites

No strict prerequisites for general modes (architecture, behavior, code, data-model). The drift mode requires product-design/product-design-as-intended.md and product-design/product-design-as-coded.md to exist for meaningful comparison.

Workflow

  1. Pre-skill runs and loads shared definitions and report conventions eagerly.
  2. Mode detection determines which explanation type to produce (prompts the user if not specified).
  3. For general modes, the skill delegates to a specialized generator agent with the brief and output path.
  4. For drift mode, the skill runs inline: reads as-intended and as-coded files, compares section by section, produces a drift summary, and optionally offers a sync workflow or promote workflow.
  5. The report is saved and post-skill commits it.

Subagent Delegations

explanation-generator
Handles behavior, code, and data-model modes.
architecture-explainer
Handles architecture mode with a multi-phase survey/identify/write workflow.
evolution-explainer
Handles behavior-evolution mode by mining plan history and building timelines.

Reference Files Loaded

Eager: general/shared-definitions.md, general/report-conventions.md. Lazy: product-design/product-design-as-coded.md, product-design/product-design-as-intended.md.

Expected Outputs

Each mode produces a report in its respective output directory: behavior-<id>-<slug>.md, architecture-<id>-<slug>.md, evolution-<id>-<slug>.md, dev-onboarding-<id>-<slug>.md, data-model-<id>-<slug>.md, or research-<id>-<slug>.md (drift mode).

Common Mistakes

Using /explain to generate documentation for others
/explain answers your questions about the system. For artifacts intended for other audiences, use /document, /communicate, or /onboard.
Running drift without design files
Drift mode compares as-intended and as-coded specs. If neither file exists, the comparison is empty. Run /design first to create the design intent artifacts.

/design

Purpose

Defines or updates a project's design foundations: stack choices, conventions, conceptual design (entities, permissions, UX patterns), metacommunication intent, standards, and constitution. Serves both initial configuration (after /seja-setup) and ongoing design evolution. Six modes cover the design lifecycle: interactive questionnaire (default), from a pre-filled spec file, adding documentation templates, generating a blank spec, interview-driven conversation, and updating existing design sections.

Parameters

ParameterDescription
[spec-file-path]Path to a pre-filled spec file for automated configuration (Mode 2)
--mode interviewRun in Interview-Driven mode: conversational intake instead of fixed questionnaire (Mode 5)
--generate-specGenerate a blank spec skeleton to fill out offline (Mode 4)
--add-docsAdd documentation templates to an existing project (Mode 3)
update <section-slug>Jump directly to an update flow for a specific section. Valid slugs: stack, conceptual, metacomm, backend-standards, frontend-standards, ux-standards, ui-standards, i18n, security, testing, constitution, full

Prerequisites

For initial design: /seja-setup should have been run first to scaffold the harness topology and populate conventions.md with stack definitions. For design updates: product-design/conventions.md and product-design/product-design-as-intended.md must exist.

Workflow

  1. Detection logic evaluates invocation arguments and the state of product-design/ files to determine the active mode (1-5 or Design Update).
  2. For initial design (Modes 1, 2, 5): walks the user through a questionnaire or interview to gather stack choices, conceptual design, metacommunication, and standards.
  3. Templates are instantiated from .claude/references/template/ into product-design/, populating design-intent artifacts with the user's answers.
  4. A verification pass checks semantic fidelity between questionnaire answers and generated files, fixing gaps.
  5. For Design Update: shows current summary, offers an interactive menu to update specific sections, and regenerates dependent files.

Subagent Delegations

/design does not delegate to subagents. All work runs inline in the current context.

Reference Files Loaded

All references loaded eagerly (no eager/lazy split): general/report-conventions.md, general/review-perspectives.md, general/shared-definitions.md. Templates in .claude/references/template/ are read during instantiation.

Expected Outputs

Generates or updates files in product-design/: conventions.md, constitution.md, product-design-as-intended.md, ux-research-results.md, standards.md, design-standards.md, security-checklists.md, and (for brownfield projects) product-design-as-coded.md. Also amends CLAUDE.md with design-intent references.

Common Mistakes

Running /design without /seja-setup first
/design expects the harness topology and conventions.md to already exist. Run /seja-setup to scaffold the project structure before configuring design intent.
Confusing /design with /plan
/design defines what to build and why (entities, permissions, metacommunication). /plan defines how to build it. Design comes before planning in the lifecycle.
Skipping the verification pass
The verification pass checks that generated files faithfully reflect questionnaire answers. Interrupting the skill before verification completes leaves semantic gaps in the design artifacts.

/plan

Purpose

Creates a step-by-step plan for a feature, bug fix, or improvement. Three modes: standard (single plan, default), lightweight (--light, quick proposal for small changes), and roadmap (--roadmap, full product roadmap with dependency-aware execution waves). Each plan is a self-contained artifact that /implement can execute without additional context.

Parameters

ParameterDescription
<brief>Description of the task to plan (required)
--lightGenerate a lightweight proposal instead of a full plan
--planForce single-plan mode (skip auto-detection)
--roadmapGenerate a full product roadmap with dependency-aware waves
--from-spec <path>Parse roadmap from a pre-filled spec file (use with --roadmap)
--autoAuto-generate roadmap from project reference files (use with --roadmap)
--only-unimplementedScope roadmap to REQ items lacking STATUS markers (use with --roadmap --auto)
--framing metacommFrame the brief as a designer's metacommunication message (I/you phrasing)
--review <level>Override complexity-gated review depth (light, standard, deep)

Prerequisites

product-design/conventions.md must exist (design guard). If missing, the skill stops and directs the user to run /design first. Research should typically precede planning to ensure architectural context is understood.

Workflow

  1. Design guard verifies conventions.md exists. Mode detection determines standard, lightweight, or roadmap based on flags or brief analysis.
  2. The plan is decomposed into steps, each with Files, References, Depends on, Interface, Verify, Tests, Docs, Deploy, and Traces metadata.
  3. A complexity-gated two-phase review runs: Phase 1 shortlists 3-6 perspectives from the 16 available; Phase 2 runs targeted deep-dives on deferred concerns.
  4. The plan file is saved with amendments from the review incorporated.
  5. Post-skill files an implement pending action so the plan is tracked for execution.

Subagent Delegations

plan-reviewer
Runs the two-phase perspective review on the drafted plan and returns a review log with amendments.

Reference Files Loaded

Eager: product-design/product-design-as-coded.md, product-design/product-design-as-intended.md, general/report-conventions.md, general/coding-standards.md, general/review-perspectives-index.md. Lazy: product-design/standards.md, product-design/security-checklists.md, product-design/design-standards.md, general/review-perspectives.md, general/review-log-template.md, template/plan-step.md, template/roadmap-summary.md, template/proposal.md.

Expected Outputs

Standard mode: _output/plans/plan-<id>-<slug>.md with header, steps, review log, and Q&A log. Lightweight mode: _output/proposals/proposal-<id>-<slug>.md. Roadmap mode: _output/roadmaps/roadmap-<id>-<slug>.md plus individual plan files for each work item.

Common Mistakes

Writing vague step descriptions
Each step must be self-contained enough for a fresh subagent to execute it without prior context. Include specific file paths, function names, and verification criteria.
Skipping the Verify field
Steps without Verify criteria cannot be objectively confirmed as complete. Every step should have at least one testable assertion.
Not checking file existence during planning
Steps that reference files which do not exist will fail during implementation. Verify that referenced source files exist before finalizing the plan.

/implement

Purpose

Executes a previously approved plan step by step. Four execution modes: auto (default, each step in a fresh subagent), manual (--manual, sequential in current context), roadmap (--roadmap, all plans wave by wave), and pending (--pending, execute all pending plans). Creates a rollback branch before starting and includes a Quality Gate at the end (validation, code review, tests, smoke tests).

Parameters

ParameterDescription
<planned-item-id>The 6-digit ID of the plan to execute (required unless --roadmap or --pending)
--manualExecute all steps sequentially in the current context
--roadmap <roadmap-id>Execute all plans in a roadmap wave by wave
--pendingExecute all pending plans by generating a lightweight roadmap
--max-iterations NCap auto-mode iterations (default: 20)
--dry-runPreview changes without applying them
--skip-checksSkip the Quality Gate at the end
--skip-docsSkip automatic documentation generation; file a pending entry instead
--checkpoint <wave|plan|none>Checkpoint granularity for roadmap mode (default: wave)

Prerequisites

A plan file must exist at _output/plans/plan-<id>-*.md (created by /plan). The plan should have been reviewed and approved before execution.

Workflow

  1. The plan file is located via the macro index. A rollback branch (pre-plan-<id>) is created from the current HEAD.
  2. In auto mode, each step is dispatched to a fresh general-purpose subagent with the step description and a progress file for cross-iteration learnings.
  3. Steps with explicit Tests: fields follow a TDD red-green cycle: write the failing test first, then implement until it passes.
  4. The Quality Gate runs at the end: /critique validate, /critique review, test runner, and optionally smoke tests. A generator-critic loop retries critical findings up to 2 times.
  5. Post-skill handles as-coded alignment, documentation auto-run, pending action creation, and commit.

Subagent Delegations

general-purpose (executor agents)
Auto mode: each plan step runs in a fresh subagent with the step description, plan context, and progress file. The skill constructs prompts dynamically from step metadata.
standards-checker
Quality Gate: runs project validation scripts.
code-reviewer
Quality Gate: reviews changes against quality perspectives.
test-runner
Quality Gate: runs the project test suite.

Reference Files Loaded

Eager: product-design/product-design-as-coded.md, product-design/product-design-as-intended.md, general/report-conventions.md, general/coding-standards.md. Lazy: product-design/standards.md, product-design/security-checklists.md, general/review-perspectives.md.

Expected Outputs

The plan file is updated with step checkboxes marked as done. A progress file (plan-<id>-progress.md) tracks cross-iteration learnings during auto mode and is merged into the plan file at wrap-up. Source code changes are committed per the plan steps.

Common Mistakes

Implementing without a plan
Ad-hoc implementation bypasses the design guard, review process, and traceability. Always create a plan first, even for small changes (use /plan --light).
Amending commits when a new commit is safer
In projects with concurrent sessions, --amend can absorb unrelated modified files. Prefer a follow-up commit over amending an existing one.
Skipping the Quality Gate
The Quality Gate catches regressions that individual step execution misses. Use --skip-checks only when you plan to run critique separately.

/critique

Purpose

Unified quality gate with ten mutually exclusive modes covering validation scripts, code review, smoke tests, preflight checks, harness health diagnostics, test plan generation, documentation consistency, git freshness, telemetry analysis, and semiotic inspection. One skill for all "is it OK?" questions.

Parameters

ParameterDescription
validate [scope]Run project validation scripts. Scope: all, i18n, auth, migrations, constants, po, coverage, tests, spec
review [scope]Structured code review against quality perspectives. Scope: staged, file path, or directory
smoke [scope]Runtime smoke tests. Scope: all, api, ui
preflight [scope]Combined validate + review in one pass. Scope: staged, all, or directory
healthHarness self-diagnosis (9 built-in checks). Supports --verbose, --source <path>
test-plan [brief]Generate a structured manual test plan
docs [--plugins LIST]Documentation consistency check via 6 plugin-based scanners
freshnessCompare local branches to upstream; advisory-only, never pulls
telemetryUsage analytics from telemetry.jsonl
semiotic-inspection [scope]SIM-based communicability evaluation of an interface
--depth <level>Override review depth for review and preflight modes (light, standard, deep)

Prerequisites

Varies by mode. validate requires validation scripts registered in the plugin registry. review requires code changes to review (staged, a file, or a directory). smoke requires a running application and smoke test registry. health requires the harness to be installed.

Workflow

  1. Pre-skill runs and parses the mode argument. Stack filtering applies to validate and preflight modes, loading only scripts matching the project's backend and frontend frameworks.
  2. The mode-appropriate agent or script is dispatched with the scope argument.
  3. Results are collected into a structured critique report with pass/fail/warning classifications.
  4. The report is saved to _output/critique-logs/ and presented to the user.

Subagent Delegations

standards-checker
validate and preflight modes: runs project validation scripts and aggregates results.
code-reviewer
review and preflight modes: reviews code against the 16 quality perspectives at the specified depth.
test-runner
smoke mode: runs the configured smoke test suite.
harness-health-evaluator
health mode: runs 9 built-in harness self-diagnosis checks.
test-plan-generator
test-plan mode: generates a structured manual test plan from a brief and recent plans.
semiotic-inspector
semiotic-inspection mode: conducts a SIM evaluation of interface communicability.

Reference Files Loaded

All loaded eagerly (no eager/lazy split): general/report-conventions.md, product-design/standards.md, product-design/design-standards.md, product-design/security-checklists.md, general/review-perspectives.md, general/review-perspectives-index.md, general/review-log-template.md.

Expected Outputs

_output/critique-logs/critique-<id>-<slug>.md containing the mode-specific report. All modes except telemetry produce a saved report. test-plan mode additionally produces a test plan artifact.

Common Mistakes

Running review without reading the diff first
The review agent needs something to review. Ensure changes are staged or specify a file or directory path as the scope.
Running all critique modes when one is sufficient
Each mode serves a specific purpose. Use validate for script-based checks, review for code changes, preflight for pre-merge, and health for harness diagnostics. Running all of them when only one applies wastes context budget.
Treating advisory findings as blocking
The review distinguishes between critical findings (must fix) and advisory findings (nice to have). Critical issues block merges; advisory ones can be deferred.

/reflect

Purpose

Helps you step back and reflect on specific work through two explicit lenses: the product lens (what you built, whether it does what you intended) and the practice lens (how you worked, what patterns emerge). Three modes: conversational (default, pick artifacts and write your reflection), deep (--deep, visualization-backed practice evolution narrative), and telemetry (--telemetry, statistical pattern mining from usage data).

Parameters

ParameterDescription
(no arguments)Conversational mode: pick artifacts, choose a lens, write your reflection
--deep [scope]Deep reflection mode with event matrix visualization and practice narrative
--telemetryStatistical telemetry mining mode (V1 analysis primitives)
--since <duration>Time window for --telemetry or --deep. Accepts ISO datetime or Nd suffix (default: 30d)
--skill <name>Filter telemetry to a single skill (use with --telemetry)
--dry-runPrint the report without writing to disk (use with --telemetry)

Prerequisites

No strict prerequisites. Works best when there are artifacts to reflect on (plans, research reports, or other outputs). The --deep and --telemetry modes require telemetry.jsonl to exist with data within the specified time window.

Workflow

  1. Conversational mode: asks the user to pick a scope (recent plans, recent research, specific artifact, time window, or free-form), summarizes chosen artifacts, asks which lens (product, practice, or both), poses the lens-appropriate open-ended question, and records the user's response verbatim.
  2. Deep mode: reads telemetry and briefs within a time window, optionally filtered by a scope keyword, and produces an event matrix visualization (Vega-Lite), a transition graph (Graphviz DOT), and a past-tense practice evolution narrative.
  3. Telemetry mode: runs 5 analysis primitives (sequence mining, duration anomalies, revision rate, stuck loops, decision reversals) over the telemetry data.
  4. All modes save a reflection report to _output/reflections/.

Subagent Delegations

/reflect does not delegate to subagents. All modes run inline using co-located Python scripts for data processing and visualization generation.

Reference Files Loaded

Eager: product-design/conventions.md, general/constraints.md. Lazy: general/shared-definitions.md, general/skill-graph.md, general/coding-standards.md.

Expected Outputs

_output/reflections/reflection-<id>-<slug>.md containing the reflection report. Deep mode additionally produces companion visualization files (event matrix and transition graph in SVG, HTML, and Vega-Lite/DOT formats).

Common Mistakes

Expecting prescriptive recommendations from /reflect
/reflect is strictly non-prescriptive: it records observations and your own words, never "you should" or "consider changing." For prescriptive follow-up, use /research.
Reflecting on work that has not been implemented
The practice lens examines how you worked; if the research or plan has not been executed yet, there is no practice to reflect on. Implement first, then reflect.

/document

Purpose

Generates or updates project documentation based on plan Docs: fields, auto-detection of recent git changes, or explicit type selection. Supports six documentation types: readme, contextual-help, api-reference, ddr, help-center, and changelog. Runs after /implement to capture user-facing changes while the implementation is fresh.

Parameters

ParameterDescription
<scope>What to document: a file path, module, feature name, or general topic
--plan <id>Read Docs: fields from a plan file and generate documentation for each identified need
--auto-detectDetect documentation needs from recent git changes using heuristics
--type <type>Force a specific doc type: readme, contextual-help, api-reference, ddr, help-center, or changelog
--since <ref>Override auto-detect bounding window (date, git SHA, or last)
--full-historyIgnore per-doc-type bounding windows and scan full git history

Prerequisites

  • product-design/conventions.md must exist (or template fallback)
  • For --plan: the plan file must exist with non-N/A Docs: fields
  • For --auto-detect: a git history with recent changes

Workflow

  1. Run pre-skill to load references and log the brief
  2. Determine scope and documentation type via mode detection (plan-driven, auto-detect, type-targeted, or bare scope)
  3. For --auto-detect: compute per-doc-type bounding windows from the briefs index to avoid re-documenting unchanged areas
  4. Launch one document-generator agent per doc type (parallel for multiple types), passing the resolved template, quality guide, and project context
  5. Record document run metadata (HEAD SHA, generated types) for future bounding-window calculations

Subagent Delegations

document-generator
Produces the actual documentation file(s). Receives the doc type, scope, template path, quality guide, and project context. Launched once per doc type; multiple types run in parallel.

Reference Files Loaded

  • Eager: general/documentation-quality.md, general/report-conventions.md
  • Lazy: none (standard budget tier)

Expected Outputs

  • Documentation files in project-appropriate locations (e.g., README.md, docs/ subdirectories)
  • Updated briefs entry with SHA and generated doc types for future bounding windows

Common Mistakes

Running /document before /implement
Documentation should reflect implemented behavior, not planned behavior. Run /implement first so the generator reads actual code.
Using --auto-detect without understanding bounding windows
Auto-detect scans only changes since the last /document run of each type. Use --full-history for a clean-slate scan, or --since last to bound by the most recent run of any type.
Confusing /document with /communicate
/document produces project documentation (README, API reference, changelog). /communicate produces stakeholder-facing material tailored to a specific audience segment.

/communicate

Purpose

Generates tailored communication material for a specific stakeholder audience segment. Four audiences are supported: Evaluators (CTOs, tech leads assessing adoption), Clients (project commissioners and funders), End Users (people using the built software), and Academics (researchers in semiotic engineering, HCI, or AI-assisted development). Each audience gets content in their language, focused on what matters to them.

Parameters

ParameterDescription
<audience>Target audience: evaluator(s) / client(s) / end-user(s) / academic(s), or tags EVL / CLT / USR / ACD
--format <type>Output format: md, html, or both (default: both)
--allGenerate material for all 4 audience segments in parallel
--source <file>Path to existing advisory or markdown file to reformat for the target audience
--deepInclude Deep-dive content sections

Prerequisites

  • product-design/product-design-as-coded.md should exist (provides the conceptual design the material is grounded in)
  • product-design/conventions.md must exist (or template fallback)

Workflow

  1. Run pre-skill to load references and log the brief
  2. Parse arguments and resolve audience tag (EVL, CLT, USR, or ACD); if missing, present an interactive menu
  3. Compute output path in a date-stamped folder (_output/communication/YYYY-MM-DD/) and reserve a global ID
  4. Launch the communication-generator agent with audience template, Diataxis mapping, project context, and output path
  5. Create or update a date-folder index if multiple artifacts exist for the same date

Subagent Delegations

communication-generator
Produces the actual stakeholder material. Receives the audience tag, audience template, Diataxis mapping, project context (conceptual design, conventions, communication style), and output path. In batch mode (--all), one agent per audience runs in parallel.

Reference Files Loaded

  • Eager: general/communication.md, general/shared-definitions.md, general/report-conventions.md, product-design/product-design-as-coded.md
  • Lazy: per-audience templates in general/communication/ (loaded by the generator agent)

Expected Outputs

  • Communication artifacts in _output/communication/YYYY-MM-DD/ with both .md and .html versions (configurable via --format)
  • Date-folder index when multiple artifacts exist for the same date

Common Mistakes

Using /communicate for project documentation
/communicate produces audience-tailored stakeholder material. For project docs (README, API reference, changelog), use /document.
Running without conceptual design
The generator grounds material in product-design/product-design-as-coded.md. Without it, the output lacks project-specific substance. Run /design first to establish the conceptual design.

/onboard

Purpose

Generates a tailored onboarding plan for a new team member based on their role family and expertise level. Three role families (Builder, Shaper, Guardian) crossed with three expertise levels (L1 Contributor, L2 Expert, L3 Leader) produce nine distinct onboarding profiles. Plans include a welcome, day-one foundation, role- and level-specific weeks, a 30-60-90 day timeline, and a prioritised reading list grounded in the actual project codebase.

Parameters

ParameterDescription
<role-family>Role: builder / shaper / guardian (or BLD / SHP / GRD). Combinations allowed (e.g., builder+guardian)
<expertise-level>Level: L1-L3 or aliases (contributor, junior, mid, expert, senior, leader, staff)
[name]Name of the new team member for personalization
--area <focus>Focus area (e.g., backend, frontend, auth)
--format <type>Output format: md, html, or both (default: both)
--allGenerate plans for all 9 role-level combinations in parallel
--all-levels <role>Generate plans for all 3 levels of a single role family
--all-roles <level>Generate plans for all 3 roles at a single level
--batch <specs>Semicolon-separated spec list for parallel generation

Prerequisites

  • product-design/conventions.md must exist (or template fallback)
  • product-design/product-design-as-coded.md should exist for project-specific content

Workflow

  1. Run pre-skill to load references and log the brief
  2. Parse arguments and resolve role tags and level; if missing, present interactive menus for role family and expertise level
  3. Compute output path in a date-stamped folder (_output/onboarding-plans/YYYY-MM-DD/) and reserve a global ID
  4. Launch the onboarding-generator agent with role/level templates, project context, and output path
  5. Verify output files exist and display a result summary

Subagent Delegations

onboarding-generator
Produces the onboarding plan. Receives the role tags, level, name, focus area, role-family template(s), level template, project context, and output path. In batch mode, one agent per spec runs in parallel.

Reference Files Loaded

  • Eager: general/onboarding.md, general/shared-definitions.md, general/report-conventions.md, product-design/product-design-as-coded.md
  • Lazy: per-role templates in general/onboarding/ and per-level templates (loaded by the generator agent)

Expected Outputs

  • Onboarding plan files in _output/onboarding-plans/YYYY-MM-DD/ with both .md and .html versions

Common Mistakes

Confusing role families with job titles
Role families (Builder, Shaper, Guardian) are SEJA abstractions. A "tech lead" might be Builder+Guardian; a "PM who codes" might be Shaper+Builder. Use the combination syntax when a single family does not fit.
Generating all 9 plans when only one person is joining
--all is useful for pre-populating a library. For a single hire, use the targeted invocation with their specific role and level.

/pending

Purpose

Lists and addresses outstanding human actions from the pending ledger. The harness automatically files pending actions during post-skill (e.g., after /implement defers marker flips, after plans identify documentation needs, or when periodic triggers fire). This skill provides the interface to review, resolve, snooze, or dismiss those actions. Twelve action types cover the full lifecycle from marker flips to spec-drift checks to plan execution.

Parameters

ParameterDescription
(none or list)List all pending items with per-item resolution advice
address <id>Run the guided resolution workflow for a specific item
add --type <type> --source <id> --description "<text>"Append a new pending action
done <id>Mark a pending item as done
snooze <id> --until <date>Snooze an item until a future date
dismiss <id> [--reason <text>]Dismiss an item without completing it

Prerequisites

  • The pending ledger (_output/pending.jsonl) must exist (created automatically by post-skill when the first action is filed)

Workflow

  1. Run pre-skill with light context budget (skips pending-check, orphan-check, compaction-check, and constitution to avoid recursion)
  2. For list: run pending.py list --status pending --json, group items by type, and display each with type-specific resolution steps
  3. For address <id>: dispatch based on item type -- marker-flip types (mark-implemented, incorporate-research-markers) get interactive guided workflows; other types get printed resolution advice
  4. For add/done/snooze/dismiss: forward arguments directly to pending.py

Subagent Delegations

None. This skill runs entirely in the main context without delegating to subagents.

Reference Files Loaded

  • Eager: none (light context budget -- only mandatory refs loaded)
  • Lazy: general/shared-definitions.md

Expected Outputs

  • Console output listing pending items with resolution advice
  • State changes in _output/pending.jsonl (done, snoozed, or dismissed entries)
  • For marker-flip types: STATUS or INCORPORATED markers applied to design files via apply_marker.py

Common Mistakes

Ignoring pending items until they accumulate
Pre-skill surfaces a banner when overdue items exist. Address items promptly after /implement rather than letting them pile up -- stale pending actions lose context.
Using done instead of address for marker-flip types
For mark-implemented and incorporate-research-markers types, use address to get the guided marker-flip workflow. Using done closes the item without actually flipping the markers.

/publish

Purpose

Publishes a tagged release to the public SEJA repository via the automated publish pipeline. Wraps tools/publish.py, which handles the full 8-step lifecycle: preflight checks, tag creation, cloning the public repo, syncing harness files, running smoke tests, committing, pushing, and closing the pending PUBLISH: entry. Supports version inference from CHANGELOG.md heuristics or an explicit version argument.

Parameters

ParameterDescription
[version]Version tag to publish (e.g., v0.3.0). When omitted, inferred from CHANGELOG.md and git tags.
--dry-runPreview the full command sequence without executing destructive actions
--yesNon-interactive mode: accept all defaults at confirmation prompts

Prerequisites

  • seja-public/CHANGELOG.md should have content under ## Unreleased
  • Working tree must be clean (no uncommitted changes)
  • The simonedjb/seja remote must be reachable

Workflow

  1. Run pre-skill with light context budget
  2. Resolve the version: use the explicit argument, or run publish.py --infer-version and confirm with the user
  3. Run preflight checks via publish.py --preflight-only --json; auto-fix missing harness changelog if needed; present remaining issues to the user
  4. Execute the full pipeline: python tools/publish.py [version] [flags]
  5. Report outcome: on success, confirm the version and closed pending entry; on failure, relay the script's recovery guidance

Subagent Delegations

document-generator
Invoked only when the preflight detects a missing harness changelog entry. Generates a ## [VERSION] entry in .claude/CHANGELOG.md from structured git history data.

Reference Files Loaded

  • Eager: none (light context budget)
  • Lazy: none

Expected Outputs

  • A git tag on the source repository
  • Updated public repository with synced harness files and prose
  • Closed PUBLISH: pending entry

Common Mistakes

Publishing with a dirty working tree
The preflight will flag uncommitted changes. Commit or stash before publishing to ensure the tag reflects a clean state.
Skipping --dry-run on the first publish
Use --dry-run to preview the full pipeline before committing to a live release. It verifies all preflight conditions without mutating any state.

/seja-setup

Purpose

Manages every harness-state transition in a project: install (copy from source), finalise in place (--here), companion workspace (--workspace), demo bootstrap (--demo), and upgrade (--upgrade). Uses state-driven dispatch: inspects the current directory via detect_setup_state.py and routes to the correct action based on detected state (no-harness, fresh-download, partial-init, finalised, or dev-repo-refuse).

Parameters

ParameterDescription
[target-directory]Path to the target project directory
--hereFinalise SEJA setup in the current directory (use when SEJA was cloned directly)
--workspaceCreate a companion workspace alongside an existing codebase
--demoSet up with the pre-configured TaskFlow demo project
--upgradeUpgrade harness files to the latest SemVer tag (or --version <tag>)
--version <tag>Pin to a specific release tag (e.g., v0.2.0)
--dry-runPreview upgrade changes without applying them

Prerequisites

  • For install: a target directory (new or existing project)
  • For --here: SEJA files already present in the current directory
  • For --upgrade: an existing SEJA installation in the current directory

Workflow

  1. Run pre-skill to load references and log the brief
  2. Detect project state via detect_setup_state.py --json
  3. Route to the appropriate flow: install (copy harness, scaffold CLAUDE.md, populate conventions), finalise (reconcile existing files), workspace (create companion directory), demo (install + pre-fill TaskFlow files), or upgrade (refresh harness files, preserve project data)
  4. For install: run the Section 1 questionnaire to populate conventions.md with stack definitions, scaffold stack-appropriate rules and CLAUDE.md
  5. Hand off to /design for design-intent configuration (entities, permissions, metacommunication)

Subagent Delegations

None. This skill runs entirely in the main context.

Reference Files Loaded

  • Eager: general/shared-definitions.md, template/questionnaire.md, template/conventions.md
  • Lazy: none

Expected Outputs

  • A fully scaffolded project directory with .claude/, product-design/, and _output/ directories
  • Populated CLAUDE.md, product-design/conventions.md, and stack-appropriate rule files
  • A .seja-version file recording the installed version

Common Mistakes

Running /seja-setup inside the SEJA development repository
The skill detects dev-repo state and refuses to run, preventing corruption of the harness source. Use standard git workflows for harness development.
Confusing /seja-setup with /design
/seja-setup scaffolds topology (stack, directory layout, CLAUDE.md, rules). /design defines design intent (entities, permissions, metacommunication, personas, standards, constitution). Setup creates; design refines.

/help

Purpose

Shows what skills are available and explains what each one does. Three layers of progressive disclosure: a no-args overview grouped by workflow category, per-skill detail cards with arguments and related skills, and an interactive category browser with a Mermaid skill-graph visualization. This is the discovery entry point for users new to the harness.

Parameters

ParameterDescription
[skill-name]Show full details for a specific skill (Quick Guide, arguments, category, related skills)
--browseInteractive category browser with skill graph

Prerequisites

  • A SEJA harness installation with .claude/skills/ directory

Workflow

  1. Layer 1 (no args): List all user-facing skills grouped by category (Getting started, Design and plan, Understand the system, Quality and review, Communicate, Housekeeping) with one-sentence summaries
  2. Layer 2 (/help <skill>): Load the skill's Quick Guide, display arguments, category, and related skills from the skill graph
  3. Layer 3 (/help --browse): Scan all skill directories, group by metadata.category, render a Mermaid skill-relationship diagram, and walk the user through picking a category, then a skill to execute

Subagent Delegations

None. This skill runs entirely in the main context.

Reference Files Loaded

  • Eager: none (light context budget)
  • Lazy: general/skill-graph.md (loaded when displaying related skills)

Expected Outputs

  • Console output: skill overviews, detail cards, or interactive category browser
  • No files produced -- /help is purely informational

Common Mistakes

Using /help to execute a skill
/help explains and navigates; it does not perform the work itself. Once you know which skill to run, invoke it directly (e.g., /plan, not /help plan).
Not using --browse for discovery
Layer 3 (--browse) provides the richest exploration experience with category grouping and skill-graph visualization. Use it when you are unsure which skill fits your task.

Running /qa-log before a meaningful conversation
The skill captures the full session; invoking it immediately after a single prompt produces a thin log with little reference value. Wait until the conversation has substance worth preserving.
Confusing standalone and companion modes
Standalone /qa-log writes to _output/qa-logs/. When invoked by post-skill, it writes a companion file next to the parent artifact. You do not need to invoke it manually after a skill invocation -- post-skill handles it.

Common Mistakes

These cross-cutting mistakes span multiple skills and reflect fundamental misunderstandings of how the skill system operates.

Running skills out of lifecycle order
The canonical path exists for a reason: /research builds understanding, /plan decomposes the work, /implement executes the plan, /critique validates the output, and /document captures the result. Skipping /plan and jumping to /implement produces unstructured changes. Skipping /critique before /document risks documenting buggy behavior. The lifecycle is sequential for a reason -- each stage depends on the output of the previous one.
Misunderstanding context budget tiers
The three tiers (light, standard, heavy) control how much context pre-skill loads into the agent's context window. Light skips references and briefs entirely -- appropriate for utility skills like /pending and /help that do not need project context. Standard loads the briefs index and skill-specific references -- the default for most skills. Heavy loads full briefs with recency windowing and the plan index -- used by skills that need broad project awareness. Running a heavy-budget skill in a session that has already consumed significant context can trigger the compaction warning. Starting a fresh conversation is the recommended response.
Skipping pre-skill or post-skill hooks
Pre-skill and post-skill are not optional ceremony -- they are load-bearing lifecycle infrastructure. Pre-skill loads the constitution, references, and permissions that constrain skill behavior. Post-skill updates the as-coded design state, files pending actions, regenerates indexes, and commits changes. A skill that skips post-skill leaves orphaned STARTED briefs, uncommitted files, and stale indexes.
Running /implement on a stale plan
A plan references specific files, line ranges, and design state at the time it was written. If the codebase has changed significantly since the plan was created (e.g., another plan was implemented, or manual edits were made), the plan's assumptions may be invalid. Review the plan's Files section against the current codebase before executing. If drift is significant, regenerate the plan with /plan.
