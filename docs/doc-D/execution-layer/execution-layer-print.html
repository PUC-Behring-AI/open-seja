The Lifecycle Pipeline

Every SEJA workflow follows a structured lifecycle that sequences investigation, design, planning, implementation, quality verification, documentation, and reflection. This chapter documents the canonical path, the pre-skill and post-skill hooks that bookend every skill invocation, the enforcement mechanisms that keep workflows on track, and the conversation trace that records non-skill exchanges.

The Canonical Path

The canonical lifecycle path defines the recommended ordering of skills for a typical feature iteration. Each stage builds on the outputs of the previous one, creating a traceable chain from investigation through reflection. 

/research (or /explain)
    |
/design  |  /plan
    |
/implement
    |
/critique
    |
/document  |  /communicate
    |
/reflect

On the first iteration of a new project, /seja-setup hands off to /design to configure project-specific files. From iteration 2 onward, start with /research (or /explain) to investigate what you are about to change, then branch into /design when design intent needs to change, or into /plan when it does not. The alignment workflow /explain drift reconciles design specs with the as-coded state at any point.

When to Deviate

The canonical path is a recommendation, not a hard gate. Several task shapes justify entering the lifecycle at a different point:

Bug fixes (FIX prefix)
May skip /research when the root cause is already known. The plan includes a root-cause section instead of a separate research artifact.
Documentation-only tasks (DOCUMENT prefix)
May start from /plan directly, since no codebase investigation is needed. The plan's scope is limited to documentation files.
Refactoring (REFACTOR prefix)
May skip /design because refactoring does not introduce new features or change design intent. Existing tests must continue to pass after implementation.

Pre-Skill Stages

Before every skill invocation, the pre-skill lifecycle hook runs a pipeline of 6 composable stages. Three stages are critical (always run): brief-log, budget-eval, and ref-load. Three stages are non-critical (error-isolated, warn and continue): help, pending-check, and constitution. Non-critical stages can be skipped by listing their IDs in the calling skill's metadata.skip_stages frontmatter field.

Stage Critical Purpose Behavior
help No Display skill quick guide Checks if arguments contain --help. If so, reads and displays .claude/skills/<skill>/SKILL-quickguide.md (falling back to the SKILL.md description field). Stops the pipeline -- no further stages or skill body execute.
brief-log Yes Log the skill invocation Obtains UTC time, inserts a STARTED entry into briefs.md (newest first), backfills the conversation trace to link the preceding exchange to this skill, and persists the brief text via brief_state.py for post-skill consumption.
budget-eval Yes Determine context budget Reads the calling skill's metadata.context_budget (default: standard). Three tiers control what gets loaded: light skips all briefs and references; standard loads the briefs index; heavy loads full briefs with recency windowing (50 most recent) plus the plan index. Sub-steps: orphan detection (standard and heavy tiers -- warns about STARTED entries with no matching DONE) and compaction warning (heavy tier only -- warns when more than 8 invocations occurred in the last 2 hours). Legacy stage IDs orphan-check and compaction-check are recognized by these sub-steps.
pending-check No Show overdue pending actions Runs pending.py status --overdue-days 14 --format banner and prints the output verbatim. Purely informational -- never blocks the skill invocation.
ref-load Yes Load reference files Loads three mandatory references: product-design/conventions.md, .claude/references/general/permissions.md, and .claude/references/general/constraints.md. Then loads skill-specific references in one of two modes: eager-only (reads all metadata.references) or demand-pull (reads eager_references upfront, lists remaining refs as available on demand). Skipped entirely for light-tier skills.
constitution No Load project constitution Reads and injects product-design/constitution.md. Skips silently if the file does not exist (backwards compatible with projects that have not generated one). Skipped for light-tier skills.

Context Budget Tiers

The context budget tier, declared in each skill's YAML frontmatter as metadata.context_budget, controls how much historical context is loaded during pre-skill:

Tier Briefs References Constitution
light Brief-log entry only; no history loaded Skipped Skipped
standard (default) Briefs index (compact summary) Mandatory + skill-specific Loaded
heavy Full briefs (50 most recent) + plan index Mandatory + skill-specific Loaded

Post-Skill Steps

After every skill completes, the post-skill lifecycle hook runs a sequence of steps that handle brief completion, telemetry, design alignment, documentation, QA logging, commit safety, index regeneration, and next-step suggestions. Each step writes a checkpoint so the pipeline can resume after a crash.

Step 0 -- Checkpoint Recovery
If a post-skill checkpoint file exists from a prior crashed run, resume from the step after the recorded checkpoint. Stale checkpoints (from a different skill ID) are deleted.
Step 1 -- Brief-Log Completion
Marks the matching STARTED entry in briefs.md as DONE with the current UTC timestamp and optional plan ID. Retrieves the original brief text from brief_state.py.
Step 1b -- Telemetry Recording
Prepares a telemetry record in memory (skill name, ID, outcome, timestamps, token count). The record is flushed to disk at step 8b after commit-dependent fields are available.
Step 2 -- As-Coded Alignment
Runs after /implement (skipped for /plan). Updates product-design/product-design-as-coded.md to reflect what actually shipped: conceptual design entities, metacommunication intents, and journey map statuses. Proposes DONE markers for as-intended items that were implemented. Creates pending actions for verification, testing, and documentation.
Step 2b -- Documentation Auto-Run
Collects non-N/A Docs: fields from the plan. If any exist, offers to run /document --plan <id> immediately or defer to the pending ledger. Can be preset to skip via --skip-docs.
Step 2c -- Design Intent Reminder
Informational message reminding the user to consider promoting implemented items to established status via /explain drift --promote. Does not perform the promotion itself.
Step 2d -- Eager Implement Entry
Runs when the parent skill is /plan. Files an implement pending action for the newly created plan so it appears in the pending ledger as work to execute.
Step 2g -- Pending Action Creation
Creates up to four pending actions from plan metadata after implementation: (i) verify-as-coded when the plan's file count exceeds a configurable threshold, (ii) test-implementation when the plan has a Test Plan section, (iii) update-documentation when documentation was skipped during post-skill, and (iv) an implement mark-done safety net that closes the pending entry filed at /plan completion. Each invocation is silent on success and non-blocking on failure.
Step 3 -- QA Log
Captures the session's Q&A exchanges. Three branches: skip (when the parent embeds its own Q&A, e.g. /research), inline (appends to the artifact file for plans, implementations, roadmaps, and critiques), or companion (creates a sibling QA file for all other artifact types).
Steps 4-6 -- Commit Preparation
Step 4 creates the commit message. Step 5 checks git state (blocks on rebase-in-progress, unmerged conflicts, or detached HEAD; warns on main/master). Step 6 verifies commit scope against expected paths via verify_commit_scope.py.
Step 6b -- Fast Preflight Gate
Runs run_preflight_fast.py as an advisory check. Non-zero exit displays failures and asks whether to proceed. The pre-commit hook (.githooks/pre-commit) is the hard gate.
Step 6c -- Human Markers Verifier
Runs check_human_markers_only.py --staged to detect unauthorized prose mutations in Human (markers) files. Violations trigger an abort recommendation.
Step 7 -- Index Regeneration
Refreshes the briefs index, macro artifact index, cross-references between artifacts, and the decision digest (conditional on research or DECISION_APPEND activity).
Step 7e -- Deferred Artifact Generation
Runs after /implement only. Generates a ## Manual Actions section in the plan file if any step requires post-deployment operator action. Generates or updates _output/docs/deploy.html if any step has a non-N/A Deploy: field, covering Docker, Linux, and Windows deployment instructions.
Step 8 -- Stage and Commit
Stages all affected files (regenerated indexes, as-coded updates, deferred artifacts) and commits. Deletes the checkpoint file on success.
Step 8b -- Telemetry Flush
Enriches the step-1b record with commit-dependent fields (SHA, files changed count, parent skill) and appends it to telemetry.jsonl. Committed as a separate trailing commit to avoid amend divergence. Skipped if step 8 produced no commit.
Steps 9-12 -- Wrap-Up
Step 9 reports any surprises encountered during execution. Step 10 outputs a link to the generated artifact. Step 11 prints the skill-complete banner. Step 12 reads the skill graph and presents contextual next-step suggestions (at most 3 options plus skip), suppressing suggestions already covered by earlier steps.

Worktree Deferred Mode

When the roadmap parallel-wave orchestrator passes --deferred after merging a worktree branch back to main, post-skill runs a reduced pipeline: only steps 0, 1b, 2, 2c, 7, 2g, and 8b execute. The orchestrator handles wave-level briefs, QA, commits, and deferred artifacts.

Enforcement Mechanisms

SEJA enforces lifecycle compliance through four complementary mechanisms, each operating at a different layer:

CLAUDE.md Context Rules
The project's CLAUDE.md is loaded into every agent context window. It declares the canonical lifecycle path, the conversation trace protocol, and key workflow instructions. Because these rules are always present in context, they guide the agent's behavior at every turn without requiring external enforcement.
Pre-Commit Hooks
The .githooks/pre-commit hook (installed via bash .githooks/install.sh) runs two checks on every commit: run_preflight_fast.py (fast validation checks) and check_no_private_leaks.py --staged (prevents private content from leaking into public-facing files). This is the hard gate -- commits that fail these checks are rejected.
Validation Scripts
run_all_checks.py is the CI-independent validation orchestrator. It discovers and runs all registered check scripts with unified exit codes and JUnit XML output. Individual check scripts cover documentation consistency (check_docs.py), design system token drift (check_design_system_token_drift.py), harness structural integrity, and project-specific validations declared in product-design/conventions.md.
Constitution Loading
The pre-skill constitution stage loads product-design/constitution.md into the agent's context before every standard and heavy-tier skill invocation. The constitution declares immutable principles (design authority, epistemic posture, privacy, lifecycle discipline, artifact integrity, authorship voice) that no other reference file can override. Subagents also receive the constitution as part of their prompt for trust boundary enforcement.

Lifecycle Variations

The lifecycle adapts its shape based on the type of work being performed. SEJA uses plan prefixes to signal these variations, and skills adjust their behavior accordingly.

Bug Fixes (FIX Prefix)

Bug fix plans may skip /research when the root cause is already known. The plan includes a root-cause analysis section instead of relying on a separate research artifact. Fix plans are gated by the FIX prefix, which signals that the work addresses an existing defect rather than adding new capability. Post-skill documentation auto-run (step 2b) triggers only when the plan has steps with non-N/A Docs: fields.

Documentation-Only Tasks (DOCUMENT Prefix)

Documentation tasks may enter the lifecycle at /plan directly, since no codebase investigation is needed. The plan's file scope is limited to documentation files. Post-skill next-step suggestions (step 12) suppress /reflect for DOCUMENT-prefixed plans as a low-value reflection target.

Refactoring (REFACTOR Prefix)

Refactoring plans may skip /design because they do not introduce new features or change design intent. The key constraint: existing tests must continue to pass after implementation. The as-coded alignment step (post-skill step 2) still runs to keep product-design/product-design-as-coded.md in sync if entity structures changed, but DONE marker proposals (step 2e) are typically skipped since refactoring does not implement new as-intended items.

Chore Tasks (CHORE Prefix)

Chore plans cover tooling, CI/CD, infrastructure, and other non-feature work. Like DOCUMENT, post-skill suppresses /reflect suggestions. Documentation auto-run triggers only when steps carry non-N/A Docs: fields.

Conversation Trace Integration

SEJA maintains a persistent conversation trace in _output/conversation-trace.jsonl that records every non-skill exchange between the user and the agent. This trace provides a complete record of the session's decision-making context beyond what skill artifacts capture.

The Append Protocol

After responding to any user message that is not within an active skill invocation, the agent silently logs the exchange:

  1. Get preceding event ID: run conversation_trace.py last-evt-id --session-id $CLAUDE_SESSION_ID to retrieve the ID of the most recent entry.
  2. Append user utterance: run conversation_trace.py append with --emitter user, the user's message text, and a type inferred from context (question, answer, or instruction). If exit code 2 indicates masking was applied, show the masked message and ask for confirmation before proceeding.
  3. Append agent response: run conversation_trace.py append with --emitter claude, a 1-2 sentence summary of the response, and optional --topic-tags (1-3 short tags when the topic is clearly identifiable).

Skill Linkage

When a skill is invoked, the pre-skill brief-log stage backfills the conversation trace by linking the most recent agent response entry to the skill invocation via conversation_trace.py backfill-skill. This creates a continuous chain: conversation exchanges flow into skill invocations, and skill artifacts reference the exchanges that preceded them.

Common Mistakes

Skipping lifecycle steps
Running /implement immediately after /research, bypassing /plan. The plan step decomposes work into executable steps, sets verify criteria, and triggers a complexity-gated review. Without it, the implementation lacks structure, traceability, and quality assurance. Follow the canonical path unless you have a clear reason to deviate (see Lifecycle Variations).
Confusing pre-skill with post-skill
Pre-skill runs before the skill body (6 stages: context setup, brief logging, reference loading). Post-skill runs after the skill body (steps that handle brief completion, as-coded alignment, QA logging, commits, and telemetry). The pre-skill constitution stage loads immutable principles; the post-skill as-coded alignment updates the implemented design record. These are complementary, not interchangeable.
Running /implement without a plan
The /implement skill expects a plan file to exist. In auto mode, it spawns one subagent per plan step, each with the step's file list, verify criteria, and dependencies. Without a plan, the executor has no steps to dispatch, no verify criteria to check, and no progress file to track. Always run /plan first, or use /plan --light for small, surgical changes.
Forgetting conversation trace after non-skill responses
The conversation trace protocol in CLAUDE.md requires logging every non-skill exchange. When the agent responds to a user message outside of a /skill invocation and forgets to append to the trace, that exchange is lost from the session record. The trace is append-only and session-scoped -- missing entries cannot be reconstructed later.

Skills In Depth

Skill System Overview

SEJA organizes agent capabilities into 17 skills: 15 user-facing skills invoked via slash commands, plus 2 internal lifecycle hooks (pre-skill and post-skill) that run automatically before and after every user-facing skill invocation. Skills are the fundamental unit of work in the harness.

The Canonical Lifecycle Path

Skills are designed to be invoked in a specific order that moves work from understanding through design, implementation, validation, and reflection. The canonical lifecycle path is: 

/research (or /explain)
    |
    v
/design  |  /plan
    |
    v
/implement
    |
    v
/critique
    |
    v
/document  |  /communicate
    |
    v
/reflect

On the first iteration, /seja-setup hands off to /design to configure the project. From iteration 2 onward, start with /research (or /explain) to investigate what you are about to change, then branch into /design when intent needs to change or into /plan when it does not.

Skill Dispatch Mechanism

Every skill invocation follows the same dispatch sequence:

  1. The user invokes a slash command (e.g., /plan Add user auth).
  2. The skill's SKILL.md file is read and its YAML frontmatter parsed for metadata: name, description, argument hints, context budget tier, and reference file lists.
  3. pre-skill runs its 6-stage pipeline (help, brief-log, budget-eval, pending-check, ref-load, constitution) to set up context.
  4. The skill body executes its mode-specific logic.
  5. post-skill runs its 13-step pipeline (brief completion, as-coded alignment, QA log, commit, index regeneration, telemetry, next-step suggestions) to close out the invocation.

Context Budget Tiers

Each skill declares a context budget tier in its YAML frontmatter that controls how much project state is loaded into the agent's context window during pre-skill:

Tier Loads Used by
light Brief-log only. Skips all reference files, briefs index, and constitution. Skills that need minimal context (e.g., /help, /pending)
standard Briefs index (not full briefs), mandatory references (conventions.md, permissions.md, constraints.md), skill-specific references (eager and lazy), and constitution. Most skills (/research, /explain, /design, /reflect)
heavy Full briefs with recency windowing (first 50 entries), plan index, mandatory references, skill-specific references, and constitution. Skills that need broad project awareness (/plan, /implement, /critique)

Within the standard and heavy tiers, skills can further control reference loading via eager vs. lazy declarations. Eager references are loaded immediately during pre-skill; lazy references are listed as available but only loaded on demand when the skill needs them.

/research

Purpose

Investigates the codebase, architecture, or design decisions and produces actionable recommendations. Use /research when you need guidance on a design decision, want to understand trade-offs, or need an overview of what exists. Two modes: research (default, question-driven Q&A with perspective analysis) and inventory (--inventory, codebase element catalog). From iteration 2 onward, /research is the usual lifecycle entry point.

Parameters

ParameterDescription
<question or topic>The question or topic to research (required)
--inventory <pattern>Switch to inventory mode: catalog codebase elements matching the pattern
--deepActivate structured expert council debate for high-stakes decisions

Prerequisites

No strict prerequisites. Works on any project with or without design files. When product-design/product-design-as-coded.md exists, it is loaded eagerly to provide design context.

Workflow

  1. Pre-skill runs and loads references (as-coded file eagerly; as-intended, shared definitions, report conventions, review perspectives on demand).
  2. The agent researches the question thoroughly, reading codebase files, design docs, and searching the web as needed.
  3. Expert analysis runs: in standard mode, the research-reviewer agent evaluates from multiple perspectives; in --deep mode, the council-debate agent convenes a 5-7 member expert council.
  4. A structured report is saved with Q&A log, perspective synthesis, and prioritized recommendations (HIGH/MEDIUM/LOW).
  5. If design decisions are detected, a decision-extract proposal flow offers to create structured D-NNN entries.

Subagent Delegations

research-reviewer
Standard mode: evaluates the question against applicable review perspectives and returns prioritized recommendations.
council-debate
--deep mode: runs a 2-round structured debate across a 5-7 member expert council with named archetypes.

Reference Files Loaded

Eager: product-design/product-design-as-coded.md. Lazy: product-design/product-design-as-intended.md, general/shared-definitions.md, general/report-conventions.md, general/review-perspectives.md, template/docs/ddr.md.

Expected Outputs

Research mode: _output/research-logs/research-<id>-<slug>.md with header, tags, Q&A log, and recommendations summary. Inventory mode: _output/inventories/inventory-<id>-<slug>.md with a structured catalog of matched elements.

Common Mistakes

Skipping /research and going straight to /plan
Leads to plans that miss architectural context or existing patterns. Research first to understand the landscape, especially from iteration 2 onward.
Using standard mode for high-stakes architectural decisions
Standard mode uses a single reviewer agent. For decisions with significant trade-offs (e.g., framework migration, data model redesign), use --deep to activate the expert council debate.
Not following up on decision-extract proposals
When the skill detects design decisions and offers D-NNN entries, deferring them is fine, but skipping them entirely loses the design rationale while it is fresh.

/explain

Purpose

Produces clear explanations of how parts of the system work, with visual diagrams and analogies. Six mode types cover different explanation needs: architecture (system structure and design choices), behavior (emergent behavior from the user's perspective), behavior-evolution (how behavior changed over time), code (how code works, aimed at junior developers), data-model (entity relationships and refactoring opportunities), and drift (compare as-coded and as-intended design specs with optional sync).

Parameters

ParameterDescription
architecture [brief]Explain system architecture, component relationships, and design choices
behavior [brief]Explain emergent behavior from a user's perspective
behavior-evolution [brief]Explain current behavior AND how it evolved over time
code [brief]Explain how code works, aimed at junior developers
data-model [brief]Explain data model, pitfalls, and refactoring opportunities
drift [scope]Compare as-coded and as-intended specs. Scope: all, conceptual-design, metacomm, --promote, --scope since-plan plan-NNNNNN

Prerequisites

No strict prerequisites for general modes (architecture, behavior, code, data-model). The drift mode requires product-design/product-design-as-intended.md and product-design/product-design-as-coded.md to exist for meaningful comparison.

Workflow

  1. Pre-skill runs and loads shared definitions and report conventions eagerly.
  2. Mode detection determines which explanation type to produce (prompts the user if not specified).
  3. For general modes, the skill delegates to a specialized generator agent with the brief and output path.
  4. For drift mode, the skill runs inline: reads as-intended and as-coded files, compares section by section, produces a drift summary, and optionally offers a sync workflow or promote workflow.
  5. The report is saved and post-skill commits it.

Subagent Delegations

explanation-generator
Handles behavior, code, and data-model modes.
architecture-explainer
Handles architecture mode with a multi-phase survey/identify/write workflow.
evolution-explainer
Handles behavior-evolution mode by mining plan history and building timelines.

Reference Files Loaded

Eager: general/shared-definitions.md, general/report-conventions.md. Lazy: product-design/product-design-as-coded.md, product-design/product-design-as-intended.md.

Expected Outputs

Each mode produces a report in its respective output directory: behavior-<id>-<slug>.md, architecture-<id>-<slug>.md, evolution-<id>-<slug>.md, dev-onboarding-<id>-<slug>.md, data-model-<id>-<slug>.md, or research-<id>-<slug>.md (drift mode).

Common Mistakes

Using /explain to generate documentation for others
/explain answers your questions about the system. For artifacts intended for other audiences, use /document, /communicate, or /onboard.
Running drift without design files
Drift mode compares as-intended and as-coded specs. If neither file exists, the comparison is empty. Run /design first to create the design intent artifacts.

/design

Purpose

Defines or updates a project's design foundations: stack choices, conventions, conceptual design (entities, permissions, UX patterns), metacommunication intent, standards, and constitution. Serves both initial configuration (after /seja-setup) and ongoing design evolution. Six modes cover the design lifecycle: interactive questionnaire (default), from a pre-filled spec file, adding documentation templates, generating a blank spec, interview-driven conversation, and updating existing design sections.

Parameters

ParameterDescription
[spec-file-path]Path to a pre-filled spec file for automated configuration (Mode 2)
--mode interviewRun in Interview-Driven mode: conversational intake instead of fixed questionnaire (Mode 5)
--generate-specGenerate a blank spec skeleton to fill out offline (Mode 4)
--add-docsAdd documentation templates to an existing project (Mode 3)
update <section-slug>Jump directly to an update flow for a specific section. Valid slugs: stack, conceptual, metacomm, backend-standards, frontend-standards, ux-standards, ui-standards, i18n, security, testing, constitution, full

Prerequisites

For initial design: /seja-setup should have been run first to scaffold the harness topology and populate conventions.md with stack definitions. For design updates: product-design/conventions.md and product-design/product-design-as-intended.md must exist.

Workflow

  1. Detection logic evaluates invocation arguments and the state of product-design/ files to determine the active mode (1-5 or Design Update).
  2. For initial design (Modes 1, 2, 5): walks the user through a questionnaire or interview to gather stack choices, conceptual design, metacommunication, and standards.
  3. Templates are instantiated from .claude/references/template/ into product-design/, populating design-intent artifacts with the user's answers.
  4. A verification pass checks semantic fidelity between questionnaire answers and generated files, fixing gaps.
  5. For Design Update: shows current summary, offers an interactive menu to update specific sections, and regenerates dependent files.

Subagent Delegations

/design does not delegate to subagents. All work runs inline in the current context.

Reference Files Loaded

All references loaded eagerly (no eager/lazy split): general/report-conventions.md, general/review-perspectives.md, general/shared-definitions.md. Templates in .claude/references/template/ are read during instantiation.

Expected Outputs

Generates or updates files in product-design/: conventions.md, constitution.md, product-design-as-intended.md, ux-research-results.md, standards.md, design-standards.md, security-checklists.md, and (for brownfield projects) product-design-as-coded.md. Also amends CLAUDE.md with design-intent references.

Common Mistakes

Running /design without /seja-setup first
/design expects the harness topology and conventions.md to already exist. Run /seja-setup to scaffold the project structure before configuring design intent.
Confusing /design with /plan
/design defines what to build and why (entities, permissions, metacommunication). /plan defines how to build it. Design comes before planning in the lifecycle.
Skipping the verification pass
The verification pass checks that generated files faithfully reflect questionnaire answers. Interrupting the skill before verification completes leaves semantic gaps in the design artifacts.

/plan

Purpose

Creates a step-by-step plan for a feature, bug fix, or improvement. Three modes: standard (single plan, default), lightweight (--light, quick proposal for small changes), and roadmap (--roadmap, full product roadmap with dependency-aware execution waves). Each plan is a self-contained artifact that /implement can execute without additional context.

Parameters

ParameterDescription
<brief>Description of the task to plan (required)
--lightGenerate a lightweight proposal instead of a full plan
--planForce single-plan mode (skip auto-detection)
--roadmapGenerate a full product roadmap with dependency-aware waves
--from-spec <path>Parse roadmap from a pre-filled spec file (use with --roadmap)
--autoAuto-generate roadmap from project reference files (use with --roadmap)
--only-unimplementedScope roadmap to REQ items lacking STATUS markers (use with --roadmap --auto)
--framing metacommFrame the brief as a designer's metacommunication message (I/you phrasing)
--review <level>Override complexity-gated review depth (light, standard, deep)

Prerequisites

product-design/conventions.md must exist (design guard). If missing, the skill stops and directs the user to run /design first. Research should typically precede planning to ensure architectural context is understood.

Workflow

  1. Design guard verifies conventions.md exists. Mode detection determines standard, lightweight, or roadmap based on flags or brief analysis.
  2. The plan is decomposed into steps, each with Files, References, Depends on, Interface, Verify, Tests, Docs, Deploy, and Traces metadata.
  3. A complexity-gated two-phase review runs: Phase 1 shortlists 3-6 perspectives from the 16 available; Phase 2 runs targeted deep-dives on deferred concerns.
  4. The plan file is saved with amendments from the review incorporated.
  5. Post-skill files an implement pending action so the plan is tracked for execution.

Subagent Delegations

plan-reviewer
Runs the two-phase perspective review on the drafted plan and returns a review log with amendments.

Reference Files Loaded

Eager: product-design/product-design-as-coded.md, product-design/product-design-as-intended.md, general/report-conventions.md, general/coding-standards.md, general/review-perspectives-index.md. Lazy: product-design/standards.md, product-design/security-checklists.md, product-design/design-standards.md, general/review-perspectives.md, general/review-log-template.md, template/plan-step.md, template/roadmap-summary.md, template/proposal.md.

Expected Outputs

Standard mode: _output/plans/plan-<id>-<slug>.md with header, steps, review log, and Q&A log. Lightweight mode: _output/proposals/proposal-<id>-<slug>.md. Roadmap mode: _output/roadmaps/roadmap-<id>-<slug>.md plus individual plan files for each work item.

Common Mistakes

Writing vague step descriptions
Each step must be self-contained enough for a fresh subagent to execute it without prior context. Include specific file paths, function names, and verification criteria.
Skipping the Verify field
Steps without Verify criteria cannot be objectively confirmed as complete. Every step should have at least one testable assertion.
Not checking file existence during planning
Steps that reference files which do not exist will fail during implementation. Verify that referenced source files exist before finalizing the plan.

Common Mistakes

These cross-cutting mistakes span multiple skills and reflect fundamental misunderstandings of how the skill system operates.

Running skills out of lifecycle order
The canonical path exists for a reason: /research builds understanding, /plan decomposes the work, /implement executes the plan, /critique validates the output, and /document captures the result. Skipping /plan and jumping to /implement produces unstructured changes. Skipping /critique before /document risks documenting buggy behavior. The lifecycle is sequential for a reason -- each stage depends on the output of the previous one.
Misunderstanding context budget tiers
The three tiers (light, standard, heavy) control how much context pre-skill loads into the agent's context window. Light skips references and briefs entirely -- appropriate for utility skills like /pending and /help that do not need project context. Standard loads the briefs index and skill-specific references -- the default for most skills. Heavy loads full briefs with recency windowing and the plan index -- used by skills that need broad project awareness. Running a heavy-budget skill in a session that has already consumed significant context can trigger the compaction warning. Starting a fresh conversation is the recommended response.
Skipping pre-skill or post-skill hooks
Pre-skill and post-skill are not optional ceremony -- they are load-bearing lifecycle infrastructure. Pre-skill loads the constitution, references, and permissions that constrain skill behavior. Post-skill updates the as-coded design state, files pending actions, regenerates indexes, and commits changes. A skill that skips post-skill leaves orphaned STARTED briefs, uncommitted files, and stale indexes.
Running /implement on a stale plan
A plan references specific files, line ranges, and design state at the time it was written. If the codebase has changed significantly since the plan was created (e.g., another plan was implemented, or manual edits were made), the plan's assumptions may be invalid. Review the plan's Files section against the current codebase before executing. If drift is significant, regenerate the plan with /plan.

Subagent Delegation

SEJA skills handle lifecycle orchestration, argument parsing, and user interaction directly. This chapter documents the delegation model, provides a per-agent reference for all 16 agents (9 evaluators and 7 generators), and explains how to write custom subagents.

The Delegation Model

Skills delegate to subagents via the Agent tool, which launches a fresh context window with a self-contained prompt. The delegating skill constructs the prompt dynamically, embedding plan step metadata, file paths, scope parameters, and any project-specific context the agent needs to do its work.

Trust Boundary

Every subagent operates within a trust boundary enforced by two mechanisms. First, generator agents receive the project constitution (product-design/constitution.md) as part of their prompt, ensuring that generated artifacts respect the project's immutable principles. Second, the agent's tool set is explicitly declared in its prompt file's YAML frontmatter -- an agent receives only the tools it needs, not the full set available to the parent skill.

Prompt Construction

The delegating skill builds the agent's prompt at invocation time. For evaluator agents, this typically includes the diff or artifact to review, the review depth, and pointers to relevant reference files. For generator agents, it includes the output path, a reserved artifact ID, the generation scope, and paths to project state files (conventions, conceptual design, communication style). The agent prompt file (.claude/agents/*.md) defines the agent's role, process, and output format; the skill fills in the invocation-specific parameters.

Result Processing

When a subagent completes, it returns a result to the parent skill. For evaluator agents, this is typically a review log or compliance report that the skill presents to the user. For generator agents, the output is a file written to the project's output directory. The parent skill's post-skill lifecycle then handles committing, indexing, and any follow-up actions.

Executor Agents

A third category exists as a pattern rather than standalone prompt files: executor agents. Used by /implement in auto mode, these agents execute individual plan steps in isolated context windows. The /implement skill constructs their prompts dynamically from plan step metadata (Files, References, Verify, Tests) -- there are no separate .claude/agents/ files for executors.

Agent Prompt Files

Each subagent is defined by a Markdown file in .claude/agents/. The file follows a consistent structure:

YAML Frontmatter
Contains name (the agent identifier), description (a concise role summary), designer_description (a first-person designer-voice paragraph for documentation and the call-graph viewer), and tools (the explicit tool set the agent receives -- e.g., Read, Bash, Glob, Grep).
Role Boundary Block
A blockquote that clarifies the division of responsibility between the agent (execution engine) and its parent skill (user-facing orchestrator). This prevents duplication of lifecycle logic.
Input Section
Documents the parameters the agent receives from the delegating skill: paths, IDs, scope strings, depth settings, and any optional overrides.
Process Section
Step-by-step instructions for the agent's work. Evaluator agents typically load references, analyze the target, and produce findings. Generator agents load templates, scan the codebase, and produce output files.
Output Section
Defines the format, file naming, and content structure of the agent's deliverable.

Agent prompt files should not replicate SKILL.md logic. The skill handles lifecycle (pre-skill, post-skill), argument parsing, and user interaction. The agent handles only the specialized work the skill delegates.

Writing Custom Subagents

To create a custom subagent, create a new Markdown file in .claude/agents/ following the established structure:

  1. Define the YAML frontmatter with name, description, designer_description, and tools. The tools field must list only the tools the agent needs -- follow the principle of least privilege.
  2. Write a role boundary blockquote clarifying which skill orchestrates this agent and what the division of responsibility is. The agent handles specialized work; the skill handles lifecycle, argument parsing, and user interaction.
  3. Document the input contract -- what parameters the agent expects to receive from the delegating skill. Be explicit about required vs. optional inputs.
  4. Define the process as step-by-step instructions. Start with loading relevant references (product-design/conventions.md for project context, product-design/constitution.md for generator agents). Then describe the analysis or generation steps.
  5. Specify the output format -- file naming, content structure, and where the output is written.
  6. Wire it into a skill by adding delegation logic to the skill's SKILL.md. The skill constructs the agent's prompt with invocation-specific parameters and launches it via the Agent tool.

The agent prompt file should not invoke /pre-skill or /post-skill -- the parent skill owns the lifecycle. Including lifecycle calls in an agent prompt causes double-execution of briefs logging, indexing, and commits.

Best Practices

  • Clear, focused role: each agent should do one thing well. If an agent's process section spans more than 10-15 steps, consider whether the work should be split across multiple agents.
  • Minimal tool set: grant only the tools the agent's process requires. Evaluator agents typically need Read, Glob, Grep, Bash; generator agents add Write.
  • Constitution loading for generators: any agent that produces user-facing content must read the constitution to enforce the trust boundary.
  • Convention-aware startup: begin the process with reading product-design/conventions.md to obtain project-specific paths and configuration.
  • Structured output: define a clear output format (header, sections, tables) so the parent skill can process the result consistently.

Common Mistakes

Giving agents too broad a tool set
An agent with Write access that only needs to read files can accidentally modify project files outside its scope. Declare only the tools the agent's process requires in the tools frontmatter field. Evaluator agents rarely need Write; most need only Read, Glob, Grep, Bash.
Not passing the constitution to generator agents
Generator agents produce user-facing artifacts that must respect the project's immutable principles. If the agent's process does not start with reading product-design/constitution.md, the generated content may violate constitutional constraints (e.g., identity, privacy, quality commitments). Every generator agent must load the constitution before beginning generation.
Confusing evaluator and generator roles
Evaluator agents analyze existing artifacts and return findings; generator agents produce new artifacts. Asking an evaluator to generate content (or a generator to review code) produces poor results because the agent's process, voice, and output format are optimized for its declared role. Use the right agent category for the task.
Writing agent prompts that duplicate SKILL.md logic
The agent should handle only the specialized work the skill delegates. Lifecycle management (pre-skill, post-skill), ID reservation, argument parsing, and user interaction belong in the skill. An agent that includes lifecycle calls will cause double-execution of briefs logging, index regeneration, and commits.

Plans and Implementation

Plans are the bridge between design intent and working code. Every non-trivial change in a SEJA project passes through a plan file that decomposes the work into self-contained steps, records metadata for traceability and review, and serves as the execution contract for the /implement skill. This chapter documents the plan file format, the three planning modes, the implementation executor, and the traceability mechanisms that connect implementation back to design decisions.

Plan File Structure

A plan file is a Markdown document stored in the plans directory (_output/plans/ by default). It carries a structured header, a body of self-contained steps, and optional sections for review logs, Q&A, and outcomes.

Plan Header

The first line of every plan follows this shape: 

# Plan 000123 | FEATURE-X | 2026-03-15 14:30 | Add user profiles | Review: standard
plan_format_version: 1

The header fields are:

Field Description
Plan ID A 6-digit numeric identifier reserved via reserve_id.py
Prefix-Scope The plan type and scope (e.g., FEATURE-X, FIX-B, REFACTOR-R, CHORE-O, DOCUMENT-X)
Datetime UTC timestamp when the plan was created
Short Title A human-readable summary of the plan's purpose
Review Depth The complexity-gated review level: light, standard, or deep
Format Version plan_format_version: 1 on the line after the header; enables version-aware parsing

Plans generated with metacommunication framing insert METACOMM | after the prefix-scope. Plans sourced from an advisory insert source: advisory-<id>.

Plan Body Sections

After the header, the plan body contains:

User brief / Designer's metacommunication message
The original request, recorded verbatim.
Agent interpretation
Problem statement, chosen approach, and (for standard/deep reviews) alternatives rejected and selection rationale.
Files
All files the plan creates, modifies, or deletes, with disposition annotations.
Best practices
Coding standards and conventions applied.
Design decisions (standard/deep only)
User-visible impact, trade-offs accepted, and metacommunication impact when the plan changes what the system communicates to users.
Steps
The structured step list (see below).
Outcomes
Expected results when all steps complete.
Smoke
true if any step creates or modifies API route files or frontend page/component files; false otherwise. Consumed by /implement to decide whether to run /critique smoke api.

Step Format

Each step follows a canonical template defined in .claude/references/template/plan-step.md. Steps must be self-contained: executable by a subagent with no shared context from prior steps. 

### Step 1: <short imperative title>
<Self-contained description of what to do.>
- **Files**: path/to/file.py (create), path/to/other.py (modify)
- **References**: product-design/standards.md § Backend
- **Depends on**: Step N, Step M
- **Interface**: exports UserService with find_by_id(id) -> User | None
- **Verify**: tests pass, endpoint returns 200
- **Tests**: Add unit tests for new service method
- **Docs**: Update API reference for /users endpoint
- **Deploy**: Add USER_DB_URL env var (connection string)
- **Traces**: REQ-ENT-001, REQ-PERM-003
- [ ] Done

The step metadata fields serve specific purposes:

Field Required Purpose
Files Yes Every path the step reads, creates, modifies, or deletes. Existing files are verified on disk during planning.
References Yes Only the product-design/ files relevant to this step. Omit irrelevant refs.
Depends on No Step numbers whose output this step requires. Omit entirely for independent steps. Dependencies must flow forward.
Interface Yes The expected public surface for dependency-producing steps (function names, class names, type signatures). N/A for leaf steps.
Verify Yes A concrete, testable condition. Prefer automated checks over subjective ones.
Tests Yes What tests to create or update. N/A for doc/config/harness-only steps. Express as observable behavior for TDD.
Docs No What documentation to create or update. Omit entirely when not applicable.
Deploy No Deployment configuration changes: env vars, ports, services, migration commands. Omit when no deployment impact.
Traces No Comma-separated REQ IDs from product-design-as-intended.md that this step implements.

Decomposition Guidelines

  • Each step must be completable in one subagent context window (rule of thumb: touches 5 or fewer files). Split larger steps.
  • Order steps so dependencies flow forward (Step 2 depends on Step 1, not the reverse).
  • Step descriptions must include enough context to make sense in isolation: what the code should do, not just which file to edit.

Three Plan Modes

The /plan skill supports three modes, selected explicitly via flags or auto-detected from the brief's scope.

Mode Flag Output When to Use
Standard --plan (or auto-detected) Full plan file with structured steps, review log, and metadata Most features, bug fixes, and refactors. The default for single-scope work.
Lightweight Proposal --light Minimal proposal with What/Why/Files/Verify/Risks plus a 2-3 perspective inline review Small, surgical changes too small for a full plan but worth tracking.
Roadmap --roadmap Multi-wave roadmap with dependency-aware execution waves and per-item plans Work spanning 3+ entities, 2+ architectural layers, or multiple pages/screens.

Standard Mode

The default mode produces a full plan with a structured header, agent interpretation, step list, review log, and outcomes. Plans undergo a complexity-gated review process (see Plan Review and Critique).

Lightweight Proposal Mode

Activated with --light. Produces a compact proposal stored in _output/proposals/ with the shape defined in .claude/references/template/proposal.md: What, Why, Files, Verify, Risks, and a light inline review covering 2-3 perspectives (always including SEC for code changes). Proposals can be executed inline immediately after creation.

Roadmap Mode

Activated with --roadmap. Decomposes a broad brief into dependency-aware execution waves. Three sub-modes control how the roadmap is sourced:

Auto-generate (--auto)
Reads project reference files (product-design-as-intended.md, product-design-as-coded.md, conventions.md, standards.md) and decomposes the delta between as-intended and as-coded states into work items. Classifies each as technical or design, groups into waves (Foundation → Service+API → Frontend → Cross-cutting → Testing+Polish), and optionally generates plans for each item. The --only-unimplemented flag scopes extraction to REQ items without a STATUS marker.
From spec (--from-spec <path>)
Parses a pre-filled roadmap-spec.md file with themes, work items, constraints, and wave groupings. Validates dependencies, classifies items, and generates plans.
Blank spec (no sub-mode flag)
Generates a blank roadmap-spec.md skeleton for offline editing. No ID reservation or plan generation occurs.

Mode Auto-Detection

When neither --plan nor --roadmap is specified, the skill scores the brief against scope signals. Briefs mentioning 3+ entities, spanning 2+ architectural layers, or describing multiple pages lean toward roadmap mode. Single-bug, single-file, or comfortably-under-12-step briefs lean toward a standard plan. If roadmap mode is auto-detected, a confirmation gate asks the user before proceeding.

Plan Generation Workflow

The end-to-end workflow for generating a standard plan follows these phases:

1. Design Guard

Before any planning, /plan verifies that product-design/conventions.md exists. If missing, the skill stops with a message directing the user to run /design first. This ensures the project has a defined stack, directory layout, and domain model before planning begins.

2. Pre-Skill and Mode Detection

Pre-skill loads the context budget (heavy tier for /plan), registers the brief, and loads reference files. Mode detection then resolves whether to produce a standard plan, lightweight proposal, or roadmap based on explicit flags or auto-detection heuristics.

3. Reference Loading

References are loaded on demand based on what the plan touches. Eager references (loaded automatically) include the as-coded and as-intended design files, report conventions, coding standards, and the review perspectives index. Lazy references (loaded when needed) include project standards, security checklists, design standards, the full review perspectives file, and the review log template.

4. Step Decomposition

The agent decomposes the brief into structured steps following the plan-step template. Each step is self-contained with Files, References, Verify, Tests, and other metadata fields. The decomposition follows layer-aware ordering: foundation (models, migrations) first, then services and APIs, then frontend, then cross-cutting concerns.

5. Coverage Check

If product-design-as-intended.md contains REQ markers, /plan runs an advisory coverage check (critique_plan_coverage.py --mode advisory) that reports which requirements are addressed by the plan's steps and which remain uncovered. This is informational only and does not block plan generation.

6. Review

The plan undergoes a complexity-gated, two-phase review process (detailed in the next section). The review log and any amendments are appended to the plan file.

7. Post-Skill and Commit

After review, the plan is committed as a durable git artifact via post-skill. The user is then asked whether to implement now or defer to a later session.

Plan Review and Critique

Every standard plan undergoes a complexity-gated, two-phase review process that evaluates the plan against the project's 16 engineering and design perspectives. The review depth scales with the plan's complexity, and the process is designed to catch regressions, standards violations, and cross-cutting concerns before implementation begins.

Complexity Gate

The review depth is determined automatically based on plan complexity:

Depth Criteria Review Scope
Light 6 or fewer action steps AND 4 or fewer files Phase 1 only
Standard 7-12 steps OR 5-8 files Phase 1; Phase 2 eligible
Deep More than 12 steps OR more than 8 files OR involves migrations, auth, or cross-scope changes Phase 1 + Phase 2 for all Deferred concerns

The --review <level> flag can override auto-detected depth. The effective depth is the maximum of the auto-detected level, the project's minimum review depth floor (from conventions.md), and the flag value.

Phase 1: Perspective Triage and Scan

Phase 1 uses the two-stage loading protocol. First, the compact perspectives index is loaded to see all 16 perspectives. Then a shortlist of 3-6 perspectives is selected using the Perspective Shortcuts table (keyed by plan prefix). Up to 2 additional perspectives may be added with justification. Only the selected perspective files are loaded from .claude/references/general/review-perspectives/.

The 16 perspectives span two categories:

Category Perspectives
Engineering (11) SEC (Security), PERF (Performance), DB (Database), API (API Design), ARCH (Architecture), DX (Developer Experience), I18N (Internationalization), TEST (Testability), OPS (Operations), COMPAT (Compatibility), DATA (Data Integrity & Privacy)
Design (5) UX (User Experience), A11Y (Accessibility), VIS (Visual Design), RESP (Responsive Design), MICRO (Microinteractions)

Each perspective receives a status: Adopted (concerns addressed), Deferred (concerns noted for Phase 2 or future work), or N/A (not applicable to this plan).

Phase 2: Targeted Deep-Dives

Phase 2 triggers only for Deferred perspectives whose concerns could cause regression, production incidents, or standards violations. For deep reviews, additive-improvement concerns also trigger deep-dives. Cosmetic or out-of-scope concerns never trigger Phase 2.

For standard and deep plans, the plan-reviewer agent is launched to perform the deep-dives autonomously. The agent returns a review log with amendments that are appended to the plan file.

Amendments and Convergence

When Phase 2 changes the plan, an amendment section is appended (additive, preserving the original text). The Steps section is updated in place since it is a living checklist. Modified perspectives are re-evaluated, and the loop continues until all findings are resolved, 3 iterations are reached, or the deep-dive budget (6) is exhausted.

Conflict Resolution

After each iteration, a conflict check identifies contradictions between perspectives (e.g., security recommending strict validation while DX recommends minimal boilerplate). Conflicts are resolved per the rules in .claude/references/general/review-perspectives.md and logged in the review log.

The /implement Executor

The /implement skill executes a previously generated plan. It supports four execution modes, each suited to different scenarios.

Mode Flag Topology When to Use
Auto (default) Each step in a fresh subagent; state via progress file Most plans, especially those with more than 6 steps where context degradation is a risk
Manual --manual Sequential in the current context Small plans (6 or fewer steps) or when per-step confirmation is needed
Roadmap --roadmap <id> Each plan in auto mode via a fresh subagent; pauses between waves Executing every plan in a roadmap without per-plan invocation
Pending --pending Generates a lightweight roadmap from pending entries, then dispatches to roadmap mode Clearing all pending implement entries in one go

Auto Mode

Auto mode is the default and recommended execution mode. It operates in three phases:

Phase 0: Setup
Reads the plan file, parses the Steps section, creates a progress file, builds the execution queue in dependency order, and creates a rollback branch (pre-plan-<id>) from the current HEAD.
Phase 1: Iteration Loop
For each step in the execution queue (up to --max-iterations, default 20): picks the next eligible step, builds a self-contained prompt, and spawns a fresh general-purpose subagent. If the step has a non-N/A Tests field, the subagent follows the TDD red-green cycle: write a failing test first, then implement until the test passes. Each subagent reports SUCCESS, PARTIAL, or FAILED.
Phase 2: Wrap-up
Runs the quality gate (validate, review, test), marks the plan as DONE, appends an aggregated summary, merges the progress file into the plan, and updates any associated roadmap.

Manual Mode

Manual mode executes all steps sequentially in the current context rather than spawning subagents. The user maintains full visibility and can intervene at each step. Tests are written after implementation (not TDD) because the user's presence provides the quality oversight that TDD substitutes for in auto mode.

Roadmap Mode

Roadmap mode executes all plans in a roadmap, wave by wave. Wave 0 always runs sequentially (migration chain safety). Subsequent waves may run plans in parallel using worktree isolation when their file lists do not overlap. An enhanced overlap check uses .claude/references/general/call-graph.json to detect transitive dependencies between files across plans.

Between waves, checkpoint behavior is controlled by --checkpoint: wave (default) pauses between waves for review, plan pauses after every plan, and none runs full autopilot with progress notes only.

Quality Gate

The quality gate runs at the end of implementation (skippable with --skip-checks):

  1. Run /critique validate (validation scripts).
  2. Run /critique review (code review against perspectives).
  3. Launch the test-runner agent with scope "all".
  4. If the plan's smoke field is true, run /critique smoke api.

In auto mode, a generator-critic loop retries critical findings (security, correctness, failing tests) up to 2 times. If critical issues remain after retries, they are logged as unresolved and implementation continues.

Design-Intent Traceability

SEJA maintains a traceability chain from design intent through planning to implementation. This chain ensures that every code change can be traced back to a design requirement, and that the implementation state of design requirements is always visible.

The Traces Field

Plan steps include an optional Traces field that lists the REQ IDs from product-design/product-design-as-intended.md that the step implements. REQ IDs follow a typed naming convention: REQ-ENT-NNN for entities, REQ-PERM-NNN for permissions, REQ-UX-NNN for UX patterns, REQ-MC-NNN for metacommunication intentions, and so on.

Coverage Check

When REQ markers exist in the as-intended file, /plan runs an advisory coverage check that reports which requirements are addressed by the plan's steps (via their Traces fields) and which remain uncovered. This is informational: it highlights gaps in traceability without blocking plan generation.

STATUS Marker Lifecycle

Design requirements progress through a lifecycle tracked by STATUS markers in product-design-as-intended.md:

  1. Unmarked: the requirement exists in the design intent but has not been implemented.
  2. Implemented: after a plan executes successfully, post-skill proposes flipping the STATUS marker to <!-- STATUS: implemented | plan-NNNNNN | YYYY-MM-DD -->. The user chooses to apply now, defer to the pending ledger, or skip.
  3. Established: a promoted state indicating the implementation has been verified and the design decision is considered stable. Promoted via /explain drift --promote, which generates a Decision entry proposal (Phase 3a) and then flips the STATUS markers (Phase 3b) via apply_marker.py.

Metacommunication Framing

Plans generated with --framing metacomm record the brief as a designer's metacommunication message using "I" (designer) and "you" (user) phrasing. After implementation, post-skill updates the per-feature metacommunication log in product-design-as-coded.md with the implemented intent and sets its status to "Implemented". This keeps the as-coded metacommunication record in sync with what actually shipped.

As-Coded Alignment

Post-skill's as-coded alignment step (step 2) updates product-design/product-design-as-coded.md after every implementation. It incrementally edits three domain sections: Conceptual Design (entities added, modified, or removed), Metacommunication (per-feature intention log), and Journey Maps (status updates for designed journeys). A changelog entry is appended to product-design/product-design-changelog.md for each update, creating an audit trail of design evolution. For details on the as-coded alignment mechanism, see Post-Skill Steps.

Common Mistakes

Implementing without a plan
Jumping straight to code without running /plan bypasses the review process, skips traceability, and produces no durable record of what was intended. Even small changes benefit from /plan --light, which creates a tracked proposal with minimal overhead.
Writing vague step descriptions
Step descriptions like "update the user module" give subagents insufficient context. Each step must be self-contained with enough detail to execute without reading other steps. Describe what the code should do, not just which file to edit.
Skipping the Verify field
Steps without concrete Verify criteria have no measurable completion condition. The executor cannot determine whether a step succeeded. Use automated checks ("tests pass", "migration runs forward and backward") rather than subjective conditions ("code looks clean").
Not checking file existence during planning
Referencing files that do not exist on disk (or misspelling paths) causes subagent failures during implementation. The plan skill validates file paths during step metadata checks; ensure all paths in the Files field resolve to real files for (modify) and (delete) dispositions.
Amending commits when a new commit is safer
In projects with concurrent sessions, git commit --amend can absorb unrelated modified files via the hook chain. Prefer creating a new commit over amending, especially in seja-priv where multiple sessions may be active.
Ignoring the coverage check output
The advisory coverage check identifies which design requirements are not addressed by the plan. While it does not block plan generation, consistently ignoring it leads to implementation drift where coded features diverge from the design intent without anyone noticing.

Quality and Critique

The /critique skill is SEJA's unified quality gate — one skill for every "is it OK?" question. It provides ten mutually exclusive modes covering static validation, structured code review, runtime smoke tests, pre-merge preflight checks, harness self-diagnosis, test plan generation, documentation consistency scanning, git freshness tracking, telemetry analysis, and semiotic inspection. Each mode produces a numbered critique log that becomes part of the project's quality trail.

The Critique System

In the SEJA lifecycle, critique occupies the verification position: it runs after /implement and before /document or /communicate. The principle is validate before you communicate — no stakeholder material should be generated until the implementation has passed quality review.

The critique system is multi-modal by design. Different quality questions require different tools: a code review needs the 16 review perspectives, a smoke test needs a running application, and a harness health check needs access to internal SEJA structure. Rather than splitting these into separate skills, /critique provides one entry point with mode dispatch. Each invocation selects exactly one mode, runs the appropriate checks, and produces a numbered report file.

All modes except telemetry follow a shared execution pattern: pre-skill lifecycle hook, mode-specific checks, report generation with a reserved ID, result presentation, and post-skill lifecycle hook. The telemetry mode is read-only and produces no artifact.

Tip: Use /critique preflight as your pre-merge checkpoint — it combines validation and code review in one pass and gives a clear go/no-go verdict.

The Two-Phase Review Process

Code review and plan review in SEJA follow a two-phase process designed to keep context lean while ensuring thorough coverage. The process is complexity-gated: simpler changes use a lighter pass, while high-stakes changes trigger deeper analysis.

Phase 1: Perspective Triage and Scan

The reviewer loads the compact perspective index (.claude/references/general/review-perspectives-index.md, under 600 tokens) and selects 4–6 relevant perspectives based on the change content. For each selected perspective, the reviewer loads the full perspective file from .claude/references/general/review-perspectives/ and evaluates the Essential (P0) questions. Perspectives that do not apply to the change are marked N/A without loading their files.

For review depth deep or when explicitly requested, all 16 perspective files are loaded and evaluated.

Phase 2: Targeted Deep-Dives

When Phase 1 identifies concerns that require further analysis, the reviewer conducts targeted deep-dives on the affected perspectives. Deep-dives evaluate Standard (P1–P2) and Deep (P3–P4) questions for the perspectives where Essential screening raised flags or where the change complexity warrants closer examination.

Deep-dives are budget-controlled to prevent unbounded review scope. The reviewer tracks convergence: once a perspective's concerns have been fully characterized and the findings have stabilized, the deep-dive concludes for that perspective.

Conflict Resolution

When two perspectives pull in opposite directions (e.g., Performance recommends caching while Security flags the cache as an attack surface), the reviewer follows a fixed resolution order:

  1. SEC wins by default — unless the user explicitly accepts the risk.
  2. A11Y is non-negotiable — never traded against visual design or performance.
  3. Document the trade-off — record both the chosen approach and the deferred concern with rationale.
  4. Ask when unclear — for non-default conflicts (e.g., PERF vs DX), ask the user rather than choosing silently.

Interpreting Results

Validation Output

Validation reports present a summary table with each check script's name, status (PASS, FAIL, or INFO), error count, and warning count. The overall result line shows X/Y checks passed. Any check with status FAIL requires attention; INFO results are advisory.

Review Logs

Review logs contain a perspective evaluation table showing Adopted/Deferred/N/A status per perspective, followed by prioritized issues. Each issue carries a severity level, the perspective that raised it, a description, and a file reference. Focus on HIGH-severity issues first — these would block a release. Deferred items include rationale and should be revisited in a future iteration.

Preflight Verdicts

A preflight report ends with an overall status: READY (all validation checks pass, no HIGH-severity review issues) or NOT READY (at least one check failed or a HIGH-severity issue was found). Treat NOT READY as a merge blocker.

Health Reports

Health reports show PASS/WARN/FAIL per diagnostic check and an overall N/9 tally. WARN results indicate degraded conditions (e.g., orphaned briefs, stale plans) that should be addressed but do not block operation. FAIL results indicate structural issues that need immediate attention.

What to Fix vs Defer

Fix immediately: HIGH-severity review findings, FAIL validation checks, security and accessibility issues (SEC and A11Y perspectives). Defer with documentation: MEDIUM-severity findings in perspectives not central to the change, WARNING-level validation results from non-critical checks. Do not defer: anything that would violate the project constitution or compromise user safety.

When to Re-Run

Re-run critique after fixing findings to confirm they are resolved. A preflight pass before merge provides confidence that the change is ready. For ongoing development, periodic health and freshness checks catch drift and staleness early.

Common Mistakes

Running review without reading the diff first
The code review mode works best when the reviewer (human or agent) has context about what changed and why. Running /critique review on staged changes without understanding the plan behind them leads to superficial findings. Read the plan and the diff before reviewing.
Ignoring Deferred findings
Deferred perspectives are not dismissed — they represent concerns that were evaluated and intentionally postponed. Review logs record the rationale for each deferral. If Deferred items accumulate across multiple reviews without being addressed, they signal growing technical or design debt.
Skipping preflight before merge
The /critique preflight mode exists specifically as a pre-merge checkpoint. Skipping it and relying solely on individual validate or review runs misses the combined verdict and the concurrent checks that preflight provides.
Treating advisory findings as blocking
INFO-level validation results, WARNING-level health check findings, and MEDIUM/LOW-severity review issues are advisory. They should be reviewed and tracked but should not block a merge if the core quality criteria (no FAIL validation, no HIGH-severity review issues) are met.
Running all critique modes when one is sufficient
Each mode targets a specific quality concern. Running validate, review, smoke, and health in sequence when only a code review was needed wastes time and context budget. Use preflight when you need the combined validate+review pass; use individual modes for targeted checks.
