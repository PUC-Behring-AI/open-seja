Subagent Delegation

SEJA skills handle lifecycle orchestration, argument parsing, and user interaction directly. When a task requires specialized analysis, generation, or evaluation, the skill delegates that work to a subagent -- a focused agent launched with a purpose-built prompt. This chapter documents the delegation model, provides a per-agent reference for all 16 agents (9 evaluators and 7 generators), and explains how to write custom subagents.

The Delegation Model

Skills delegate to subagents via the Agent tool, which launches a fresh context window with a self-contained prompt. The delegating skill constructs the prompt dynamically, embedding plan step metadata, file paths, scope parameters, and any project-specific context the agent needs to do its work.

Trust Boundary

Every subagent operates within a trust boundary enforced by two mechanisms. First, generator agents receive the project constitution (product-design/constitution.md) as part of their prompt, ensuring that generated artifacts respect the project's immutable principles. Second, the agent's tool set is explicitly declared in its prompt file's YAML frontmatter -- an agent receives only the tools it needs, not the full set available to the parent skill.

Prompt Construction

The delegating skill builds the agent's prompt at invocation time. For evaluator agents, this typically includes the diff or artifact to review, the review depth, and pointers to relevant reference files. For generator agents, it includes the output path, a reserved artifact ID, the generation scope, and paths to project state files (conventions, conceptual design, communication style). The agent prompt file (.claude/agents/*.md) defines the agent's role, process, and output format; the skill fills in the invocation-specific parameters.

Result Processing

When a subagent completes, it returns a result to the parent skill. For evaluator agents, this is typically a review log or compliance report that the skill presents to the user. For generator agents, the output is a file written to the project's output directory. The parent skill's post-skill lifecycle then handles committing, indexing, and any follow-up actions.

Executor Agents

A third category exists as a pattern rather than standalone prompt files: executor agents. Used by /implement in auto mode, these agents execute individual plan steps in isolated context windows. The /implement skill constructs their prompts dynamically from plan step metadata (Files, References, Verify, Tests) -- there are no separate .claude/agents/ files for executors.

Agent Prompt Files

Each subagent is defined by a Markdown file in .claude/agents/. The file follows a consistent structure:

YAML Frontmatter
Contains name (the agent identifier), description (a concise role summary), designer_description (a first-person designer-voice paragraph for documentation and the call-graph viewer), and tools (the explicit tool set the agent receives -- e.g., Read, Bash, Glob, Grep).
Role Boundary Block
A blockquote that clarifies the division of responsibility between the agent (execution engine) and its parent skill (user-facing orchestrator). This prevents duplication of lifecycle logic.
Input Section
Documents the parameters the agent receives from the delegating skill: paths, IDs, scope strings, depth settings, and any optional overrides.
Process Section
Step-by-step instructions for the agent's work. Evaluator agents typically load references, analyze the target, and produce findings. Generator agents load templates, scan the codebase, and produce output files.
Output Section
Defines the format, file naming, and content structure of the agent's deliverable.

Agent prompt files should not replicate SKILL.md logic. The skill handles lifecycle (pre-skill, post-skill), argument parsing, and user interaction. The agent handles only the specialized work the skill delegates.

Evaluator Agents

Evaluator agents review artifacts against quality perspectives, validate compliance, or assess design decisions. They receive a target (diff, plan, migration chain, interface) and return a structured report with findings.

code-reviewer

AttributeDetail
RoleReviews code changes against engineering and design perspectives. Depth-gated: deep evaluates all 16 perspectives; standard and light use a shortlisted subset.
ToolsRead, Glob, Grep, Bash
InputsA file path, directory, "staged" (git staged changes), or a diff. Optional review depth: light, standard, or deep (default).
OutputsA review log with Adopted/Deferred/N/A status per perspective, issues found with severity levels, and a summary table.
Invoked by/critique review, /code-review

The code-reviewer performs a vulnerability pattern pre-scan using patterns from .claude/references/general/threat-model.md before the full perspective pass. Matches in test files are triaged as MEDIUM rather than HIGH.

council-debate

AttributeDetail
RoleRuns a structured expert council debate for high-stakes design decisions. Five fixed archetypes plus 0-2 brief-specific domain experts surface trade-offs through position statements and cross-examination.
ToolsRead, WebSearch
InputsThe question or decision to debate, optional selected council members from the brief-specific pool, and optional context pointers.
OutputsA debate transcript with position statements, cross-examination, areas of agreement and tension, and a recommended path with named trade-offs.
Invoked by/research (for high-stakes design questions)

The five fixed archetypes are: Security Advocate, DX Pragmatist, UX Champion, Architecture Purist, and Product Strategist. Brief-specific experts (Agentic AI Expert, Data Engineer, DevOps/Platform Engineer, Domain Specialist) can be added when the question warrants domain depth.

harness-health-evaluator

AttributeDetail
RoleRuns 9 harness self-diagnosis checks and produces a Harness Health Report with PASS/WARN/FAIL per check and an overall tally.
ToolsRead, Bash, Grep, Write
InputsA reserved check-NNN ID, output path, optional verbose flag, and optional source path for drift comparison.
OutputsA Harness Health Report with a nine-row status table (skill system integrity, orphaned briefs, stale plans, reference completeness, conventions completeness, constitution presence, spec compliance, pending ledger, harness drift).
Invoked by/critique health

migration-validator

AttributeDetail
RoleValidates Alembic migration chain integrity, checks for broken links, cycles, orphaned revisions, and multiple heads. Inspects migration files for idempotency issues, PostgreSQL syntax problems, and common pitfalls.
ToolsRead, Bash, Glob, Grep
Inputsall (full chain), a specific migration file path, or recent (since last tag).
OutputsA validation report separating critical issues, warnings, and best-practice suggestions with file and line references.
Invoked by/critique validate (migration scope)

plan-reviewer

AttributeDetail
RoleReviews a plan against engineering and design perspectives using the complexity-gated two-phase review process. Phase 1 scans across shortlisted perspectives; Phase 2 runs targeted deep-dives on deferred concerns.
ToolsRead, Glob, Grep, Bash
InputsThe full plan text, plan file path, and review depth (Light, Standard, or Deep).
OutputsA review log with Adopted/Deferred/N/A status per perspective, deep-dive findings, and recommended amendments.
Invoked by/plan (review step)

research-reviewer

AttributeDetail
RoleEvaluates design decisions, open-ended questions, and trade-offs against engineering and design perspectives. Handles research questions and recommendations (unlike code-reviewer for diffs and plan-reviewer for plans).
ToolsRead, Glob, Grep, WebSearch
InputsThe question, decision, or trade-off to evaluate. Optional context file paths and review depth (light, standard, deep).
OutputsA structured analysis with a perspective status table, per-perspective evaluation, prioritized recommendations with trade-offs, and open concerns.
Invoked by/research (review step)

semiotic-inspector

AttributeDetail
RoleConducts a Semiotic Inspection Method (SIM) evaluation of a project's interface communicability. Examines metalinguistic, static, and dynamic sign classes independently, then synthesizes findings into a communicability judgment.
ToolsRead, Glob, Grep, Write
InputsA scope string (feature name, page, user flow, or all), a reserved check-NNN ID, and output path.
OutputsA SIM report with per-sign-class analysis, a metacommunication reconstruction, a cross-class comparison, and a communicability verdict flagging where the interface's three voices agree or contradict.
Invoked by/critique semiotic-inspection

standards-checker

AttributeDetail
RoleRuns all project validation scripts registered in product-design/conventions.md and aggregates results into a unified compliance report.
ToolsRead, Bash, Glob, Grep
Inputsall (run every registered script) or a specific check name (e.g., i18n, auth, migrations).
OutputsA unified compliance report with a pass/fail summary table across all checks, then specific errors and warnings from failed checks with file and line references.
Invoked by/critique validate

test-runner

AttributeDetail
RoleRuns backend (pytest) and frontend (vitest) test suites, parses output, and reports failures with context. Classifies each failure as test bug, source bug, environment issue, or flaky.
ToolsRead, Bash, Glob, Grep
Inputsall, backend, frontend, a specific test file path, or integration.
OutputsA test report with pass/fail/skip counts, and for each failure: file, test name, error message, classification, and suggested next step.
Invoked by/critique smoke, /critique test-plan (verification)

Generator Agents

Generator agents produce self-contained artifacts from well-defined inputs. They are invoked by thin-skill wrappers that handle argument parsing, interactive prompts, and lifecycle hooks. All generator agents receive the project constitution (product-design/constitution.md) as part of their prompt to enforce the trust boundary -- generated content must respect the project's immutable principles.

communication-generator

AttributeDetail
RoleProduces stakeholder-facing communication material for one audience segment (evaluators, clients, end users, or academics). Reads audience tone and content guidance, pulls in project identity and value proposition.
ToolsRead, Bash, Glob, Grep, Write
InputsAudience tag (EVL, CLT, USR, ACD), audience file path, Diataxis mapping path, project context paths, output path, artifact ID, and format (md, html, or both).
OutputsA Markdown and/or HTML deliverable tailored to the audience's register, with no meta-commentary or internal notes.
Invoked by/communicate

onboarding-generator

AttributeDetail
RoleProduces a personalized onboarding plan for a new team member. Combines role family (Builder, Shaper, Guardian) with expertise level (L1-L3) to shape a plan grounded in the actual codebase.
ToolsRead, Bash, Glob, Grep, Write
InputsRole tags (BLD, SHP, GRD), level (L1-L3), optional name and focus area, role and level file paths, project context paths, output path, artifact ID, and format.
OutputsAn onboarding plan with welcome, day-one foundation, role- and level-specific weeks, a 30-60-90 timeline, and a prioritized reading list pointing at real project files.
Invoked by/onboard

document-generator

AttributeDetail
RoleProduces or updates project documentation for a specific documentation type. Reads the right template, scans the codebase for concrete specifics, and produces a user-facing document that fits its Diataxis category.
ToolsRead, Bash, Glob, Grep, Write
InputsDoc type (readme, contextual-help, api-reference, ddr, help-center, changelog), scope, template path, quality guide path, project context paths, output path, and optional plan context.
OutputsA documentation file at the specified output path, following the template structure and documentation quality standards.
Invoked by/document

The spo (Structured Product Overview) doc type is handled by generate_spo.py directly, not by the document-generator agent.

test-plan-generator

AttributeDetail
RoleSynthesizes a structured manual test plan from a user-supplied brief and the most recently executed plans. Carries forward unchecked items from earlier test reports so they are not lost.
ToolsRead, Glob, Grep, Write
InputsA test brief string, a reserved usertest-NNN ID, output path, and optional directory overrides.
OutputsA user-test artifact with header, user brief, agent interpretation, and each step written as an imperative with its expected outcome.
Invoked by/critique test-plan

explanation-generator

AttributeDetail
RoleProduces explanation reports for the behavior, code, and data-model modes. Reads project sources, applies the mode's skeleton and voice, and produces a structured report.
ToolsRead, Glob, Grep, Bash, WebSearch, Write
InputsMode (behavior, code, or data-model), user brief, output path, and artifact ID.
OutputsAn ID-stamped explanation report. Behavior and data-model modes use a conversational, user-centered voice; code mode is aimed at junior developers with multiple analogies.
Invoked by/explain (behavior, code, data-model modes)

architecture-explainer

AttributeDetail
RoleProduces architecture explanation reports. Surveys the system structure, maps component boundaries and communication patterns, surfaces key design decisions and trade-offs.
ToolsRead, Glob, Grep, Bash, WebSearch, Write
InputsUser brief, output path, artifact ID, and optional scope (component or subsystem to focus on).
OutputsAn architecture explanation report aimed at onboarding developers, focusing on the why behind the architecture with multiple analogies. Covers the full system when unscoped, or a specific component and its dependencies when scoped.
Invoked by/explain (architecture mode)

evolution-explainer

AttributeDetail
RoleProduces behavior-evolution explanation reports. Mines the plan history to trace how a feature reached its current state, builds a timeline of waves and design rationale.
ToolsRead, Glob, Grep, Bash, WebSearch, Write
InputsUser brief (the feature area to trace), output path, and artifact ID.
OutputsA behavior-evolution report showing both the current behavior snapshot and the full evolution story via plan history. Includes all plan prefixes (FEATURE, FIX, REFACTOR, REDESIGN, CHORE) that touched the feature.
Invoked by/explain (behavior-evolution mode)

Writing Custom Subagents

To create a custom subagent, create a new Markdown file in .claude/agents/ following the established structure:

  1. Define the YAML frontmatter with name, description, designer_description, and tools. The tools field must list only the tools the agent needs -- follow the principle of least privilege.
  2. Write a role boundary blockquote clarifying which skill orchestrates this agent and what the division of responsibility is. The agent handles specialized work; the skill handles lifecycle, argument parsing, and user interaction.
  3. Document the input contract -- what parameters the agent expects to receive from the delegating skill. Be explicit about required vs. optional inputs.
  4. Define the process as step-by-step instructions. Start with loading relevant references (product-design/conventions.md for project context, product-design/constitution.md for generator agents). Then describe the analysis or generation steps.
  5. Specify the output format -- file naming, content structure, and where the output is written.
  6. Wire it into a skill by adding delegation logic to the skill's SKILL.md. The skill constructs the agent's prompt with invocation-specific parameters and launches it via the Agent tool.

The agent prompt file should not invoke /pre-skill or /post-skill -- the parent skill owns the lifecycle. Including lifecycle calls in an agent prompt causes double-execution of briefs logging, indexing, and commits.

Best Practices

  • Clear, focused role: each agent should do one thing well. If an agent's process section spans more than 10-15 steps, consider whether the work should be split across multiple agents.
  • Minimal tool set: grant only the tools the agent's process requires. Evaluator agents typically need Read, Glob, Grep, Bash; generator agents add Write.
  • Constitution loading for generators: any agent that produces user-facing content must read the constitution to enforce the trust boundary.
  • Convention-aware startup: begin the process with reading product-design/conventions.md to obtain project-specific paths and configuration.
  • Structured output: define a clear output format (header, sections, tables) so the parent skill can process the result consistently.

Common Mistakes

Giving agents too broad a tool set
An agent with Write access that only needs to read files can accidentally modify project files outside its scope. Declare only the tools the agent's process requires in the tools frontmatter field. Evaluator agents rarely need Write; most need only Read, Glob, Grep, Bash.
Not passing the constitution to generator agents
Generator agents produce user-facing artifacts that must respect the project's immutable principles. If the agent's process does not start with reading product-design/constitution.md, the generated content may violate constitutional constraints (e.g., identity, privacy, quality commitments). Every generator agent must load the constitution before beginning generation.
Confusing evaluator and generator roles
Evaluator agents analyze existing artifacts and return findings; generator agents produce new artifacts. Asking an evaluator to generate content (or a generator to review code) produces poor results because the agent's process, voice, and output format are optimized for its declared role. Use the right agent category for the task.
Writing agent prompts that duplicate SKILL.md logic
The agent should handle only the specialized work the skill delegates. Lifecycle management (pre-skill, post-skill), ID reservation, argument parsing, and user interaction belong in the skill. An agent that includes lifecycle calls will cause double-execution of briefs logging, index regeneration, and commits.
