The Lifecycle Pipeline

Every SEJA workflow follows a structured lifecycle that sequences investigation, design, planning, implementation, quality verification, documentation, and reflection. This chapter documents the canonical path, the pre-skill and post-skill hooks that bookend every skill invocation, the enforcement mechanisms that keep workflows on track, and the conversation trace that records non-skill exchanges.

The Canonical Path

The canonical lifecycle path defines the recommended ordering of skills for a typical feature iteration. Each stage builds on the outputs of the previous one, creating a traceable chain from investigation through reflection. 

/research (or /explain)
    |
/design  |  /plan
    |
/implement
    |
/critique
    |
/document  |  /communicate
    |
/reflect

On the first iteration of a new project, /seja-setup hands off to /design to configure project-specific files. From iteration 2 onward, start with /research (or /explain) to investigate what you are about to change, then branch into /design when design intent needs to change, or into /plan when it does not. The alignment workflow /explain drift reconciles design specs with the as-coded state at any point.

When to Deviate

The canonical path is a recommendation, not a hard gate. Several task shapes justify entering the lifecycle at a different point:

Bug fixes (FIX prefix)
May skip /research when the root cause is already known. The plan includes a root-cause section instead of a separate research artifact.
Documentation-only tasks (DOCUMENT prefix)
May start from /plan directly, since no codebase investigation is needed. The plan's scope is limited to documentation files.
Refactoring (REFACTOR prefix)
May skip /design because refactoring does not introduce new features or change design intent. Existing tests must continue to pass after implementation.

Pre-Skill Stages

Before every skill invocation, the pre-skill lifecycle hook runs a pipeline of 6 composable stages. Three stages are critical (always run): brief-log, budget-eval, and ref-load. Three stages are non-critical (error-isolated, warn and continue): help, pending-check, and constitution. Non-critical stages can be skipped by listing their IDs in the calling skill's metadata.skip_stages frontmatter field.

Stage Critical Purpose Behavior
help No Display skill quick guide Checks if arguments contain --help. If so, reads and displays .claude/skills/<skill>/SKILL-quickguide.md (falling back to the SKILL.md description field). Stops the pipeline -- no further stages or skill body execute.
brief-log Yes Log the skill invocation Obtains UTC time, inserts a STARTED entry into briefs.md (newest first), backfills the conversation trace to link the preceding exchange to this skill, and persists the brief text via brief_state.py for post-skill consumption.
budget-eval Yes Determine context budget Reads the calling skill's metadata.context_budget (default: standard). Three tiers control what gets loaded: light skips all briefs and references; standard loads the briefs index; heavy loads full briefs with recency windowing (50 most recent) plus the plan index. Sub-steps: orphan detection (standard and heavy tiers -- warns about STARTED entries with no matching DONE) and compaction warning (heavy tier only -- warns when more than 8 invocations occurred in the last 2 hours). Legacy stage IDs orphan-check and compaction-check are recognized by these sub-steps.
pending-check No Show overdue pending actions Runs pending.py status --overdue-days 14 --format banner and prints the output verbatim. Purely informational -- never blocks the skill invocation.
ref-load Yes Load reference files Loads three mandatory references: product-design/conventions.md, .claude/references/general/permissions.md, and .claude/references/general/constraints.md. Then loads skill-specific references in one of two modes: eager-only (reads all metadata.references) or demand-pull (reads eager_references upfront, lists remaining refs as available on demand). Skipped entirely for light-tier skills.
constitution No Load project constitution Reads and injects product-design/constitution.md. Skips silently if the file does not exist (backwards compatible with projects that have not generated one). Skipped for light-tier skills.

Context Budget Tiers

The context budget tier, declared in each skill's YAML frontmatter as metadata.context_budget, controls how much historical context is loaded during pre-skill:

Tier Briefs References Constitution
light Brief-log entry only; no history loaded Skipped Skipped
standard (default) Briefs index (compact summary) Mandatory + skill-specific Loaded
heavy Full briefs (50 most recent) + plan index Mandatory + skill-specific Loaded

Post-Skill Steps

After every skill completes, the post-skill lifecycle hook runs a sequence of steps that handle brief completion, telemetry, design alignment, documentation, QA logging, commit safety, index regeneration, and next-step suggestions. Each step writes a checkpoint so the pipeline can resume after a crash.

Step 0 -- Checkpoint Recovery
If a post-skill checkpoint file exists from a prior crashed run, resume from the step after the recorded checkpoint. Stale checkpoints (from a different skill ID) are deleted.
Step 1 -- Brief-Log Completion
Marks the matching STARTED entry in briefs.md as DONE with the current UTC timestamp and optional plan ID. Retrieves the original brief text from brief_state.py.
Step 1b -- Telemetry Recording
Prepares a telemetry record in memory (skill name, ID, outcome, timestamps, token count). The record is flushed to disk at step 8b after commit-dependent fields are available.
Step 2 -- As-Coded Alignment
Runs after /implement (skipped for /plan). Updates product-design/product-design-as-coded.md to reflect what actually shipped: conceptual design entities, metacommunication intents, and journey map statuses. Proposes DONE markers for as-intended items that were implemented. Creates pending actions for verification, testing, and documentation.
Step 2b -- Documentation Auto-Run
Collects non-N/A Docs: fields from the plan. If any exist, offers to run /document --plan <id> immediately or defer to the pending ledger. Can be preset to skip via --skip-docs.
Step 2c -- Design Intent Reminder
Informational message reminding the user to consider promoting implemented items to established status via /explain drift --promote. Does not perform the promotion itself.
Step 2d -- Eager Implement Entry
Runs when the parent skill is /plan. Files an implement pending action for the newly created plan so it appears in the pending ledger as work to execute.
Step 2g -- Pending Action Creation
Creates up to four pending actions from plan metadata after implementation: (i) verify-as-coded when the plan's file count exceeds a configurable threshold, (ii) test-implementation when the plan has a Test Plan section, (iii) update-documentation when documentation was skipped during post-skill, and (iv) an implement mark-done safety net that closes the pending entry filed at /plan completion. Each invocation is silent on success and non-blocking on failure.
Step 3 -- QA Log
Captures the session's Q&A exchanges. Three branches: skip (when the parent embeds its own Q&A, e.g. /research), inline (appends to the artifact file for plans, implementations, roadmaps, and critiques), or companion (creates a sibling QA file for all other artifact types).
Steps 4-6 -- Commit Preparation
Step 4 creates the commit message. Step 5 checks git state (blocks on rebase-in-progress, unmerged conflicts, or detached HEAD; warns on main/master). Step 6 verifies commit scope against expected paths via verify_commit_scope.py.
Step 6b -- Fast Preflight Gate
Runs run_preflight_fast.py as an advisory check. Non-zero exit displays failures and asks whether to proceed. The pre-commit hook (.githooks/pre-commit) is the hard gate.
Step 6c -- Human Markers Verifier
Runs check_human_markers_only.py --staged to detect unauthorized prose mutations in Human (markers) files. Violations trigger an abort recommendation.
Step 7 -- Index Regeneration
Refreshes the briefs index, macro artifact index, cross-references between artifacts, and the decision digest (conditional on research or DECISION_APPEND activity).
Step 7e -- Deferred Artifact Generation
Runs after /implement only. Generates a ## Manual Actions section in the plan file if any step requires post-deployment operator action. Generates or updates _output/docs/deploy.html if any step has a non-N/A Deploy: field, covering Docker, Linux, and Windows deployment instructions.
Step 8 -- Stage and Commit
Stages all affected files (regenerated indexes, as-coded updates, deferred artifacts) and commits. Deletes the checkpoint file on success.
Step 8b -- Telemetry Flush
Enriches the step-1b record with commit-dependent fields (SHA, files changed count, parent skill) and appends it to telemetry.jsonl. Committed as a separate trailing commit to avoid amend divergence. Skipped if step 8 produced no commit.
Steps 9-12 -- Wrap-Up
Step 9 reports any surprises encountered during execution. Step 10 outputs a link to the generated artifact. Step 11 prints the skill-complete banner. Step 12 reads the skill graph and presents contextual next-step suggestions (at most 3 options plus skip), suppressing suggestions already covered by earlier steps.

Worktree Deferred Mode

When the roadmap parallel-wave orchestrator passes --deferred after merging a worktree branch back to main, post-skill runs a reduced pipeline: only steps 0, 1b, 2, 2c, 7, 2g, and 8b execute. The orchestrator handles wave-level briefs, QA, commits, and deferred artifacts.

Enforcement Mechanisms

SEJA enforces lifecycle compliance through four complementary mechanisms, each operating at a different layer:

CLAUDE.md Context Rules
The project's CLAUDE.md is loaded into every agent context window. It declares the canonical lifecycle path, the conversation trace protocol, and key workflow instructions. Because these rules are always present in context, they guide the agent's behavior at every turn without requiring external enforcement.
Pre-Commit Hooks
The .githooks/pre-commit hook (installed via bash .githooks/install.sh) runs two checks on every commit: run_preflight_fast.py (fast validation checks) and check_no_private_leaks.py --staged (prevents private content from leaking into public-facing files). This is the hard gate -- commits that fail these checks are rejected.
Validation Scripts
run_all_checks.py is the CI-independent validation orchestrator. It discovers and runs all registered check scripts with unified exit codes and JUnit XML output. Individual check scripts cover documentation consistency (check_docs.py), design system token drift (check_design_system_token_drift.py), harness structural integrity, and project-specific validations declared in product-design/conventions.md.
Constitution Loading
The pre-skill constitution stage loads product-design/constitution.md into the agent's context before every standard and heavy-tier skill invocation. The constitution declares immutable principles (design authority, epistemic posture, privacy, lifecycle discipline, artifact integrity, authorship voice) that no other reference file can override. Subagents also receive the constitution as part of their prompt for trust boundary enforcement.

Lifecycle Variations

The lifecycle adapts its shape based on the type of work being performed. SEJA uses plan prefixes to signal these variations, and skills adjust their behavior accordingly.

Bug Fixes (FIX Prefix)

Bug fix plans may skip /research when the root cause is already known. The plan includes a root-cause analysis section instead of relying on a separate research artifact. Fix plans are gated by the FIX prefix, which signals that the work addresses an existing defect rather than adding new capability. Post-skill documentation auto-run (step 2b) triggers only when the plan has steps with non-N/A Docs: fields.

Documentation-Only Tasks (DOCUMENT Prefix)

Documentation tasks may enter the lifecycle at /plan directly, since no codebase investigation is needed. The plan's file scope is limited to documentation files. Post-skill next-step suggestions (step 12) suppress /reflect for DOCUMENT-prefixed plans as a low-value reflection target.

Refactoring (REFACTOR Prefix)

Refactoring plans may skip /design because they do not introduce new features or change design intent. The key constraint: existing tests must continue to pass after implementation. The as-coded alignment step (post-skill step 2) still runs to keep product-design/product-design-as-coded.md in sync if entity structures changed, but DONE marker proposals (step 2e) are typically skipped since refactoring does not implement new as-intended items.

Chore Tasks (CHORE Prefix)

Chore plans cover tooling, CI/CD, infrastructure, and other non-feature work. Like DOCUMENT, post-skill suppresses /reflect suggestions. Documentation auto-run triggers only when steps carry non-N/A Docs: fields.

Conversation Trace Integration

SEJA maintains a persistent conversation trace in _output/conversation-trace.jsonl that records every non-skill exchange between the user and the agent. This trace provides a complete record of the session's decision-making context beyond what skill artifacts capture.

The Append Protocol

After responding to any user message that is not within an active skill invocation, the agent silently logs the exchange:

  1. Get preceding event ID: run conversation_trace.py last-evt-id --session-id $CLAUDE_SESSION_ID to retrieve the ID of the most recent entry.
  2. Append user utterance: run conversation_trace.py append with --emitter user, the user's message text, and a type inferred from context (question, answer, or instruction). If exit code 2 indicates masking was applied, show the masked message and ask for confirmation before proceeding.
  3. Append agent response: run conversation_trace.py append with --emitter claude, a 1-2 sentence summary of the response, and optional --topic-tags (1-3 short tags when the topic is clearly identifiable).

Skill Linkage

When a skill is invoked, the pre-skill brief-log stage backfills the conversation trace by linking the most recent agent response entry to the skill invocation via conversation_trace.py backfill-skill. This creates a continuous chain: conversation exchanges flow into skill invocations, and skill artifacts reference the exchanges that preceded them.

Common Mistakes

Skipping lifecycle steps
Running /implement immediately after /research, bypassing /plan. The plan step decomposes work into executable steps, sets verify criteria, and triggers a complexity-gated review. Without it, the implementation lacks structure, traceability, and quality assurance. Follow the canonical path unless you have a clear reason to deviate (see Lifecycle Variations).
Confusing pre-skill with post-skill
Pre-skill runs before the skill body (6 stages: context setup, brief logging, reference loading). Post-skill runs after the skill body (steps that handle brief completion, as-coded alignment, QA logging, commits, and telemetry). The pre-skill constitution stage loads immutable principles; the post-skill as-coded alignment updates the implemented design record. These are complementary, not interchangeable.
Running /implement without a plan
The /implement skill expects a plan file to exist. In auto mode, it spawns one subagent per plan step, each with the step's file list, verify criteria, and dependencies. Without a plan, the executor has no steps to dispatch, no verify criteria to check, and no progress file to track. Always run /plan first, or use /plan --light for small, surgical changes.
Forgetting conversation trace after non-skill responses
The conversation trace protocol in CLAUDE.md requires logging every non-skill exchange. When the agent responds to a user message outside of a /skill invocation and forgets to append to the trace, that exchange is lost from the session record. The trace is append-only and session-scoped -- missing entries cannot be reconstructed later.
