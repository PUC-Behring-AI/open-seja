Quality and Critique

The /critique skill is SEJA's unified quality gate — one skill for every "is it OK?" question. It provides ten mutually exclusive modes covering static validation, structured code review, runtime smoke tests, pre-merge preflight checks, harness self-diagnosis, test plan generation, documentation consistency scanning, git freshness tracking, telemetry analysis, and semiotic inspection. Each mode produces a numbered critique log that becomes part of the project's quality trail.

The Critique System

In the SEJA lifecycle, critique occupies the verification position: it runs after /implement and before /document or /communicate. The principle is validate before you communicate — no stakeholder material should be generated until the implementation has passed quality review.

The critique system is multi-modal by design. Different quality questions require different tools: a code review needs the 16 review perspectives, a smoke test needs a running application, and a harness health check needs access to internal SEJA structure. Rather than splitting these into separate skills, /critique provides one entry point with mode dispatch. Each invocation selects exactly one mode, runs the appropriate checks, and produces a numbered report file.

All modes except telemetry follow a shared execution pattern: pre-skill lifecycle hook, mode-specific checks, report generation with a reserved ID, result presentation, and post-skill lifecycle hook. The telemetry mode is read-only and produces no artifact.

Tip: Use /critique preflight as your pre-merge checkpoint — it combines validation and code review in one pass and gives a clear go/no-go verdict.

Critique Modes

Ten modes are available, each targeting a different quality concern. Modes are mutually exclusive — specify exactly one per invocation. A global --depth <light|standard|deep> flag overrides review depth for the review and preflight modes.

Mode Purpose Scope Options Output
validate Run project validation scripts all (default), i18n, auth, migrations, constants, po, coverage, tests, spec Validation report with pass/fail per check
review Structured code review against quality perspectives staged (default), file path, directory path Review log with perspective evaluations
smoke Runtime smoke tests against API endpoints or UI pages all (default), api, ui Smoke test report with PASS/WARN/FAIL per endpoint
preflight Combined validate + review as a pre-merge checkpoint staged (default), all, directory path Preflight report with go/no-go verdict
health Harness self-diagnosis and integrity check None (runs all 9 built-in checks); --source <path> enables drift check Harness Health Report with PASS/WARN/FAIL per check
test-plan Generate a structured manual test plan A brief describing what to test User test artifact with scenarios and expected results
docs Documentation consistency check via plugin scanners --plugins <list>, --verbose, --filter <severity> Documentation consistency report
freshness Compare local branches to upstream remotes Implicit (configured repos) Git freshness report with ahead/behind counts
telemetry Usage analytics from telemetry.jsonl None Displayed inline (no report file saved)
semiotic-inspection SIM-based communicability evaluation Feature name, page, user flow, or all SIM report with communicability judgment

validate

Orchestrates project validation scripts through the standards-checker agent. Stack filtering reads BACKEND_FRAMEWORK and FRONTEND_FRAMEWORK from product-design/conventions.md and runs only scripts matching the project's stack from the plugin registry at .claude/skills/scripts/check_plugin_registry.json.

Scope dispatch routes specific checks to specialized agents: the migrations scope launches both the standards-checker and the migration-validator agent for deep inspection; the tests scope launches the test-runner agent; the spec scope runs check_spec_conformance.py directly; the all scope runs the full standards check plus spec conformance.

Output: a validation report with a summary table (check name, status, error count, warning count) and per-failure details.

review

Launches the code-reviewer agent against staged changes (default), a specific file, or a directory. The agent follows the two-stage loading protocol: load the perspective index, select 4–6 relevant perspectives based on the change content, load only those perspective files, evaluate, and return a structured report.

Review depth is controlled by --depth with a floor set by MINIMUM_REVIEW_DEPTH in product-design/conventions.md. The effective depth is max(floor, flag). Without a --depth flag, all 16 perspectives are evaluated (equivalent to deep).

Output: a review log with a perspective evaluation table (Adopted/Deferred/N/A per perspective), prioritized issues with severity and file references, and recommendations.

smoke

Runs runtime smoke tests driven by the endpoint registry at .claude/skills/scripts/smoke_test_registry.json. API smoke tests use the Flask test client against an in-memory SQLite database — no servers required. UI smoke tests require Playwright with both backend and frontend servers running.

Output: PASS/WARN/FAIL counts per endpoint, captured errors, and an overall verdict. When failures are found, the user is asked whether to investigate immediately, create a plan, or dismiss.

preflight

The pre-merge checkpoint that combines validation and code review into a single pass. Launches the standards-checker, code-reviewer, and optionally smoke tests as concurrent agent invocations. If one check fails, the others still produce results — preflight does not abort on partial failure.

Output: a merged report with validation summary, review perspective table, and prioritized issues. The overall status is READY only if all validation checks pass and no HIGH-severity review issues were found; otherwise NOT READY.

health

Launches the harness-health-evaluator agent to run 9 built-in diagnostic checks:

  1. Skill system integrity
  2. Orphaned briefs (STARTED without matching DONE)
  3. Stale plans
  4. Reference file completeness
  5. Conventions completeness
  6. Constitution presence
  7. Skill spec compliance
  8. Pending ledger summary
  9. Harness drift (when --source <path> is provided)

Output: a Harness Health Report with PASS/WARN/FAIL per check and an overall N/9 tally. The --verbose flag adds detailed output per check. The --source flag enables drift detection against a canonical source harness directory.

test-plan

Launches the test-plan-generator agent with a brief describing what to test. The agent reads the plan index, filters for recently completed plans relevant to the brief, carries forward unchecked items from earlier user tests, and produces a structured manual test plan. Each scenario is phrased as an imperative command with its expected outcome.

Output: a user test artifact saved to ${USER_TESTS_DIR} with a reserved usertest-NNN ID.

docs

Runs check_docs.py with its 6 plugin-based scanners: harness integrity, path liveness, environment variables, command references, terminology, and structural completeness. Plugins can be filtered with --plugins, output verbosity controlled with --verbose, and severity filtered with --filter.

Output: a documentation consistency report with error/warning/info counts grouped by plugin, along with specific locations and messages for each finding.

freshness

Runs check_git_freshness.py to compare local branches against their upstream remotes for all configured repositories (workspace root plus codebase directory when distinct). The check is advisory-only and never pulls automatically.

Output: per-repo sections with branch name, ahead/behind counts, and suggested actions (pull, push, or investigate divergence).

telemetry

A read-only informational mode that reads telemetry.jsonl and displays skill invocation statistics. Unlike all other modes, telemetry does not reserve an ID, does not save a report file, and does not invoke post-skill.

semiotic-inspection

Launches the semiotic-inspector agent for a Semiotic Inspection Method (SIM) evaluation. The agent reconstructs the designer's metacommunication message across three sign classes — metalinguistic (help text, error messages), static (layout, labels), and dynamic (state transitions) — then collates them to produce a communicability judgment.

The agent acts as evaluator-as-user-advocate, representing users' interests through HCI knowledge. It applies the 5 SIM scaffold questions and the 4 SigniFYIng Interaction dimensions to surface where the three sign classes agree, where they contradict, and where users are likely to lose the thread.

Output: a SIM report with per-sign-class analysis and an overall communicability verdict.

Review Perspectives

SEJA evaluates changes through 16 domain lenses organized into engineering and design categories. Each perspective defines a checklist of prioritized questions at three tiers: Essential (P0 critical/blocking questions, always evaluated), Standard (P1–P2 questions for thorough review), and Deep (P3–P4 questions for exhaustive analysis). The full perspective checklists are agent-facing reference files at .claude/references/general/review-perspectives/; this section provides the summary index.

Engineering Perspectives

Tag Name Tier Scope
SEC Security Essential Auth, input validation, secrets management, dependency vulnerabilities
PERF Performance Deep-dive N+1 queries, unbounded loops, indexes, caching, bundle size
DB Database Essential Schema migrations, backward compatibility, idempotency, constraints
API API Design Deep-dive RESTful conventions, route consistency, request/response contracts
ARCH Architecture Essential Layer boundaries, separation of concerns, dependency direction
DX Developer Experience Essential Readability, conventions, documentation, error messages
I18N Internationalization Essential i18n keys, locale support, pluralization, RTL, date/number formats
TEST Testability Essential Test coverage, new test needs, mocking strategy, test isolation
OPS Operations / DevOps Deep-dive Environment parity, logging, monitoring, deployment, config management
COMPAT Compatibility Deep-dive API contract stability, schema evolution, browser/version support
DATA Data Integrity & Privacy Deep-dive PII handling, GDPR compliance, validation, audit trails

Design Perspectives

Tag Name Tier Scope
UX User Experience Essential User flows, feedback, error handling, navigation, discoverability
A11Y Accessibility Essential WCAG AAA, contrast, keyboard nav, screen readers, focus management

Perspective Status Vocabulary

Each perspective in a review is assigned one of three statuses:

Adopted
Evaluated; concerns addressed in the current change.
Deferred
Evaluated; concerns identified but not addressed — the review log records why, with pros and cons of deferral.
N/A
The perspective does not apply to this change (e.g., the Database perspective for a pure frontend change).

The Two-Phase Review Process

Code review and plan review in SEJA follow a two-phase process designed to keep context lean while ensuring thorough coverage. The process is complexity-gated: simpler changes use a lighter pass, while high-stakes changes trigger deeper analysis.

Phase 1: Perspective Triage and Scan

The reviewer loads the compact perspective index (.claude/references/general/review-perspectives-index.md, under 600 tokens) and selects 4–6 relevant perspectives based on the change content. For each selected perspective, the reviewer loads the full perspective file from .claude/references/general/review-perspectives/ and evaluates the Essential (P0) questions. Perspectives that do not apply to the change are marked N/A without loading their files.

For review depth deep or when explicitly requested, all 16 perspective files are loaded and evaluated.

Phase 2: Targeted Deep-Dives

When Phase 1 identifies concerns that require further analysis, the reviewer conducts targeted deep-dives on the affected perspectives. Deep-dives evaluate Standard (P1–P2) and Deep (P3–P4) questions for the perspectives where Essential screening raised flags or where the change complexity warrants closer examination.

Deep-dives are budget-controlled to prevent unbounded review scope. The reviewer tracks convergence: once a perspective's concerns have been fully characterized and the findings have stabilized, the deep-dive concludes for that perspective.

Conflict Resolution

When two perspectives pull in opposite directions (e.g., Performance recommends caching while Security flags the cache as an attack surface), the reviewer follows a fixed resolution order:

  1. SEC wins by default — unless the user explicitly accepts the risk.
  2. A11Y is non-negotiable — never traded against visual design or performance.
  3. Document the trade-off — record both the chosen approach and the deferred concern with rationale.
  4. Ask when unclear — for non-default conflicts (e.g., PERF vs DX), ask the user rather than choosing silently.

Interpreting Results

Validation Output

Validation reports present a summary table with each check script's name, status (PASS, FAIL, or INFO), error count, and warning count. The overall result line shows X/Y checks passed. Any check with status FAIL requires attention; INFO results are advisory.

Review Logs

Review logs contain a perspective evaluation table showing Adopted/Deferred/N/A status per perspective, followed by prioritized issues. Each issue carries a severity level, the perspective that raised it, a description, and a file reference. Focus on HIGH-severity issues first — these would block a release. Deferred items include rationale and should be revisited in a future iteration.

Preflight Verdicts

A preflight report ends with an overall status: READY (all validation checks pass, no HIGH-severity review issues) or NOT READY (at least one check failed or a HIGH-severity issue was found). Treat NOT READY as a merge blocker.

Health Reports

Health reports show PASS/WARN/FAIL per diagnostic check and an overall N/9 tally. WARN results indicate degraded conditions (e.g., orphaned briefs, stale plans) that should be addressed but do not block operation. FAIL results indicate structural issues that need immediate attention.

What to Fix vs Defer

Fix immediately: HIGH-severity review findings, FAIL validation checks, security and accessibility issues (SEC and A11Y perspectives). Defer with documentation: MEDIUM-severity findings in perspectives not central to the change, WARNING-level validation results from non-critical checks. Do not defer: anything that would violate the project constitution or compromise user safety.

When to Re-Run

Re-run critique after fixing findings to confirm they are resolved. A preflight pass before merge provides confidence that the change is ready. For ongoing development, periodic health and freshness checks catch drift and staleness early.

Common Mistakes

Running review without reading the diff first
The code review mode works best when the reviewer (human or agent) has context about what changed and why. Running /critique review on staged changes without understanding the plan behind them leads to superficial findings. Read the plan and the diff before reviewing.
Ignoring Deferred findings
Deferred perspectives are not dismissed — they represent concerns that were evaluated and intentionally postponed. Review logs record the rationale for each deferral. If Deferred items accumulate across multiple reviews without being addressed, they signal growing technical or design debt.
Skipping preflight before merge
The /critique preflight mode exists specifically as a pre-merge checkpoint. Skipping it and relying solely on individual validate or review runs misses the combined verdict and the concurrent checks that preflight provides.
Treating advisory findings as blocking
INFO-level validation results, WARNING-level health check findings, and MEDIUM/LOW-severity review issues are advisory. They should be reviewed and tracked but should not block a merge if the core quality criteria (no FAIL validation, no HIGH-severity review issues) are met.
Running all critique modes when one is sufficient
Each mode targets a specific quality concern. Running validate, review, smoke, and health in sequence when only a code review was needed wastes time and context budget. Use preflight when you need the combined validate+review pass; use individual modes for targeted checks.
