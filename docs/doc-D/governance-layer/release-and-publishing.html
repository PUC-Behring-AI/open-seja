Release and Publishing

This chapter documents the /publish pipeline end to end -- from tag conventions and version inference through the ephemeral publish workspace to the final priv/public sync -- explaining how SEJA releases are cut, validated, and pushed to the public repository.

The /publish Pipeline

To cut a release, invoke /publish [version] in Claude Code. The skill accepts an optional version argument in vMAJOR.MINOR.PATCH format (e.g., v2.14.0). When no version is provided, publish.py infers the next tag from CHANGELOG.md and existing git tags, then prompts for confirmation. Two flags modify behavior: --dry-run previews the full command sequence without executing any destructive actions, and --yes accepts all defaults at confirmation prompts for non-interactive use.

The pipeline delegates to tools/publish.py, which orchestrates a 10-step lifecycle:

  1. Preflight checks. Validates that the working tree is clean, seja-public/CHANGELOG.md has unreleased content, no pre-existing tag matches the target version, and the remote origin is reachable. If .claude/CHANGELOG.md lacks a heading for the target version, the skill auto-generates the entry by collecting structured change data from git history via generate_changelog_data.py and delegating to the document-generator agent.
  2. Cut tag. Creates the git tag in the local seja-priv repository via cut_tag.py.
  3. Clone public repo. Shallow-clones the public seja repository into _output/tmp/publish-workspace/.
  4. Copy authored prose. Copies public-only prose from seja-public/ -- files like CHANGELOG.md, README.md, LICENSE, and the docs/ directory -- into the clone.
  5. Sync harness files. Runs sync_to_public.py --target <clone-dir> to generate the .claude/ directory in the clone. This copies the harness from seja-priv, strips content between <!-- priv-only-start --> / <!-- priv-only-end --> markers, unwraps <!-- pub-only-start --> / <!-- pub-only-end --> markers, and excludes private directories (priv/, project/), settings files, and test scripts.
  6. Smoke test. Runs pre_publish_smoke.py --candidate <clone-dir> to validate the clone, including a final check_no_private_leaks.py scan to ensure no private content has leaked into the publish workspace.
  7. Commit. Stages all changes in the clone and commits with a Release vX.Y.Z message.
  8. Push. Pushes the commit and tag to the public repository's main branch.
  9. Cleanup. Deletes the temporary clone directory (in a finally block to ensure cleanup even on failure).
  10. Close pending entry. Marks the PUBLISH: pending-ledger entry as done via pending.py.

On success, the skill reports the published version. On failure, it relays the error message and recovery instructions printed by publish.py -- the script's recovery guidance is authoritative and should not be second-guessed.

Tag Conventions

SEJA uses semantic versioning. Tags follow the format vMAJOR.MINOR.PATCH -- always prefixed with v. Any core-team member may cut a tag. The cadence is manual: releases happen when a coherent batch of changes is ready, targeting at most roughly one release per week. Smaller changes are batched together rather than shipped individually.

Version inference

When no explicit version is provided, publish.py infers the next tag through a two-step process:

  1. Discover the baseline. The baseline is max(highest_git_tag, highest_changelog_heading) using semver comparison. Ties prefer git tags because a tag represents an actual cut, while a changelog heading may describe a planned entry not yet released. When the changelog heading wins, the script emits a note so the operator knows which source drove the baseline.
  2. Determine the bump level. The script first checks for an explicit hint comment in the ## Unreleased section of seja-public/CHANGELOG.md: <!-- bump: patch|minor|major -->. If no hint is present, the script applies a heuristic based on subsection headings: a ### Breaking changes heading triggers a major bump, ### Added triggers minor, and everything else defaults to patch. Under v0.x, a major intent collapses to a minor bump (the contract-evolving rule).

Unified version namespace

SEJA uses one version, one CHANGELOG entry, one tag. Both .claude/CHANGELOG.md (the harness changelog) and seja-public/CHANGELOG.md (the public changelog) use the same version number. SemVer allows gaps, so the public repository jumped from v0.2.0 to the first internal version issued under the unified namespace policy. A gap note in the public changelog explains the jump for consumers.

Hotfix policy

The default rule is forward-fix on main and tag the next patch version. If a consumer is actively blocked on an older version, the team revisits per-case whether a release/<minor>.x branch is warranted.

The Ephemeral Publish Workspace

A key architectural decision in SEJA's release model is that seja-public/.claude/ does not exist on disk. The harness files that consumers receive in the public seja repository are never stored persistently in seja-public/ -- they are generated ephemerally during each publish cycle.

When /publish runs, publish.py creates a temporary clone of the public repository at _output/tmp/publish-workspace/. This clone is populated in two passes: first, authored public-only prose (CHANGELOG, README, LICENSE, docs) is copied from seja-public/; second, sync_to_public.py --target generates the .claude/ directory by copying harness files from seja-priv and stripping private content. The clone is then committed, tagged, and pushed to the public repository. Afterward, the clone directory is deleted.

This ephemeral approach provides several guarantees:

  • The harness files in the public repository always match the private repository at the time of release -- there is no opportunity for the two to drift because the public copy is regenerated from scratch each time.
  • Private content is stripped during generation, not after the fact. The sync_to_public.py script excludes entire directories (priv/, project/), specific files (settings.json, settings.local.json, test scripts), and inline content between priv-only-start / priv-only-end markers. The pre_publish_smoke.py test suite validates the result before any push occurs.
  • There is no stale .claude/ directory sitting in seja-public/ between releases that could accidentally be committed, modified, or mistaken for the canonical source. The canonical source is always seja-priv/.claude/.

The check_no_private_leaks.py script reinforces this model: its default invocation warns if seja-public/.claude/ exists on disk at all, since its presence indicates a cleanup failure from a previous publish run.

The Priv/Public Boundary

The separation between seja-priv and the public seja repository is not a deployment convenience -- it is a security boundary codified in the project constitution. Constitution invariant S1 states that private content must never reach seja-public without explicit opt-in. Compliance requirement C2 specifies that the product-design/ directory is permanently private and never synced. The Enforcement Architecture chapter documents the layered gates that enforce this boundary.

What stays in seja-priv

  • product-design/ -- constitution, conventions, design-intent files, as-coded state, UX research results, and all agent-facing structured specifications.
  • _output/ -- plans, research logs, critiques, roadmaps, briefs, conversation traces, pending ledger, and this documentation collection.
  • .claude/skills/scripts/priv/ -- private-only scripts such as check_no_private_leaks.py and generate_changelog_data.py.
  • .claude/skills/scripts/project/ -- project-specific scripts that are not part of the reusable harness.
  • tools/ -- release tooling including publish.py, sync_to_public.py, and the sync runbook.
  • Inline content between <!-- priv-only-start --> and <!-- priv-only-end --> markers in any .md file -- stripped during sync.

What reaches seja (public)

  • .claude/ harness files -- skills, agents, references, rules, and shared scripts (excluding the priv/ and project/ subdirectories, settings files, and test scripts). Generated by sync_to_public.py during publish.
  • CLAUDE.md -- the project instructions file, with private sections stripped.

Public-only prose

Certain files exist only in the public repository and have no counterpart in seja-priv: the public CHANGELOG.md, README.md, LICENSE, TRADEMARKS, and the docs/ directory. These are authored directly in seja-public/ (a Git submodule within seja-priv) and copied into the temporary clone during publish. They do not flow back to seja-priv.

Common Mistakes

Editing the standalone seja/ clone instead of seja-public/
The public seja repository should never be edited directly. Public-only prose is authored in seja-public/ within seja-priv, and harness files are generated during publish. Edits made directly to a standalone seja/ clone will be overwritten on the next release.
Recreating seja-public/.claude/ on disk
The .claude/ directory in seja-public/ is generated ephemerally during publish and should never exist on disk between releases. If it appears, check_no_private_leaks.py will warn about it. Delete it rather than trying to maintain it manually.
Publishing without running --dry-run first
The --dry-run flag prints the full sequence of commands that would execute -- including the git clone URL, target directory, and push commands -- so you can visually verify correctness before a live run. Skipping this step risks publishing with an unexpected version number or against an incorrect remote.
Forgetting to update CHANGELOG.md before tagging
The pipeline checks that seja-public/CHANGELOG.md has content in its ## Unreleased section before proceeding. If the harness changelog (.claude/CHANGELOG.md) is also missing an entry for the target version, the skill will auto-generate one -- but the public changelog must be updated manually. The preflight check will block the release if it finds an empty unreleased section.
