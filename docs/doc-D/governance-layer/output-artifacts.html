Output Artifacts

Every skill invocation in SEJA produces artifacts -- plan files, research logs, critique reports, reflections, and more. All of these land in the output directory (_output/), which serves as the single root for generated content. This chapter catalogs the output subdirectories, documents the key files that provide observability and traceability, explains how artifacts move through their lifecycle, and flags common mistakes that can break the governance model.

The Output Directory

The output directory (_output/) is defined by the OUTPUT_DIR variable in the project's conventions.md. Every subdirectory within it is owned by a specific skill or set of skills, and each follows a consistent naming pattern that embeds the brief number for traceability.

Directory Contents Producing skill(s) Typical naming pattern

research-logs/ Structured research reports answering codebase or architecture questions /research research-NNNNNN-<slug>.md

All subdirectory paths are defined as variables in conventions.md (e.g., PLANS_DIR, RESEARCH_DIR, REFLECTIONS_DIR), making them relocatable if a project overrides the output root.

Key Files

Beyond the subdirectories, the output directory and the product design directory contain several key files that provide observability, traceability, and design-state tracking. These files are registered in the Key Files table of conventions.md.

File Purpose Format Maintained by
_output/briefs.md Execution log of all skill invocations. Each brief records what skill ran, what it produced, and its outcome. The chronological record of harness activity. Markdown (append-only) Agent
_output/briefs-index.md Lightweight briefs index with one-line summaries per brief. Enables fast lookup without reading the full briefs log. Markdown Agent
_output/INDEX.md Single global artifact index. Maps every generated artifact to its brief number, type, and location. Markdown Agent
product-design/constitution.md Project constitution -- immutable principles (tenets T1--T4) that constrain agent behavior. Cannot be overridden by any skill or plan. Markdown Human
product-design/product-design-as-coded.md Unified implementation state. The agent-maintained mirror of what is actually built, as opposed to what was intended. Markdown Agent
product-design/product-design-changelog.md As-built conceptual design changelog. Records when and why the as-coded state changed. Markdown Agent
product-design/product-design-as-intended.md Unified working intent (sections 0--17) plus Decisions plus CHANGELOG. The designer's authoritative description of what SEJA should be. Markdown Human (markers)
product-design/ux-research-results.md UX research: personas, problem scenarios, journeys, and CHANGELOG. Records the user research that grounds design decisions. Markdown Human (markers)
product-design/standards.md Unified engineering standards governing code quality, testing, and implementation conventions. Markdown Human / Agent
product-design/design-standards.md Unified design standards governing UX patterns, documentation structure, and communication conventions. Markdown Human / Agent
_output/tmp/session-notes.md Session-scoped working memory. A scratchpad for cross-session persistence of notes, decisions, and context the agent needs to carry forward. Markdown Agent
_output/decision-digest.jsonl Machine-readable decision index. Each line records a design decision with its rationale, alternatives considered, and outcome. JSONL Agent
_output/conversation-trace.jsonl Append-only conversation trace log. Records every user-agent exchange outside of active skills, enabling session reconstruction and audit. JSONL Agent

The "Maintained by" column reflects a key governance distinction. Agent files are written exclusively by skills and lifecycle hooks -- humans should not hand-edit them (see Common Mistakes). Human files are authored entirely by the designer. Human (markers) files are authored by the designer but receive structured lifecycle markers (STATUS, INCORPORATED, DECISION_APPEND, CHANGELOG_APPEND) written by the agent via apply_marker.py after explicit confirmation.

Artifact Lifecycle

SEJA artifacts are not static files -- they move through a predictable lifecycle driven by the skill execution pipeline. Understanding this lifecycle clarifies why certain files exist, how they relate to each other, and what happens when a skill completes.

Creation

Artifacts are created by skill execution. When a user invokes a skill (e.g., /plan, /research, /reflect), the skill writes its output to the appropriate subdirectory under _output/. The file name embeds the brief number assigned by pre-skill, which links the artifact back to its entry in the briefs log.

Commit and Registration

After the skill completes, post-skill commits the new artifact to version control and registers it in _output/INDEX.md. The INDEX entry records the artifact's type, brief number, file path, and a one-line summary. This ensures that every artifact is discoverable through a single index, regardless of which subdirectory it landed in.

The Briefs Log as Chronological Record

The briefs log (_output/briefs.md) is the chronological backbone of the output directory. Each brief entry records what skill ran, the parameters it received, the artifacts it produced, and the outcome. Because briefs are append-only and sequentially numbered, they provide a total ordering of all harness activity. The lightweight briefs index (_output/briefs-index.md) provides fast lookups into this log without requiring the agent to read the entire file.

The Conversation Trace as Inter-Skill Record

Between skill invocations, the conversation trace (_output/conversation-trace.jsonl) records every user-agent exchange. Each entry carries a session ID, an event ID, and a preceding-event-ID that chains entries into a directed sequence. This trace fills the gap that the briefs log leaves: while briefs capture skill executions, the conversation trace captures the discussions, decisions, and context that happen between skills.

The Session Scratchpad for Cross-Session Persistence

The session notes file (_output/tmp/session-notes.md) serves as working memory that persists across Claude Code sessions. Unlike the briefs log (which is a historical record) or the conversation trace (which is an audit trail), the session scratchpad is a living document that the agent reads at session start and updates as needed. It carries forward context, open questions, and in-progress state that would otherwise be lost when a session ends.

Common Mistakes

Hand-editing generated artifacts
Constitution tenet T3 states that generated artifacts (plans, research logs, reflections, as-coded files) are agent-maintained and must never be hand-edited by the designer. Agents write them via post-skill or designated skill steps only. Hand-editing creates divergence between the artifact's content and the machine-readable record (briefs, INDEX, decision digest), which can cause validation scripts to report false drift.
Deleting _output/ files without understanding dependencies
Artifacts in _output/ are cross-referenced by the briefs log, the artifact index, the decision digest, and sometimes by other artifacts (e.g., a roadmap references its constituent plans). Deleting an artifact without updating these references leaves dangling pointers that confuse both the agent and validation checks. If cleanup is needed, use /pending to manage lifecycle transitions rather than manual deletion.
Confusing briefs.md with the session scratchpad
The briefs log (_output/briefs.md) is an append-only historical record of skill executions -- it is never edited or truncated. The session scratchpad (_output/tmp/session-notes.md) is a living working memory document that is read and rewritten across sessions. They serve fundamentally different purposes: the briefs log answers "what happened," while the session scratchpad answers "what do I need to remember right now." Writing working notes into the briefs log or treating the scratchpad as a permanent record both lead to confusion.
