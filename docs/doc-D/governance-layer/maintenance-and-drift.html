Maintenance and Drift

SEJA treats maintenance as a first-class concern rather than an afterthought. Freshness policies define how long artifacts can go without review, periodic triggers automate the scheduling of maintenance tasks, the /explain drift workflow detects and resolves discrepancies between design intent and implementation, and the upgrade flow keeps the harness current across releases. Together these mechanisms prevent the slow accumulation of staleness that erodes design-intent fidelity over time.

Freshness Policies

SEJA defines staleness thresholds for recurring maintenance activities and pending-action governance. These values are configured in the Periodic Triggers table in product-design/conventions.md and consumed by the scripts that enforce them.

Periodic Activity Intervals

Activity Interval Action Type What Happens
Periodic curation 30 days periodic-curation Review product-design-as-intended.md for items ready to promote from implemented to established.
Spec-drift check 14 days spec-drift-check Run /explain drift to surface drift between design intent and as-coded state.
Git freshness check 7 days check-git-freshness Compare local branches in the workspace and codebase repositories to their upstreams; surface ahead/behind counts. Never pulls automatically.

Pending-Action Thresholds

Threshold Value Effect
Pending plan age escalation 30 days An open implement pending entry is surfaced with the overdue banner during pre-skill.
Pending age escalation 14 days Any pending action older than 14 days is flagged as overdue in pre-skill notices.
Verify-as-coded file threshold 5 files When a plan implementation touches 5 or more files, post-skill auto-creates a verify-as-coded pending action so the as-coded state can be reconciled.
Pending auto-dismiss 90 days Unaddressed pending actions are auto-dismissed by pending.py cleanup after 90 days. The dismissal is recorded with the reason auto-dismissed: aged out.

Periodic Triggers

Periodic triggers are the mechanism that converts freshness policies into concrete pending actions. They run automatically during pre-skill and are throttled by stamp files to avoid redundant work.

How the Trigger Pipeline Works

Every skill invocation begins with pre-skill, which includes a pending-check stage. This stage calls pending.py status, which conditionally runs two maintenance sub-tasks before assembling its output:

  1. Cleanup (24-hour throttle): runs pending.py cleanup to auto-dismiss pending actions that have exceeded the 90-day threshold and to dismiss orphaned implement entries whose source plan file has been deleted or already marked as done. The throttle is tracked by the stamp file _output/.pending-cleanup-stamp.
  2. Periodic check (1-hour throttle): runs pending.py periodic-check, which reads the Periodic Triggers table from product-design/conventions.md, computes how many intervals have elapsed since the last pending action of each trigger type, and creates new pending actions for any that are due. The throttle is tracked by the stamp file _output/.pending-periodic-stamp.

Both sub-tasks are wrapped in broad exception handling so that a failure in either one never blocks the pre-skill pipeline. If a sub-task fails, a warning line is appended to the pre-skill status output instead of crashing the skill invocation.

Pre-Skill Pending Notices

After cleanup and periodic check complete, the pending-check stage formats a notice banner that includes:

  • A publish banner for any PUBLISH:-prefixed pending actions (these have a shorter 3-day overdue window).
  • An implement banner showing up to 5 open plan-implementation items, with age in days.
  • A general pending notice listing the count of remaining open actions. When the count is zero, this line is suppressed.

The banner is purely informational -- it never blocks the skill invocation. Its purpose is to keep the designer aware of accumulating maintenance debt so it can be addressed at a natural pause point.

Git Freshness Check

The git freshness check is implemented by check_git_freshness.py, located in the .claude/skills/critique/ directory. It can be invoked directly via /critique freshness or triggered as a periodic action.

The script resolves which repositories to check by reading the harness root and CODEBASE_DIR from conventions.md. When the codebase directory is an absolute path distinct from the workspace root, both are checked. For each repository, the script:

  1. Identifies the current branch and its upstream tracking ref.
  2. Fetches from the upstream remote (with a configurable timeout, default 5 seconds).
  3. Computes ahead/behind counts using git rev-list --count.
  4. Reports the result with a suggested action: git pull --ff-only when behind, check divergence when both ahead and behind, or mark as up-to-date.

The script never pulls changes automatically. It exits 0 in all cases to avoid disrupting the caller. It also skips harness-dev repositories (detected by the presence of seja-public, tools/sync_to_public.py, or .claude/skills/scripts/priv markers).

Worktree Health Check

check_worktree_health.py detects orphaned git worktrees left behind by parallel wave execution. It runs git worktree list --porcelain and flags any worktrees beyond the main working tree. Orphaned worktrees can lock files on Windows and waste disk space. The script is invoked by /critique health and suggests removal via git worktree remove <path> && git worktree prune.

The /explain drift Workflow

Spec drift occurs when the as-coded state diverges from the as-intended design -- features get added without updating the design files, or design intent evolves without corresponding implementation. The /explain drift workflow detects these discrepancies and provides structured paths to resolve them.

Running a Drift Analysis

Invoke /explain drift with an optional scope argument:

  • all (default) -- scan both conceptual design and metacommunication.
  • conceptual-design -- scan only the conceptual design sections (entities, permissions, UX patterns, business rules).
  • metacomm -- scan only the metacommunication sections (feature intentions, implementation status, designer intent).
  • --scope since-plan plan-NNNNNN -- narrow the scan to registry rows touched by a specific plan, comparing only the as-intended and as-coded files referenced by that plan's Files section.

The drift analysis reads the As-Intended / As-Coded Registry from product-design/conventions.md and compares each registered pair file by file, section by section. For conceptual design, it compares entities, permissions, UX patterns, and business rules. For metacommunication, it compares feature intentions, implementation status markers, and stated designer intent. Each difference is classified as Added (present in as-intended but not as-coded), Removed (present in as-coded but not as-intended), or Modified (in both but different).

The analysis also scans for pending promotions: items marked STATUS: implemented in registered Human (markers) files that have not yet been promoted to established. These are listed in the Pending Promotions section of the drift report.

Sync and Promote Sub-Modes

After the drift report is presented, the designer chooses a sync direction:

  1. Conceptual-design to metacomm -- for each entity, feature, or UX pattern in the as-intended file lacking a metacommunication entry, draft a metacommunication intention and present it for confirmation.
  2. Metacomm to conceptual-design -- for each metacommunication intention implying entities, permissions, or UX patterns not present in the conceptual design, propose additions.
  3. Bidirectional -- run both directions sequentially, presenting all gaps and conflicts together for human resolution.
  4. Promote implemented items -- enter the Phase 3a promote workflow (see below).
  5. No -- skip sync entirely.

Conflict detection is built in: when the two files disagree, both sides are presented and the designer resolves. The workflow never auto-resolves conflicts.

Phase 3a: Decision Entry Proposal Generation

Invoked via /explain drift --promote. This phase reads registered Human (markers) files for STATUS: implemented markers lacking an ESTABLISHED: stamp, groups candidates by plan ID, and for each candidate drafts a DDR-shaped Decision entry (following the template in template/docs/ddr.md). Each entry gets a stable D-NNN ID assigned by scanning existing Decision entries in product-design-as-intended.md.

The proposals are written to _output/promote-proposals/promote-proposal-plan-<id>.md as designer-owned drafts. The designer reviews, rewrites the prose to their voice, and copies the entries into the Decisions section of product-design-as-intended.md. A pending action of type apply-promote-markers is filed to track the follow-up (with deduplication: if one already exists for the same plan, no duplicate is created).

Phase 3b: STATUS Marker Flip

Invoked via /explain drift --promote --apply-markers plan-NNNNNN. This phase verifies that the designer has copied the D-NNN entries into the as-intended file by performing a heading-only grep (^###\s+D-NNN(?::|\s*$)) -- it intentionally does not match title text or body prose, preserving the designer's voice.

For each verified entry, the designer is asked to confirm the STATUS flip. Confirmed items are processed by apply_marker.py: 

python .claude/skills/scripts/apply_marker.py \
  --file product-design/product-design-as-intended.md \
  --id D-<NNN> \
  --marker STATUS \
  --value established \
  --plan plan-<id> \
  --date <today>

Post-skill's check_human_markers_only.py and check_changelog_append_only.py verify that marker flips do not bleed prose into Human (markers) files. The apply-promote-markers pending action is closed when all proposed entries have been verified and flipped; otherwise it remains open with a message enumerating which entries are still missing or were declined.

Upgrade and Migration

The /seja-setup --upgrade command refreshes harness files from a newer SEJA release while preserving all project-specific configuration and output. It is the recommended way to keep a project's harness current without losing design history.

What Gets Upgraded

Category Files Action
Skills .claude/skills/*/SKILL.md Auto-updated
General references .claude/references/general/*.md Auto-updated
Templates .claude/references/template/** Auto-updated
Harness metadata .claude/CHANGELOG.md, VERSION, CHEATSHEET.md Auto-updated
Scripts .claude/skills/scripts/*.py Auto-updated
Agents .claude/agents/*.md Show diff, ask per file (may have local tweaks)

What Is Preserved

Category Files Why
Rules .claude/rules/*.md Project-specific conventions; show diff for manual merge
Project definitions product-design/** Never overwritten -- this is the project's design history
Settings .claude/settings.json, settings.local.json User-configured permissions and preferences
Output _output/ Plans, research logs, briefs, and all generated artifacts
Project README CLAUDE.md Contains project-specific build commands and architecture notes

How It Works

  1. Resolve target version: the upgrade flow resolves the target release tag (latest SemVer tag on the public seja repository, or an explicit --version <tag>). If the resolved tag matches the current .seja-version, the upgrade exits with "Harness already up to date."
  2. Locate source: if no local path is provided, a shallow clone of the public repository at the target tag is created in a temporary directory.
  3. Run the upgrade script: upgrade_harness.py copies auto-update files, reports diffs for manual-merge files, and updates .seja-version. Use --dry-run to preview changes without applying them.
  4. Review and follow up: the upgrade summary highlights the version change, files auto-updated, and files needing manual merge. Post-upgrade offers include adding new convention variables, updating stale path references, and regenerating CLAUDE.md.

Upgrade never re-runs the Section 1 scaffolding questionnaire. Projects with unresolved {{VAR}} placeholders in conventions.md (from pre-scaffolding era) retain them through the upgrade; run /design update stack afterwards to fill them and regenerate downstream artifacts.

Common Mistakes

Ignoring spec-drift warnings
The 14-day spec-drift check creates a pending action reminding you to run /explain drift. Ignoring it allows the gap between design intent and implementation to widen silently. Small drift is easy to reconcile; large drift requires painful forensics. Address drift reports promptly -- even if the resolution is "the as-intended file needs updating," that is a valid outcome worth recording.
Hand-fixing drift instead of using the promote workflow
When you see STATUS: implemented items awaiting promotion, it is tempting to manually edit product-design-as-intended.md to flip the markers and write the Decision entries yourself. This bypasses the governance pipeline: apply_marker.py validates transition rules, check_human_markers_only.py verifies that only marker content was changed, and check_changelog_append_only.py ensures the CHANGELOG was not corrupted. Use /explain drift --promote (Phase 3a) to generate the proposal, review and copy the entries, then run Phase 3b to flip markers through the validated path.
Letting pending actions accumulate past 90 days
Pending actions older than 90 days are auto-dismissed by pending.py cleanup with the reason auto-dismissed: aged out. If the underlying work was still needed, the auto-dismissal silently drops it from the active ledger. Review pending items regularly -- either address them, snooze them with an explicit date (/pending snooze <id> --until YYYY-MM-DD), or dismiss them with a reason before the 90-day window closes.
Upgrading without reading the CHANGELOG
/seja-setup --upgrade auto-updates skills, scripts, references, and templates. If a release introduces breaking changes -- new convention variables, renamed scripts, altered skill behavior -- the upgrade succeeds but downstream workflows may behave unexpectedly. Always read .claude/CHANGELOG.md for the target version before upgrading. The upgrade summary highlights new files and diffs, but the CHANGELOG provides the rationale and migration guidance that diffs alone cannot convey.
