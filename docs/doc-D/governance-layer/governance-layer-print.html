Output Artifacts

Every skill invocation in SEJA produces artifacts -- plan files, research logs, critique reports, reflections, and more. All of these land in the output directory (_output/), which serves as the single root for generated content. This chapter catalogs the output subdirectories, documents the key files that provide observability and traceability, explains how artifacts move through their lifecycle, and flags common mistakes that can break the governance model.

The Output Directory

The output directory (_output/) is defined by the OUTPUT_DIR variable in the project's conventions.md. Every subdirectory within it is owned by a specific skill or set of skills, and each follows a consistent naming pattern that embeds the brief number for traceability.

Artifact Lifecycle

SEJA artifacts are not static files -- they move through a predictable lifecycle driven by the skill execution pipeline. Understanding this lifecycle clarifies why certain files exist, how they relate to each other, and what happens when a skill completes.

Creation

Artifacts are created by skill execution. When a user invokes a skill (e.g., /plan, /research, /reflect), the skill writes its output to the appropriate subdirectory under _output/. The file name embeds the brief number assigned by pre-skill, which links the artifact back to its entry in the briefs log.

Commit and Registration

After the skill completes, post-skill commits the new artifact to version control and registers it in _output/INDEX.md. The INDEX entry records the artifact's type, brief number, file path, and a one-line summary. This ensures that every artifact is discoverable through a single index, regardless of which subdirectory it landed in.

The Briefs Log as Chronological Record

The briefs log (_output/briefs.md) is the chronological backbone of the output directory. Each brief entry records what skill ran, the parameters it received, the artifacts it produced, and the outcome. Because briefs are append-only and sequentially numbered, they provide a total ordering of all harness activity. The lightweight briefs index (_output/briefs-index.md) provides fast lookups into this log without requiring the agent to read the entire file.

The Conversation Trace as Inter-Skill Record

Between skill invocations, the conversation trace (_output/conversation-trace.jsonl) records every user-agent exchange. Each entry carries a session ID, an event ID, and a preceding-event-ID that chains entries into a directed sequence. This trace fills the gap that the briefs log leaves: while briefs capture skill executions, the conversation trace captures the discussions, decisions, and context that happen between skills.

The Session Scratchpad for Cross-Session Persistence

The session notes file (_output/tmp/session-notes.md) serves as working memory that persists across Claude Code sessions. Unlike the briefs log (which is a historical record) or the conversation trace (which is an audit trail), the session scratchpad is a living document that the agent reads at session start and updates as needed. It carries forward context, open questions, and in-progress state that would otherwise be lost when a session ends.

Common Mistakes

Hand-editing generated artifacts
Constitution tenet T3 states that generated artifacts (plans, research logs, reflections, as-coded files) are agent-maintained and must never be hand-edited by the designer. Agents write them via post-skill or designated skill steps only. Hand-editing creates divergence between the artifact's content and the machine-readable record (briefs, INDEX, decision digest), which can cause validation scripts to report false drift.
Deleting _output/ files without understanding dependencies
Artifacts in _output/ are cross-referenced by the briefs log, the artifact index, the decision digest, and sometimes by other artifacts (e.g., a roadmap references its constituent plans). Deleting an artifact without updating these references leaves dangling pointers that confuse both the agent and validation checks. If cleanup is needed, use /pending to manage lifecycle transitions rather than manual deletion.
Confusing briefs.md with the session scratchpad
The briefs log (_output/briefs.md) is an append-only historical record of skill executions -- it is never edited or truncated. The session scratchpad (_output/tmp/session-notes.md) is a living working memory document that is read and rewritten across sessions. They serve fundamentally different purposes: the briefs log answers "what happened," while the session scratchpad answers "what do I need to remember right now." Writing working notes into the briefs log or treating the scratchpad as a permanent record both lead to confusion.

Enforcement Architecture

SEJA enforces its governance model through a layered defense: advisory checks that guide the agent during skill execution, blocking gates that prevent bad commits from landing, and a comprehensive validation orchestrator for CI pipelines. Each layer catches a different category of issue. Together they ensure that design intent, privacy boundaries, and authorship rules are maintained without relying on any single checkpoint.

Multi-Layer Enforcement

Enforcement in SEJA operates at three layers, ordered from earliest (in-session) to latest (CI pipeline). Each layer is designed so that it catches issues that escaped the layer before it, and so that the most disruptive failures are caught at the cheapest point -- inside the skill session -- rather than after a commit has already landed.

Layer 1: Post-Skill Advisory

After every skill execution, the post-skill lifecycle hook (.claude/skills/post-skill/SKILL.md) runs a 13-step pipeline. Several of these steps perform enforcement-relevant checks:

  • Step 2e -- DONE marker proposal: the agent proposes STATUS markers for as-intended items that appear to have been implemented. The human confirms, defers, or skips via AskUserQuestion.
  • Step 5 -- Git-state safety check: detects rebase-in-progress, unmerged conflicts, or detached HEAD and blocks the commit with a warning.
  • Step 6 -- Commit scope verification: verify_commit_scope.py compares staged files against the expected set for the skill and artifact type. Unexpected files trigger a warning.
  • Step 6b -- Fast preflight gate: run_preflight_fast.py runs the curated subset of fast validation scripts (see Layer 2 below). At this stage the gate is advisory -- it warns but does not block, because post-skill runs after lengthy work and the pre-commit hook provides the hard gate.
  • Step 6c -- Human markers verifier: check_human_markers_only.py --staged rejects any prose mutations in Human (markers) files. Violations prompt an AskUserQuestion recommending abort.

Advisory-layer checks surface problems early and give the agent and designer the opportunity to correct them before any commit is attempted. They do not block execution -- a designer can choose to proceed -- but they ensure awareness.

Layer 2: Pre-Commit Blocking

The pre-commit hook (.githooks/pre-commit) is the hard gate. It runs automatically on every git commit and blocks the commit on failure. The hook executes two scripts in sequence:

  1. run_preflight_fast.py -- runs a curated set of fast validation checks designed to complete in under 10 seconds. These include convention consistency, retired-token detection, skill-system integrity, secrets scanning, skill-spec compliance, version-changelog sync, design-output validation, plan coverage (blocking mode), human-markers enforcement, changelog append-only verification, section-boundary write enforcement, harness reference coverage, docs frontmatter validation, mantra-banner consistency, and (in seja-priv) the private-leak, call-graph, and harness-reference freshness checks.
  2. check_no_private_leaks.py --staged -- scans staged .md files for private content that would leak to seja-public on the next sync. This is the pre-sync leak gate (see the Leak Prevention section below).

To install the pre-commit hook, run bash .githooks/install.sh once per clone. The install script sets core.hooksPath to .githooks/. The hook can be bypassed with git commit --no-verify, but constitution S2 prohibits this without explicit designer approval recorded in a D-NNN decision entry.

Layer 3: CI Coverage

run_all_checks.py is the CI-independent validation orchestrator. It discovers and runs every check_*.py script in the .claude/skills/scripts/ directory and its co-located skill subdirectories. Unlike run_preflight_fast.py (which runs a curated subset optimized for speed), run_all_checks.py provides full coverage including checks that are too slow or too broad for the pre-commit hook -- such as lifecycle-fact-uniqueness, which performs O(N^2) comparisons and can produce false positives during transitional doc states.

Key features of the CI orchestrator:

  • Automatic discovery: finds all check_*.py scripts without a manual registry.
  • Stack filtering: --filter flask or --filter react limits execution to checks matching the project's stack (via check_plugin_registry.json).
  • JUnit XML output: --junit results.xml produces a report consumable by CI platforms.
  • Unified exit codes: 0 (all pass), 1 (one or more failures), 2 (orchestrator error).

Why Three Layers

Each layer catches a different category of problem at a different cost point:

Layer When it runs Blocking? What it catches
Post-skill advisory End of every skill session No (warns, recommends) Scope contamination, unauthorized prose edits, missing markers, git-state anomalies
Pre-commit blocking Every git commit Yes (blocks commit) Convention drift, secrets, stale manifests, private-content leaks, human-marker violations
CI coverage CI pipeline or on-demand Yes (fails the build) Full validation suite including slow/broad checks excluded from the pre-commit hot path

A problem detected at Layer 1 costs seconds to fix. The same problem detected at Layer 3 costs a CI round-trip. The layered model ensures that most issues never reach Layer 3.

Human (markers) Classification

The File Maintainer Classification (defined in .claude/references/general/shared-definitions.md) assigns one of four values to every reference file: Human, Human (markers), Agent, and Human / Agent. Files classified as Human (markers) are governed by constitution T2: the prose in these files belongs exclusively to the human designer, and agents may write only fixed-format lifecycle markers via apply_marker.py -- never direct prose.

What Agents May Write

The allowed marker types are defined in human_markers_registry.py and enforced by check_human_markers_only.py:

  • STATUS: lifecycle state tracking (proposed, implemented, established, superseded, or legacy uppercase IMPLEMENTED).
  • ESTABLISHED: legacy promotion stamp, retained for migration.
  • INCORPORATED: records absorption of research findings into design.
  • CHANGELOG_APPEND: timestamped changelog entries with HTML-injection prevention.
  • DECISION_APPEND: new DDR-shaped ### D-NNN: decision entries appended to the Decisions section.
  • REQ_TRACED_BY: annotates existing <!-- REQ-TYPE-NNN --> markers with a traced-by pseudo-plan.

Every marker write must pass through apply_marker.py after explicit AskUserQuestion confirmation in the same turn. The check_human_markers_only.py verifier parses the staged git diff, filters to files in the registry, and rejects any added or removed non-blank line that does not match an allowed marker regex. Violations block the commit during post-skill step 6c and during the pre-commit hook via run_preflight_fast.py.

Registered Human (markers) Files

The following files are registered in human_markers_registry.py:

  • .claude/skills/scripts/tests/fixtures/marker_fixture.md (test fixture)
  • .claude/references/template/ux-research-results.md
  • product-design/ux-research-results.md
  • .claude/references/template/product-design-as-intended.md
  • product-design/product-design-as-intended.md

Both the template and project paths are registered for each real file. The template path is what /design seeds (and what harness-level tests touch); the project path is what designer commits exercise via post-skill step 2e. For a detailed treatment of the marker system itself -- types, formats, state transitions, and the promote workflow -- see Vol. 2 Ch. 4: The Marker System.

Leak Prevention

check_no_private_leaks.py (.claude/skills/scripts/priv/check_no_private_leaks.py) enforces the boundary between private (seja-priv) and public (seja-public) content. Constitution S1 codifies this invariant: private content -- design files, research logs, plans, product-design files, and the constitution itself -- must never reach seja-public without explicit opt-in. Accidental exposure is irreversible once cached by search engines or CI logs.

What the Script Prevents

The script operates in three modes, each targeting a different stage of the content lifecycle:

Pre-commit gate (--staged)
Scans staged .md files in seja-priv before they are committed. For each file, it applies the same strip-private-sections transform as sync_to_public.py (removing content between <!-- priv-only-start --> and <!-- priv-only-end --> markers), then checks the stripped output for residual priv-only markers (indicating malformed or unbalanced marker pairs) and private-content fingerprints that survived the strip. Files under product-design/, _output/, .claude/skills/scripts/priv/, and seja-public/ are excluded from staged-file scanning because they are private by convention.
Candidate scan (--candidate DIR)
Performs a full leak scan of a candidate publish directory. Used by pre_publish_smoke.py to validate a publish workspace before release. Checks for priv-only markers, private files (e.g., generate_changelog_data.py), private directories (priv/, project/), private patterns, and SKILL.md content fingerprints.
Default mode (no arguments)
Scans authored prose in seja-public/ (top-level *.md and docs/**/*.md) for residual priv-only markers. Also warns if seja-public/.claude/ exists on disk (it should have been cleaned up after the last publish).

Content Fingerprints

Beyond marker stripping, the script maintains a list of content fingerprints -- patterns like --harness, seja-priv, sync_to_public, scripts/priv, and pre_publish_smoke -- that are inherently private terminology. These fingerprints are checked only in SKILL.md files (other files may legitimately reference these terms). Matches inside fenced code blocks are ignored.

Where It Runs

  • Pre-commit hook: the .githooks/pre-commit script runs check_no_private_leaks.py --staged as its second gate (after run_preflight_fast.py). A failure blocks the commit.
  • Preflight fast checks: run_preflight_fast.py includes the no-private-leaks check in its curated set (priv-only; silently omitted in public repos where the priv/ directory is absent).
  • Publish pipeline: pre_publish_smoke.py calls check_no_private_leaks.py --candidate to validate the workspace before tagging a release.

Anti-patterns

The following practices undermine SEJA's enforcement guarantees. Each pattern describes what goes wrong and what to do instead.

Bypassing the lifecycle

Running code changes without first creating a plan via /plan. Without a plan, there is no artifact trail, no commit-scope verification, no coverage check, and no post-skill alignment. The enforcement layers assume a plan exists; skipping it disables most of their value.

Instead: always start with /plan (or /plan --light for small changes). The plan is the anchor that connects design intent to implementation to verification.

Hand-editing Human (markers) files

Directly editing the prose or markers in files classified as Human (markers) -- such as product-design-as-intended.md or ux-research-results.md -- outside of apply_marker.py. The check_human_markers_only.py verifier will reject the diff, and the commit will be blocked at the pre-commit hook.

Instead: use apply_marker.py for all marker writes, and edit prose content as the human designer (not through the agent). The agent proposes marker changes via AskUserQuestion and routes confirmed changes through the designated script.

Skipping pre-commit hooks

Using git commit --no-verify to bypass the pre-commit hook chain. Constitution S2 explicitly prohibits this without designer approval recorded in a D-NNN decision entry. The hook is the last automated gate before private content, convention violations, or stale manifests land in the repository.

Instead: fix the failing check. If a legitimate exception is needed, document it in a D-NNN decision record first, then bypass with full traceability.

Mixing private content into public docs

Allowing seja-priv content -- design rationale, internal research, decision records, product-design files -- to reach seja-public. Constitution S1 codifies the invariant: private content must never cross the boundary without explicit opt-in. The leak is irreversible once cached by search engines or CI pipelines.

Instead: wrap private content in <!-- priv-only-start --> / <!-- priv-only-end --> markers so the sync tool strips it automatically. The pre-commit hook and publish pipeline both verify that no private fingerprints survive the strip.

Circumventing constitution principles without D-NNN decision records

Overriding or ignoring a constitution-level constraint (T1-T4, Q1-Q3, S1-S2, C1-C2) without creating a formal decision entry. The constitution is loaded into every agent context via pre-skill and takes precedence over all other guidance. Silent violations erode the governance model because they leave no audit trail.

Instead: if a constitution principle genuinely needs to be amended or temporarily overridden, create a D-NNN decision entry documenting the context, the decision, and the consequences. The entry provides traceability and ensures the override is deliberate.

Scripts and Automation

The SEJA harness automates its governance, validation, and artifact management through a suite of Python scripts distributed across several directories. This chapter provides a per-script reference grouped by functional category, followed by how-to guidance on using the validation orchestrator and extending it with new checks.

Scripts live in four locations: .claude/skills/scripts/ (shared utilities), co-located skill subdirectories such as .claude/skills/critique/, .claude/skills/design/, .claude/skills/explain/, and .claude/skills/post-skill/ (skill-owned scripts next to their SKILL.md), .claude/skills/scripts/priv/ (private-only scripts excluded from public releases), and tools/ (release pipeline utilities). The validation orchestrator run_all_checks.py discovers scripts across all of these locations automatically.

Using run_all_checks.py

run_all_checks.py is the CI-independent validation orchestrator. It discovers every check_*.py script in .claude/skills/scripts/ and in co-located skill subdirectories (such as critique/, design/, explain/, and post-skill/), runs each one sequentially, and rolls the results into a single pass/fail verdict.

Running the full suite

python .claude/skills/scripts/run_all_checks.py --root .

The --root flag tells the orchestrator where the repository root is. Each check script is executed as a subprocess with a 120-second timeout.

Reading the output

As each check runs, the orchestrator prints its name followed by PASS, FAIL, or ERROR. After all checks complete, a summary table is printed: 

SEJA Validation Orchestrator -- Results
----------------------------------------------
Script                              Status  Duration
----------------------------------------------
check_conventions.py                PASS      0.42s
check_design_output.py              FAIL      1.23s
check_skill_system.py               PASS      0.87s
----------------------------------------------
2 passed, 1 failed, 3.52s total

For failed or errored checks, the script's stdout and stderr are printed indented below the status line in non-verbose mode. In --verbose mode, child output streams directly to the console as it runs.

JUnit XML output

python .claude/skills/scripts/run_all_checks.py --root . --junit results.xml

The --junit flag writes a standard JUnit XML report. Each check becomes a <testcase> in a seja-checks testsuite. Failures include the check's combined stdout/stderr as the failure message text. This format integrates with CI platforms that parse JUnit XML (GitHub Actions, Jenkins, GitLab CI).

Filtering by stack

python .claude/skills/scripts/run_all_checks.py --root . --filter flask

When check_plugin_registry.json exists in the scripts directory, the --filter flag restricts execution to checks whose registry entry matches the given stack keyword. Checks marked with "any" in their stack always run. Checks not in the registry also run by default.

Exit codes

0
All checks passed.
1
One or more checks failed (validation violations found).
2
Orchestrator error (no scripts found, script directory missing) or one or more checks encountered a runtime error.

When to use which orchestrator

Use run_preflight_fast.py for git hooks and quick local validation -- it runs a curated subset of fast checks and completes in under 10 seconds. Use run_all_checks.py for CI pipelines and thorough validation sweeps -- it discovers and runs every check script, with JUnit XML support for CI integration.

Extending the Validation Suite

To add a new validation check that integrates with run_all_checks.py, follow these conventions:

  1. Name the script check_<what>.py. The orchestrator discovers scripts by globbing for check_*.py in .claude/skills/scripts/ and in co-located skill subdirectories. Any file matching this pattern is automatically included.
  2. Exit 0 for pass, 1 for failure. The orchestrator interprets any non-zero exit code as a failure. Use exit code 2 for script errors (missing dependencies, invalid arguments) to distinguish them from validation findings.
  3. Print findings to stdout. When violations are found, print human-readable diagnostics to stdout. The orchestrator captures this output and includes it in the JUnit XML report for failed checks. Print errors and warnings to stderr.
  4. Accept --root or auto-detect. Import project_config.py for repository root detection: 
    from project_config import REPO_ROOT
    This ensures the script works regardless of the current working directory.
  5. Keep execution fast. The orchestrator enforces a 120-second timeout per script. If your check should run in the fast preflight gate (under 10 seconds total for all fast checks), add it to the FAST_CHECKS list in run_preflight_fast.py.
  6. Optionally register in check_plugin_registry.json. If your check is stack-specific (e.g., only relevant for Flask or React projects), add an entry with the script name and stack metadata so the --filter flag can include or exclude it.

A minimal check script looks like this: 

#!/usr/bin/env python3
"""check_example.py -- Validate example constraint.

Invocation: agent-invoked
Lifecycle: active

Exit codes: 0 = pass, 1 = violations found, 2 = script error.
"""
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent))
from project_config import REPO_ROOT

def main() -> int:
    violations = []
    # ... scan for violations ...
    for v in violations:
        print(v)
    return 1 if violations else 0

if __name__ == "__main__":
    sys.exit(main())

Common Mistakes

Running individual check scripts instead of run_all_checks.py
Individual scripts report their own findings but produce no aggregated summary, no JUnit XML, and no unified exit code. The orchestrator provides a single pass/fail verdict, a summary table with per-check durations, and optional CI-compatible XML output. Always use run_all_checks.py for comprehensive validation and run_preflight_fast.py for quick pre-commit checks.
Ignoring exit codes
Every check and orchestrator script communicates its verdict through its exit code. A script that prints warnings but exits 0 is considered passing. Piping output to grep or visually scanning for keywords is unreliable -- check $? or the process return code. CI pipelines should fail the build on non-zero exit from run_all_checks.py.
Not updating run_all_checks.py when adding new check scripts
run_all_checks.py discovers check_*.py scripts automatically via glob, so new scripts in the standard locations are included without changes. However, if you want your script in the fast preflight gate, you must manually add it to the FAST_CHECKS list in run_preflight_fast.py. Forgetting this means the check runs in full CI sweeps but not in git hooks.
Editing generated files that scripts will overwrite
Files produced by generation scripts -- such as _output/INDEX.md, .claude/CHEATSHEET.md, skill-graph.json, and decision-digest.jsonl -- are regenerated automatically. Manual edits to these files will be silently overwritten on the next generation run. Edit the source data instead.
Modifying Human (markers) files directly
Human (markers) files must be modified exclusively through apply_marker.py. Direct edits bypass the marker-type validation and will be rejected by check_human_markers_only.py in the preflight gate. Use the appropriate --marker type flag to apply the desired change.

Maintenance and Drift

SEJA treats maintenance as a first-class concern rather than an afterthought. Freshness policies define how long artifacts can go without review, periodic triggers automate the scheduling of maintenance tasks, the /explain drift workflow detects and resolves discrepancies between design intent and implementation, and the upgrade flow keeps the harness current across releases. Together these mechanisms prevent the slow accumulation of staleness that erodes design-intent fidelity over time.

Freshness Policies

SEJA defines staleness thresholds for recurring maintenance activities and pending-action governance. These values are configured in the Periodic Triggers table in product-design/conventions.md and consumed by the scripts that enforce them.

Periodic Activity Intervals

Activity Interval Action Type What Happens
Periodic curation 30 days periodic-curation Review product-design-as-intended.md for items ready to promote from implemented to established.
Spec-drift check 14 days spec-drift-check Run /explain drift to surface drift between design intent and as-coded state.
Git freshness check 7 days check-git-freshness Compare local branches in the workspace and codebase repositories to their upstreams; surface ahead/behind counts. Never pulls automatically.

Pending-Action Thresholds

Threshold Value Effect
Pending plan age escalation 30 days An open implement pending entry is surfaced with the overdue banner during pre-skill.
Pending age escalation 14 days Any pending action older than 14 days is flagged as overdue in pre-skill notices.
Verify-as-coded file threshold 5 files When a plan implementation touches 5 or more files, post-skill auto-creates a verify-as-coded pending action so the as-coded state can be reconciled.
Pending auto-dismiss 90 days Unaddressed pending actions are auto-dismissed by pending.py cleanup after 90 days. The dismissal is recorded with the reason auto-dismissed: aged out.

Periodic Triggers

Periodic triggers are the mechanism that converts freshness policies into concrete pending actions. They run automatically during pre-skill and are throttled by stamp files to avoid redundant work.

How the Trigger Pipeline Works

Every skill invocation begins with pre-skill, which includes a pending-check stage. This stage calls pending.py status, which conditionally runs two maintenance sub-tasks before assembling its output:

  1. Cleanup (24-hour throttle): runs pending.py cleanup to auto-dismiss pending actions that have exceeded the 90-day threshold and to dismiss orphaned implement entries whose source plan file has been deleted or already marked as done. The throttle is tracked by the stamp file _output/.pending-cleanup-stamp.
  2. Periodic check (1-hour throttle): runs pending.py periodic-check, which reads the Periodic Triggers table from product-design/conventions.md, computes how many intervals have elapsed since the last pending action of each trigger type, and creates new pending actions for any that are due. The throttle is tracked by the stamp file _output/.pending-periodic-stamp.

Both sub-tasks are wrapped in broad exception handling so that a failure in either one never blocks the pre-skill pipeline. If a sub-task fails, a warning line is appended to the pre-skill status output instead of crashing the skill invocation.

Pre-Skill Pending Notices

After cleanup and periodic check complete, the pending-check stage formats a notice banner that includes:

  • A publish banner for any PUBLISH:-prefixed pending actions (these have a shorter 3-day overdue window).
  • An implement banner showing up to 5 open plan-implementation items, with age in days.
  • A general pending notice listing the count of remaining open actions. When the count is zero, this line is suppressed.

The banner is purely informational -- it never blocks the skill invocation. Its purpose is to keep the designer aware of accumulating maintenance debt so it can be addressed at a natural pause point.

Git Freshness Check

The git freshness check is implemented by check_git_freshness.py, located in the .claude/skills/critique/ directory. It can be invoked directly via /critique freshness or triggered as a periodic action.

The script resolves which repositories to check by reading the harness root and CODEBASE_DIR from conventions.md. When the codebase directory is an absolute path distinct from the workspace root, both are checked. For each repository, the script:

  1. Identifies the current branch and its upstream tracking ref.
  2. Fetches from the upstream remote (with a configurable timeout, default 5 seconds).
  3. Computes ahead/behind counts using git rev-list --count.
  4. Reports the result with a suggested action: git pull --ff-only when behind, check divergence when both ahead and behind, or mark as up-to-date.

The script never pulls changes automatically. It exits 0 in all cases to avoid disrupting the caller. It also skips harness-dev repositories (detected by the presence of seja-public, tools/sync_to_public.py, or .claude/skills/scripts/priv markers).

Worktree Health Check

check_worktree_health.py detects orphaned git worktrees left behind by parallel wave execution. It runs git worktree list --porcelain and flags any worktrees beyond the main working tree. Orphaned worktrees can lock files on Windows and waste disk space. The script is invoked by /critique health and suggests removal via git worktree remove <path> && git worktree prune.

The /explain drift Workflow

Spec drift occurs when the as-coded state diverges from the as-intended design -- features get added without updating the design files, or design intent evolves without corresponding implementation. The /explain drift workflow detects these discrepancies and provides structured paths to resolve them.

Running a Drift Analysis

Invoke /explain drift with an optional scope argument:

  • all (default) -- scan both conceptual design and metacommunication.
  • conceptual-design -- scan only the conceptual design sections (entities, permissions, UX patterns, business rules).
  • metacomm -- scan only the metacommunication sections (feature intentions, implementation status, designer intent).
  • --scope since-plan plan-NNNNNN -- narrow the scan to registry rows touched by a specific plan, comparing only the as-intended and as-coded files referenced by that plan's Files section.

The drift analysis reads the As-Intended / As-Coded Registry from product-design/conventions.md and compares each registered pair file by file, section by section. For conceptual design, it compares entities, permissions, UX patterns, and business rules. For metacommunication, it compares feature intentions, implementation status markers, and stated designer intent. Each difference is classified as Added (present in as-intended but not as-coded), Removed (present in as-coded but not as-intended), or Modified (in both but different).

The analysis also scans for pending promotions: items marked STATUS: implemented in registered Human (markers) files that have not yet been promoted to established. These are listed in the Pending Promotions section of the drift report.

Sync and Promote Sub-Modes

After the drift report is presented, the designer chooses a sync direction:

  1. Conceptual-design to metacomm -- for each entity, feature, or UX pattern in the as-intended file lacking a metacommunication entry, draft a metacommunication intention and present it for confirmation.
  2. Metacomm to conceptual-design -- for each metacommunication intention implying entities, permissions, or UX patterns not present in the conceptual design, propose additions.
  3. Bidirectional -- run both directions sequentially, presenting all gaps and conflicts together for human resolution.
  4. Promote implemented items -- enter the Phase 3a promote workflow (see below).
  5. No -- skip sync entirely.

Conflict detection is built in: when the two files disagree, both sides are presented and the designer resolves. The workflow never auto-resolves conflicts.

Phase 3a: Decision Entry Proposal Generation

Invoked via /explain drift --promote. This phase reads registered Human (markers) files for STATUS: implemented markers lacking an ESTABLISHED: stamp, groups candidates by plan ID, and for each candidate drafts a DDR-shaped Decision entry (following the template in template/docs/ddr.md). Each entry gets a stable D-NNN ID assigned by scanning existing Decision entries in product-design-as-intended.md.

The proposals are written to _output/promote-proposals/promote-proposal-plan-<id>.md as designer-owned drafts. The designer reviews, rewrites the prose to their voice, and copies the entries into the Decisions section of product-design-as-intended.md. A pending action of type apply-promote-markers is filed to track the follow-up (with deduplication: if one already exists for the same plan, no duplicate is created).

Phase 3b: STATUS Marker Flip

Invoked via /explain drift --promote --apply-markers plan-NNNNNN. This phase verifies that the designer has copied the D-NNN entries into the as-intended file by performing a heading-only grep (^###\s+D-NNN(?::|\s*$)) -- it intentionally does not match title text or body prose, preserving the designer's voice.

For each verified entry, the designer is asked to confirm the STATUS flip. Confirmed items are processed by apply_marker.py: 

python .claude/skills/scripts/apply_marker.py \
  --file product-design/product-design-as-intended.md \
  --id D-<NNN> \
  --marker STATUS \
  --value established \
  --plan plan-<id> \
  --date <today>

Post-skill's check_human_markers_only.py and check_changelog_append_only.py verify that marker flips do not bleed prose into Human (markers) files. The apply-promote-markers pending action is closed when all proposed entries have been verified and flipped; otherwise it remains open with a message enumerating which entries are still missing or were declined.

Upgrade and Migration

The /seja-setup --upgrade command refreshes harness files from a newer SEJA release while preserving all project-specific configuration and output. It is the recommended way to keep a project's harness current without losing design history.

What Gets Upgraded

Category Files Action
Skills .claude/skills/*/SKILL.md Auto-updated
General references .claude/references/general/*.md Auto-updated
Templates .claude/references/template/** Auto-updated
Harness metadata .claude/CHANGELOG.md, VERSION, CHEATSHEET.md Auto-updated
Scripts .claude/skills/scripts/*.py Auto-updated
Agents .claude/agents/*.md Show diff, ask per file (may have local tweaks)

What Is Preserved

Category Files Why
Rules .claude/rules/*.md Project-specific conventions; show diff for manual merge
Project definitions product-design/** Never overwritten -- this is the project's design history
Settings .claude/settings.json, settings.local.json User-configured permissions and preferences
Output _output/ Plans, research logs, briefs, and all generated artifacts
Project README CLAUDE.md Contains project-specific build commands and architecture notes

How It Works

  1. Resolve target version: the upgrade flow resolves the target release tag (latest SemVer tag on the public seja repository, or an explicit --version <tag>). If the resolved tag matches the current .seja-version, the upgrade exits with "Harness already up to date."
  2. Locate source: if no local path is provided, a shallow clone of the public repository at the target tag is created in a temporary directory.
  3. Run the upgrade script: upgrade_harness.py copies auto-update files, reports diffs for manual-merge files, and updates .seja-version. Use --dry-run to preview changes without applying them.
  4. Review and follow up: the upgrade summary highlights the version change, files auto-updated, and files needing manual merge. Post-upgrade offers include adding new convention variables, updating stale path references, and regenerating CLAUDE.md.

Upgrade never re-runs the Section 1 scaffolding questionnaire. Projects with unresolved {{VAR}} placeholders in conventions.md (from pre-scaffolding era) retain them through the upgrade; run /design update stack afterwards to fill them and regenerate downstream artifacts.

Common Mistakes

Ignoring spec-drift warnings
The 14-day spec-drift check creates a pending action reminding you to run /explain drift. Ignoring it allows the gap between design intent and implementation to widen silently. Small drift is easy to reconcile; large drift requires painful forensics. Address drift reports promptly -- even if the resolution is "the as-intended file needs updating," that is a valid outcome worth recording.
Hand-fixing drift instead of using the promote workflow
When you see STATUS: implemented items awaiting promotion, it is tempting to manually edit product-design-as-intended.md to flip the markers and write the Decision entries yourself. This bypasses the governance pipeline: apply_marker.py validates transition rules, check_human_markers_only.py verifies that only marker content was changed, and check_changelog_append_only.py ensures the CHANGELOG was not corrupted. Use /explain drift --promote (Phase 3a) to generate the proposal, review and copy the entries, then run Phase 3b to flip markers through the validated path.
Letting pending actions accumulate past 90 days
Pending actions older than 90 days are auto-dismissed by pending.py cleanup with the reason auto-dismissed: aged out. If the underlying work was still needed, the auto-dismissal silently drops it from the active ledger. Review pending items regularly -- either address them, snooze them with an explicit date (/pending snooze <id> --until YYYY-MM-DD), or dismiss them with a reason before the 90-day window closes.
Upgrading without reading the CHANGELOG
/seja-setup --upgrade auto-updates skills, scripts, references, and templates. If a release introduces breaking changes -- new convention variables, renamed scripts, altered skill behavior -- the upgrade succeeds but downstream workflows may behave unexpectedly. Always read .claude/CHANGELOG.md for the target version before upgrading. The upgrade summary highlights new files and diffs, but the CHANGELOG provides the rationale and migration guidance that diffs alone cannot convey.

Release and Publishing

This chapter documents the /publish pipeline end to end -- from tag conventions and version inference through the ephemeral publish workspace to the final priv/public sync -- explaining how SEJA releases are cut, validated, and pushed to the public repository.

The /publish Pipeline

To cut a release, invoke /publish [version] in Claude Code. The skill accepts an optional version argument in vMAJOR.MINOR.PATCH format (e.g., v2.14.0). When no version is provided, publish.py infers the next tag from CHANGELOG.md and existing git tags, then prompts for confirmation. Two flags modify behavior: --dry-run previews the full command sequence without executing any destructive actions, and --yes accepts all defaults at confirmation prompts for non-interactive use.

The pipeline delegates to tools/publish.py, which orchestrates a 10-step lifecycle:

  1. Preflight checks. Validates that the working tree is clean, seja-public/CHANGELOG.md has unreleased content, no pre-existing tag matches the target version, and the remote origin is reachable. If .claude/CHANGELOG.md lacks a heading for the target version, the skill auto-generates the entry by collecting structured change data from git history via generate_changelog_data.py and delegating to the document-generator agent.
  2. Cut tag. Creates the git tag in the local seja-priv repository via cut_tag.py.
  3. Clone public repo. Shallow-clones the public seja repository into _output/tmp/publish-workspace/.
  4. Copy authored prose. Copies public-only prose from seja-public/ -- files like CHANGELOG.md, README.md, LICENSE, and the docs/ directory -- into the clone.
  5. Sync harness files. Runs sync_to_public.py --target <clone-dir> to generate the .claude/ directory in the clone. This copies the harness from seja-priv, strips content between <!-- priv-only-start --> / <!-- priv-only-end --> markers, unwraps <!-- pub-only-start --> / <!-- pub-only-end --> markers, and excludes private directories (priv/, project/), settings files, and test scripts.
  6. Smoke test. Runs pre_publish_smoke.py --candidate <clone-dir> to validate the clone, including a final check_no_private_leaks.py scan to ensure no private content has leaked into the publish workspace.
  7. Commit. Stages all changes in the clone and commits with a Release vX.Y.Z message.
  8. Push. Pushes the commit and tag to the public repository's main branch.
  9. Cleanup. Deletes the temporary clone directory (in a finally block to ensure cleanup even on failure).
  10. Close pending entry. Marks the PUBLISH: pending-ledger entry as done via pending.py.

On success, the skill reports the published version. On failure, it relays the error message and recovery instructions printed by publish.py -- the script's recovery guidance is authoritative and should not be second-guessed.

Tag Conventions

SEJA uses semantic versioning. Tags follow the format vMAJOR.MINOR.PATCH -- always prefixed with v. Any core-team member may cut a tag. The cadence is manual: releases happen when a coherent batch of changes is ready, targeting at most roughly one release per week. Smaller changes are batched together rather than shipped individually.

Version inference

When no explicit version is provided, publish.py infers the next tag through a two-step process:

  1. Discover the baseline. The baseline is max(highest_git_tag, highest_changelog_heading) using semver comparison. Ties prefer git tags because a tag represents an actual cut, while a changelog heading may describe a planned entry not yet released. When the changelog heading wins, the script emits a note so the operator knows which source drove the baseline.
  2. Determine the bump level. The script first checks for an explicit hint comment in the ## Unreleased section of seja-public/CHANGELOG.md: <!-- bump: patch|minor|major -->. If no hint is present, the script applies a heuristic based on subsection headings: a ### Breaking changes heading triggers a major bump, ### Added triggers minor, and everything else defaults to patch. Under v0.x, a major intent collapses to a minor bump (the contract-evolving rule).

Unified version namespace

SEJA uses one version, one CHANGELOG entry, one tag. Both .claude/CHANGELOG.md (the harness changelog) and seja-public/CHANGELOG.md (the public changelog) use the same version number. SemVer allows gaps, so the public repository jumped from v0.2.0 to the first internal version issued under the unified namespace policy. A gap note in the public changelog explains the jump for consumers.

Hotfix policy

The default rule is forward-fix on main and tag the next patch version. If a consumer is actively blocked on an older version, the team revisits per-case whether a release/<minor>.x branch is warranted.

The Ephemeral Publish Workspace

A key architectural decision in SEJA's release model is that seja-public/.claude/ does not exist on disk. The harness files that consumers receive in the public seja repository are never stored persistently in seja-public/ -- they are generated ephemerally during each publish cycle.

When /publish runs, publish.py creates a temporary clone of the public repository at _output/tmp/publish-workspace/. This clone is populated in two passes: first, authored public-only prose (CHANGELOG, README, LICENSE, docs) is copied from seja-public/; second, sync_to_public.py --target generates the .claude/ directory by copying harness files from seja-priv and stripping private content. The clone is then committed, tagged, and pushed to the public repository. Afterward, the clone directory is deleted.

This ephemeral approach provides several guarantees:

  • The harness files in the public repository always match the private repository at the time of release -- there is no opportunity for the two to drift because the public copy is regenerated from scratch each time.
  • Private content is stripped during generation, not after the fact. The sync_to_public.py script excludes entire directories (priv/, project/), specific files (settings.json, settings.local.json, test scripts), and inline content between priv-only-start / priv-only-end markers. The pre_publish_smoke.py test suite validates the result before any push occurs.
  • There is no stale .claude/ directory sitting in seja-public/ between releases that could accidentally be committed, modified, or mistaken for the canonical source. The canonical source is always seja-priv/.claude/.

The check_no_private_leaks.py script reinforces this model: its default invocation warns if seja-public/.claude/ exists on disk at all, since its presence indicates a cleanup failure from a previous publish run.

The Priv/Public Boundary

The separation between seja-priv and the public seja repository is not a deployment convenience -- it is a security boundary codified in the project constitution. Constitution invariant S1 states that private content must never reach seja-public without explicit opt-in. Compliance requirement C2 specifies that the product-design/ directory is permanently private and never synced. The Enforcement Architecture chapter documents the layered gates that enforce this boundary.

What stays in seja-priv

  • product-design/ -- constitution, conventions, design-intent files, as-coded state, UX research results, and all agent-facing structured specifications.
  • _output/ -- plans, research logs, critiques, roadmaps, briefs, conversation traces, pending ledger, and this documentation collection.
  • .claude/skills/scripts/priv/ -- private-only scripts such as check_no_private_leaks.py and generate_changelog_data.py.
  • .claude/skills/scripts/project/ -- project-specific scripts that are not part of the reusable harness.
  • tools/ -- release tooling including publish.py, sync_to_public.py, and the sync runbook.
  • Inline content between <!-- priv-only-start --> and <!-- priv-only-end --> markers in any .md file -- stripped during sync.

What reaches seja (public)

  • .claude/ harness files -- skills, agents, references, rules, and shared scripts (excluding the priv/ and project/ subdirectories, settings files, and test scripts). Generated by sync_to_public.py during publish.
  • CLAUDE.md -- the project instructions file, with private sections stripped.

Public-only prose

Certain files exist only in the public repository and have no counterpart in seja-priv: the public CHANGELOG.md, README.md, LICENSE, TRADEMARKS, and the docs/ directory. These are authored directly in seja-public/ (a Git submodule within seja-priv) and copied into the temporary clone during publish. They do not flow back to seja-priv.

Common Mistakes

Editing the standalone seja/ clone instead of seja-public/
The public seja repository should never be edited directly. Public-only prose is authored in seja-public/ within seja-priv, and harness files are generated during publish. Edits made directly to a standalone seja/ clone will be overwritten on the next release.
Recreating seja-public/.claude/ on disk
The .claude/ directory in seja-public/ is generated ephemerally during publish and should never exist on disk between releases. If it appears, check_no_private_leaks.py will warn about it. Delete it rather than trying to maintain it manually.
Publishing without running --dry-run first
The --dry-run flag prints the full sequence of commands that would execute -- including the git clone URL, target directory, and push commands -- so you can visually verify correctness before a live run. Skipping this step risks publishing with an unexpected version number or against an incorrect remote.
Forgetting to update CHANGELOG.md before tagging
The pipeline checks that seja-public/CHANGELOG.md has content in its ## Unreleased section before proceeding. If the harness changelog (.claude/CHANGELOG.md) is also missing an entry for the target version, the skill will auto-generate one -- but the public changelog must be updated manually. The preflight check will block the release if it finds an empty unreleased section.
