Enforcement Architecture

SEJA enforces its governance model through a layered defense: advisory checks that guide the agent during skill execution, blocking gates that prevent bad commits from landing, and a comprehensive validation orchestrator for CI pipelines. Each layer catches a different category of issue. Together they ensure that design intent, privacy boundaries, and authorship rules are maintained without relying on any single checkpoint.

Multi-Layer Enforcement

Enforcement in SEJA operates at three layers, ordered from earliest (in-session) to latest (CI pipeline). Each layer is designed so that it catches issues that escaped the layer before it, and so that the most disruptive failures are caught at the cheapest point -- inside the skill session -- rather than after a commit has already landed.

Layer 1: Post-Skill Advisory

After every skill execution, the post-skill lifecycle hook (.claude/skills/post-skill/SKILL.md) runs a 13-step pipeline. Several of these steps perform enforcement-relevant checks:

  • Step 2e -- DONE marker proposal: the agent proposes STATUS markers for as-intended items that appear to have been implemented. The human confirms, defers, or skips via AskUserQuestion.
  • Step 5 -- Git-state safety check: detects rebase-in-progress, unmerged conflicts, or detached HEAD and blocks the commit with a warning.
  • Step 6 -- Commit scope verification: verify_commit_scope.py compares staged files against the expected set for the skill and artifact type. Unexpected files trigger a warning.
  • Step 6b -- Fast preflight gate: run_preflight_fast.py runs the curated subset of fast validation scripts (see Layer 2 below). At this stage the gate is advisory -- it warns but does not block, because post-skill runs after lengthy work and the pre-commit hook provides the hard gate.
  • Step 6c -- Human markers verifier: check_human_markers_only.py --staged rejects any prose mutations in Human (markers) files. Violations prompt an AskUserQuestion recommending abort.

Advisory-layer checks surface problems early and give the agent and designer the opportunity to correct them before any commit is attempted. They do not block execution -- a designer can choose to proceed -- but they ensure awareness.

Layer 2: Pre-Commit Blocking

The pre-commit hook (.githooks/pre-commit) is the hard gate. It runs automatically on every git commit and blocks the commit on failure. The hook executes two scripts in sequence:

  1. run_preflight_fast.py -- runs a curated set of fast validation checks designed to complete in under 10 seconds. These include convention consistency, retired-token detection, skill-system integrity, secrets scanning, skill-spec compliance, version-changelog sync, design-output validation, plan coverage (blocking mode), human-markers enforcement, changelog append-only verification, section-boundary write enforcement, harness reference coverage, docs frontmatter validation, mantra-banner consistency, and (in seja-priv) the private-leak, call-graph, and harness-reference freshness checks.
  2. check_no_private_leaks.py --staged -- scans staged .md files for private content that would leak to seja-public on the next sync. This is the pre-sync leak gate (see the Leak Prevention section below).

To install the pre-commit hook, run bash .githooks/install.sh once per clone. The install script sets core.hooksPath to .githooks/. The hook can be bypassed with git commit --no-verify, but constitution S2 prohibits this without explicit designer approval recorded in a D-NNN decision entry.

Layer 3: CI Coverage

run_all_checks.py is the CI-independent validation orchestrator. It discovers and runs every check_*.py script in the .claude/skills/scripts/ directory and its co-located skill subdirectories. Unlike run_preflight_fast.py (which runs a curated subset optimized for speed), run_all_checks.py provides full coverage including checks that are too slow or too broad for the pre-commit hook -- such as lifecycle-fact-uniqueness, which performs O(N^2) comparisons and can produce false positives during transitional doc states.

Key features of the CI orchestrator:

  • Automatic discovery: finds all check_*.py scripts without a manual registry.
  • Stack filtering: --filter flask or --filter react limits execution to checks matching the project's stack (via check_plugin_registry.json).
  • JUnit XML output: --junit results.xml produces a report consumable by CI platforms.
  • Unified exit codes: 0 (all pass), 1 (one or more failures), 2 (orchestrator error).

Why Three Layers

Each layer catches a different category of problem at a different cost point:

Layer When it runs Blocking? What it catches
Post-skill advisory End of every skill session No (warns, recommends) Scope contamination, unauthorized prose edits, missing markers, git-state anomalies
Pre-commit blocking Every git commit Yes (blocks commit) Convention drift, secrets, stale manifests, private-content leaks, human-marker violations
CI coverage CI pipeline or on-demand Yes (fails the build) Full validation suite including slow/broad checks excluded from the pre-commit hot path

A problem detected at Layer 1 costs seconds to fix. The same problem detected at Layer 3 costs a CI round-trip. The layered model ensures that most issues never reach Layer 3.

Human (markers) Classification

The File Maintainer Classification (defined in .claude/references/general/shared-definitions.md) assigns one of four values to every reference file: Human, Human (markers), Agent, and Human / Agent. Files classified as Human (markers) are governed by constitution T2: the prose in these files belongs exclusively to the human designer, and agents may write only fixed-format lifecycle markers via apply_marker.py -- never direct prose.

What Agents May Write

The allowed marker types are defined in human_markers_registry.py and enforced by check_human_markers_only.py:

  • STATUS: lifecycle state tracking (proposed, implemented, established, superseded, or legacy uppercase IMPLEMENTED).
  • ESTABLISHED: legacy promotion stamp, retained for migration.
  • INCORPORATED: records absorption of research findings into design.
  • CHANGELOG_APPEND: timestamped changelog entries with HTML-injection prevention.
  • DECISION_APPEND: new DDR-shaped ### D-NNN: decision entries appended to the Decisions section.
  • REQ_TRACED_BY: annotates existing <!-- REQ-TYPE-NNN --> markers with a traced-by pseudo-plan.

Every marker write must pass through apply_marker.py after explicit AskUserQuestion confirmation in the same turn. The check_human_markers_only.py verifier parses the staged git diff, filters to files in the registry, and rejects any added or removed non-blank line that does not match an allowed marker regex. Violations block the commit during post-skill step 6c and during the pre-commit hook via run_preflight_fast.py.

Registered Human (markers) Files

The following files are registered in human_markers_registry.py:

  • .claude/skills/scripts/tests/fixtures/marker_fixture.md (test fixture)
  • .claude/references/template/ux-research-results.md
  • product-design/ux-research-results.md
  • .claude/references/template/product-design-as-intended.md
  • product-design/product-design-as-intended.md

Both the template and project paths are registered for each real file. The template path is what /design seeds (and what harness-level tests touch); the project path is what designer commits exercise via post-skill step 2e. For a detailed treatment of the marker system itself -- types, formats, state transitions, and the promote workflow -- see Vol. 2 Ch. 4: The Marker System.

Leak Prevention

check_no_private_leaks.py (.claude/skills/scripts/priv/check_no_private_leaks.py) enforces the boundary between private (seja-priv) and public (seja-public) content. Constitution S1 codifies this invariant: private content -- design files, research logs, plans, product-design files, and the constitution itself -- must never reach seja-public without explicit opt-in. Accidental exposure is irreversible once cached by search engines or CI logs.

What the Script Prevents

The script operates in three modes, each targeting a different stage of the content lifecycle:

Pre-commit gate (--staged)
Scans staged .md files in seja-priv before they are committed. For each file, it applies the same strip-private-sections transform as sync_to_public.py (removing content between <!-- priv-only-start --> and <!-- priv-only-end --> markers), then checks the stripped output for residual priv-only markers (indicating malformed or unbalanced marker pairs) and private-content fingerprints that survived the strip. Files under product-design/, _output/, .claude/skills/scripts/priv/, and seja-public/ are excluded from staged-file scanning because they are private by convention.
Candidate scan (--candidate DIR)
Performs a full leak scan of a candidate publish directory. Used by pre_publish_smoke.py to validate a publish workspace before release. Checks for priv-only markers, private files (e.g., generate_changelog_data.py), private directories (priv/, project/), private patterns, and SKILL.md content fingerprints.
Default mode (no arguments)
Scans authored prose in seja-public/ (top-level *.md and docs/**/*.md) for residual priv-only markers. Also warns if seja-public/.claude/ exists on disk (it should have been cleaned up after the last publish).

Content Fingerprints

Beyond marker stripping, the script maintains a list of content fingerprints -- patterns like --harness, seja-priv, sync_to_public, scripts/priv, and pre_publish_smoke -- that are inherently private terminology. These fingerprints are checked only in SKILL.md files (other files may legitimately reference these terms). Matches inside fenced code blocks are ignored.

Where It Runs

  • Pre-commit hook: the .githooks/pre-commit script runs check_no_private_leaks.py --staged as its second gate (after run_preflight_fast.py). A failure blocks the commit.
  • Preflight fast checks: run_preflight_fast.py includes the no-private-leaks check in its curated set (priv-only; silently omitted in public repos where the priv/ directory is absent).
  • Publish pipeline: pre_publish_smoke.py calls check_no_private_leaks.py --candidate to validate the workspace before tagging a release.

Path-Scoped Rules

SEJA uses 7 rule files in .claude/rules/ that are auto-loaded when the agent works on files matching their declared path scope. Each rule file surfaces domain-specific review questions, standards references, and P0 review perspectives relevant to the files being edited.

Rule File Scope (path patterns) Summary
backend.md backend/** Surfaces P0 review questions for security, database, and architecture alongside backend standards
frontend.md frontend/src/** Loads UX, accessibility, visual design, and responsive-behaviour review lenses with frontend and testing conventions
tests.md **/*.test.*, **/test_*.py, backend/tests/** Surfaces testability and developer-experience review questions alongside testing conventions
i18n.md frontend/src/i18n/**, backend/translations/** Loads internationalization review questions covering missing keys, locale formatting, plural rules, and RTL
migrations.md backend/migrations/** Surfaces database-change and security review questions for reversibility, data-loss risk, and lock behaviour
e2e.md e2e/** Loads testability, UX, and accessibility review lenses for end-to-end test files
harness-structure.md .claude/** Loads the harness structural inventory -- skills, agents, scripts, references, and rules

Rules are loaded automatically by Claude Code's built-in path-matching mechanism. When a file matching a rule's paths pattern is opened for editing, the corresponding rule content is injected into the agent's context. This ensures that domain-specific governance is always active without requiring the designer to remember which standards apply.

Anti-patterns

The following practices undermine SEJA's enforcement guarantees. Each pattern describes what goes wrong and what to do instead.

Bypassing the lifecycle

Running code changes without first creating a plan via /plan. Without a plan, there is no artifact trail, no commit-scope verification, no coverage check, and no post-skill alignment. The enforcement layers assume a plan exists; skipping it disables most of their value.

Instead: always start with /plan (or /plan --light for small changes). The plan is the anchor that connects design intent to implementation to verification.

Hand-editing Human (markers) files

Directly editing the prose or markers in files classified as Human (markers) -- such as product-design-as-intended.md or ux-research-results.md -- outside of apply_marker.py. The check_human_markers_only.py verifier will reject the diff, and the commit will be blocked at the pre-commit hook.

Instead: use apply_marker.py for all marker writes, and edit prose content as the human designer (not through the agent). The agent proposes marker changes via AskUserQuestion and routes confirmed changes through the designated script.

Skipping pre-commit hooks

Using git commit --no-verify to bypass the pre-commit hook chain. Constitution S2 explicitly prohibits this without designer approval recorded in a D-NNN decision entry. The hook is the last automated gate before private content, convention violations, or stale manifests land in the repository.

Instead: fix the failing check. If a legitimate exception is needed, document it in a D-NNN decision record first, then bypass with full traceability.

Mixing private content into public docs

Allowing seja-priv content -- design rationale, internal research, decision records, product-design files -- to reach seja-public. Constitution S1 codifies the invariant: private content must never cross the boundary without explicit opt-in. The leak is irreversible once cached by search engines or CI pipelines.

Instead: wrap private content in <!-- priv-only-start --> / <!-- priv-only-end --> markers so the sync tool strips it automatically. The pre-commit hook and publish pipeline both verify that no private fingerprints survive the strip.

Circumventing constitution principles without D-NNN decision records

Overriding or ignoring a constitution-level constraint (T1-T4, Q1-Q3, S1-S2, C1-C2) without creating a formal decision entry. The constitution is loaded into every agent context via pre-skill and takes precedence over all other guidance. Silent violations erode the governance model because they leave no audit trail.

Instead: if a constitution principle genuinely needs to be amended or temporarily overridden, create a D-NNN decision entry documenting the context, the decision, and the consequences. The entry provides traceability and ensures the override is deliberate.
