Scripts and Automation

The SEJA harness automates its governance, validation, and artifact management through a suite of Python scripts distributed across several directories. This chapter provides a per-script reference grouped by functional category, followed by how-to guidance on using the validation orchestrator and extending it with new checks.

Scripts live in four locations: .claude/skills/scripts/ (shared utilities), co-located skill subdirectories such as .claude/skills/critique/, .claude/skills/design/, .claude/skills/explain/, and .claude/skills/post-skill/ (skill-owned scripts next to their SKILL.md), .claude/skills/scripts/priv/ (private-only scripts excluded from public releases), and tools/ (release pipeline utilities). The validation orchestrator run_all_checks.py discovers scripts across all of these locations automatically.

Script Categories

The tables below group every script by its functional role. The Typical invocation column shows the most common way each script is called; most scripts also accept --help for full option details.

Validation

Validation scripts enforce harness invariants, project conventions, and codebase integrity constraints. Each script exits 0 on pass, 1 when violations are found, and 2 on script error. Two orchestrators aggregate them: run_all_checks.py (full sweep with JUnit XML) and run_preflight_fast.py (curated fast subset for git hooks, under 10 seconds).

Marker Management

apply_marker.py is the sole write path for Human (markers) files -- the design files whose content is classified as human-authored and whose mutations are restricted to structured marker operations. No other script or direct edit is permitted to modify these files.

Script Purpose Typical invocation
apply_marker.py Applies lifecycle markers to design files. Supported marker types: STATUS (flip implementation status), ESTABLISHED (mark items as established), INCORPORATED (mark research as incorporated), CHANGELOG_APPEND (append changelog entries), DECISION_APPEND (append new D-NNN decision entries with auto-assigned IDs), and REQ_TRACED_BY (annotate REQ markers with traceability links to implementing plans) python .claude/skills/scripts/apply_marker.py --marker STATUS --file <path> --id <id>

Using run_all_checks.py

run_all_checks.py is the CI-independent validation orchestrator. It discovers every check_*.py script in .claude/skills/scripts/ and in co-located skill subdirectories (such as critique/, design/, explain/, and post-skill/), runs each one sequentially, and rolls the results into a single pass/fail verdict.

Running the full suite

python .claude/skills/scripts/run_all_checks.py --root .

The --root flag tells the orchestrator where the repository root is. Each check script is executed as a subprocess with a 120-second timeout.

Reading the output

As each check runs, the orchestrator prints its name followed by PASS, FAIL, or ERROR. After all checks complete, a summary table is printed: 

SEJA Validation Orchestrator -- Results
----------------------------------------------
Script                              Status  Duration
----------------------------------------------
check_conventions.py                PASS      0.42s
check_design_output.py              FAIL      1.23s
check_skill_system.py               PASS      0.87s
----------------------------------------------
2 passed, 1 failed, 3.52s total

For failed or errored checks, the script's stdout and stderr are printed indented below the status line in non-verbose mode. In --verbose mode, child output streams directly to the console as it runs.

JUnit XML output

python .claude/skills/scripts/run_all_checks.py --root . --junit results.xml

The --junit flag writes a standard JUnit XML report. Each check becomes a <testcase> in a seja-checks testsuite. Failures include the check's combined stdout/stderr as the failure message text. This format integrates with CI platforms that parse JUnit XML (GitHub Actions, Jenkins, GitLab CI).

Filtering by stack

python .claude/skills/scripts/run_all_checks.py --root . --filter flask

When check_plugin_registry.json exists in the scripts directory, the --filter flag restricts execution to checks whose registry entry matches the given stack keyword. Checks marked with "any" in their stack always run. Checks not in the registry also run by default.

Exit codes

0
All checks passed.
1
One or more checks failed (validation violations found).
2
Orchestrator error (no scripts found, script directory missing) or one or more checks encountered a runtime error.

When to use which orchestrator

Use run_preflight_fast.py for git hooks and quick local validation -- it runs a curated subset of fast checks and completes in under 10 seconds. Use run_all_checks.py for CI pipelines and thorough validation sweeps -- it discovers and runs every check script, with JUnit XML support for CI integration.

Extending the Validation Suite

To add a new validation check that integrates with run_all_checks.py, follow these conventions:

  1. Name the script check_<what>.py. The orchestrator discovers scripts by globbing for check_*.py in .claude/skills/scripts/ and in co-located skill subdirectories. Any file matching this pattern is automatically included.
  2. Exit 0 for pass, 1 for failure. The orchestrator interprets any non-zero exit code as a failure. Use exit code 2 for script errors (missing dependencies, invalid arguments) to distinguish them from validation findings.
  3. Print findings to stdout. When violations are found, print human-readable diagnostics to stdout. The orchestrator captures this output and includes it in the JUnit XML report for failed checks. Print errors and warnings to stderr.
  4. Accept --root or auto-detect. Import project_config.py for repository root detection: 
    from project_config import REPO_ROOT
    This ensures the script works regardless of the current working directory.
  5. Keep execution fast. The orchestrator enforces a 120-second timeout per script. If your check should run in the fast preflight gate (under 10 seconds total for all fast checks), add it to the FAST_CHECKS list in run_preflight_fast.py.
  6. Optionally register in check_plugin_registry.json. If your check is stack-specific (e.g., only relevant for Flask or React projects), add an entry with the script name and stack metadata so the --filter flag can include or exclude it.

A minimal check script looks like this: 

#!/usr/bin/env python3
"""check_example.py -- Validate example constraint.

Invocation: agent-invoked
Lifecycle: active

Exit codes: 0 = pass, 1 = violations found, 2 = script error.
"""
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent))
from project_config import REPO_ROOT

def main() -> int:
    violations = []
    # ... scan for violations ...
    for v in violations:
        print(v)
    return 1 if violations else 0

if __name__ == "__main__":
    sys.exit(main())

Common Mistakes

Running individual check scripts instead of run_all_checks.py
Individual scripts report their own findings but produce no aggregated summary, no JUnit XML, and no unified exit code. The orchestrator provides a single pass/fail verdict, a summary table with per-check durations, and optional CI-compatible XML output. Always use run_all_checks.py for comprehensive validation and run_preflight_fast.py for quick pre-commit checks.
Ignoring exit codes
Every check and orchestrator script communicates its verdict through its exit code. A script that prints warnings but exits 0 is considered passing. Piping output to grep or visually scanning for keywords is unreliable -- check $? or the process return code. CI pipelines should fail the build on non-zero exit from run_all_checks.py.
Not updating run_all_checks.py when adding new check scripts
run_all_checks.py discovers check_*.py scripts automatically via glob, so new scripts in the standard locations are included without changes. However, if you want your script in the fast preflight gate, you must manually add it to the FAST_CHECKS list in run_preflight_fast.py. Forgetting this means the check runs in full CI sweeps but not in git hooks.
Editing generated files that scripts will overwrite
Files produced by generation scripts -- such as _output/INDEX.md, .claude/CHEATSHEET.md, skill-graph.json, and decision-digest.jsonl -- are regenerated automatically. Manual edits to these files will be silently overwritten on the next generation run. Edit the source data instead.
Modifying Human (markers) files directly
Human (markers) files must be modified exclusively through apply_marker.py. Direct edits bypass the marker-type validation and will be rejected by check_human_markers_only.py in the preflight gate. Use the appropriate --marker type flag to apply the desired change.
