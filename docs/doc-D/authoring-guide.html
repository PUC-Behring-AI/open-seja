Authoring Guide

This reference codifies the seven conventions that govern content authoring across the SEJA Documentation Collection. Authors creating or expanding chapter content must follow these conventions to ensure structural consistency, Diataxis compliance, and cross-reference integrity across all five volumes.

For HTML template structure, CSS specifications, and accessibility requirements, see doc-guidelines.md. This authoring guide addresses content-level conventions that the template does not cover.

1. Section-Level Diataxis Tagging

The standard Diataxis framework classifies each documentation page as exactly one type: tutorial, how-to, reference, or explanation. In this collection, many chapters serve multiple purposes within a single page -- a design-layer chapter might explain the rationale for a mechanism, provide reference tables for its configuration, and include how-to steps for common tasks. Rather than splitting these into separate pages (which would fragment the narrative), apply Diataxis classification at the section level.

How to Apply

Add a data-diataxis attribute to each <section> element within the chapter: 

<section id="marker-types" data-diataxis="reference">
  <h2>Marker Types</h2>
  <!-- Reference content: tables, exhaustive lists -->
</section>

<section id="when-to-use-markers" data-diataxis="explanation">
  <h2>When to Use Markers</h2>
  <!-- Explanation content: rationale, trade-offs -->
</section>

<section id="applying-a-marker" data-diataxis="how-to">
  <h2>Applying a Marker</h2>
  <!-- How-to content: task-oriented steps -->
</section>

Page-Level Meta Tag

When a chapter contains sections of more than one Diataxis type, set the page-level <meta name="diataxis"> tag to "mixed": 

<meta name="diataxis" content="mixed">

When all sections share the same type (common in Vol. 5 where every section is explanation), use that type directly instead of "mixed".

Valid Values

Value Usage
tutorial Learning-oriented: guided exercises with guaranteed outcomes
how-to Task-oriented: steps to accomplish a specific goal
reference Information-oriented: exhaustive, factual, dry
explanation Understanding-oriented: rationale, context, trade-offs

2. Mixed-Type Chapter Guidelines

When a chapter contains sections of different Diataxis types, three principles govern the content organization:

Topic Locality First

Group content by topic, not by Diataxis type. A chapter on the marker system should keep all marker-related content together -- the explanation of why markers exist, the reference table of marker types, and the how-to for applying markers -- rather than separating all explanations into one section and all references into another.

Tip: A useful test: if a reader is looking for "everything about markers," can they find it in one chapter, or must they jump between the explanation chapter and the reference chapter? Topic locality keeps it in one place.

Diataxis Discipline Per Section

Within each section, maintain strict Diataxis discipline. A section tagged data-diataxis="reference" must not include narrative prose explaining rationale; a section tagged data-diataxis="how-to" must not include exhaustive reference tables. If a section naturally mixes types, split it into subsections with distinct tags, or restructure so each section serves exactly one purpose.

Transition Sentences Between Types

When adjacent sections differ in Diataxis type, include a brief transition sentence at the end of the preceding section or the beginning of the following one. The transition helps readers adjust their reading mode:

  • Reference to explanation: "The table above lists all marker types. The following section explains when each type is appropriate and the design rationale behind the taxonomy."
  • Explanation to how-to: "With the rationale established, the following steps show how to apply a marker in practice."
  • How-to to reference: "For a complete list of parameters and their valid values, see the reference table below."

3. "Common Mistakes" Section Convention

Certain chapter types require a dedicated "Common Mistakes" section. This section collects errors that practitioners frequently make, framed as problem-solution pairs.

Required In

  • Each skill chapter (Vol. 3, Ch. 2 "Skills In Depth") -- one "Common Mistakes" subsection per skill within the per-skill template, plus a cross-cutting "Common Mistakes" section for the chapter as a whole.
  • Each design-layer chapter (Vol. 2, Ch. 1-5) -- one "Common Mistakes" section per chapter covering errors specific to that design-layer component.

Format

Each entry in a "Common Mistakes" section follows this structure: 

<section id="common-mistakes" data-diataxis="how-to">
  <h2>Common Mistakes</h2>
  <dl>
    <dt>Mistake description (what goes wrong)</dt>
    <dd>
      Why it happens, what the symptom looks like, and how to
      fix or avoid it. Include a code example if applicable.
    </dd>
  </dl>
</section>

Use a definition list (<dl>) for problem-solution pairs. The <dt> is the mistake; the <dd> is the explanation and fix. Tag the section as data-diataxis="how-to" because the purpose is task-oriented: help the reader avoid or recover from the mistake.

4. "Anti-patterns" Section Convention

Vol. 4, Ch. 2 ("Enforcement Architecture") uses "Anti-patterns" instead of "Common Mistakes." The distinction is intentional: anti-patterns are structural misuses of the governance system, not simple errors. They represent patterns that appear reasonable but undermine the harness's integrity.

Required Anti-Pattern Items

  • Bypassing the lifecycle -- executing implementation without a preceding plan, skipping critique before documentation.
  • Hand-editing Human marker files -- modifying product-design-as-intended.md or product-design-as-coded.md directly instead of using apply_marker.py.
  • Skipping pre-commit hooks -- using --no-verify to bypass the leak gate and preflight checks.
  • Mixing private content into public docs -- including seja-priv-only content in files that propagate to seja-public.
  • Circumventing constitution principles -- overriding immutable constraints defined in constitution.md through skill parameters or prompt engineering.

Format

Use the same definition list format as "Common Mistakes" but with stronger framing: each <dt> names the anti-pattern, and the <dd> explains why it is structurally harmful (not merely inconvenient), what symptom surfaces, and what the correct alternative is. Tag the section as data-diataxis="how-to".

5. Publication-Quality Guidelines for Vol. 5

Vol. 5 (Foundations and Philosophy) targets publication-quality writing. Every chapter in this volume carries <meta name="quality" content="publication">, which signals the following standards:

Citation Density

Every substantive claim must be traceable to a cited source. Primary sources are preferred over secondary summaries. When referencing semiotic engineering concepts, cite de Souza (2005) directly, not a downstream textbook's summary. Use the <cite> element for work titles and provide full bibliographic details in a "Key Citations" section at the end of each chapter.

Counter-Readings

Every Vol. 5 chapter must include a "Critical Counter-Reading" section as its final substantive section (before "Source Material" and "Key Citations"). This section presents genuine objections to the chapter's argument -- not straw-man dismissals. A good counter-reading:

  • Identifies a specific weakness in the argument, not a general caveat.
  • References an alternative theoretical framework that would reach different conclusions.
  • Acknowledges limitations that the chapter's framing cannot resolve.
  • Avoids the "however, despite these concerns, our approach is still correct" pattern. The counter-reading should leave genuine tension unresolved.

Acknowledged Limitations

Publication-quality writing is honest about what it does not cover. Each chapter should state its scope explicitly and acknowledge where the argument is speculative, where evidence is thin, and where the theoretical framework might not apply. Do not present conjectures as established facts.

Warning: The publication-quality standard applies only to Vol. 5. Applying it to Vol. 1-4 chapters would slow practical documentation with unnecessary academic apparatus. Vol. 1-4 chapters should be clear and accurate but do not require citation density or counter-readings.

6. Content Phasing

Content development is organized into three phases, prioritized by immediate value to readers. The doc-phase meta tag on each page records its phase assignment.

Phase Volumes Rationale doc-phase Value
Phase 1 Vol. 1 (Onboarding) + Vol. 3 (Execution Layer) Highest immediate value: gets users started and covers the skills and workflows they interact with daily. 1
Phase 2 Vol. 2 (Design Layer) + Vol. 5 (Foundations) Deepens understanding: explains the design artifacts and theoretical foundations that shape how the harness works. 2
Phase 3 Vol. 4 (Governance Layer) Completes the collection: covers output artifacts, enforcement, scripts, maintenance, and release -- topics that matter most to maintainers and contributors. 3

Phasing Rules

  • Stub pages are phase-tagged at creation. Every stub carries the doc-phase meta tag from the moment it is created, even before content development begins.
  • Phase 1 content is developed first. When prioritizing content work, always complete Phase 1 chapters before starting Phase 2, and Phase 2 before Phase 3.
  • Cross-phase references are permitted. A Phase 1 chapter may link to a Phase 2 or Phase 3 stub. The stub's status notice tells the reader that content is planned but not yet available.
  • Phase does not determine reading order. The Reading Map defines recommended reading sequences that cross phase boundaries. A researcher might start with Vol. 5 (Phase 2) even though Vol. 1 (Phase 1) was developed first.

7. Cross-Reference Link Format

All cross-references within the collection follow the conventions defined in doc-guidelines.md Section C. This section summarizes the key rules for quick reference.

Inter-Volume Links

Links between chapters in different volumes use relative paths from the chapter file: 

<!-- From onboarding/quickstart.html to execution-layer/lifecycle-pipeline.html -->
<a href="../execution-layer/lifecycle-pipeline.html">Lifecycle Pipeline</a>

Pattern: ../volume-dir/chapter.html

Intra-Volume Links

Links between chapters in the same volume use sibling paths: 

<!-- From design-layer/metacommunication.html to design-layer/constitution-guide.html -->
<a href="constitution-guide.html">Constitution Guide</a>

<!-- Link to a specific section -->
<a href="marker-system.html#marker-types">Marker Types</a>

Pattern: chapter.html or chapter.html#section-id

Collection-Root Links

Links from chapter pages to collection-root pages (index, reading map, this authoring guide) use the parent directory: 

<!-- From any chapter page to the collection index -->
<a href="../index.html">Collection Index</a>

<!-- From any chapter page to the authoring guide -->
<a href="../authoring-guide.html">Authoring Guide</a>

Descriptive Link Text

Link text must describe the target. Use the chapter's short title or section heading. Do not use generic phrases:

Correct Incorrect
<a href="...">Lifecycle Pipeline</a> <a href="...">click here</a>
<a href="...">Marker Types reference</a> <a href="...">this page</a>
<a href="...">Constitution Guide</a> <a href="...">read more</a>

Anchor ID Format

Section anchor IDs use kebab-case derived from the heading text:

Heading Anchor ID
The Metacommunication Message the-metacommunication-message
Common Mistakes common-mistakes
Design Decisions and Trade-offs design-decisions-and-trade-offs

Rules:

  • Lowercase all characters.
  • Replace spaces with hyphens.
  • Remove punctuation (colons, parentheses, quotes).
  • Preserve numbers as-is.

No External References

Per the self-containment rule, pages in this collection must not link to files outside the collection's folder tree. If a concept is documented elsewhere (e.g., in seja-public/docs/), summarize or reproduce the relevant content in the appropriate chapter rather than linking out.

8. Generated Navigation and Print View

Each in-volume page carries a sticky per-volume table-of-contents sidebar (<nav class="volume-toc">), and every volume offers a consolidated single-page "print view" at <volume>/<volume>-print.html. Neither is hand-written. Both are produced by the generator script _output/generated-scripts/build_doc_volume_nav.py, which reads the volume indexes and chapter files and injects the sidebar, the layout wrapper, the navigation script tag, and the print-view link into the pages that need them. Authors write only the chapter skeleton (see doc-guidelines.md Section E, "Two Sidebar Scopes"); the generator owns the rest.

How to Run It

From the repository root, run the generator with no arguments to regenerate every marked region across the collection: 

python _output/generated-scripts/build_doc_volume_nav.py

Two flags are available:

  • --dry-run lists the pages that would change without writing anything -- use it to preview the effect before committing.
  • --root <path> targets a different collection directory (the default is this collection's root).

The generator is idempotent: it is safe to re-run, and re-running replaces the contents of the marked regions in place rather than duplicating them. Running it twice in a row produces no further changes.

When to Re-Run

Re-run the generator whenever the volume or chapter structure changes, so the sidebars and print pages stay in sync with the content:

  • After adding, renaming, reordering, or removing a chapter.
  • After changing a chapter's section headings or its <section id> values (the sidebar's nested section links and the print page's anchors are derived from these).
  • After editing a volume index.html's .chapter-list (the chapter roster and ordering come from there).

Do Not Hand-Edit the Generated Regions

The generator delimits everything it owns with HTML-comment markers. Do not edit the content between these markers by hand -- the next generator run overwrites it:

Marker pair Owns
<!-- VOLUME-TOC:START --> / END The <nav class="volume-toc"> sidebar.
<!-- DOC-LAYOUT:START --> / END The <div class="doc-layout"> grid wrapper around <main> and the sidebar.
<!-- NAV-SCRIPT:START --> / END The <script src="../nav.js" defer> tag before </body>.
<!-- PRINT-LINK:START --> / END The "Single-page / print view" link in each volume index.

The has-doc-layout class on <body> is likewise added by the generator (it gates the wider two-column layout). Do not add or remove it by hand.

Which Pages Get the Sidebar

The generator injects the sidebar into the pages that belong to a volume: the 25 chapter pages, the 5 volume index pages, and reading-map.html (which is Vol. 1, Ch. 3). Three collection-root pages are excluded and receive no sidebar, no layout wrapper, and no script tag:

  • index.html (the collection landing page).
  • authoring-guide.html (this page).
  • _template.html (the chapter template).

Because this authoring guide is on the exclude list, the generator never modifies it -- any edits here are made by hand.

The Consolidated Print View

The <volume>/<volume>-print.html pages are per-volume, single-page views: each concatenates all of its volume's in-volume chapters into one document (with a single <h1>, demoted chapter headings, and namespaced section ids) for printing or single-page reading. Each volume index links its print page through the generated PRINT-LINK region as "Single-page / print view". The print pages are not sidebar pages -- they are the single-page view.

Progressive Enhancement

The sidebar works fully without JavaScript: every chapter and section entry is a plain <a href> that navigates correctly, and the current chapter and anchored section are marked with a non-color cue (font weight plus a leading marker). The collection's nav.js is a progressive enhancement layered on top: it adds scroll-spy (highlighting the section currently in view) and a mobile toggle for collapsing the sidebar on narrow viewports. With JavaScript disabled, the sidebar still renders and navigates -- nothing depends on the script.
