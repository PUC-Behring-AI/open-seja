The Marker System

SEJA uses lifecycle markers to track the status of design-intent items as they move from proposal through implementation to establishment. Markers are the mechanism by which the agent records lifecycle state changes in human-authored files without altering the designer's prose. All marker writes go through a single script -- apply_marker.py -- which validates format, enforces transition rules, and requires explicit human confirmation before every write.

Marker Types

SEJA's marker system comprises five marker types organized in three functional categories: status tracking (STATUS), research absorption (INCORPORATED), structured-entry appending (DECISION_APPEND, CHANGELOG_APPEND), and traceability (REQ_TRACED_BY). Each type serves a distinct governance purpose and follows a specific format.

Type Purpose Format Triggered By
STATUS Tracks lifecycle state of design-intent items <!-- STATUS: <value> | <plan-id> | <date> --> Post-skill (agent proposes, human confirms)
INCORPORATED Records absorption of research findings into design <!-- INCORPORATED: <plan-id> | <date> --> Post-skill after research findings are acted upon
DECISION_APPEND Appends DDR-shaped decision entries to the Decisions section ### D-NNN: <title> with Context, Decision, Consequences /research step 9b or /design Phase C
CHANGELOG_APPEND Appends timestamped entries to the CHANGELOG section Table row: | <date> | <action> | <source> | Post-skill after marker flips or design changes
REQ_TRACED_BY Annotates REQ markers with traceability links to implementing plans <!-- REQ-TYPE-NNN | traced_by: <value> --> Post-skill after plan implementation traces to a REQ

STATUS: Lifecycle State Machine

The STATUS marker is an inline HTML comment placed immediately before a section heading. It is invisible in rendered Markdown but machine-parseable by agent tooling. The state machine enforces a strict progression: 

proposed  →  implemented  →  established  →  superseded

Each transition requires a plan ID and date. Regressions (such as established → implemented) are rejected by the script. A STATUS marker in context looks like this: 

<!-- STATUS: implemented | plan-000178 | 2026-04-02 -->
### Platform Purpose

Legacy uppercase markers (STATUS: IMPLEMENTED) from pre-2.8.3 files are still recognized. When a Phase 3b promotion flip targets a legacy marker, apply_marker.py replaces the line in place rather than stacking a new marker above it.

ESTABLISHED: The Promotion Stamp

When a human confirms that an implemented item should be promoted to established, two things happen: the STATUS marker is flipped to established, and an ESTABLISHED stamp is applied. The stamp records the promotion event: 

<!-- ESTABLISHED: plan-000178 | 2026-04-02 | v2.8.3 -->

The version field (vX.Y.Z) is optional. Projects without semantic versioning use the date alone.

INCORPORATED: Research Absorption

The INCORPORATED marker records that research findings from a specific plan or research log have been absorbed into the design-intent file. It is inserted before the heading of the section that was informed by the research: 

<!-- INCORPORATED: plan-000268 | 2026-04-11 -->
### Entity Hierarchy

DECISION_APPEND and CHANGELOG_APPEND: Structured Entries

These two marker types do not modify existing lines -- they append new structured content to designated sections. DECISION_APPEND adds a DDR-shaped decision entry (### D-NNN: Title with Context, Decision, Consequences fields) to the ## Decisions section. The D-NNN ID is auto-assigned by scanning existing entries. CHANGELOG_APPEND adds a timestamped row to the ## CHANGELOG table.

The reference above catalogues each marker type and its format. The following section shows how to apply these markers in practice using the apply_marker.py script.

Using apply_marker.py

apply_marker.py is the sole write path for files classified as Human (markers). Agents that need to update a marker must invoke this script rather than using Edit or Write on the file directly. The companion verifier check_human_markers_only.py rejects any prose mutations that bypass this path.

Command-Line Interface

python .claude/skills/scripts/apply_marker.py \
    --file <path> \
    --id <entry-id> \
    --marker <kind> \
    --value <value> \
    [--plan <plan-id>] \
    [--date <YYYY-MM-DD>] \
    [--note <text>] \
    [--dry-run]
Parameter Required Description
--file Yes Path to the target Human (markers) file
--id Yes Entry ID or section heading to locate (e.g., "Platform Purpose" or "D-001")
--marker Yes Marker kind: STATUS, ESTABLISHED, INCORPORATED, DECISION_APPEND, CHANGELOG_APPEND, or REQ_TRACED_BY
--value Conditional Marker value (e.g., implemented for STATUS, entry text for DECISION_APPEND). Required for STATUS, CHANGELOG_APPEND, DECISION_APPEND, and REQ_TRACED_BY; ignored by stamp-kind markers (ESTABLISHED, INCORPORATED)
--plan Depends Plan ID (required for ESTABLISHED and INCORPORATED; recommended for STATUS)
--date No Date in YYYY-MM-DD format (defaults to today in UTC)
--note No Optional annotation text
--dry-run No Preview the change without writing to disk

The Confirmation Flow

Before invoking apply_marker.py, the agent must ask the designer for confirmation using AskUserQuestion. This is not optional -- it is the human-in-the-loop governance check that ensures no lifecycle state change happens without explicit designer approval. The flow is:

  1. The agent identifies that a marker write is needed (e.g., post-skill detects a plan step was completed).
  2. The agent presents the proposed change via AskUserQuestion: which file, which entry, which marker, which value.
  3. The designer confirms or rejects.
  4. On confirmation, the agent runs apply_marker.py with the agreed parameters.

Examples

Marking a section as implemented

python .claude/skills/scripts/apply_marker.py \
    --file product-design/product-design-as-intended.md \
    --id "Platform Purpose" \
    --marker STATUS \
    --value implemented \
    --plan plan-000178

This inserts <!-- STATUS: implemented | plan-000178 | 2026-07-15 --> immediately before the ### Platform Purpose heading.

Recording research incorporation

python .claude/skills/scripts/apply_marker.py \
    --file product-design/product-design-as-intended.md \
    --id "Entity Hierarchy" \
    --marker INCORPORATED \
    --plan plan-000268

Appending a decision entry

python .claude/skills/scripts/apply_marker.py \
    --file product-design/product-design-as-intended.md \
    --id "_" \
    --marker DECISION_APPEND \
    --value "Use HTML-only output for product topology
**Context**: Mermaid cannot support persona-filter or roadmap-lane views.
**Decision**: Adopt HTML as the canonical topology deliverable.
**Consequences**: No Mermaid dependency; requires custom rendering logic." \
    --plan plan-000200

The --id parameter is ignored for DECISION_APPEND -- the script auto-assigns the next D-NNN ID by scanning existing entries in the ## Decisions section.

Previewing a change

Add --dry-run to any command to see what would be written without modifying the file. The script prints the marker line and target location, then exits without writing.

With the practical mechanics established, the following section explains why markers are structured this way and what role they play in SEJA's governance model.

Markers as Designed Signification

Markers in SEJA are not arbitrary metadata tags. They are a designed signification system -- a set of conventionalized expression-content pairs where each marker type carries a specific, governance-relevant meaning. This is a deliberate application of the semiotic engineering concept of signification systems, where signs are designed to convey particular meanings within a particular context of use.

The STATUS marker signifies where a design-intent item stands in its lifecycle: has it been proposed, built, confirmed by the designer, or superseded? The INCORPORATED marker signifies that external knowledge (research findings) has been absorbed into the design layer. The DECISION_APPEND marker signifies that a new design decision -- with its rationale, consequences, and rejected alternatives -- has been formally recorded.

The Human (markers) file classification enforces the boundary between these structured signs and free-form prose. In a file classified as Human (markers), the designer writes all narrative content -- the descriptions, rationale, and design intent. The agent writes only lifecycle markers, and only through apply_marker.py. This is constitution principle T2 in action: the boundary preserves the distinction between design intent (human-authored) and implementation state (agent-maintained).

The practical consequence is that markers serve as an audit trail. Every STATUS flip, every INCORPORATED stamp, every DECISION_APPEND entry records which plan triggered it and when. A designer reviewing product-design-as-intended.md can trace any lifecycle change back to the plan that caused it. The signification is not just labeling -- it is accountable record-keeping.

For the theoretical foundations of signification systems and their role in SEJA's design, see Software as Designed Communication.

Common Mistakes

Writing markers by hand instead of via apply_marker.py
Manually typing a <!-- STATUS: implemented | ... --> comment into a design-intent file bypasses format validation, transition-rule enforcement, and the audit trail. check_human_markers_only.py will flag the write as a prose mutation during post-skill. Always use apply_marker.py -- it validates the marker format against allowed regular expressions, checks that the state transition is permitted, and records the plan ID for traceability.
Using STATUS markers on non-design files
STATUS markers belong on entries within files registered in the As-Intended / As-Coded Registry in product-design/conventions.md -- specifically, the as-intended files like product-design/product-design-as-intended.md. Applying STATUS markers to arbitrary Markdown files, plans, or output artifacts has no governance effect: the marker tooling does not track those files, and the promote workflow (/explain drift --promote) will not find them.
Confusing implemented with established
implemented means the item has been built -- a plan executed it, and the code exists. established means the designer has reviewed the implementation, confirmed it matches intent, and promoted it via /explain drift --promote. The distinction matters: an implemented item is still subject to review and may be revised. An established item is confirmed as the accepted design-to-code mapping. Skipping the promotion step leaves the design layer in a permanently provisional state.
Skipping the AskUserQuestion confirmation
Running apply_marker.py without first asking the designer for confirmation violates the human-in-the-loop governance model. The confirmation step is not ceremony -- it is the moment where the designer exercises authority over what gets recorded as the lifecycle state of their design intent. An agent that writes markers autonomously is making governance decisions on the designer's behalf, which undermines constitution principle T2.
