The Metacommunication Message

The metacommunication message is a SEJA project's highest-authority design artifact. This chapter explains what it is, how to write one using the Extended Metacommunication Template, why the I/you phrasing rule matters, and how to avoid common pitfalls.

What Is a Metacommunication Message

In semiotic engineering, software is understood as a designer's deputy -- an artifact that communicates the designer's message to the user on the designer's behalf. The metacommunication message makes this implicit communication explicit. It is the designer's canonical first-person statement to the user, expressing:

"Here is my understanding of who you are, what I've learned you want or need to do, in which preferred ways, and why. This is the system that I have therefore designed for you, and this is the way you can or should use it in order to fulfill a range of purposes that fall within this vision."

This template, drawn from semiotic engineering theory, structures every metacommunication message in SEJA. It is always voiced in first person: the designer as "I," the user as "you." Third-person restatements are never permitted as the canonical form.

In a SEJA project, the metacommunication message lives in §11 (Global Metacommunication Vision) of product-design/product-design-as-intended.md. It is the highest-authority artifact in the design layer alongside the constitution: all other design decisions -- entity hierarchies, permission models, UX patterns, feature-level intentions -- are ultimately accountable to it. No plan or implementation step may contradict the metacommunication message without an explicit decision record (D-NNN) approved by the designer.

The metacommunication message is not a feature list, a README, or a mission statement. It is the designer's personal, first-person communication about what they understand the user to be and what they have designed for them. For the semiotic engineering theory that underpins this concept, see Software as Designed Communication.

The following section walks through the practical process of writing a metacommunication message using SEJA's interview-driven design workflow.

How to Write a Metacommunication Message

SEJA's /design skill includes a dedicated interview mode (Mode 5: Interview-Driven) that guides the designer through writing a metacommunication message. The interview covers five dimensions drawn from the Extended Metacommunication Template (EMT):

  1. Who are your users? -- Target users, personas, their backgrounds, expertise levels, and contexts of use.
  2. What problems do they face? -- Pain points, problem scenarios, unmet needs, and frustrations with current solutions.
  3. How should they solve them? -- Design solutions, workflows, interaction patterns, and the system's approach to addressing the identified problems.
  4. What should they know? -- Domain knowledge the user needs, constraints they should be aware of, and conceptual models they must understand.
  5. What is the overall metacommunication vision? -- The unified I/you message that weaves the preceding four dimensions into a single coherent designer-to-user statement.

The Interview Process

To write a metacommunication message, invoke /design --mode interview. The process unfolds in four phases:

Phase A: Open-Ended Interview
The agent asks open-ended questions covering the five EMT dimensions. There is no fixed question order -- the conversation adapts based on your answers. Each exchange is recorded as a triple: the agent's question, your verbatim response, and the agent's interpretation of how your answer maps to design fields. The transcript is saved to specs/design-interview-YYYYMMDD.md.
Phase B: Synthesis
The agent iterates over every design field and assigns a confidence level to each: DS (directly stated by the designer), INF (inferred from context), or PAC (proposed by the agent and confirmed by the designer). The synthesis is written to specs/design-confidence-YYYYMMDD.md.
Phase C: Confirmation
Security-critical fields (permission model, validation constants, constitution invariants) require mandatory confirmation -- no inferred values are accepted without explicit designer approval. Other inferred fields are batched for review. Any gaps are filled with focused follow-up questions.
Phase D: Instantiation
The confirmed field values are used to instantiate the project's design files, including the metacommunication message in §11 of product-design/product-design-as-intended.md.

Tip: If you already have a metacommunication message drafted, you can provide it at invocation time. The interview will treat it as a pre-answered Section 0.1 and skip the vision question, extracting project name, description, target user type, and primary use case as hints for subsequent questions.

The I/you phrasing rule applies to the final message produced by this process. The following section explains why this rule exists and how to verify your message conforms to it.

The I/You Phrasing Rule

Constitution principle T4 mandates that the metacommunication message is always voiced in first person -- the designer as "I," the user as "you." This is not a stylistic preference; it is a structural requirement grounded in semiotic engineering theory.

Why First Person Is Mandatory

The I/you frame is the semiotic contract between the designer and the user. When a designer writes "I designed this for you because I understand that you need..." they are taking personal responsibility for the design decisions. They are asserting that a specific person studied a specific user's situation and made deliberate choices in response to it. This directness is the metacommunication message's defining quality.

Third-person rewrites -- "The system provides..." or "Users can..." -- sever this relationship. They anonymize the designer, obscure the intentionality of the design, and reduce the message to a feature description. Passive-voice formulations ("Privacy is enforced with minimal friction") are equally problematic: they describe a property of the system without attributing it to a designer's deliberate choice for a specific user.

How to Self-Check Phrasing

Read every sentence of your metacommunication message aloud as if you were speaking directly to your user. If a sentence cannot naturally be voiced as the designer addressing the user, it needs rephrasing. Two tests:

  • The "I" test: Does the sentence begin with or contain "I" (the designer)? If the subject is "the system," "the application," or "the feature," rephrase.
  • The "you" test: Does the sentence address "you" (the user) or refer to "the user," "users," or "they"? If the latter, rephrase to address the user directly.

Common Mistakes

Writing in third person
A metacommunication message that says "The system provides automated backups" or "Users can configure their dashboard" has lost the designer's voice. Rephrase as: "I have designed automated backups for you because I know you cannot afford to lose work" or "I want you to be able to arrange your dashboard the way that makes sense for your workflow." The I/you frame is not optional -- it is what distinguishes a metacommunication message from a feature list.
Conflating the metacommunication message with a README
A README describes what the software does and how to install it. A metacommunication message expresses what the designer understands about the user and why the software was designed the way it was. The two serve different audiences and purposes. The README is for anyone evaluating or setting up the software; the metacommunication message is the designer's personal communication to the user about the design intent behind the system. If your message reads like installation instructions or a feature catalogue, it is a README, not a metacommunication message.
Making the message too abstract
A message that says "I want you to have a good experience" or "I have designed this system to be useful" communicates nothing specific. Every paragraph should contain concrete "I want you to..." or "I have designed... because I know you..." statements that a reader can verify against the actual system. If you cannot point to a specific design decision that implements what the message claims, the message is too abstract.
Forgetting to update the message when design evolves
The metacommunication message is not written once and forgotten. As the designer's understanding of the user deepens -- through UX research, problem scenario analysis, or field observation -- the message should evolve to reflect that new understanding. An outdated metacommunication message creates a gap between what the system claims to be for and what it actually does. Use /design update metacomm to revise the message when your understanding changes.

The Constitution

A SEJA project constitution declares the immutable principles that every skill, agent, and plan must observe. It is the first artifact loaded by pre-skill -- before conventions, standards, or any other reference -- and its rules take precedence over everything else. This chapter explains what a constitution contains, how to write and maintain one, and why immutable principles are essential for governing agent behavior.

What a Constitution Contains

Every constitution follows the same four-section structure, defined in the template at .claude/references/template/constitution.md. Each section serves a distinct governance purpose:

Section Purpose Typical entries
Technical Principles Non-negotiable architectural decisions that shape how the system is built. Lifecycle discipline, file classification rules, authoring boundaries, voice and phrasing rules.
Quality Principles Quality gates that cannot be bypassed -- the standards the project is committed to regardless of schedule pressure. Design-intent authority, epistemic posture requirements, governance-plus-epistemic mandate.
Security Invariants Security rules that must never be relaxed without explicit sign-off from the project lead. Private-content isolation, hook-bypass controls, credential handling rules.
Compliance Requirements Regulatory, contractual, or policy obligations the project is bound by. Repository visibility rules, sync-boundary constraints, data-residency requirements.

Every entry in the constitution is a row in a principles table with three columns: a stable identifier (T1, Q2, S1, C1, etc.), the principle itself, and a rationale explaining why the rule exists. The rationale is not optional -- it is what allows the agent (and future maintainers) to judge edge cases rather than blindly following the letter of the rule.

Writing and Maintaining a Constitution

Starting from the Template

When you run /design on a new project (or select the "Constitution" option from the update menu), SEJA copies the template from .claude/references/template/constitution.md into product-design/constitution.md. The template contains placeholder rows with {{…}} tokens and HTML comments showing examples for each section. Replace the placeholders with your project's actual commitments and delete the example comments.

Adding Principles over Time

New principles often emerge from design decisions. When a D-NNN decision record in product-design-as-intended.md identifies a commitment that should be immutable -- one that should never be overridden by a plan or implementation step without explicit approval -- promote it to a constitution entry. Assign the next available identifier in the appropriate section (e.g., T5, Q4) and write a rationale that explains why this rule exists.

The Amendment Protocol

Constitutions change rarely, and every change requires:

  1. Explicit approval from the project lead (the designer).
  2. A new version entry in the constitution's Changelog section, recording the date and what changed.

This protocol ensures that constitution changes are deliberate and auditable. An agent cannot amend the constitution unilaterally -- the file is classified as Human, meaning only the designer writes to it.

Constitution vs. Conventions vs. Standards

Three different artifacts capture project rules at different levels of mutability:

Constitution (product-design/constitution.md)
Immutable principles. Loaded first by pre-skill. Violations are blocking -- they must be resolved before commit. Change requires explicit designer approval and a changelog entry.
Conventions (product-design/conventions.md)
Project structure: directory paths, stack choices, key file locations, review configuration. Mutable -- updated when the stack changes or the project reorganizes. Does not carry governance weight.
Standards (product-design/standards.md, product-design/design-standards.md)
Engineering standards: coding patterns, testing rules, UX patterns, accessibility requirements. Mutable -- Human / Agent classification, so both the designer and the agent can update them. Advisory rather than blocking unless a constitution principle elevates a specific standard.

The decision rule: if a commitment should survive any refactoring, any stack change, and any team turnover, it belongs in the constitution. If it describes how the project is structured today, it belongs in conventions. If it describes how code should be written, it belongs in standards.

With the mechanics of writing and maintaining a constitution covered, the next section explains why immutable principles are worth the governance overhead.

Why Immutable Principles Matter

The constitution is the first artifact loaded during pre-skill's constitution stage. It enters the agent's context before conventions, before skill-specific references, and before the plan being executed. This loading order is deliberate: it means every subsequent decision the agent makes is bounded by the constitution's constraints.

Without immutable principles, an agent operating under schedule pressure or optimization heuristics can silently drift from the designer's commitments. A plan might skip review steps to save time. An implementation might bypass the Human (markers) boundary because direct writes are faster than routing through apply_marker.py. A critique might overlook a security invariant because it was not salient in the current context.

The constitution prevents this drift by making certain commitments non-negotiable. When /critique validate runs, it checks the agent's output against the constitution's principles and classifies violations as blocking. The agent cannot merge a change that contradicts a constitution entry without an explicit D-NNN decision record approved by the designer -- and that decision record itself becomes part of the project's audit trail.

This is the governance half of what SEJA calls the "governable and epistemic" thesis: immutable principles provide the governance floor, while epistemic mechanisms (gap detection, drift surfacing, uncertainty tracking) provide the awareness ceiling. Neither alone is sufficient. For the theoretical foundations of this thesis, see The Governable AND Epistemic Thesis.

Common Mistakes

Putting mutable conventions in the constitution
Directory paths, stack choices, and other structural details change as a project evolves. If these are encoded as constitution principles, every reorganization requires a formal amendment. Put structural details in product-design/conventions.md instead, and reserve the constitution for commitments that should survive any refactoring.
Writing principles without rationale
The rationale column in the principles table is not optional. A principle without a rationale is an unexplained rule that the agent cannot reason about at the edges. When an edge case arises, the agent needs the "why" to determine whether the principle applies or whether the case falls outside its scope. Always explain why the rule exists.
Making the constitution too long
The constitution is loaded into every agent context window via pre-skill. A bloated constitution consumes token budget that could be used for the actual task. Keep the constitution focused on genuinely immutable commitments -- typically 4 to 12 principles total. If a rule is important but not immutable, it belongs in standards, not the constitution.
Confusing the constitution with standards
Standards (product-design/standards.md) are mutable engineering rules that evolve as the project matures. Constitution principles are immutable commitments that require explicit designer approval to change. A coding convention ("use snake_case for function names") is a standard. A governance commitment ("no plan may bypass the pre-commit hook") is a constitution principle. Putting standards in the constitution makes the constitution noisy and makes standards unnecessarily hard to update.

Design Intent Files

SEJA maintains a pair of parallel design files for every project: one that records what the designer intends the system to be, and one that records what the system actually is. This chapter explains why that split exists, walks through the structure of the primary design-intent file, describes the workflow for promoting items from one lifecycle state to the next, and surfaces the design trade-offs behind the marker system that governs these files.

The As-Intended / As-Coded Split

Every SEJA project maintains two complementary artifacts that together capture the full picture of a system's design:

product-design-as-intended.md
The designer's vision -- what the system should be. This file is classified as Human (markers): its prose is authored exclusively by the human designer. Agents may not write free-form text into it. They may only apply structured lifecycle markers (STATUS, INCORPORATED, DECISION_APPEND, CHANGELOG_APPEND) through apply_marker.py, and only after explicit confirmation from the designer.
product-design-as-coded.md
The implementation state -- what the system actually is right now. This file is classified as Agent: it is maintained automatically by post-skill and designated skill steps. The designer does not hand-edit it.

The As-Intended / As-Coded Registry in product-design/conventions.md is the single source of truth for which file pairs exist in a project. It maps each as-intended file and section to its as-coded counterpart:

As-Intended file Section As-Coded counterpart
product-design-as-intended.md §0--§17 design intent + Decisions + CHANGELOG product-design-as-coded.md
product-design-as-intended.md §15 designed journeys product-design-as-coded.md § Journey Maps
ux-research-results.md all (personas, scenarios, journeys, CHANGELOG) --

This split enforces Constitution principle T2: design intent is human-authored; implementation state is agent-maintained. The boundary is not merely a convention -- it is validated at commit time by check_human_markers_only.py, which rejects any agent prose writes to Human (markers) files.

The gap between what the designer intends and what the system currently implements is the subject of the /explain drift command, which compares the two files and surfaces misalignments before they compound into design debt.

The reference table above covers the structure of the as-intended file in detail. The following section walks through its eighteen numbered sections.

Structure of product-design-as-intended.md

The design-intent file is organized into eighteen numbered sections (§0 through §17), followed by a Decisions section and a CHANGELOG. Together they form the project's unified working intent -- the single artifact that records what the designer wants the system to be across every design dimension.

Section inventory

§ Section Purpose
0 Planned Changes Upcoming design changes with target version and rationale
1 Platform Purpose What the system is and why it exists
2 Entity Hierarchy Domain model: entities, relationships, ownership tree
3 Domain-Specific Concepts Terminology and concepts unique to the project's domain
4 Permission Model System-level roles and resource-level access rules
5 Content Authoring and Attribution Authoring model and marker attribution rules
6 Content Import and Export Data portability: import formats, export mechanisms
7 User Community and Localization i18n strategy and community features
8 User Experience Patterns (Domain-Driven) UX patterns derived from domain needs
9 Administrative Domain Admin capabilities and operational controls
10 Validation Constants (Domain) Field constraints: lengths, ranges, formats
11 Global Metacommunication Vision The designer's I/you message to the user (highest-authority artifact)
12 Extended Metacommunication Template Guiding Questions EMT answers: who the users are, what they need, how the system helps
13 Solution Representations How the system represents its solutions to the user
14 Per-Feature Metacommunication Intentions Feature-level I/you statements for individual capabilities
15 Designed User Journeys JM-TB-NNN designed journey maps linking personas to tasks
16 Conceptual Design Delta Structural changes since the last design iteration
17 Delta Rationale Why each delta was introduced

Decisions section

Below the eighteen numbered sections, a ## Decisions section holds DDR-shaped (Design Decision Record) entries under ### D-NNN: Title headings. Each entry records:

  • Context -- the situation that prompted the decision
  • Decision -- what was decided
  • Consequences -- downstream effects
  • Rejected Alternatives -- what was considered and set aside

Decision IDs (D-001, D-002, ...) are auto-assigned by apply_marker.py --marker DECISION_APPEND. They use a namespace orthogonal to REQ-TYPE-NNN requirement markers -- the two are never intermixed.

CHANGELOG section

A ## CHANGELOG at the bottom of the file provides a chronological record of marker flips and design-intent changes. Entries are appended via apply_marker.py --marker CHANGELOG_APPEND, never written by hand. The CHANGELOG serves as the audit trail for when and why design-intent items changed lifecycle state.

File classification

The entire file carries the Human (markers) classification. This means:

  • Prose (section content, decision rationale, entity descriptions) is written exclusively by the human designer.
  • Markers (STATUS comments, DECISION_APPEND entries, CHANGELOG_APPEND lines) are written by the agent through apply_marker.py, but only after the designer confirms via an explicit prompt.
  • Enforcement: check_human_markers_only.py runs during post-skill and rejects any agent prose mutations that bypass the marker pathway.

With the file's structure established, the next section explains how design-intent items advance through their lifecycle.

The Promote Workflow

Design-intent items move through a four-state lifecycle tracked by STATUS markers. The state machine enforces a strict forward progression: 

proposed  →  implemented  →  established  →  superseded

Regression (moving backward, such as established back to implemented) is rejected by apply_marker.py. Each transition requires a plan ID and date.

The primary promotion path -- moving items from implemented to established -- uses the /explain drift --promote command and proceeds in two phases:

Phase 3a: Decision entry proposal

/explain drift --promote scans product-design-as-intended.md for items marked STATUS: implemented. For each one, it generates a DDR-shaped decision entry proposal and writes it to _output/promote-proposals/promote-proposal-plan-<id>.md. The designer reviews the proposal, edits it to their voice, and copies approved entries into the ## Decisions section of the design-intent file.

Phase 3b: STATUS marker flip

Once the decision entry is in place, the designer runs /explain drift --apply-markers plan-<id>. This invokes apply_marker.py to flip the STATUS marker from implemented to established. The script verifies the entry heading exists (using heading-only grep to avoid matching prose) before applying the transition.

Tip: The two-phase split exists to preserve the designer's voice. Phase 3a generates a proposal that the designer edits before it enters the permanent record. Phase 3b is a mechanical marker flip that happens only after the human-authored entry is confirmed.

The rationale behind the marker types and the as-intended/as-coded split is explored in the following section.

Design Decisions and Trade-offs

Why three marker types

SEJA's marker system uses three distinct marker types, each serving a different governance purpose:

STATUS markers
Track the lifecycle of individual design-intent items through the proposed → implemented → established → superseded state machine. STATUS markers answer: "has this design intention been realized in code, and has that realization been confirmed?"
INCORPORATED markers
Record when research findings have been absorbed into design intent. An INCORPORATED stamp links a research log to the design-intent section it informed, creating traceability from discovery to design.
DECISION_APPEND / CHANGELOG_APPEND
Structured append operations that add new entries to the Decisions or CHANGELOG sections. These are not status transitions -- they are content additions that extend the design record without modifying existing prose.

Each type has a specific regex-validated format, preventing free-form mutations from slipping through the marker pathway.

Why the as-intended / as-coded split

The split enforces Constitution principle T2: design intent is human-authored; implementation state is agent-maintained. Without this boundary, two failure modes emerge:

  • Agent drift: if the agent can write design intent, it can silently rewrite the designer's vision to match what it built, eliminating the gap signal that /explain drift relies on.
  • Stale intent: if the designer must also maintain the implementation record, the as-coded file falls behind, and drift detection produces false positives that erode trust.

The split is not duplication -- each file serves a distinct audience. The as-intended file is the designer's authoritative statement of what should exist. The as-coded file is the agent's honest report of what does exist. The productive tension between them is the engine of SEJA's governance model.

Why path-scoped rules

Rules in .claude/rules/ are auto-loaded by Claude when editing files that match the rule's scope. This means governance constraints are applied contextually: a rule about product-design/ files loads when the agent touches those files, but does not clutter the context window when working on unrelated code. Path scoping keeps governance lightweight by loading constraints only when they are relevant. For details on the marker mechanics, see The Marker System.

Common Mistakes

Hand-editing Human (markers) files
Writing prose directly into product-design-as-intended.md or ux-research-results.md as an agent, instead of using apply_marker.py. The check_human_markers_only.py verifier catches this during post-skill and rejects the mutation. The fix: always use apply_marker.py with the appropriate --marker type (STATUS, INCORPORATED, DECISION_APPEND, or CHANGELOG_APPEND) and wait for designer confirmation via the AskUserQuestion prompt.
Treating as-coded as authoritative over as-intended
Assuming that because product-design-as-coded.md reflects the current implementation, it represents the "real" design. It does not. The as-intended file is the designer's authoritative vision; the as-coded file is the agent's report of current state. When the two diverge, the as-intended file is correct and the implementation needs to catch up -- not the other way around. Use /explain drift to surface and manage these gaps.
Forgetting the Registry when adding new design files
Creating a new as-intended or as-coded file without registering it in the As-Intended / As-Coded Registry in product-design/conventions.md. Unregistered files are invisible to /explain drift, post-skill DONE marker proposals, and /design template generation. Always add a row to the Registry when introducing a new design-intent artifact pair.
Confusing STATUS markers with git status
STATUS markers (<!-- STATUS: implemented | plan-000123 | 2026-07-01 -->) track the design lifecycle of an item -- whether a design intention has been proposed, implemented, established, or superseded. They have no relation to git status, which tracks file modifications in the working tree. A file can have STATUS: implemented markers on all its sections while showing as unmodified in git status, and vice versa.

The Marker System

SEJA uses lifecycle markers to track the status of design-intent items as they move from proposal through implementation to establishment. Markers are the mechanism by which the agent records lifecycle state changes in human-authored files without altering the designer's prose. All marker writes go through a single script -- apply_marker.py -- which validates format, enforces transition rules, and requires explicit human confirmation before every write.

Marker Types

SEJA's marker system comprises five marker types organized in three functional categories: status tracking (STATUS), research absorption (INCORPORATED), structured-entry appending (DECISION_APPEND, CHANGELOG_APPEND), and traceability (REQ_TRACED_BY). Each type serves a distinct governance purpose and follows a specific format.

Type Purpose Format Triggered By
STATUS Tracks lifecycle state of design-intent items <!-- STATUS: <value> | <plan-id> | <date> --> Post-skill (agent proposes, human confirms)
INCORPORATED Records absorption of research findings into design <!-- INCORPORATED: <plan-id> | <date> --> Post-skill after research findings are acted upon
DECISION_APPEND Appends DDR-shaped decision entries to the Decisions section ### D-NNN: <title> with Context, Decision, Consequences /research step 9b or /design Phase C
CHANGELOG_APPEND Appends timestamped entries to the CHANGELOG section Table row: | <date> | <action> | <source> | Post-skill after marker flips or design changes
REQ_TRACED_BY Annotates REQ markers with traceability links to implementing plans <!-- REQ-TYPE-NNN | traced_by: <value> --> Post-skill after plan implementation traces to a REQ

STATUS: Lifecycle State Machine

The STATUS marker is an inline HTML comment placed immediately before a section heading. It is invisible in rendered Markdown but machine-parseable by agent tooling. The state machine enforces a strict progression: 

proposed  →  implemented  →  established  →  superseded

Each transition requires a plan ID and date. Regressions (such as established → implemented) are rejected by the script. A STATUS marker in context looks like this: 

<!-- STATUS: implemented | plan-000178 | 2026-04-02 -->
### Platform Purpose

Legacy uppercase markers (STATUS: IMPLEMENTED) from pre-2.8.3 files are still recognized. When a Phase 3b promotion flip targets a legacy marker, apply_marker.py replaces the line in place rather than stacking a new marker above it.

ESTABLISHED: The Promotion Stamp

When a human confirms that an implemented item should be promoted to established, two things happen: the STATUS marker is flipped to established, and an ESTABLISHED stamp is applied. The stamp records the promotion event: 

<!-- ESTABLISHED: plan-000178 | 2026-04-02 | v2.8.3 -->

The version field (vX.Y.Z) is optional. Projects without semantic versioning use the date alone.

INCORPORATED: Research Absorption

The INCORPORATED marker records that research findings from a specific plan or research log have been absorbed into the design-intent file. It is inserted before the heading of the section that was informed by the research: 

<!-- INCORPORATED: plan-000268 | 2026-04-11 -->
### Entity Hierarchy

DECISION_APPEND and CHANGELOG_APPEND: Structured Entries

These two marker types do not modify existing lines -- they append new structured content to designated sections. DECISION_APPEND adds a DDR-shaped decision entry (### D-NNN: Title with Context, Decision, Consequences fields) to the ## Decisions section. The D-NNN ID is auto-assigned by scanning existing entries. CHANGELOG_APPEND adds a timestamped row to the ## CHANGELOG table.

The reference above catalogues each marker type and its format. The following section shows how to apply these markers in practice using the apply_marker.py script.

Using apply_marker.py

apply_marker.py is the sole write path for files classified as Human (markers). Agents that need to update a marker must invoke this script rather than using Edit or Write on the file directly. The companion verifier check_human_markers_only.py rejects any prose mutations that bypass this path.

Command-Line Interface

python .claude/skills/scripts/apply_marker.py \
    --file <path> \
    --id <entry-id> \
    --marker <kind> \
    --value <value> \
    [--plan <plan-id>] \
    [--date <YYYY-MM-DD>] \
    [--note <text>] \
    [--dry-run]
Parameter Required Description
--file Yes Path to the target Human (markers) file
--id Yes Entry ID or section heading to locate (e.g., "Platform Purpose" or "D-001")
--marker Yes Marker kind: STATUS, ESTABLISHED, INCORPORATED, DECISION_APPEND, CHANGELOG_APPEND, or REQ_TRACED_BY
--value Conditional Marker value (e.g., implemented for STATUS, entry text for DECISION_APPEND). Required for STATUS, CHANGELOG_APPEND, DECISION_APPEND, and REQ_TRACED_BY; ignored by stamp-kind markers (ESTABLISHED, INCORPORATED)
--plan Depends Plan ID (required for ESTABLISHED and INCORPORATED; recommended for STATUS)
--date No Date in YYYY-MM-DD format (defaults to today in UTC)
--note No Optional annotation text
--dry-run No Preview the change without writing to disk

The Confirmation Flow

Before invoking apply_marker.py, the agent must ask the designer for confirmation using AskUserQuestion. This is not optional -- it is the human-in-the-loop governance check that ensures no lifecycle state change happens without explicit designer approval. The flow is:

  1. The agent identifies that a marker write is needed (e.g., post-skill detects a plan step was completed).
  2. The agent presents the proposed change via AskUserQuestion: which file, which entry, which marker, which value.
  3. The designer confirms or rejects.
  4. On confirmation, the agent runs apply_marker.py with the agreed parameters.

Examples

Marking a section as implemented
python .claude/skills/scripts/apply_marker.py \
    --file product-design/product-design-as-intended.md \
    --id "Platform Purpose" \
    --marker STATUS \
    --value implemented \
    --plan plan-000178

This inserts <!-- STATUS: implemented | plan-000178 | 2026-07-15 --> immediately before the ### Platform Purpose heading.

Recording research incorporation
python .claude/skills/scripts/apply_marker.py \
    --file product-design/product-design-as-intended.md \
    --id "Entity Hierarchy" \

Appending a decision entry
python .claude/skills/scripts/apply_marker.py \
    --file product-design/product-design-as-intended.md \
    --id "_" \

Previewing a change

Add --dry-run to any command to see what would be written without modifying the file. The script prints the marker line and target location, then exits without writing.

With the practical mechanics established, the following section explains why markers are structured this way and what role they play in SEJA's governance model.

Markers as Designed Signification

Markers in SEJA are not arbitrary metadata tags. They are a designed signification system -- a set of conventionalized expression-content pairs where each marker type carries a specific, governance-relevant meaning. This is a deliberate application of the semiotic engineering concept of signification systems, where signs are designed to convey particular meanings within a particular context of use.

The STATUS marker signifies where a design-intent item stands in its lifecycle: has it been proposed, built, confirmed by the designer, or superseded? The INCORPORATED marker signifies that external knowledge (research findings) has been absorbed into the design layer. The DECISION_APPEND marker signifies that a new design decision -- with its rationale, consequences, and rejected alternatives -- has been formally recorded.

The Human (markers) file classification enforces the boundary between these structured signs and free-form prose. In a file classified as Human (markers), the designer writes all narrative content -- the descriptions, rationale, and design intent. The agent writes only lifecycle markers, and only through apply_marker.py. This is constitution principle T2 in action: the boundary preserves the distinction between design intent (human-authored) and implementation state (agent-maintained).

The practical consequence is that markers serve as an audit trail. Every STATUS flip, every INCORPORATED stamp, every DECISION_APPEND entry records which plan triggered it and when. A designer reviewing product-design-as-intended.md can trace any lifecycle change back to the plan that caused it. The signification is not just labeling -- it is accountable record-keeping.

For the theoretical foundations of signification systems and their role in SEJA's design, see Software as Designed Communication.

Common Mistakes

Writing markers by hand instead of via apply_marker.py
Manually typing a <!-- STATUS: implemented | ... --> comment into a design-intent file bypasses format validation, transition-rule enforcement, and the audit trail. check_human_markers_only.py will flag the write as a prose mutation during post-skill. Always use apply_marker.py -- it validates the marker format against allowed regular expressions, checks that the state transition is permitted, and records the plan ID for traceability.
Using STATUS markers on non-design files
STATUS markers belong on entries within files registered in the As-Intended / As-Coded Registry in product-design/conventions.md -- specifically, the as-intended files like product-design/product-design-as-intended.md. Applying STATUS markers to arbitrary Markdown files, plans, or output artifacts has no governance effect: the marker tooling does not track those files, and the promote workflow (/explain drift --promote) will not find them.
Confusing implemented with established
implemented means the item has been built -- a plan executed it, and the code exists. established means the designer has reviewed the implementation, confirmed it matches intent, and promoted it via /explain drift --promote. The distinction matters: an implemented item is still subject to review and may be revised. An established item is confirmed as the accepted design-to-code mapping. Skipping the promotion step leaves the design layer in a permanently provisional state.
Skipping the AskUserQuestion confirmation
Running apply_marker.py without first asking the designer for confirmation violates the human-in-the-loop governance model. The confirmation step is not ceremony -- it is the moment where the designer exercises authority over what gets recorded as the lifecycle state of their design intent. An agent that writes markers autonomously is making governance decisions on the designer's behalf, which undermines constitution principle T2.

UX Research Artifacts

SEJA projects ground their design in structured UX research artifacts: personas that model target users, problem scenarios that capture pain points motivating the design, and discovered journeys that record how users actually interact with the system. These artifacts live in product-design/ux-research-results.md, classified as Human (markers) -- prose is human-authored only, and agents may write only INCORPORATED markers and CHANGELOG appends via apply_marker.py.

This chapter documents the structure, purpose, and maintenance of each artifact type, and explains the critical distinction between discovered journeys (evidence from observation) and designed journeys (intent from the designer).

Personas

In SEJA's context, personas are structured archetypes of the project's target users. They are not exhaustive user profiles but focused models that capture the goals, frustrations, and relevant context that shape design decisions. Each persona answers a slice of the metacommunication message's opening clause: "Here is my understanding of who you are."

Where Personas Live

Personas are defined in sections 1 and 2 of product-design/ux-research-results.md. Section 1 contains a Persona Inventory table (summary) and full persona profiles. Section 3 (Cross-Reference Map) links each persona to the design artifacts it feeds.

How Personas Are Created

The /design skill generates personas during its Mode 5 (Interview-Driven) workflow. Phase A collects open-ended information about the project's target users through conversational Q&A. Phase B synthesizes the interview data into structured persona entries, assigning stable IDs and mapping goals to the Extended Metacommunication Template (EMT) dimensions. The designer reviews and confirms each persona during Phase C before the artifacts are written.

Persona Entry Structure

Each persona entry follows a fixed structure with stable identifiers:

Field Format Purpose
ID R-P-NNN Stable identifier; never reused, even for superseded personas
Name Short given name Human-readable label for cross-references
Role / Archetype Free text The user's primary relationship to the system
Bio Narrative paragraph Background, expertise, and context for design reasoning
Goals G-NNN entries What the persona wants or needs to accomplish; referenced by problem scenarios and design features
Key Frustrations Bullet list Pain points that motivate design decisions
Relevant Context Structured fields Technical proficiency, usage frequency, domain knowledge

Persona IDs use the R-P-NNN format (zero-padded, starting at 001). IDs are stable and never reassigned -- a superseded persona gets a new ID rather than reusing the old one.

The reference tables above describe the structure of individual personas. The following section covers problem scenarios -- the artifacts that connect personas to the design features they motivate.

Problem Scenarios

Problem scenarios are structured narratives that capture specific pain points users experience without SEJA (or with earlier versions of it). Each scenario describes a concrete situation where a user's goals are frustrated, grounding abstract persona frustrations in observable, testable contexts.

Where Problem Scenarios Live

Problem scenarios are defined in section 2 of product-design/ux-research-results.md. The Cross-Reference Map in section 3 links each scenario to the design artifacts it feeds -- typically specific sections of product-design/product-design-as-intended.md and per-feature metacommunication intentions.

Scenario Entry Structure

Each problem scenario entry includes:

Field Format Purpose
ID R-PS-NNN Stable identifier for cross-referencing
Persona(s) R-P-NNN references Which personas experience this pain point
Goals G-NNN references Which persona goals are frustrated
Setting Narrative sentence When and where the scenario occurs
Narrative Multi-paragraph prose What happens, why it is a problem, what the user cannot do

Connecting Scenarios to Design

The traceability chain runs: Persona (who) → Goal (what they need) → Problem Scenario (what goes wrong) → Design Feature (what SEJA does about it). The Cross-Reference Map in section 3 of product-design/ux-research-results.md records these links explicitly, mapping each artifact ID to the design-intent section it feeds. This ensures that no design feature exists without a traceable motivation and no problem scenario is left unaddressed without a conscious decision to defer it.

With personas and problem scenarios defining what users need and where they struggle, the next section covers discovered journeys -- the artifacts that record how users actually behave once the system is in use.

Discovered Journeys

SEJA distinguishes two kinds of journey maps, identified by their ID prefixes. Understanding this distinction is essential for maintaining accurate design records.

Discovered vs. Designed Journeys

Attribute Discovered Journeys Designed Journeys
ID prefix JM-E-NNN JM-TB-NNN
Source Field observation of actual use Designer's planned interaction flow
Nature Evidence (what happened) Intent (what should happen)
Location (as-intended) ux-research-results.md §5 product-design-as-intended.md §15
Location (as-coded) N/A product-design-as-coded.md Journey Maps
Maintained by Human (researcher/designer) Human (markers) / Agent (as-coded)

The distinction matters because discovered journeys are evidence -- they record what actually happened when a user interacted with the system, including unexpected paths, workarounds, and breakdowns. Designed journeys are intent -- they describe the interaction flow the designer planned. When discovered journeys diverge from designed journeys, the gap is a signal for design review, not a bug to fix.

Recording a Discovered Journey

Discovered journeys are recorded by the human designer or researcher in section 5 of product-design/ux-research-results.md. The section is structurally append-only: new journeys are added at the end; existing entries are never removed or reordered.

To record a discovered journey:

  1. Observe the user's actual interaction path during field use of the harness.
  2. Write a narrative entry in ux-research-results.md section 5, assigning the next available JM-E-NNN ID.
  3. Note the personas involved, the context, and any divergence from designed journeys.
  4. If the journey reveals a design gap, record it in the Processing Status table (section 4) for future incorporation into design intent.

Tip: Harness tooling discriminates journey types by ID prefix -- JM-E- for discovered, JM-TB- for designed. Using the wrong prefix will cause the journey to appear in the wrong file context and confuse drift detection.

Common Mistakes

Confusing discovered and designed journeys
Discovered journeys (JM-E-NNN) and designed journeys (JM-TB-NNN) use different ID prefixes, live in different files, and serve different purposes. Discovered journeys are evidence from field observation; designed journeys are intent from the designer. Mixing them up -- recording a planned flow as JM-E-NNN or an observed path as JM-TB-NNN -- corrupts the evidence/intent distinction and confuses drift detection, which relies on the ID prefix to determine where each journey belongs.
Hand-editing the UX research file with agent prose
product-design/ux-research-results.md is classified as Human (markers). All narrative prose must be written by the human designer or researcher. Agents may write only INCORPORATED markers and CHANGELOG_APPEND entries, and only via apply_marker.py after explicit AskUserQuestion confirmation. Direct agent prose writes are rejected by check_human_markers_only.py during post-skill. If an agent needs to propose UX research content, it should present the proposal to the designer for manual incorporation.
Treating personas as exhaustive user descriptions
Personas are design archetypes, not comprehensive user profiles. They capture enough about a user type to ground design reasoning -- goals, frustrations, relevant context -- but they are deliberately simplified. A persona named "Ana" does not describe every semiotic engineer who might use SEJA; she models the concerns and workflow that shape design decisions for that user type. Personas evolve as the designer's understanding grows: new observations may refine existing personas or prompt new ones with fresh R-P-NNN IDs.
