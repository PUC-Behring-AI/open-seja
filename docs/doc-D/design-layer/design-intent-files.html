Design Intent Files

SEJA maintains a pair of parallel design files for every project: one that records what the designer intends the system to be, and one that records what the system actually is. This chapter explains why that split exists, walks through the structure of the primary design-intent file, describes the workflow for promoting items from one lifecycle state to the next, and surfaces the design trade-offs behind the marker system that governs these files.

The As-Intended / As-Coded Split

Every SEJA project maintains two complementary artifacts that together capture the full picture of a system's design:

product-design-as-intended.md
The designer's vision -- what the system should be. This file is classified as Human (markers): its prose is authored exclusively by the human designer. Agents may not write free-form text into it. They may only apply structured lifecycle markers (STATUS, INCORPORATED, DECISION_APPEND, CHANGELOG_APPEND) through apply_marker.py, and only after explicit confirmation from the designer.
product-design-as-coded.md
The implementation state -- what the system actually is right now. This file is classified as Agent: it is maintained automatically by post-skill and designated skill steps. The designer does not hand-edit it.

The As-Intended / As-Coded Registry in product-design/conventions.md is the single source of truth for which file pairs exist in a project. It maps each as-intended file and section to its as-coded counterpart:

As-Intended file Section As-Coded counterpart
product-design-as-intended.md §0--§17 design intent + Decisions + CHANGELOG product-design-as-coded.md
product-design-as-intended.md §15 designed journeys product-design-as-coded.md § Journey Maps
ux-research-results.md all (personas, scenarios, journeys, CHANGELOG) --

This split enforces Constitution principle T2: design intent is human-authored; implementation state is agent-maintained. The boundary is not merely a convention -- it is validated at commit time by check_human_markers_only.py, which rejects any agent prose writes to Human (markers) files.

The gap between what the designer intends and what the system currently implements is the subject of the /explain drift command, which compares the two files and surfaces misalignments before they compound into design debt.

The reference table above covers the structure of the as-intended file in detail. The following section walks through its eighteen numbered sections.

Structure of product-design-as-intended.md

The design-intent file is organized into eighteen numbered sections (§0 through §17), followed by a Decisions section and a CHANGELOG. Together they form the project's unified working intent -- the single artifact that records what the designer wants the system to be across every design dimension.

Section inventory

§ Section Purpose
0 Planned Changes Upcoming design changes with target version and rationale
1 Platform Purpose What the system is and why it exists
2 Entity Hierarchy Domain model: entities, relationships, ownership tree
3 Domain-Specific Concepts Terminology and concepts unique to the project's domain
4 Permission Model System-level roles and resource-level access rules
5 Content Authoring and Attribution Authoring model and marker attribution rules
6 Content Import and Export Data portability: import formats, export mechanisms
7 User Community and Localization i18n strategy and community features
8 User Experience Patterns (Domain-Driven) UX patterns derived from domain needs
9 Administrative Domain Admin capabilities and operational controls
10 Validation Constants (Domain) Field constraints: lengths, ranges, formats
11 Global Metacommunication Vision The designer's I/you message to the user (highest-authority artifact)
12 Extended Metacommunication Template Guiding Questions EMT answers: who the users are, what they need, how the system helps
13 Solution Representations How the system represents its solutions to the user
14 Per-Feature Metacommunication Intentions Feature-level I/you statements for individual capabilities
15 Designed User Journeys JM-TB-NNN designed journey maps linking personas to tasks
16 Conceptual Design Delta Structural changes since the last design iteration
17 Delta Rationale Why each delta was introduced

Decisions section

Below the eighteen numbered sections, a ## Decisions section holds DDR-shaped (Design Decision Record) entries under ### D-NNN: Title headings. Each entry records:

  • Context -- the situation that prompted the decision
  • Decision -- what was decided
  • Consequences -- downstream effects
  • Rejected Alternatives -- what was considered and set aside

Decision IDs (D-001, D-002, ...) are auto-assigned by apply_marker.py --marker DECISION_APPEND. They use a namespace orthogonal to REQ-TYPE-NNN requirement markers -- the two are never intermixed.

CHANGELOG section

A ## CHANGELOG at the bottom of the file provides a chronological record of marker flips and design-intent changes. Entries are appended via apply_marker.py --marker CHANGELOG_APPEND, never written by hand. The CHANGELOG serves as the audit trail for when and why design-intent items changed lifecycle state.

File classification

The entire file carries the Human (markers) classification. This means:

  • Prose (section content, decision rationale, entity descriptions) is written exclusively by the human designer.
  • Markers (STATUS comments, DECISION_APPEND entries, CHANGELOG_APPEND lines) are written by the agent through apply_marker.py, but only after the designer confirms via an explicit prompt.
  • Enforcement: check_human_markers_only.py runs during post-skill and rejects any agent prose mutations that bypass the marker pathway.

With the file's structure established, the next section explains how design-intent items advance through their lifecycle.

The Promote Workflow

Design-intent items move through a four-state lifecycle tracked by STATUS markers. The state machine enforces a strict forward progression: 

proposed  →  implemented  →  established  →  superseded

Regression (moving backward, such as established back to implemented) is rejected by apply_marker.py. Each transition requires a plan ID and date.

The primary promotion path -- moving items from implemented to established -- uses the /explain drift --promote command and proceeds in two phases:

Phase 3a: Decision entry proposal

/explain drift --promote scans product-design-as-intended.md for items marked STATUS: implemented. For each one, it generates a DDR-shaped decision entry proposal and writes it to _output/promote-proposals/promote-proposal-plan-<id>.md. The designer reviews the proposal, edits it to their voice, and copies approved entries into the ## Decisions section of the design-intent file.

Phase 3b: STATUS marker flip

Once the decision entry is in place, the designer runs /explain drift --apply-markers plan-<id>. This invokes apply_marker.py to flip the STATUS marker from implemented to established. The script verifies the entry heading exists (using heading-only grep to avoid matching prose) before applying the transition.

Tip: The two-phase split exists to preserve the designer's voice. Phase 3a generates a proposal that the designer edits before it enters the permanent record. Phase 3b is a mechanical marker flip that happens only after the human-authored entry is confirmed.

The rationale behind the marker types and the as-intended/as-coded split is explored in the following section.

Design Decisions and Trade-offs

Why three marker types

SEJA's marker system uses three distinct marker types, each serving a different governance purpose:

STATUS markers
Track the lifecycle of individual design-intent items through the proposed → implemented → established → superseded state machine. STATUS markers answer: "has this design intention been realized in code, and has that realization been confirmed?"
INCORPORATED markers
Record when research findings have been absorbed into design intent. An INCORPORATED stamp links a research log to the design-intent section it informed, creating traceability from discovery to design.
DECISION_APPEND / CHANGELOG_APPEND
Structured append operations that add new entries to the Decisions or CHANGELOG sections. These are not status transitions -- they are content additions that extend the design record without modifying existing prose.

Each type has a specific regex-validated format, preventing free-form mutations from slipping through the marker pathway.

Why the as-intended / as-coded split

The split enforces Constitution principle T2: design intent is human-authored; implementation state is agent-maintained. Without this boundary, two failure modes emerge:

  • Agent drift: if the agent can write design intent, it can silently rewrite the designer's vision to match what it built, eliminating the gap signal that /explain drift relies on.
  • Stale intent: if the designer must also maintain the implementation record, the as-coded file falls behind, and drift detection produces false positives that erode trust.

The split is not duplication -- each file serves a distinct audience. The as-intended file is the designer's authoritative statement of what should exist. The as-coded file is the agent's honest report of what does exist. The productive tension between them is the engine of SEJA's governance model.

Why path-scoped rules

Rules in .claude/rules/ are auto-loaded by Claude when editing files that match the rule's scope. This means governance constraints are applied contextually: a rule about product-design/ files loads when the agent touches those files, but does not clutter the context window when working on unrelated code. Path scoping keeps governance lightweight by loading constraints only when they are relevant. For details on the marker mechanics, see The Marker System.

Common Mistakes

Hand-editing Human (markers) files
Writing prose directly into product-design-as-intended.md or ux-research-results.md as an agent, instead of using apply_marker.py. The check_human_markers_only.py verifier catches this during post-skill and rejects the mutation. The fix: always use apply_marker.py with the appropriate --marker type (STATUS, INCORPORATED, DECISION_APPEND, or CHANGELOG_APPEND) and wait for designer confirmation via the AskUserQuestion prompt.
Treating as-coded as authoritative over as-intended
Assuming that because product-design-as-coded.md reflects the current implementation, it represents the "real" design. It does not. The as-intended file is the designer's authoritative vision; the as-coded file is the agent's report of current state. When the two diverge, the as-intended file is correct and the implementation needs to catch up -- not the other way around. Use /explain drift to surface and manage these gaps.
Forgetting the Registry when adding new design files
Creating a new as-intended or as-coded file without registering it in the As-Intended / As-Coded Registry in product-design/conventions.md. Unregistered files are invisible to /explain drift, post-skill DONE marker proposals, and /design template generation. Always add a row to the Registry when introducing a new design-intent artifact pair.
Confusing STATUS markers with git status
STATUS markers (<!-- STATUS: implemented | plan-000123 | 2026-07-01 -->) track the design lifecycle of an item -- whether a design intention has been proposed, implemented, established, or superseded. They have no relation to git status, which tracks file modifications in the working tree. A file can have STATUS: implemented markers on all its sections while showing as unmodified in git status, and vice versa.
