The Metacommunication Message

The metacommunication message is a SEJA project's highest-authority design artifact. This chapter explains what it is, how to write one using the Extended Metacommunication Template, why the I/you phrasing rule matters, and how to avoid common pitfalls.

What Is a Metacommunication Message

In semiotic engineering, software is understood as a designer's deputy -- an artifact that communicates the designer's message to the user on the designer's behalf. The metacommunication message makes this implicit communication explicit. It is the designer's canonical first-person statement to the user, expressing:

"Here is my understanding of who you are, what I've learned you want or need to do, in which preferred ways, and why. This is the system that I have therefore designed for you, and this is the way you can or should use it in order to fulfill a range of purposes that fall within this vision."

This template, drawn from semiotic engineering theory, structures every metacommunication message in SEJA. It is always voiced in first person: the designer as "I," the user as "you." Third-person restatements are never permitted as the canonical form.

In a SEJA project, the metacommunication message lives in §11 (Global Metacommunication Vision) of product-design/product-design-as-intended.md. It is the highest-authority artifact in the design layer alongside the constitution: all other design decisions -- entity hierarchies, permission models, UX patterns, feature-level intentions -- are ultimately accountable to it. No plan or implementation step may contradict the metacommunication message without an explicit decision record (D-NNN) approved by the designer.

The metacommunication message is not a feature list, a README, or a mission statement. It is the designer's personal, first-person communication about what they understand the user to be and what they have designed for them. For the semiotic engineering theory that underpins this concept, see Software as Designed Communication.

The following section walks through the practical process of writing a metacommunication message using SEJA's interview-driven design workflow.

How to Write a Metacommunication Message

SEJA's /design skill includes a dedicated interview mode (Mode 5: Interview-Driven) that guides the designer through writing a metacommunication message. The interview covers five dimensions drawn from the Extended Metacommunication Template (EMT):

  1. Who are your users? -- Target users, personas, their backgrounds, expertise levels, and contexts of use.
  2. What problems do they face? -- Pain points, problem scenarios, unmet needs, and frustrations with current solutions.
  3. How should they solve them? -- Design solutions, workflows, interaction patterns, and the system's approach to addressing the identified problems.
  4. What should they know? -- Domain knowledge the user needs, constraints they should be aware of, and conceptual models they must understand.
  5. What is the overall metacommunication vision? -- The unified I/you message that weaves the preceding four dimensions into a single coherent designer-to-user statement.

The Interview Process

To write a metacommunication message, invoke /design --mode interview. The process unfolds in four phases:

Phase A: Open-Ended Interview
The agent asks open-ended questions covering the five EMT dimensions. There is no fixed question order -- the conversation adapts based on your answers. Each exchange is recorded as a triple: the agent's question, your verbatim response, and the agent's interpretation of how your answer maps to design fields. The transcript is saved to specs/design-interview-YYYYMMDD.md.
Phase B: Synthesis
The agent iterates over every design field and assigns a confidence level to each: DS (directly stated by the designer), INF (inferred from context), or PAC (proposed by the agent and confirmed by the designer). The synthesis is written to specs/design-confidence-YYYYMMDD.md.
Phase C: Confirmation
Security-critical fields (permission model, validation constants, constitution invariants) require mandatory confirmation -- no inferred values are accepted without explicit designer approval. Other inferred fields are batched for review. Any gaps are filled with focused follow-up questions.
Phase D: Instantiation
The confirmed field values are used to instantiate the project's design files, including the metacommunication message in §11 of product-design/product-design-as-intended.md.

Tip: If you already have a metacommunication message drafted, you can provide it at invocation time. The interview will treat it as a pre-answered Section 0.1 and skip the vision question, extracting project name, description, target user type, and primary use case as hints for subsequent questions.

The I/you phrasing rule applies to the final message produced by this process. The following section explains why this rule exists and how to verify your message conforms to it.

The I/You Phrasing Rule

Constitution principle T4 mandates that the metacommunication message is always voiced in first person -- the designer as "I," the user as "you." This is not a stylistic preference; it is a structural requirement grounded in semiotic engineering theory.

Why First Person Is Mandatory

The I/you frame is the semiotic contract between the designer and the user. When a designer writes "I designed this for you because I understand that you need..." they are taking personal responsibility for the design decisions. They are asserting that a specific person studied a specific user's situation and made deliberate choices in response to it. This directness is the metacommunication message's defining quality.

Third-person rewrites -- "The system provides..." or "Users can..." -- sever this relationship. They anonymize the designer, obscure the intentionality of the design, and reduce the message to a feature description. Passive-voice formulations ("Privacy is enforced with minimal friction") are equally problematic: they describe a property of the system without attributing it to a designer's deliberate choice for a specific user.

How to Self-Check Phrasing

Read every sentence of your metacommunication message aloud as if you were speaking directly to your user. If a sentence cannot naturally be voiced as the designer addressing the user, it needs rephrasing. Two tests:

  • The "I" test: Does the sentence begin with or contain "I" (the designer)? If the subject is "the system," "the application," or "the feature," rephrase.
  • The "you" test: Does the sentence address "you" (the user) or refer to "the user," "users," or "they"? If the latter, rephrase to address the user directly.

Common Mistakes

Writing in third person
A metacommunication message that says "The system provides automated backups" or "Users can configure their dashboard" has lost the designer's voice. Rephrase as: "I have designed automated backups for you because I know you cannot afford to lose work" or "I want you to be able to arrange your dashboard the way that makes sense for your workflow." The I/you frame is not optional -- it is what distinguishes a metacommunication message from a feature list.
Conflating the metacommunication message with a README
A README describes what the software does and how to install it. A metacommunication message expresses what the designer understands about the user and why the software was designed the way it was. The two serve different audiences and purposes. The README is for anyone evaluating or setting up the software; the metacommunication message is the designer's personal communication to the user about the design intent behind the system. If your message reads like installation instructions or a feature catalogue, it is a README, not a metacommunication message.
Making the message too abstract
A message that says "I want you to have a good experience" or "I have designed this system to be useful" communicates nothing specific. Every paragraph should contain concrete "I want you to..." or "I have designed... because I know you..." statements that a reader can verify against the actual system. If you cannot point to a specific design decision that implements what the message claims, the message is too abstract.
Forgetting to update the message when design evolves
The metacommunication message is not written once and forgotten. As the designer's understanding of the user deepens -- through UX research, problem scenario analysis, or field observation -- the message should evolve to reflect that new understanding. An outdated metacommunication message creates a gap between what the system claims to be for and what it actually does. Use /design update metacomm to revise the message when your understanding changes.
