UX Research Artifacts

SEJA projects ground their design in structured UX research artifacts: personas that model target users, problem scenarios that capture pain points motivating the design, and discovered journeys that record how users actually interact with the system. These artifacts live in product-design/ux-research-results.md, classified as Human (markers) -- prose is human-authored only, and agents may write only INCORPORATED markers and CHANGELOG appends via apply_marker.py.

This chapter documents the structure, purpose, and maintenance of each artifact type, and explains the critical distinction between discovered journeys (evidence from observation) and designed journeys (intent from the designer).

Personas

In SEJA's context, personas are structured archetypes of the project's target users. They are not exhaustive user profiles but focused models that capture the goals, frustrations, and relevant context that shape design decisions. Each persona answers a slice of the metacommunication message's opening clause: "Here is my understanding of who you are."

Where Personas Live

Personas are defined in sections 1 and 2 of product-design/ux-research-results.md. Section 1 contains a Persona Inventory table (summary) and full persona profiles. Section 3 (Cross-Reference Map) links each persona to the design artifacts it feeds.

How Personas Are Created

The /design skill generates personas during its Mode 5 (Interview-Driven) workflow. Phase A collects open-ended information about the project's target users through conversational Q&A. Phase B synthesizes the interview data into structured persona entries, assigning stable IDs and mapping goals to the Extended Metacommunication Template (EMT) dimensions. The designer reviews and confirms each persona during Phase C before the artifacts are written.

Persona Entry Structure

Each persona entry follows a fixed structure with stable identifiers:

Field Format Purpose
ID R-P-NNN Stable identifier; never reused, even for superseded personas
Name Short given name Human-readable label for cross-references
Role / Archetype Free text The user's primary relationship to the system
Bio Narrative paragraph Background, expertise, and context for design reasoning
Goals G-NNN entries What the persona wants or needs to accomplish; referenced by problem scenarios and design features
Key Frustrations Bullet list Pain points that motivate design decisions
Relevant Context Structured fields Technical proficiency, usage frequency, domain knowledge

Persona IDs use the R-P-NNN format (zero-padded, starting at 001). IDs are stable and never reassigned -- a superseded persona gets a new ID rather than reusing the old one.

The reference tables above describe the structure of individual personas. The following section covers problem scenarios -- the artifacts that connect personas to the design features they motivate.

Problem Scenarios

Problem scenarios are structured narratives that capture specific pain points users experience without SEJA (or with earlier versions of it). Each scenario describes a concrete situation where a user's goals are frustrated, grounding abstract persona frustrations in observable, testable contexts.

Where Problem Scenarios Live

Problem scenarios are defined in section 2 of product-design/ux-research-results.md. The Cross-Reference Map in section 3 links each scenario to the design artifacts it feeds -- typically specific sections of product-design/product-design-as-intended.md and per-feature metacommunication intentions.

Scenario Entry Structure

Each problem scenario entry includes:

Field Format Purpose
ID R-PS-NNN Stable identifier for cross-referencing
Persona(s) R-P-NNN references Which personas experience this pain point
Goals G-NNN references Which persona goals are frustrated
Setting Narrative sentence When and where the scenario occurs
Narrative Multi-paragraph prose What happens, why it is a problem, what the user cannot do

Connecting Scenarios to Design

The traceability chain runs: Persona (who) → Goal (what they need) → Problem Scenario (what goes wrong) → Design Feature (what SEJA does about it). The Cross-Reference Map in section 3 of product-design/ux-research-results.md records these links explicitly, mapping each artifact ID to the design-intent section it feeds. This ensures that no design feature exists without a traceable motivation and no problem scenario is left unaddressed without a conscious decision to defer it.

With personas and problem scenarios defining what users need and where they struggle, the next section covers discovered journeys -- the artifacts that record how users actually behave once the system is in use.

Discovered Journeys

SEJA distinguishes two kinds of journey maps, identified by their ID prefixes. Understanding this distinction is essential for maintaining accurate design records.

Discovered vs. Designed Journeys

Attribute Discovered Journeys Designed Journeys
ID prefix JM-E-NNN JM-TB-NNN
Source Field observation of actual use Designer's planned interaction flow
Nature Evidence (what happened) Intent (what should happen)
Location (as-intended) ux-research-results.md §5 product-design-as-intended.md §15
Location (as-coded) N/A product-design-as-coded.md Journey Maps
Maintained by Human (researcher/designer) Human (markers) / Agent (as-coded)

The distinction matters because discovered journeys are evidence -- they record what actually happened when a user interacted with the system, including unexpected paths, workarounds, and breakdowns. Designed journeys are intent -- they describe the interaction flow the designer planned. When discovered journeys diverge from designed journeys, the gap is a signal for design review, not a bug to fix.

Recording a Discovered Journey

Discovered journeys are recorded by the human designer or researcher in section 5 of product-design/ux-research-results.md. The section is structurally append-only: new journeys are added at the end; existing entries are never removed or reordered.

To record a discovered journey:

  1. Observe the user's actual interaction path during field use of the harness.
  2. Write a narrative entry in ux-research-results.md section 5, assigning the next available JM-E-NNN ID.
  3. Note the personas involved, the context, and any divergence from designed journeys.
  4. If the journey reveals a design gap, record it in the Processing Status table (section 4) for future incorporation into design intent.

Tip: Harness tooling discriminates journey types by ID prefix -- JM-E- for discovered, JM-TB- for designed. Using the wrong prefix will cause the journey to appear in the wrong file context and confuse drift detection.

Common Mistakes

Confusing discovered and designed journeys
Discovered journeys (JM-E-NNN) and designed journeys (JM-TB-NNN) use different ID prefixes, live in different files, and serve different purposes. Discovered journeys are evidence from field observation; designed journeys are intent from the designer. Mixing them up -- recording a planned flow as JM-E-NNN or an observed path as JM-TB-NNN -- corrupts the evidence/intent distinction and confuses drift detection, which relies on the ID prefix to determine where each journey belongs.
Hand-editing the UX research file with agent prose
product-design/ux-research-results.md is classified as Human (markers). All narrative prose must be written by the human designer or researcher. Agents may write only INCORPORATED markers and CHANGELOG_APPEND entries, and only via apply_marker.py after explicit AskUserQuestion confirmation. Direct agent prose writes are rejected by check_human_markers_only.py during post-skill. If an agent needs to propose UX research content, it should present the proposal to the designer for manual incorporation.
Treating personas as exhaustive user descriptions
Personas are design archetypes, not comprehensive user profiles. They capture enough about a user type to ground design reasoning -- goals, frustrations, relevant context -- but they are deliberately simplified. A persona named "Ana" does not describe every semiotic engineer who might use SEJA; she models the concerns and workflow that shape design decisions for that user type. Personas evolve as the designer's understanding grows: new observations may refine existing personas or prompt new ones with fresh R-P-NNN IDs.
