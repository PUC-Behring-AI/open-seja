The Constitution

A SEJA project constitution declares the immutable principles that every skill, agent, and plan must observe. It is the first artifact loaded by pre-skill -- before conventions, standards, or any other reference -- and its rules take precedence over everything else. This chapter explains what a constitution contains, how to write and maintain one, and why immutable principles are essential for governing agent behavior.

What a Constitution Contains

Every constitution follows the same four-section structure, defined in the template at .claude/references/template/constitution.md. Each section serves a distinct governance purpose:

Section Purpose Typical entries
Technical Principles Non-negotiable architectural decisions that shape how the system is built. Lifecycle discipline, file classification rules, authoring boundaries, voice and phrasing rules.
Quality Principles Quality gates that cannot be bypassed -- the standards the project is committed to regardless of schedule pressure. Design-intent authority, epistemic posture requirements, governance-plus-epistemic mandate.
Security Invariants Security rules that must never be relaxed without explicit sign-off from the project lead. Private-content isolation, hook-bypass controls, credential handling rules.
Compliance Requirements Regulatory, contractual, or policy obligations the project is bound by. Repository visibility rules, sync-boundary constraints, data-residency requirements.

Every entry in the constitution is a row in a principles table with three columns: a stable identifier (T1, Q2, S1, C1, etc.), the principle itself, and a rationale explaining why the rule exists. The rationale is not optional -- it is what allows the agent (and future maintainers) to judge edge cases rather than blindly following the letter of the rule.

Writing and Maintaining a Constitution

Starting from the Template

When you run /design on a new project (or select the "Constitution" option from the update menu), SEJA copies the template from .claude/references/template/constitution.md into product-design/constitution.md. The template contains placeholder rows with {{…}} tokens and HTML comments showing examples for each section. Replace the placeholders with your project's actual commitments and delete the example comments.

Adding Principles over Time

New principles often emerge from design decisions. When a D-NNN decision record in product-design-as-intended.md identifies a commitment that should be immutable -- one that should never be overridden by a plan or implementation step without explicit approval -- promote it to a constitution entry. Assign the next available identifier in the appropriate section (e.g., T5, Q4) and write a rationale that explains why this rule exists.

The Amendment Protocol

Constitutions change rarely, and every change requires:

  1. Explicit approval from the project lead (the designer).
  2. A new version entry in the constitution's Changelog section, recording the date and what changed.

This protocol ensures that constitution changes are deliberate and auditable. An agent cannot amend the constitution unilaterally -- the file is classified as Human, meaning only the designer writes to it.

Constitution vs. Conventions vs. Standards

Three different artifacts capture project rules at different levels of mutability:

Constitution (product-design/constitution.md)
Immutable principles. Loaded first by pre-skill. Violations are blocking -- they must be resolved before commit. Change requires explicit designer approval and a changelog entry.
Conventions (product-design/conventions.md)
Project structure: directory paths, stack choices, key file locations, review configuration. Mutable -- updated when the stack changes or the project reorganizes. Does not carry governance weight.
Standards (product-design/standards.md, product-design/design-standards.md)
Engineering standards: coding patterns, testing rules, UX patterns, accessibility requirements. Mutable -- Human / Agent classification, so both the designer and the agent can update them. Advisory rather than blocking unless a constitution principle elevates a specific standard.

The decision rule: if a commitment should survive any refactoring, any stack change, and any team turnover, it belongs in the constitution. If it describes how the project is structured today, it belongs in conventions. If it describes how code should be written, it belongs in standards.

With the mechanics of writing and maintaining a constitution covered, the next section explains why immutable principles are worth the governance overhead.

Why Immutable Principles Matter

The constitution is the first artifact loaded during pre-skill's constitution stage. It enters the agent's context before conventions, before skill-specific references, and before the plan being executed. This loading order is deliberate: it means every subsequent decision the agent makes is bounded by the constitution's constraints.

Without immutable principles, an agent operating under schedule pressure or optimization heuristics can silently drift from the designer's commitments. A plan might skip review steps to save time. An implementation might bypass the Human (markers) boundary because direct writes are faster than routing through apply_marker.py. A critique might overlook a security invariant because it was not salient in the current context.

The constitution prevents this drift by making certain commitments non-negotiable. When /critique validate runs, it checks the agent's output against the constitution's principles and classifies violations as blocking. The agent cannot merge a change that contradicts a constitution entry without an explicit D-NNN decision record approved by the designer -- and that decision record itself becomes part of the project's audit trail.

This is the governance half of what SEJA calls the "governable and epistemic" thesis: immutable principles provide the governance floor, while epistemic mechanisms (gap detection, drift surfacing, uncertainty tracking) provide the awareness ceiling. Neither alone is sufficient. For the theoretical foundations of this thesis, see The Governable AND Epistemic Thesis.

Common Mistakes

Putting mutable conventions in the constitution
Directory paths, stack choices, and other structural details change as a project evolves. If these are encoded as constitution principles, every reorganization requires a formal amendment. Put structural details in product-design/conventions.md instead, and reserve the constitution for commitments that should survive any refactoring.
Writing principles without rationale
The rationale column in the principles table is not optional. A principle without a rationale is an unexplained rule that the agent cannot reason about at the edges. When an edge case arises, the agent needs the "why" to determine whether the principle applies or whether the case falls outside its scope. Always explain why the rule exists.
Making the constitution too long
The constitution is loaded into every agent context window via pre-skill. A bloated constitution consumes token budget that could be used for the actual task. Keep the constitution focused on genuinely immutable commitments -- typically 4 to 12 principles total. If a rule is important but not immutable, it belongs in standards, not the constitution.
Confusing the constitution with standards
Standards (product-design/standards.md) are mutable engineering rules that evolve as the project matures. Constitution principles are immutable commitments that require explicit designer approval to change. A coding convention ("use snake_case for function names") is a standard. A governance commitment ("no plan may bypass the pre-commit hook") is a constitution principle. Putting standards in the constitution makes the constitution noisy and makes standards unnecessarily hard to update.
