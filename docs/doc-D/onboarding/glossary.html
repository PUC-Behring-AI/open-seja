Glossary and Shared Definitions

This chapter introduces the most important SEJA terms, organized by conceptual domain. Each definition is a brief orientation for new readers, with a cross-reference to the chapter that covers the concept in depth. Use this glossary as a companion while reading any volume in the collection.

Core Terms

Brief
A short description of the task or goal that a designer provides when invoking a skill. The brief is logged in the brief log (_output/briefs.md) by pre-skill and serves as the audit trail connecting every skill invocation to its purpose. See Lifecycle Pipeline.
Constitution
The project's immutable principles, stored in product-design/constitution.md. The constitution is loaded by pre-skill before all other reference files and takes precedence over conventions, standards, and plan-level decisions. No plan or implementation step may contradict it without an explicit decision record approved by the designer. See Constitution Guide.
Design Intent (As-Intended / As-Coded)
SEJA maintains paired artifacts for each design domain. The as-intended file (product-design/product-design-as-intended.md) records the target state -- what the designer wants the system to be. The as-coded file (product-design/product-design-as-coded.md) records the current state -- what the system actually is. The gap between the two is the subject of drift detection. See Design Intent.
Marker
An inline lifecycle annotation that tracks the status of a design item across registered as-intended files. Markers follow a state machine (proposed → implemented → established → superseded) and are written exclusively through apply_marker.py after explicit designer confirmation. See Marker System.
Metacommunication Message
The designer's canonical first-person statement to the user, expressed in I/you format. It articulates who the designer understands the user to be, what the designer has learned they want or need to do, in what contexts they will use the system, and how the system has been designed to serve them. The metacommunication message is the highest-authority artifact in the design layer; all other design decisions are accountable to it. See Metacommunication.
Pending Action
An outstanding human action registered in _output/pending.jsonl. Pending actions track work that requires designer attention -- unexecuted plans, unverified implementations, unincorporated research findings, and periodic curation tasks. Pre-skill surfaces overdue actions with a banner warning at the start of every skill invocation. See Pending Actions.
Plan
A structured implementation roadmap produced by the /plan skill. A plan consists of numbered steps with rationale, affected files, documentation fields, and verification criteria. Plans serve as the contract between design intent and implementation: they define how to build what the designer intends and why those approaches were chosen. See Skills In Depth.
Roadmap
A multi-wave plan produced by /plan --roadmap that organizes a large body of work into dependency-aware execution waves. Each wave contains one or more plans that can be executed in sequence or in parallel. Roadmaps are used when a brief spans multiple entities, architectural layers, or user flows. See Skills In Depth.
Skill
A lifecycle capability exposed to the designer. SEJA provides 15 user-facing skills (including /research, /design, /plan, /implement, /critique, /document, /communicate, and /reflect) plus 2 internal lifecycle hooks (pre-skill and post-skill). Each skill has a SKILL.md instruction file and a SKILL-quickguide.md user-facing summary. See Skills In Depth.
Subagent
A specialized agent delegated to by the main harnessed agent via the Agent tool. Subagents run in isolated context windows with focused prompts -- for example, code-reviewer, document-generator, or harness-health-evaluator. Subagents cannot interact with the designer directly; all interactions flow through the harnessed agent. See Skills In Depth.

The terms above name the artifacts and capabilities you will encounter daily. The following section introduces the theoretical vocabulary that underpins SEJA's design.

Semiotic Engineering Terms

Abduction
A mode of reasoning that infers the most plausible explanation from incomplete evidence. In semiotic engineering, abduction describes how users interpret interface signs: they observe the system's behavior and form hypotheses about the designer's intent. SEJA's council-debate mechanism formalizes abductive reasoning by having multiple expert perspectives propose competing interpretations of a design decision. See Abduction and Plural Readings.
Communicability
The quality of a system's ability to convey the designer's intent to the user through the interface. A system with high communicability makes it easy for users to understand what the designer intended -- not just what buttons to press, but why the system is shaped the way it is. SEJA's review perspectives evaluate communicability across multiple dimensions. See Software as Designed Communication.
Dynamic Sign
An interface element whose meaning emerges from interaction over time -- for example, a workflow that reveals its logic step by step, or a system response that changes based on prior user actions. Dynamic signs are one of three sign classes in semiotic engineering, alongside static signs and metalinguistic signs. See Sign Systems.
Metacommunication
The designer's message to the user about the system, conveyed through the totality of the system's interface and behavior. Metacommunication is not just the UI -- it is what the system as a whole says about the designer's understanding of the user. In SEJA, the metacommunication message is made explicit as a structured artifact rather than being implicit in the interface. See Extended Metacommunication.
Metalinguistic Sign
An interface element that explains other signs -- help text, tooltips, documentation, error messages, and onboarding flows. Metalinguistic signs teach the user the system's own language. They are one of three sign classes in semiotic engineering. See Sign Systems.
Semiotic Inspection
A method for evaluating a system's communicability by systematically examining its metalinguistic, static, and dynamic signs, then comparing the messages they convey. The Semiotic Inspection Method (SIM) looks for inconsistencies between what the system says about itself (metalinguistic signs) and what it actually does (dynamic signs). SEJA includes a semiotic-inspector agent that applies this method. See Sign Systems.
Sign
Anything that stands for something else to someone in some context. In semiotic engineering, every element of a user interface is a sign: a button, a color, an animation, an error message. Signs are the atomic units through which the designer communicates with the user. See Sign Systems.
Sign System
A coherent set of signs and the rules governing their combination. A project's conventions file (product-design/conventions.md) defines part of the project's sign system: the agreed-upon meanings of directory structures, file naming patterns, variable conventions, and output formats. Consistency within the sign system is what makes the interface interpretable. See Sign Systems.
Static Sign
An interface element whose meaning can be interpreted without interaction -- labels, icons, layout structure, color coding. Static signs are perceived at a glance and form the user's first impression of the system's intent. They are one of three sign classes in semiotic engineering, alongside dynamic signs and metalinguistic signs. See Sign Systems.

With the theoretical vocabulary established, the final section covers the terms that describe SEJA's operational lifecycle -- the mechanisms that enforce governance and surface the unknown.

Lifecycle Terms

Checkpoint
A pause point during roadmap execution where the orchestrator stops and asks the designer whether to continue. Checkpoints can be set at wave boundaries (the default) or after each individual plan, giving the designer control over how much work proceeds before review. See Lifecycle Pipeline.
Council Debate
A structured expert deliberation mechanism for high-stakes design decisions. Five fixed archetypes (plus up to two brief-specific experts) surface trade-offs, tensions, and insights through position statements and cross-examination. Council debates formalize the abductive reasoning that semiotic engineering describes -- multiple perspectives competing to explain the same evidence. See Skills In Depth.
Drift
The divergence between a project's as-intended state (what the designer wants) and its as-coded state (what the system actually is). Drift is not inherently a problem -- it is the natural result of ongoing development. SEJA surfaces drift through /explain drift so the designer can decide whether to update the intent, update the code, or accept the gap. See Design Intent.
Human (Markers) Classification
A file classification that distinguishes files whose prose is exclusively human-authored from files that are agent-maintained. Files classified as Human (markers) accept only lifecycle markers (STATUS, INCORPORATED, DECISION_APPEND, CHANGELOG_APPEND) from agents, applied via apply_marker.py after explicit designer confirmation. Direct agent prose writes to these files are rejected. See Marker System.
Periodic Trigger
A pending action that recurs on a schedule rather than being filed once and closed. Periodic triggers surface maintenance tasks -- spec-drift checks, git freshness validation, curation sweeps -- that the designer should attend to regularly. They appear as banner warnings during pre-skill when overdue. See Pending Actions.
Post-Skill
The lifecycle hook that runs after every user-facing skill completes. Post-skill handles DONE marking on the brief log entry, git commit of changes, and decision digest flush. It ensures that every skill invocation leaves a complete audit trail. See Lifecycle Pipeline.
Pre-Skill
The lifecycle hook that runs before every user-facing skill. The pre-skill pipeline has six composable stages: help, brief log, budget evaluation (including orphan and compaction checks), pending check, reference loading, and constitution loading. Three stages are critical (always run); three are non-critical (error-isolated and skippable). No skill may skip pre-skill entirely. See Lifecycle Pipeline.
Reflection Register
A structured retrospective produced by the /reflect skill after completing a piece of work. Reflection registers capture what was built, how it went, what surprised the designer, and what should change next time. They are the mechanism through which practice-level learning is made explicit and persistent. See Skills In Depth.
