What SEJA Is (and Is Not)

What SEJA Is

SEJA (Software Engineering with AI) is a governance layer for Claude Code, grounded in semiotic engineering theory. It structures the entire lifecycle of AI-assisted software development -- from research and design through planning, implementation, critique, documentation, communication, and reflection -- in a way that keeps the AI aligned with the designer's intent at every step.

SEJA is an agent harness. It is not a programming framework, not a library, and not a runtime abstraction. An agent harness provides governance, constraints, and lifecycle management. It shapes how an AI agent behaves without replacing the agent's underlying capabilities.

The Agent vs. the Harnessed Agent

A key distinction runs through everything SEJA does: the difference between the agent and the harnessed agent.

The agent
Claude -- the LLM and CLI tool. The agent can generate code, answer questions, and use tools. Without governance, it skips planning, bypasses review, and follows its own heuristics rather than the designer's intent.
The harnessed agent
The composite of Claude operating within the SEJA harness. When the harness shapes the agent's behavior -- reading the constitution, following lifecycle skills, applying review perspectives, consulting design intent before coding -- the result is the harnessed agent. The harnessed agent plans before building, reads the constitution, and follows review perspectives.

Design Intent as the Anchor

A software project governed by SEJA has a stable design layer. At its apex sits the metacommunication message -- a first-person, designer-to-user statement that expresses who the designer understands the user to be, what they want or need to do, and how the system has been designed to serve them. Every other design and implementation decision is ultimately accountable to this message.

Below the metacommunication message, the design layer includes a constitution that captures immutable principles, design intent files that record the target state, and as-coded files that track the current state. The harness enforces the boundary between these layers: it ensures that plans serve design intent, implementations serve plans, and critiques evaluate against design intent -- not against the agent's own heuristics.

Lifecycle Discipline

Every user-facing skill in SEJA runs through a mandatory pipeline. Each skill starts with pre-skill (loading the constitution, checking pending actions, evaluating budget) and ends with post-skill (marking completion, committing changes, flushing decision records). Skills may opt out of non-critical stages, but no skill may skip pre-skill entirely. This lifecycle discipline is the core value SEJA provides -- bypassing it defeats the governance model.

What SEJA Is Not

Several categories of tooling share surface similarities with SEJA but serve fundamentally different purposes. Understanding what SEJA is not helps set accurate expectations.

Not a CI/CD pipeline
SEJA governs the design-to-implementation lifecycle: the intellectual journey from "what should we build and why" through "build it" to "verify it serves the intent." It does not automate builds, run deployment pipelines, or manage infrastructure. A project using SEJA still needs its own CI/CD tooling.
Not a testing framework
SEJA includes critique and validation capabilities, but these evaluate alignment with design intent -- whether the implementation serves the metacommunication message and satisfies the constitution's principles. They do not replace unit tests, integration tests, or end-to-end testing frameworks that verify functional correctness.
Not a prompt library
Skills are structured lifecycle capabilities with pre-skill and post-skill hooks, constitution loading, pending-action checks, and brief logging. They are not reusable prompt templates that you copy into other tools. Each skill is part of a governed pipeline, not a standalone text fragment.
Not a code generator
The harnessed agent writes code, but SEJA's value is governance, not generation. SEJA ensures that the code the agent produces serves the designer's intent, follows the project's standards, and has been planned, reviewed, and documented. The code generation itself is Claude's capability; SEJA's contribution is making sure that capability is directed well.
Not a project management tool
Plans and roadmaps structure implementation work, but they serve design accountability -- tracing each implementation step back to a design rationale. They do not manage team assignments, track sprints, or coordinate across multiple contributors. SEJA governs the design-to-code pipeline for a single designer working with an AI collaborator.

The Dual Thesis Preview

SEJA embodies two structural commitments that, taken together, distinguish it from other approaches to AI-assisted development. These commitments are not incidental features but deliberate design choices that shape every aspect of the harness.

Governable
The designer can see, verify, and control what the agent does. Lifecycle hooks ensure that every skill invocation passes through constitution loading and pending-action checks. The Human (markers) file classification enforces the boundary between human-authored design intent and agent-maintained implementation state. Plans require rationale. Critiques evaluate against design intent. Nothing happens silently.
Epistemic
The agent surfaces what it does not know. Gap detection flags objectives without supporting tasks, tasks without implementing features. Drift detection identifies where the as-coded state has diverged from the as-intended state. Research logs label heuristic inferences with explicit confidence indicators. Pending actions surface unincorporated research and unverified implementations. The designer's epistemic posture -- knowing what you don't know -- is mirrored in SEJA's tooling.

Governance without epistemic support produces brittleness: the harness enforces rules but cannot tell the designer where understanding is incomplete. Epistemic support without governance produces drift: the agent surfaces unknowns but has no mechanism to ensure they are addressed. SEJA requires both.

The full argument for this dual thesis -- its theoretical grounding, its implications for harness design, and its relationship to semiotic engineering theory -- is developed in The Governable AND Epistemic Thesis.

Quickstart

The fastest path from zero to a working SEJA project. This chapter walks you through cloning the harness, setting up a project, and completing your first design-plan-implement cycle with concrete commands and expected outcomes.

Prerequisites

Before you begin, make sure you have the following installed:

  • Git -- for cloning the harness repository and version-controlling your project.
  • Claude Code CLI -- the AI agent that SEJA governs. SEJA is an agent harness for Claude Code; without it, there is nothing to harness.
  • Python 3 -- for harness scripts that handle validation, marker management, state detection, and lifecycle automation.

Clone and Setup

There are two paths into SEJA, depending on whether you are starting a new project or adding the harness to an existing one.

Option A: New Project from Clone

Clone the public SEJA repository and use it as the foundation for your project: 

git clone https://github.com/simonedjb/seja my-project
cd my-project

Then open Claude Code in the project directory and run: 

/seja-setup --here

The --here flag tells SEJA to finalize setup in the current directory without copying harness files (they are already present from the clone). The harness detects the fresh-download state -- conventions.md is present but _output/ is not yet populated -- and scaffolds the project directories around the existing files. It pins your project to the latest release tag and writes the version to .seja-version.

Option B: Existing Project

If you already have a project and want to add SEJA governance to it, run the following from any Claude Code session: 

/seja-setup /path/to/your/project

This copies the harness files from the SEJA source into your existing project directory. The harness detects the no-harness state and guides you through setup interactively.

The Scaffolding Questionnaire

Both paths end with a scaffolding questionnaire. SEJA asks about your stack -- backend framework, frontend framework, test runner, and other project characteristics. Your answers populate the initial product-design/conventions.md, which becomes the single source of truth for your project's directory structure, file paths, and tooling configuration. After scaffolding completes, the harness hands off to /design for design-intent configuration.

First Lifecycle Cycle

With your project scaffolded, walk through three skills to complete your first design-plan-implement cycle.

Step 1: Design Your Project

/design

The design skill configures your project's design foundations. It creates product-design/product-design-as-intended.md (your design intent -- the target state of what you want the system to be), writes the project constitution (immutable principles), and establishes the metacommunication message (your first-person statement to the user about who they are and how the system serves them). It also manages conceptual design, standards, and documentation templates.

For a first project, the interactive interview mode walks you through each design section. Answer the questions to build up your design layer; you can always refine it later with /design update <section>.

Step 2: Plan a Feature

/plan add a hello-world endpoint

The plan skill takes your brief and produces a structured implementation plan. It first verifies that project design exists (product-design/conventions.md must be present), then auto-detects whether the brief warrants a single plan or a multi-wave roadmap. For a small feature like this, it generates a single plan.

The plan file lands in _output/plans/ with a six-digit ID (e.g., plan-000001-add-hello-world-endpoint.md). It contains numbered steps, each with rationale, affected files, and verification criteria. A pending action is registered so the harness knows the plan awaits implementation.

Step 3: Implement the Plan

/implement 000001

The implement skill takes the six-digit plan ID, creates a rollback branch (so you can undo if needed), and executes each plan step. In auto mode (the default), it delegates steps to specialized subagents that work in isolated context windows. After all steps complete, it runs quality checks -- /critique validate to verify design-intent alignment and /critique review for code quality -- then commits the results.

You now have a working SEJA project with a committed plan and implemented feature.

For deeper coverage of each skill's behavior, options, and common patterns, see Skills In Depth.

What Just Happened

The three skills you just used -- /design, /plan, /implement -- are part of a larger canonical lifecycle path that structures all work in a SEJA project: 

/research > /design > /plan > /implement > /critique > /document > /communicate > /reflect

You entered the lifecycle at /design (since this was a new project with no prior research needed) and exited after /implement (which auto-ran /critique as part of its quality gate). The remaining skills complete the picture:

/research
Investigate questions, explore the codebase, and produce research logs with findings and recommendations. Use before planning when you need to understand something first -- a bug you haven't diagnosed, a library you haven't evaluated, a design question you haven't resolved.
/critique
Validate implementations against design intent, review code quality, run smoke tests, and check harness health. The implement skill auto-runs critique as part of its quality gate, but you can also invoke it directly at any point to assess the current state of your project.
/document
Generate or update project documentation -- README, API reference, changelog, decision records, and more -- based on what was implemented. Plans can specify which documentation types to generate via their Docs: fields.
/communicate
Generate tailored material for specific audiences. A stakeholder briefing, a team update, a user-facing announcement -- each audience gets content shaped for their concerns and vocabulary.
/reflect
Record what you learned after completing work. Reflection can focus on the product (what was built and why it matters) or on your practice (how you worked and what you would do differently). Reflections are anchored on specific artifacts -- plans, research reports, or other outputs.

Not every task uses every skill. A bug fix might start at /research and end at /implement. A design evolution might use only /design and /reflect. The lifecycle is a path, not a mandate -- enter where you need to and exit when the work is done.

Glossary and Shared Definitions

This chapter introduces the most important SEJA terms, organized by conceptual domain. Each definition is a brief orientation for new readers, with a cross-reference to the chapter that covers the concept in depth. Use this glossary as a companion while reading any volume in the collection.

Core Terms

Brief
A short description of the task or goal that a designer provides when invoking a skill. The brief is logged in the brief log (_output/briefs.md) by pre-skill and serves as the audit trail connecting every skill invocation to its purpose. See Lifecycle Pipeline.
Constitution
The project's immutable principles, stored in product-design/constitution.md. The constitution is loaded by pre-skill before all other reference files and takes precedence over conventions, standards, and plan-level decisions. No plan or implementation step may contradict it without an explicit decision record approved by the designer. See Constitution Guide.
Design Intent (As-Intended / As-Coded)
SEJA maintains paired artifacts for each design domain. The as-intended file (product-design/product-design-as-intended.md) records the target state -- what the designer wants the system to be. The as-coded file (product-design/product-design-as-coded.md) records the current state -- what the system actually is. The gap between the two is the subject of drift detection. See Design Intent.
Marker
An inline lifecycle annotation that tracks the status of a design item across registered as-intended files. Markers follow a state machine (proposed → implemented → established → superseded) and are written exclusively through apply_marker.py after explicit designer confirmation. See Marker System.
Metacommunication Message
The designer's canonical first-person statement to the user, expressed in I/you format. It articulates who the designer understands the user to be, what the designer has learned they want or need to do, in what contexts they will use the system, and how the system has been designed to serve them. The metacommunication message is the highest-authority artifact in the design layer; all other design decisions are accountable to it. See Metacommunication.
Pending Action
An outstanding human action registered in _output/pending.jsonl. Pending actions track work that requires designer attention -- unexecuted plans, unverified implementations, unincorporated research findings, and periodic curation tasks. Pre-skill surfaces overdue actions with a banner warning at the start of every skill invocation. See Pending Actions.
Plan
A structured implementation roadmap produced by the /plan skill. A plan consists of numbered steps with rationale, affected files, documentation fields, and verification criteria. Plans serve as the contract between design intent and implementation: they define how to build what the designer intends and why those approaches were chosen. See Skills In Depth.
Roadmap
A multi-wave plan produced by /plan --roadmap that organizes a large body of work into dependency-aware execution waves. Each wave contains one or more plans that can be executed in sequence or in parallel. Roadmaps are used when a brief spans multiple entities, architectural layers, or user flows. See Skills In Depth.
Skill
A lifecycle capability exposed to the designer. SEJA provides 15 user-facing skills (including /research, /design, /plan, /implement, /critique, /document, /communicate, and /reflect) plus 2 internal lifecycle hooks (pre-skill and post-skill). Each skill has a SKILL.md instruction file and a SKILL-quickguide.md user-facing summary. See Skills In Depth.
Subagent
A specialized agent delegated to by the main harnessed agent via the Agent tool. Subagents run in isolated context windows with focused prompts -- for example, code-reviewer, document-generator, or harness-health-evaluator. Subagents cannot interact with the designer directly; all interactions flow through the harnessed agent. See Skills In Depth.

The terms above name the artifacts and capabilities you will encounter daily. The following section introduces the theoretical vocabulary that underpins SEJA's design.

Semiotic Engineering Terms

Abduction
A mode of reasoning that infers the most plausible explanation from incomplete evidence. In semiotic engineering, abduction describes how users interpret interface signs: they observe the system's behavior and form hypotheses about the designer's intent. SEJA's council-debate mechanism formalizes abductive reasoning by having multiple expert perspectives propose competing interpretations of a design decision. See Abduction and Plural Readings.
Communicability
The quality of a system's ability to convey the designer's intent to the user through the interface. A system with high communicability makes it easy for users to understand what the designer intended -- not just what buttons to press, but why the system is shaped the way it is. SEJA's review perspectives evaluate communicability across multiple dimensions. See Software as Designed Communication.
Dynamic Sign
An interface element whose meaning emerges from interaction over time -- for example, a workflow that reveals its logic step by step, or a system response that changes based on prior user actions. Dynamic signs are one of three sign classes in semiotic engineering, alongside static signs and metalinguistic signs. See Sign Systems.
Metacommunication
The designer's message to the user about the system, conveyed through the totality of the system's interface and behavior. Metacommunication is not just the UI -- it is what the system as a whole says about the designer's understanding of the user. In SEJA, the metacommunication message is made explicit as a structured artifact rather than being implicit in the interface. See Extended Metacommunication.
Metalinguistic Sign
An interface element that explains other signs -- help text, tooltips, documentation, error messages, and onboarding flows. Metalinguistic signs teach the user the system's own language. They are one of three sign classes in semiotic engineering. See Sign Systems.
Semiotic Inspection
A method for evaluating a system's communicability by systematically examining its metalinguistic, static, and dynamic signs, then comparing the messages they convey. The Semiotic Inspection Method (SIM) looks for inconsistencies between what the system says about itself (metalinguistic signs) and what it actually does (dynamic signs). SEJA includes a semiotic-inspector agent that applies this method. See Sign Systems.
Sign
Anything that stands for something else to someone in some context. In semiotic engineering, every element of a user interface is a sign: a button, a color, an animation, an error message. Signs are the atomic units through which the designer communicates with the user. See Sign Systems.
Sign System
A coherent set of signs and the rules governing their combination. A project's conventions file (product-design/conventions.md) defines part of the project's sign system: the agreed-upon meanings of directory structures, file naming patterns, variable conventions, and output formats. Consistency within the sign system is what makes the interface interpretable. See Sign Systems.
Static Sign
An interface element whose meaning can be interpreted without interaction -- labels, icons, layout structure, color coding. Static signs are perceived at a glance and form the user's first impression of the system's intent. They are one of three sign classes in semiotic engineering, alongside dynamic signs and metalinguistic signs. See Sign Systems.

With the theoretical vocabulary established, the final section covers the terms that describe SEJA's operational lifecycle -- the mechanisms that enforce governance and surface the unknown.

Lifecycle Terms

Checkpoint
A pause point during roadmap execution where the orchestrator stops and asks the designer whether to continue. Checkpoints can be set at wave boundaries (the default) or after each individual plan, giving the designer control over how much work proceeds before review. See Lifecycle Pipeline.
Council Debate
A structured expert deliberation mechanism for high-stakes design decisions. Five fixed archetypes (plus up to two brief-specific experts) surface trade-offs, tensions, and insights through position statements and cross-examination. Council debates formalize the abductive reasoning that semiotic engineering describes -- multiple perspectives competing to explain the same evidence. See Skills In Depth.
Drift
The divergence between a project's as-intended state (what the designer wants) and its as-coded state (what the system actually is). Drift is not inherently a problem -- it is the natural result of ongoing development. SEJA surfaces drift through /explain drift so the designer can decide whether to update the intent, update the code, or accept the gap. See Design Intent.
Human (Markers) Classification
A file classification that distinguishes files whose prose is exclusively human-authored from files that are agent-maintained. Files classified as Human (markers) accept only lifecycle markers (STATUS, INCORPORATED, DECISION_APPEND, CHANGELOG_APPEND) from agents, applied via apply_marker.py after explicit designer confirmation. Direct agent prose writes to these files are rejected. See Marker System.
Periodic Trigger
A pending action that recurs on a schedule rather than being filed once and closed. Periodic triggers surface maintenance tasks -- spec-drift checks, git freshness validation, curation sweeps -- that the designer should attend to regularly. They appear as banner warnings during pre-skill when overdue. See Pending Actions.
Post-Skill
The lifecycle hook that runs after every user-facing skill completes. Post-skill handles DONE marking on the brief log entry, git commit of changes, and decision digest flush. It ensures that every skill invocation leaves a complete audit trail. See Lifecycle Pipeline.
Pre-Skill
The lifecycle hook that runs before every user-facing skill. The pre-skill pipeline has six composable stages: help, brief log, budget evaluation (including orphan and compaction checks), pending check, reference loading, and constitution loading. Three stages are critical (always run); three are non-critical (error-isolated and skippable). No skill may skip pre-skill entirely. See Lifecycle Pipeline.
Reflection Register
A structured retrospective produced by the /reflect skill after completing a piece of work. Reflection registers capture what was built, how it went, what surprised the designer, and what should change next time. They are the mechanism through which practice-level learning is made explicit and persistent. See Skills In Depth.
