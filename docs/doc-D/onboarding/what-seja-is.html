What SEJA Is (and Is Not)

What SEJA Is

SEJA (Software Engineering with AI) is a governance layer for Claude Code, grounded in semiotic engineering theory. It structures the entire lifecycle of AI-assisted software development -- from research and design through planning, implementation, critique, documentation, communication, and reflection -- in a way that keeps the AI aligned with the designer's intent at every step.

SEJA is an agent harness. It is not a programming framework, not a library, and not a runtime abstraction. An agent harness provides governance, constraints, and lifecycle management. It shapes how an AI agent behaves without replacing the agent's underlying capabilities.

The Agent vs. the Harnessed Agent

A key distinction runs through everything SEJA does: the difference between the agent and the harnessed agent.

The agent
Claude -- the LLM and CLI tool. The agent can generate code, answer questions, and use tools. Without governance, it skips planning, bypasses review, and follows its own heuristics rather than the designer's intent.
The harnessed agent
The composite of Claude operating within the SEJA harness. When the harness shapes the agent's behavior -- reading the constitution, following lifecycle skills, applying review perspectives, consulting design intent before coding -- the result is the harnessed agent. The harnessed agent plans before building, reads the constitution, and follows review perspectives.

Design Intent as the Anchor

A software project governed by SEJA has a stable design layer. At its apex sits the metacommunication message -- a first-person, designer-to-user statement that expresses who the designer understands the user to be, what they want or need to do, and how the system has been designed to serve them. Every other design and implementation decision is ultimately accountable to this message.

Below the metacommunication message, the design layer includes a constitution that captures immutable principles, design intent files that record the target state, and as-coded files that track the current state. The harness enforces the boundary between these layers: it ensures that plans serve design intent, implementations serve plans, and critiques evaluate against design intent -- not against the agent's own heuristics.

Lifecycle Discipline

Every user-facing skill in SEJA runs through a mandatory pipeline. Each skill starts with pre-skill (loading the constitution, checking pending actions, evaluating budget) and ends with post-skill (marking completion, committing changes, flushing decision records). Skills may opt out of non-critical stages, but no skill may skip pre-skill entirely. This lifecycle discipline is the core value SEJA provides -- bypassing it defeats the governance model.

What SEJA Is Not

Several categories of tooling share surface similarities with SEJA but serve fundamentally different purposes. Understanding what SEJA is not helps set accurate expectations.

Not a CI/CD pipeline
SEJA governs the design-to-implementation lifecycle: the intellectual journey from "what should we build and why" through "build it" to "verify it serves the intent." It does not automate builds, run deployment pipelines, or manage infrastructure. A project using SEJA still needs its own CI/CD tooling.
Not a testing framework
SEJA includes critique and validation capabilities, but these evaluate alignment with design intent -- whether the implementation serves the metacommunication message and satisfies the constitution's principles. They do not replace unit tests, integration tests, or end-to-end testing frameworks that verify functional correctness.
Not a prompt library
Skills are structured lifecycle capabilities with pre-skill and post-skill hooks, constitution loading, pending-action checks, and brief logging. They are not reusable prompt templates that you copy into other tools. Each skill is part of a governed pipeline, not a standalone text fragment.
Not a code generator
The harnessed agent writes code, but SEJA's value is governance, not generation. SEJA ensures that the code the agent produces serves the designer's intent, follows the project's standards, and has been planned, reviewed, and documented. The code generation itself is Claude's capability; SEJA's contribution is making sure that capability is directed well.
Not a project management tool
Plans and roadmaps structure implementation work, but they serve design accountability -- tracing each implementation step back to a design rationale. They do not manage team assignments, track sprints, or coordinate across multiple contributors. SEJA governs the design-to-code pipeline for a single designer working with an AI collaborator.

The Dual Thesis Preview

SEJA embodies two structural commitments that, taken together, distinguish it from other approaches to AI-assisted development. These commitments are not incidental features but deliberate design choices that shape every aspect of the harness.

Governable
The designer can see, verify, and control what the agent does. Lifecycle hooks ensure that every skill invocation passes through constitution loading and pending-action checks. The Human (markers) file classification enforces the boundary between human-authored design intent and agent-maintained implementation state. Plans require rationale. Critiques evaluate against design intent. Nothing happens silently.
Epistemic
The agent surfaces what it does not know. Gap detection flags objectives without supporting tasks, tasks without implementing features. Drift detection identifies where the as-coded state has diverged from the as-intended state. Research logs label heuristic inferences with explicit confidence indicators. Pending actions surface unincorporated research and unverified implementations. The designer's epistemic posture -- knowing what you don't know -- is mirrored in SEJA's tooling.

Governance without epistemic support produces brittleness: the harness enforces rules but cannot tell the designer where understanding is incomplete. Epistemic support without governance produces drift: the agent surfaces unknowns but has no mechanism to ensure they are addressed. SEJA requires both.

The full argument for this dual thesis -- its theoretical grounding, its implications for harness design, and its relationship to semiotic engineering theory -- is developed in The Governable AND Epistemic Thesis.
